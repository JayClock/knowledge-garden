## 本轮目标

练习把四个项目组织成一条能力主线：定义问题，形成工程契约，用 AI 与软件实现，再通过测试和运行证据验收。重点检查个人动作、技术机制、协作接口与交付验证是否说得清楚。

本文件是练习计划与问题库，不是已经完成的练习记录。

## 项目追问库

下面是后续可选择的问题，不在首轮一次性提问。根据用户实际回答，每次只选一道，回答后再决定下一步。

### 领域建模：问题澄清与 AI 协作

1. 你怎样把不断发散的业务讨论收敛为模型？你亲自交付了什么？
2. 在实际使用版本里，AI 补充的一条 Rule 怎样记录来源，又怎样进入下游 API 与测试数据生成？
3. 来源可追溯、模型结构合法和业务审核通过分别回答什么问题？
4. 用采购履约案例说明，哪些业务信息进入模型，发布模型怎样被下游消费。

### HATEOAS：工程判断与存量改造

1. 为什么把多端规则重复的问题推进到资源与动作契约层，而不是只抽一个公共前端函数？
2. 后端担心成本和数据更新风险时，你怎样限定增量改造范围，怎样协作落地？
3. MSW／Vitest 导航组件测试和 workflow 保存／发布端到端回归，各自检查什么？
4. AI 辅助生成测试后，你怎样确定保存场景的验收预期，怎样检查输入输出兼容性？
5. 修改响应触发失效或缓存写回时，资源与 React 消费层怎样协作？

### 工作流：执行机制与稳定性

1. 为什么使用拓扑顺序，GraphBuilder 与 WorkflowEngine 分别负责什么？
2. 未选分支被排除时，怎样判断公共汇合节点应该保留？
3. 不同运行的数据怎样隔离？共享执行器与独立 ExecutionContext 有什么区别？
4. 从节点业务方法抛异常，到返回整次工作流失败结果，完整链路是什么？
5. 变量标签与公式 AST 分别怎样连接编辑、保存与执行？

### 监控 SDK：可观测性与低侵入

1. 为什么从下游排障问题倒推事件设计？举例说明需要哪些上下文。
2. core、browser、框架适配与 Transport 分别面对什么变化？
3. Fetch／XHR 采集怎样保持业务调用和返回行为？
4. 事件何时入队、何时批量发送？失败重试怎样参与上报链路？
5. Sourcemap、构建版本和异常堆栈如何配合定位？你与后端及大数据团队怎样对接？

## 综合题

这些题检验迁移判断，回答中的新场景应作为方案讨论，不改写成历史交付。

- 面对一个描述不清楚的内部工具需求，你会先确认哪些信息，再决定是否使用 AI？
- AI 很快生成了一套实现，你如何确定验收条件，判断应该保留、局部修改还是重做？
- 存量流程需要改造时，怎样设计最小试点、兼容检查和回退路径？
- 真实结果与预期不符时，你怎样判断应该回到需求、模型、契约、实现还是测试数据？

## 观察与收束

反馈只依据实际回答，区分主线结构、机制解释、事实一致性和现场表达。文字转写只支持内容判断；字符时长是估算，实际用时以用户计时或可读取媒体元数据为准。

每轮只选一个主要调整，尽量通过 30～90 秒局部重讲验证。收束保留一个有效表现、一个主要卡点、重讲是否发生及下一次唯一任务。原始回答与 AI 建议分开。

当前仅授权生成材料。用户明确说“记录这轮”或授权持续记录后，才保存私有练习日志；本包不创建空练习记录，也不将模拟练习记为真实投递或面试。
