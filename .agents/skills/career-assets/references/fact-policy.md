# 职业事实与派生规则

## 事实来源等级

从高到低：

1. 用户明确确认的事实、角色、完成状态和边界。
2. 实际源码、交付物、测试、运行记录和可验证项目材料。
3. 公司或项目文档中能对应到本人工作的内容。
4. 旧简历、旧讲稿和旧自我介绍：只作为线索和旧表达样本。
5. 课程、文章和面试资料：只提供问题框架、方案比较和追问思路。
6. AI 建议：必须保持候选状态。

用户明确确认某组原始文稿就是实际项目范围时，这项确认属于第 1 级事实。配套仓库如果只是代表性重实现，代码缺失不能反向否定已确认范围；个人职责、事故、客户、规模和数字仍要分别确认。

## 状态转换

```text
candidate → confirmed → deprecated
          ↘ contested
reference_only 保持独立，不进入对外事实
```

- `candidate`：材料或下游表达提供的线索。
- `confirmed`：可以进入保真对外材料。
- `contested`：存在相互冲突的版本，等待用户判断。
- `deprecated`：历史上确认过，但已被更准确表述替代；保留追踪。
- `reference_only`：通用技术方案、未来方向或课程建议。

Agent 不能自行把 candidate 升级为 confirmed。

## 个人与团队边界

每条项目 claim 必须同时回答：

- 谁提出或决定；
- 谁直接实现；
- 谁负责协作接口；
- 哪些只是完整系统背景；
- 哪些是架构延展或后续方向。

对外压缩时可以省略不相关背景，但不能把 `collaborative` 或 `team` 改写为 `direct`。

## 完成状态

- `implemented`：功能或代码已经完成。
- `validated`：实现存在且有明确验证证据。
- `ongoing`：正在实施，不写成完整交付。
- `design_only`：只完成方案设计。
- `planned`：后续方向。
- `unknown`：材料不足。

算法原理、框架默认能力和通用最佳实践不能自动证明项目已完成对应工程化能力。

## 数字和结果

数字 claim 必须记录：

- 指标名称；
- 数值与单位；
- 时间范围；
- 分子／分母或统计口径；
- 来源。

课程简历示例、客户目标、技术理论上限和营销文案中的百分比不进入 metrics。没有数字时正向描述具体实现、覆盖范围、验证方式和实际应用交付，不生硬宣称未统计，也不附加反夸大免责声明。

## 表达呈现与去防御化原则

面向读者的文档、简历与面试表达中：

1. 严禁出现防御性声明：如“不编造”、“不捏造”、“不作跨界归功”、“防穿帮”、“不越俎代庖”、“不能表述为无人工干预生成系统”等。
2. 职责与协作自然化：用正向动作说明个人所做事项及与团队的对接点，不写“xx 非个人成果”。
3. 缺失与延展信息处理：未完成的延展功能与未统计指标直接不在正文中展开，不主动罗列未完成负向清单；如有需要，在面试追问中讨论未来演进；需后续核验的问题统一记录到内部 `positioning.open_questions`，默认不在职业经历文档中展示。

## 单向派生

```text
证据与用户确认
→ claims
→ content/Knowledge/Outputs/职业经历.md（长期可读文档）
→ positioning / opportunity
→ resume / self-introduction / interview package
→ feedback
```

职业经历中的人工修改和其他下游材料暴露新线索时，交给 `career-evidence` 核对。用户本轮明确确认的纠正记录为 user_confirmation 后更新 claims；来源不清的线索保持 candidate，冲突保持 contested。写入职业经历前保留用户新增和批注，不能用旧账本覆盖，也不能未经确认反向改写 confirmed claim。确认后同步账本、职业经历和依赖记录。

## 修改授权

- 未经用户明确要求执行或落盘，只展示草稿和影响范围。
- 授权只覆盖已确认的修改，不自动扩展到新的事实选择。
- claim 变化后运行影响扫描；先修复事实错误，再决定是否重写表达。
- 不重置、覆盖或整理任务外的用户修改。
