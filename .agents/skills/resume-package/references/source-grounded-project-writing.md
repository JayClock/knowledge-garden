# 源材料驱动的项目经历写作

本规范只约束事实检索与取舍，不提供统一的项目段落模板。Word 模板负责字体、颜色、栏位、间距和页面风格；素材与 confirmed claims 决定项目经历写什么、先写什么以及需要多少条。

## 参考来源

优先检索与目标项目直接对应的来源：

- 项目原始文稿、架构设计、实战复盘和专项面试材料；
- “中级／高级简历描述”中的项目目标与技术线索；
- “项目重难点、核心难点、面试问题”中的问题本质、约束、技术决策、故障处理和验证方式；
- 实际源码、测试、发布记录和用户确认。

素材中的简历示例只是检索入口，不是格式范本，也不是候选人的事实源。

## 检索与映射

1. 读取 opportunity 的 JD、项目排序和 selected claim IDs。
2. 按项目回到素材，寻找能解释业务问题、系统边界、复杂机制、取舍、排障和结果验证的具体段落。
3. 将每个候选信息映射到 `.career/claims.json`；未被 selected confirmed claim 支持的内容不得进入简历。
4. confirmed 但未入选的强证据，先由 `career-positioning` 判断是否加入 selected 集。
5. 保留 claim 的 ownership、completion 和 constraints，不用课程措辞扩大个人职责、完成范围或结果。

## 自然组织原则

- 项目标题是唯一固定锚点；正文不强制设置“技术栈、项目简介、工作内容与成果”等同构小节。
- 根据素材最强证据决定入口：可以先写业务矛盾、架构决策、核心机制、真实排障或验证结果。
- 技术名词放进实际动作和机制中，不为凑“技术栈”单独罗列。
- 不要求所有项目使用相同标签、相同顺序或相同条目数。
- 一条可以表达“约束 → 决策 → 实现 → 验证”中的必要部分，但不机械补齐四段。
- 强边界直接写进相关事实附近，例如后端协作、重实现故障、未验证规模和未完成能力；不要统一堆到项目末尾。
- 详细 Markdown 可以保留更多证据；两页 DOCX 优先通过删除空占位段、收紧项目内部间距、调整模块距离和利用文本框剩余空间容纳证据。只有仍然溢出时，才按 JD 相关性删除重复或弱相关内容，不能压掉核心机制、真实排障和事实边界。

## 事实 Gate

- `ownership=collaborative/team` 不得改写为“独立”“主导”或“全权负责”。
- `design_only/planned/unknown` 不得写成已上线或已验证。
- Kafka、ClickHouse、SSE 服务端、RAG、Qdrant、性能数字、三端发布等，只在 selected confirmed claim 明确支持时使用。
- 不引入未确认客户、规模、生产事故、业务收益、采用效果或课程示例百分比。
- 没有可信数字时，用实现范围、消费路径、测试、发布物、故障修复和运行证据表达结果。
