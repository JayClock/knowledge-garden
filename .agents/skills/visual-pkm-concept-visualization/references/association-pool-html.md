# 第 4 步固定视觉参考 HTML

## 固定交付

用户在第 3 步确认视觉框架后，第 4 步必须生成一个可在浏览器打开的实际图像预览 HTML。HTML 分为两个层级：上方按已选视觉框架展示知识卡整体的框架草图＋文字注释提示；下方把所需主体、动作、关系和辅助组件作为可独立选择的 icon 并排展示。第 5 步经授权把入选 icon 确保落地为 Vault 内 `.excalidraw` 组件并嵌入知识卡初始视图，再由用户亲自移动、组合和补画第一张草图。

生成前必须已经具备：

- 用户确认的单一核心信息；
- 用户先列出的 3–5 个关键词及 AI 扩展联想；
- 用户在第 3 步选定的视觉框架。

HTML 是临时视觉参考，不是知识卡正面、最终构图或 AI Express。PDF 第 3 步要求先让视觉结构匹配概念结构，并鼓励尝试多个 format；第 4 步再寻找、复用、分层和重组视觉元素。因此，框架草图与文字注释属于知识卡整体而不是单个 icon：每个已选框架对应一张只画抽象占位形状、区域、方向和层级的空间骨架草图，以及说明布局动作与强调重点的文字注释。草图不复刻下方 icon，不绑定具体 icon，也不给出完整主体—动作—关系。如果用户选择多个框架，每个框架形成一个独立的草图实验提示，不自动融合；数量等于本轮选定的框架数，不固定为三个。PDF 中“三种不同视觉表达”是练习多个整体草图，不是 HTML 的硬性提示数或 icon 上限。组件可以相对完整；快速、粗糙、不润色描述的是第 5 步首次 Express 的整体构图，而不是第 4 步 icon 的质量。

## 固定内容

每个预览候选都必须包含实际可见图像，而不只是文字占位：

- 先使用已有本地图标和用户已有草图；优先通过分层、叠加、小幅调整和选择性复用形成可重组组件；
- 本地 Icon Library 没有合适组件时，才依次到 [Flaticon](https://www.flaticon.com/)、[The Noun Project](https://thenounproject.com/) 和 [Google Images](https://images.google.com/) 检索主体、动作或关系；外部不使用其他来源，把候选当作观察轮廓与结构的视觉字典；
- 不下载、转换、截图、描摹路径或嵌入外部 PNG／SVG；观察后在系统临时目录重新绘制 SVG 视觉组件；
- 临时重绘组件必须保留可识别轮廓、关键动作、部件关系和必要细节，并适合分层、替换和重组。可以用基础形状和自制路径完成，但不能只是几个几何形状组成的低完成度占位符，也不能成为精炼的最终构图；其颜色可以取自项目语义色板，也可以采用与本轮视觉意图一致的其他配色，第 5 步应保留用户在预览中确认的颜色；
- 不保留外部候选的详情页、作者、素材 ID、权利说明或其他逐项来源记录；本轮第 4 步不得把这些字段新增到 JSON、HTML 或 Vault，永久组件只在规定文件名末尾保留来源名称；
- 用顶层 `selected_frameworks` 按用户第 3 步确认的顺序记录视觉框架；在 icon 区之前单独展示 `layout_hints`。每项包含 `framework`、`sketch`、`spatial_grammar`、`layout_hint` 与 `emphasis`：`sketch` 由本地 `src` 和 `alt` 组成，实际显示一张抽象空间骨架草图；其余字段作为文字注释，说明整体空间关系、可尝试的布局动作，以及该结构会突出核心信息的哪一部分；
- `layout_hints` 必须与 `selected_frameworks` 按顺序一一对应。单个视觉框架生成一张草图及其文字注释；用户明确选择多个框架时，每个框架各生成一组，作为分开的草图实验。不要为了凑数固定生成三组，也不要把多个框架自动融合成一张完整构图；
- 框架草图可以用抽象占位形状、区域、虚线、方向和层级显示并置、极性、序列、流动、嵌套、层叠、中心—外围、角色—环境等空间语法；文字注释解释怎样读这张骨架。两者都不绑定具体 icon 编号、不复刻下方 icon、不指定精确坐标，也不完成完整主体—动作—关系安排；
- 每个 icon 编号只对应一个本地已有 Excalidraw icon 组件或本轮临时重绘的 SVG／其他本地图像参考，使用户能够逐项取舍；编号对应当前任务中的一个最小语义选择单位，只有内部对象需要被独立选择或重组时才拆分，不按图形部件数量机械拆分；
- 每个 icon 项只说明名称、类型、怎样画、承担的角色和突出什么，不再承载知识卡布局提示，也不附加素材追溯、误读或风险；同时必须填写 `atomic_unit` 与 `assembly_later`，把本编号的唯一语义单位和留给画布完成的组合动作显式展示出来；所有非 `.excalidraw` 项都只是预览参考，入选后必须先描摹为原生 Excalidraw 组件；
- 预览只帮助人类理解整体空间语法，并模仿、选择和重组视觉零件，不能做成可直接充当最终视觉的精炼构图。

### icon 的语义原子性

“一个编号一个图像”只保证文件级原子性；第 4 步还必须保证语义级原子性。语义原子不是最小几何部件，而是**当前任务中用户会整体选择、移动和复用的最小语义单位**。原子性依赖本轮选择意图，同一个图形在不同任务中可能需要不同粒度。

生成图像前逐项执行三个判断：

1. **整体选择**：用户是否通常会把它作为一个整体接受、拒绝、移动或复用？如果是，可以保留复合结构。
2. **独立操作**：内部对象是否在本轮需要被单独选择、重复、替换或重新建立关系？如果是，才拆成多个编号。
3. **约定识别**：拆开后是否会破坏一个常规符号的含义？如果会，而且内部部件不承担独立选择任务，就不要拆。

因此不要机械执行固定拆分表：

- 用户要亲自排列追踪路径时，连续脚印可拆成单枚脚印；若“足迹路径”本身就是要整体选择的符号，也可以保留；
- 用户要亲自组织现金流向时，金钱轨迹可拆成硬币与方向；若“资金流”作为整体符号被选择，也可以保留；
- 图表通常作为一个完整符号被整体选择，数据、基准和坐标等内部部件共同构成其约定含义；只有本轮需要分别操作这些部件时才拆；
- 参与方与角色只有在本轮需要重新匹配时才拆成人物和角色徽章；若选择单位是完整身份卡，则保持完整；
- 凭证、清单、图表等常规复合符号可以保留内部记录行、印章、勾选框、数据柱和目标线。

不要把语义原子误解为只允许一个 Excalidraw 基础元素。侦探的帽子、衣领和面部，脚印的鞋底纹路，凭证的纸张轮廓、记录行和印章，以及图表的基准与数据，都是让同一选择单位可识别的内部部件。需要拆分的是本轮要被单独操作的对象，不是每条线和每个形状。

每个 item 都用两个字段把检查结果外显：

- `atomic_unit`：本编号由用户整体选择的语义单位，例如“单枚脚印”或“一张图表”；
- `assembly_later`：不进入该选择单位、留给用户在第 5 步完成的重复、连接、并置或与其他 icon 的组合；即使复合符号无需内部拆分，也要说明它将在画布中与哪些外部对象组合。

Icon 候选数量按实际需要决定。使用 `scripts/render_association_pool.py` 生成包含“框架草图＋文字注释提示”和“icon 选择”两个独立区域的 HTML；用户从中选择或重组当前视觉结构所需的 icon，选择数量不设硬上限，以用户认为能支撑核心信息的元素为准。页面按钮只复制全部入选 icon 编号；布局提示不参与编号选择，也不会进入第 5 步执行计划。只有实际入选且获得写入授权的 icon 才在第 5 步落地。

## 临时位置与生成

固定输出写入系统临时目录，避免未经单独授权改动 Vault：

```text
/tmp/visual-pkm-concept-visualization/<concept-slug>/
├── step-4-preview.json
└── step-4-preview.html
```

从 Vault 根目录运行：

```bash
PREVIEW_DIR="/tmp/visual-pkm-concept-visualization/<concept-slug>"
mkdir -p "$PREVIEW_DIR"

python3 ../.agents/skills/visual-pkm-concept-visualization/scripts/render_association_pool.py \
  "$PREVIEW_DIR/step-4-preview.json" \
  "$PREVIEW_DIR/step-4-preview.html" \
  --asset-root "$PWD" \
  --open
```

若浏览器无法自动打开，返回完整 HTML 路径供用户手动打开。第 4 步期间 JSON、HTML 和临时图像参考都不发布、不写进知识卡正文，也不写入 Icon Library。第 5 步只有用户实际入选且授权落地的参考才按预览外观描摹为 Vault 内原生 `.excalidraw` 文件；不复制或封装 SVG、PNG/JPG 等源图，未入选项继续留在 `/tmp/`。

## 快速检查

- 用户是否已经确认核心信息、首批关键词和第 3 步视觉框架？
- 第 4 步是否实际生成并打开了 HTML，而不是只给文字候选或文件路径？
- 是否先检索本地实际 Excalidraw icon 组件，只有本地不足时才检索 Flaticon、The Noun Project 和 Google Images？
- 外部搜索是否没有使用这三者以外的来源？
- 是否只观察外部候选后临时重绘 SVG 组件，没有下载、转换、截图、描摹路径或嵌入原素材？
- JSON、HTML 和其他记录中是否没有外部候选的详情页、作者、素材 ID 或权利说明？
- 每个临时重绘组件是否结构完整、可识别、可分层重组，而不是低完成度几何占位符；第 5 步是否保留了用户确认的颜色？
- HTML 是否把框架草图＋文字注释提示与 icon 选择分成两个区域，而没有把整体空间提示附着到单个 icon？
- `selected_frameworks` 是否按用户确认顺序保存框架，且 `layout_hints` 是否逐项一一对应；每项是否包含一个可加载的本地 `sketch`；多个框架是否被视为分开的草图实验，没有固定凑成三组或自动融合？
- 框架草图是否只用抽象占位形状、区域、方向或层级显示空间骨架，文字注释是否只说明布局动作与强调重点；两者是否都没有复刻或绑定具体 icon、指定精确坐标或固定完整的主体—动作—关系安排？
- 是否一个编号只对应一个可独立选择的本地 Excalidraw icon 或临时图像参考，并只包含怎样画、角色和突出什么，同时不附加知识卡布局、素材追溯或逐项风险？
- 是否按当前任务的选择意图检查语义原子性：`atomic_unit` 是否命名用户会整体选择的最小语义单位，`assembly_later` 是否说明留给画布的外部组合；是否只在内部对象需要独立操作时拆分，并避免把图表、凭证或清单等常规复合符号过度拆成几何部件？
- HTML 是否只提供知识卡整体的松散空间语法和可模仿的完整组件，而没有预制完整知识卡视觉或替用户完成最终构图？
- 是否把快速、不润色的粗草图留到第 5 步首次 Express？
- 用户是否能够选择任意数量的必要 icon，而没有被最多三个的硬限制阻挡；随后才进入第 5 步授权初始化、落地和嵌入，并由自己在知识卡中完成组合？
- 第 4 步是否把 JSON、HTML 和临时图像参考保存在系统临时目录；第 5 步是否把所有非 `.excalidraw` 入选项先描摹为原生 `.excalidraw`，不复制、封装或直接嵌入源图，并采用规定文件名进入 Icon Library？
