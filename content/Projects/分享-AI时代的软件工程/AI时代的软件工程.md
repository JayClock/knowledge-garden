# AI 时代软件工程会如何演化
从知识管理的角度重新审视软件开发，在不同的阶段中，提取 LLM 易于理解的核心知识与载体。未来个人与 LLM 合作的核心技能在于编码阶段的知识提取和传递。
- 对个人：从自己编码变成指导 LLM 编码
- 对团队：借助 LLM 有效沉淀大量知识。解决问题如：关键岗位人才流失造成大量上下文缺失；团队中难以形成共识；新人培养时间长难以上手。

# 为何要从知识管理的角度审视软件开发
知识工程的关键是提升知识传递效率。在不同的知识类型中，有一类知识被称为**不可言说知识/经验知识**。比如特定的编码技巧、项目管理的非正式流程、代码审查的潜规则，甚至是如何有效地与特定同事沟通的技巧。

这类知识的特点是无法被文档和记录传递，需要通过社会化活动来实现。在软件架构中，我们很多时候提供的仅仅是架构的对外文档，来说明当前架构的功能县长。但很少为架构提供教程或使用手册。也就是缺乏针对在不同场景下，如何应用架构中的概念解决问题的指引（业务发生变化时，架构改如何演化）。缺乏训练法，架构中的不可言说知识就无法稳定地传播。最后架构腐化甚至无法落地。

知识管理的角度审视软件开发，就是把软件开发的整个流程，看作产生、传递、应用、消费知识的过程。

# 知识过程下的软件工程
- 软件中包含的知识：真正的产品的是软件中所包含的知识，软件自身仅仅是知识的载体。
	- 业务知识：什么是正确的软件
	- 软件架构：如何正确的构造软件
- 宏观角度看，软件研发的过程，是**不可言说知识**传递与学习的过程，只能是**复杂认知模式**。
	探测（根据已知情况构造软件）- 感知（收集反馈以验证当前软件是否有效）- 响应（根据反馈改进后续方案以及后续计划）
- 交付流程前，构造一个确定的**目标解决方案**进入**庞杂模式**
	感知（对于要解决的已有初步理解）- 分析（按照业务架构/解决方案处理问题）-响应（得到不同软件系统的软件需求
- 确立了计划，进入交付流程后。围绕功能性质量和非功能性质量。使架构知识发挥作用的过程，也是**庞杂模式**
	感知（对于要解决的问题已有初步理解）- 分析（按照软件架构处理问题）- 响应（得到针对不同架构组件的任务）。
	
平时开发工作中，debug 时极其低效的**复杂认知模式**，**探测**（打断点）- **感知**（查看断点表现）- **响应**（定位问题）。为什么需要有 debug 行为，因为我们并不理解代码的具体实行逻辑。但是我们 debug 之后，并没有在 debug 过程中学到的知识有效传递下去，这里极低的知识传递效率，严重拖累了我们团队之间的合作。

但是在反直觉的[[../../Resources/Notes/TDD|TDD]]中，我们对最后的结果表现有着明确的认知，唯一要做的事情是根据自己的经验，去找出一个合适的解决方案。属于一种**庞杂认知模式**。所以 TDD 的效率，比 debug 的效率更高。

# LLM提取和传递知识

LLM 具有很强的泛化能力，通过提示词进行迁移学习训练。如何进行提示词的迁移，转化为了提取上下文、如何提取知识上。

在过往使用 LLM 辅助开发的流程下，我们往往把要做的**任务本身***（比如：目前我在编写一个...功能，请使用 typescript 实现一个具体的代码）提交给 LLM，期许 LLM 直接帮助我们解决问题。但是这里缺少了引导 LLM 进入我们领域的上下文。在过往的经验下，我们习惯性认为**一件事情越快做出来越好**，但是在 LLM 时代下，**做出来很容易**，**做对却很难**。这里的做对，其实就是让 LLM 进入到我们预期的领域上下文中。

清晰模式下，认知行为表现为：感知（sense）- 归类（cateorize）- 响应（Responsed）。归类是对于任务的选择，也就是根据任务选择不同的提示词模板。

庞杂模式下，认知行为表现为：感知（sense）- 分析（analysis）- 响应（Respond）。我们并不知道具体的任务有哪些，分别是什么。利用**知识生成**（抛弃最终诉求，生成一些关于最终诉求的知识）。我们要做的是生成任务列表，在思路对齐后，进入清晰模式。额外补充一点是可以借助**思维链**指导知识生成。

复杂模式下，我们的重点是获取思路。然后在不断的迭代中，进行不可言说知识外显，即提取 COT。随着知识的累积，我们可以利用 langchain 中的**检索增强生成（Retrieval Augmented Generated， RAG）**，整合知识库中相关片段，生成最终的 prompt。

# LLM 的效率提升
- 自动化带来的效率提升
	- prompt 模板的复用，达到类似于**自动化脚本**的效果。比如 prompt 中 API 要求保持一致，那么员工生成 API 代码的要求也会保持一致
- 知识传递带来效率的提高
	- 对个人（庞杂模式下）：自动化不高，将**不可言说知识转化为文字性的描述**非常复杂。最终就是觉得与其 LLM 处理，不如自己解决。
	- 对团队：提高知识传递的准确性、一致性和及时性，提高团队的效率。
		- 共享同样的思维链，使得团队对于架构形成了一致的认知；而当架构修改时，只要更新所使用的模板，架构的改变就能准确且及时地传递。
		eg: 同一个问题不同的人在不同的[[../../Resources/Notes/Cynefin框架|认知模式]]下。比如平时设计的架构。对架构师而言，他是在应用充分掌握的架构知识下，对需求进行分解，然后在架构指导下，进行软件的开发。但如果是处于复杂认知模式下的新员工，就需要先实现功能，然后在架构的 review 下，逐步修改出符合架构要求的代码。但是在 LLM 的帮助下，就可以直接利用已存的思维链，辅助研发任务的分解以保证代码符合基础的架构。
- 缩短反馈周期带来的效率的提高

# LLM 辅助软件交付
关键：将需求分解为足够小的任务，然后将这个任务转化为 LLM 提示词
角度：
- 软件架构：设计和构建系统时所选择的**组件（Component）以及组件间交互方式**。指导每日工作的任务划分。当任务划分和架构规划不一致时，架构就会开始腐化。
- 测试策略：确保项目的测试活动能够达到预期目标而定义的一组指导性原则和方法。
