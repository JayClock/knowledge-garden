# 全流程序员

> [!abstract] 核心定义
> 全流程序员沿软件交付的知识流扩展上下文与判断能力，使业务问题、方案、任务、实现、验证和运行反馈能够被上下游持续消费，而不是沿技术栈无限扩张个人职责。

## 概念边界

| 比较维度 | 全栈程序员 | 全流程序员 |
| --- | --- | --- |
| 扩展方向 | 前端、后端、数据和部署等技术层 | 问题、建模、任务、实现、验证和运营等知识环节 |
| 共享对象 | 代码、接口和技术栈知识 | 业务上下文、方案意图、工程约束和验证证据 |
| 协同目标 | 减少跨技术层等待 | 减少知识传递、消费和验证损耗 |
| 角色边界 | 容易被理解为掌握所有技术 | 理解上下游，但不替代所有岗位专家 |

## 知识地图

### 1. 技术栈纵向扩张的价值与边界

- [[全栈程序员的生效前提]]：代码集体所有和端到端交付曾让跨技术层理解减少协作阻塞。
- [[微服务的独立交付边界]]：API 使业务能力能够脱离特定前台和用户旅程独立交付。
- [[现代架构下的全栈边界]]：微服务、BFF 和微前端重新划分交付单元，使“一整条栈”不再对应自然交付边界。
- [[全栈能力的知识边界]]：即使能够跨层执行，看懂技术产物也不等于理解业务上下文和架构取舍。

### 2. Agent 横向扩张的授权瓶颈

- [[中心化 Agent 委派的阶段授权瓶颈]]：多 Agent 可以扩大执行带宽；若 Stage Authority 仍汇聚到一个 Human，系统吞吐仍受中央人工 Gate 限制。

### 3. 为什么应该从栈转向流

- [[软件交付中的知识流]]：需求、模型、代码、测试和运行反馈是业务知识在不同环节中的载体。
- [[知识消费]]：知识只有能被下游理解、执行、验证和继续演进，才真正转化为生产力。
- [[统一语言]]：共享概念、规则和示例可以降低跨角色与人机协作中的理解偏差。
- [[全流程序员的上下文扩展]]：优化对象从个人覆盖范围转向上下游知识能否持续保真和被消费。

### 4. Kickoff–Respond 的阶段证据循环

- [[业务问题的分析与建模]]：Kickoff 冻结 Story 边界，Understand 形成可共享的 Scenario 和 Model。
- [[架构与任务分解]]：Tasking 把场景映射为组件职责、Q1/Q2、依赖和可审查计划。
- [[测试策略与实现验证]]：Pair 通过 Red–Green–Refactor 形成可验证增量和测试证据。
- [[上线运营与反馈验证]]：Showcase 作出产品决策，Respond 把运行反馈提升为下一轮 Knowledge 和 Probe。
- [[测试四象限的核心思想和实践要点]]：Q1/Q2 支持交付，Q3/Q4 评价产品，并沿阶段明确质量证据责任。

### 5. AI 时代的可验证交付系统

- [[AI 时代的可验证知识流]]：生成成本下降后，用 Stage State、Assignment、Evidence 和 Gate 维持上下文、约束和责任的可追踪性。
- [[Harness Engineering 的可执行知识流]]：把项目知识、行动边界和验证机制装配为 Agent 可执行、可检查的工作环境。

## 实践落点

- 对个人而言，全流不是成为每个环节的专家，而是能还原上游意图、向下游交付可消费的结果，并根据反馈识别知识失真。
- 对团队而言，关键经验应沉淀为统一语言、模型、任务模板、接口契约、测试、检查清单、工具边界和评审规则。
- 对人机协作而言，人负责问题定义、价值取舍、验收判断和风险责任，AI 更适合检索、生成、执行和汇总证据。
