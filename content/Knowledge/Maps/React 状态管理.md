## 核心判断

- React 状态管理不是“在几个库之间做静态选型”，而是围绕状态作用域、更新复杂度、协作治理和系统边界逐层升级的 [[渐进增强]]。
- 升级顺序不代表替代关系，而代表问题形态的变化：从组件通信，到局部状态，到复杂更新逻辑，到跨层共享，再到外部 store 与跨应用集成。
- 判断是否需要升级的关键不是“哪个库更流行”，而是当前问题是否已经超出上一层方案能低成本解决的范围。

## 这个主题要回答的问题

- 当前状态只是局部 UI 细节，还是已经成为多个组件、多个模块甚至多个应用共同依赖的协作对象？
- 状态管理方案需要增强的是“更新逻辑”“传播方式”“建模粒度”“调试治理”，还是“跨边界集成”？
- 什么时候应该停留在简单方案，什么时候才值得引入外部 store 或更强的工程约束？

## 主题结构

- **组件通信层**：在进入状态管理之前，先判断问题是否只是组件之间的数据传递；如果只是父子、兄弟或跨层传值，优先回到 [[从渐进增强角度理解 react 组件通信方式|组件通信问题]]。
- **局部状态层**：状态只属于单个组件或少数子组件时，优先使用 [[React useState 的问题解决和核心用法|useState 作为最小状态单元]]，避免过早抽象状态流。
- **复杂更新层**：当多个状态片段开始相互影响、更新依赖前一个状态或出现明确状态迁移时，用 [[React useReducer 的问题解决和核心用法|useReducer 集中更新逻辑]]，但不扩大状态共享范围。
- **跨层共享层**：当问题从“怎么更新”变成“怎么让组件树多处消费同一份状态”时，引入 [[React-useContext|useContext 解决传播路径]]，但不要把它误当成高频更新和复杂调试的完整方案。
- **外部 store 层**：当共享范围、拆分粒度、调试需求和协作规模继续上升时，再在轻量 store、原子化建模和治理型数据流之间选择增强方向。
- **跨应用集成层**：当状态不再只属于单个 React 应用，而涉及跨应用、跨团队或跨系统边界时，状态管理会升级为 [[微前端的渐进式集成|渐进式集成问题]]。

## 相关概念 / 下层卡片

- [[React useState 的问题解决和核心用法|useState 是局部状态的最小解]]：适合布尔值、输入框、展开收起、分页页码等结构简单、作用域很小的 UI 状态。
- [[React useReducer 的问题解决和核心用法|useReducer 增强的是更新逻辑]]：适合状态结构复杂、更新依赖前态、一个行为会同时影响多个字段的场景。
- [[React-useContext|useContext 增强的是状态传播方式]]：适合主题、当前用户、语言、轻量 UI 状态等跨层共享需求，但不天然解决高频更新、复杂调试和大规模拆分问题。
- [[React Zustand 的核心作用和使用场景|Zustand 是从 Context 平滑升级的轻量 store]]：适合需要全局共享状态，但更关注开发效率和低心智负担的场景。
- [[React Jotai 的核心作用和使用场景|Jotai 把增强方向转向状态建模粒度]]：适合把状态拆成细粒度 atom，并把依赖关系看成图而不是单棵中心化状态树。
- [[React Redux 的核心作用和使用场景|Redux 把增强方向转向工程治理]]：适合团队规模更大、需要确定性数据流、可追踪性、中间件生态和调试规范的场景。

## 升级判断

1. **只是组件内部状态**：停留在 [[React useState 的问题解决和核心用法|useState]]，不要引入额外状态层。
2. **更新逻辑复杂，但不需要扩大共享范围**：升级到 [[React useReducer 的问题解决和核心用法|useReducer]]。
3. **多个层级需要消费同一份状态**：用 [[React-useContext|useContext]] 解决传播路径。
4. **共享范围扩大，并且更新、拆分或调试开始变复杂**：按增强方向选择 [[React Zustand 的核心作用和使用场景|Zustand]]、[[React Jotai 的核心作用和使用场景|Jotai]] 或 [[React Redux 的核心作用和使用场景|Redux]]。
5. **状态跨应用、跨团队、跨系统边界**：把问题上移到 [[微前端的渐进式集成|微前端集成]] 与系统级状态协作。

## 相关入口

- [[渐进增强|渐进增强提供状态管理的升级主线]]：先用最小方案解决当前问题，再随着复杂度自然增强。
- [[React Hooks|React Hooks 是局部状态和状态逻辑组织的基础入口]]：理解 Hooks 后，才能判断 useState、useReducer、useContext 各自增强的边界。
- [[从渐进增强角度理解 react 组件通信方式|组件通信是状态管理之前的前置分流]]：很多“状态管理问题”其实只是组件通信问题。

## 暂时结论

React 状态管理的演进本质上是一个渐进增强过程：问题没有升级，就不要过度增强；问题一旦升级，就顺着作用域、更新复杂度、协作治理和系统边界自然上移。
