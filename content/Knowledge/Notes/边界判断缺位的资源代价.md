# 边界判断缺位的资源代价

> [!abstract] 核心观点
> 当人没有先划清服务边界或当前工作的相关性边界，系统便会用更多基础设施或模型能力消化本应由设计完成的筛选，边界判断缺位最终转化为持续资源支出。

[[微服务的独立交付边界]]说明，微服务真正需要追求的是围绕业务能力形成合理的独立交付边界，而不是把服务拆得越小越好。边界划分失控后，服务之间的通信、事务、部署、监控和编排成本，只能由更多云基础设施兜底。

LLM 系统中也存在相似机制。人的责任不是逐条手工选择所有材料，而是先定义当前工作的目标、范围、限制以及什么算相关。系统可以在这个边界内自动检索和压缩，但不能把相关性判断完全替换为“把所有知识和记忆塞进 Context，让更强的模型自行筛选”。

| 比较层次 | 云计算时期                                         | LLM 时期                                                         |
| -------- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 原本价值 | 微服务强调 bounded context、独立部署和团队自治     | LLM 根据当前工作处理相关知识、记忆与材料                         |
| 人的责任 | 人负责划定合理的服务边界                           | 人负责定义工作目标并判断什么与当前工作相关                       |
| 叙事偷换 | 从“边界清楚”变成“服务越小越先进”                   | 从“提供相关信息”变成“知识、记忆集成得越多越强”                   |
| 直接结果 | 服务拆分过碎，产生网络、事务、监控和编排成本       | 相关与无关信息混入 Context，产生噪声、冲突、延迟和注意力稀释     |
| 补救方式 | 用 Kubernetes、Service Mesh 和更多云服务治理复杂度 | 用更长 Context、更大参数和更新模型筛选信息                       |
| 商业后果 | 边界判断缺位，协调成本变成云账单                   | 相关性判断缺位，筛选成本变成 Token 和模型账单                    |
| 更优方向 | 根据真实业务边界选择合适粒度，而不是越小越好       | 人先确定工作边界，再将知识局部化、压缩并按需加载，而不是越多越好 |
| 核心原则 | 云基础设施不能代替人的架构判断                     | 大模型不能代替人对工作相关性的判断                               |

这一判断把[[大代码库里如何管理上下文|正确上下文依赖人的导航]]扩展为更一般的原则：没有在设计层消化的复杂度，最终会在资源消费层付费。

它也与[[记忆 Memory]]形成呼应：Context window 是当前工作的工作台，不是等待模型自行筛选的知识仓库。

> [!note] 判断边界
> 这里比较的是两种相似的资源激励结构，并不等于已经证明厂商有意制造技术债；“供应商主动强化扩容叙事”仍属于需要单独寻找证据的判断。
