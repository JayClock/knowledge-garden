# 全流程序员的上下文扩展

> [!abstract] 核心观点
> 全流程序员扩展的是沿交付知识流理解上下游、保存意图并消费证据的能力，而不是包办所有岗位职责。

全流程序员扩展的是自己的**上下文边界、判断能力和知识消费能力**，而不是把业务分析、产品、架构、开发、测试和运维全部变成一个人的职责。关键不在于亲自完成每项工作，而在于能够还原上游意图、向下游交付可消费结果，并根据反馈识别知识失真。

画布中的交付主循环包含六个阶段：

`Kickoff → Understand → Tasking → Pair → Showcase → Respond → 下一轮 Probe`

这六个阶段可以映射为四组需要持续掌握的能力：

1. **Kickoff + Understand｜[[业务问题的分析与建模|问题分析与建模]]**：从信号和候选 Story 中对齐问题边界，再用场景与模型形成共同上下文。
2. **Tasking｜[[架构与任务分解|架构与任务分解]]**：把 Scenario 和 Model 映射为组件职责、依赖、Q1/Q2 测试以及可审查计划。
3. **Pair｜[[测试策略与实现验证|实现与验证]]**：通过短反馈循环把计划转成可验证增量，并保留执行和测试证据。
4. **Showcase + Respond｜[[上线运营与反馈验证|产品评价与运行学习]]**：用产品观察作出接受或回退决定，再把运行反馈提升为 Knowledge 和下一轮 Probe。

每个阶段都应同时回答三类问题：

- **输入是否可消费**：我能否还原上游产物背后的意图、成立条件和版本？
- **处理是否有边界**：谁以什么角色处理，拥有什么权限，何时需要 Handoff 或升级？
- **退出是否有证据**：我能否把判断转成下游可以理解、执行和验证的 Evidence？

因此，全流不是把所有角色合并成一个人，而是让 Human 与 Agent 都能在明确角色和边界内参与同一知识流。生成和执行可以被分配，价值取舍与组织问责仍需要人承担；阶段是否继续前进，则应由共享状态、可消费证据和显式 Gate 决定。参见 [[AI 时代的可验证知识流]]。
