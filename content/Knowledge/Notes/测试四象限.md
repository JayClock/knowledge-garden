# 测试四象限的核心思想和实践要点

> [!abstract] 核心观点
> 测试四象限按“支持团队／评价产品”和“业务导向／技术导向”区分测试用途，使质量活动能够在业务建模、任务分解、TDD 和产品验收之间合理分工。

测试策略不是把测试类型按技术名称装进四个盒子，而是根据**测试的目的**和**测试的受众**设计验证流程。同一种测试技术可能因用途不同进入不同象限；真正重要的是它回答什么问题、服务谁的判断，以及在哪个阶段被生产和消费。

| 象限                 | 目的与受众          | 核心问题                      | 常见证据                                     | 主要阶段                      |
| ------------------ | -------------- | ------------------------- | ---------------------------------------- | ------------------------- |
| **Q1 · 技术导向／支持团队** | 给技术人员快速反馈并定位失败 | 失败具体发生在哪里？                | 领域、组件、Adapter、契约测试                       | [[架构与任务分解]]；[[TDD 与结对编程]] |
| **Q2 · 业务导向／支持团队** | 证明预期业务行为       | Given / When / Then 实现了吗？ | 功能测试、Story Test、Specification by Example | [[业务建模]]；[[TDD 与结对编程]]    |
| **Q3 · 业务导向／评价产品** | 从功能和用户交互评价产品价值 | 真实使用体验是否合适？               | 探索性、可用性、可访问性、兼容性评价                       | [[产品验收]]                  |
| **Q4 · 技术导向／评价产品** | 评价现实约束下的跨功能特性  | 系统在现实约束下是否可靠？             | 性能、安全、可靠性、容量和可运维性评价                      | [[产品验收]]                  |

## Q1 与 Q2 必须形成支撑关系

每个验收条件都可以形成一组 Q2，用来证明业务场景是否成立；在该验收条件的上下文中，每个可测试任务又形成一组 Q1，用来定位具体功能上下文。架构负责划分这些上下文，测试策略负责保持两层证据之间的对应关系。

只有 Q2 时，团队知道业务行为失败，却不知道哪个组件需要修复；只有 Q1 时，团队知道某个组件失败，却无法说明它影响了哪个用户价值。因此，每个 Q1 应支撑一个 Q2，共享组件可以去重，但不应形成与验收意图无关的测试孤岛。

## 质量活动沿知识流分工

- [[业务建模]]：具体场景和 Then 为 Q2 提供业务预期，并暴露需要进一步评价的风险。
- [[架构与任务分解]]：围绕功能上下文建立 Q1 与 Q2 的对应关系，并选择合适的验证边界。
- [[TDD 与结对编程]]：Q1 帮助快速定位失败，Q2 持续证明已表达的业务行为。
- [[产品验收]]：结合可工作软件、用户旅程与必要的 Q3 / Q4，判断原始问题是否得到解决。

命令通过不能替代产品观察。Q1/Q2 为[[知识工程师#持续知识回流与三层循环|实现知识反馈循环]]和[[知识工程师#持续知识回流与三层循环|功能方案反馈循环]]提供快速感知，Q3/Q4 则让[[知识工程师#持续知识回流与三层循环|业务价值反馈循环]]从业务与技术两个方向评价已经形成的产品；四个象限共同支持从业务理解到产品验收的质量判断。
