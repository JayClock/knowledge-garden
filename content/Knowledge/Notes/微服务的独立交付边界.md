# 微服务的独立交付边界

> [!abstract] 核心观点
> 微服务通过 API 封装可复用的业务能力，使其能够脱离特定前台和用户旅程独立交付。

微服务封装的是可以被多个前台、BFF、内部系统或自动化流程共同消费的业务能力，而不是只服务于几个页面跳转的数据处理逻辑。即使没有某个特定前台，这项能力仍然可以独立演进、发布和复用。

API 在这里分开了两个变化方向：

- 服务内部围绕业务规则、数据一致性和能力演进；
- 上层应用围绕用户旅程、交互和渠道体验进行组合。

例如，商品服务更适合提供商品、价格和可售状态等稳定业务能力，而不是按照某个页面划分出 `detail`、`total` 一类只对当前界面有意义的接口。不同渠道可以在这些能力之上组织各自的用户旅程。

这改变了传统端到端交付的边界，也让“从前到后一条栈”的全栈叙事变得不稳定。本卡回答的是**业务能力为何能够独立交付**；[[现代架构下的全栈边界]]进一步说明这如何使“全栈”失去稳定范围，而[[全栈能力的知识边界]]讨论即使看懂边界内外的代码，为何仍不等于理解跨边界流动的业务规则。

更有价值的能力，是沿着[[全流程序员的上下文扩展|知识流]]理解能力为什么存在、被谁消费，以及一次变化会影响哪些上下游。
