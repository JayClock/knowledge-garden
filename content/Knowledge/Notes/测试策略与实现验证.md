# 测试策略与实现验证

> [!abstract] 核心观点
> Pair 用相互关联的 Q1 / Q2 测试驱动实现，使业务验收意图、组件定位和代码增量形成可追溯证据。

验收条件描述业务场景在什么前提下发生、执行什么行为、期望得到什么结果。它不仅用于项目末尾验收，还应在 Understand 阶段形成 Q2 意图，并在 Tasking 阶段指导功能上下文和 Q1 任务分解。

测试策略需要连接两个层次：

- **Q2｜业务导向、支持团队**：证明 Given / When / Then 场景是否成立，回答“预期业务行为实现了吗”。
- **Q1｜技术导向、支持团队**：在领域、组件、Adapter 或契约粒度定位失败，回答“具体哪里没有满足预期”。

每个 Q1 都应支撑某个 Q2；共享组件可以去重，但不能形成与业务验收无关的测试孤岛。只有 Q2 时，团队知道行为失败却难以定位；只有 Q1 时，团队知道组件失败却无法说明用户价值受到什么影响。

Pair 阶段按照 `Red → Green → Refactor` 推进：先让 Q1 或 Q2 暴露缺失行为，再以最小改动通过测试，最后在证据保持全绿的前提下改善设计。架构决定功能上下文，测试策略决定真实依赖、测试替身、开发顺序和反馈粒度。

Pair 的 Evidence 是执行记录、代码增量和测试结果；退出 Gate 是 `Quality / Increment`。测试命令通过能证明已表达的自动化行为，却不能替代 Showcase 中的产品观察，也不能单独证明原始业务问题已经解决。Q3 / Q4 的风险型评价由[[测试四象限的核心思想和实践要点|测试四象限]]补充。

AI 适合承担测试代码和生产代码的具体生成，并根据失败结果快速修正；人更适合设计验证路径、审查测试是否真的对应需求，并判断证据是否足以进入下一阶段。最终交付的不是孤立代码，而是 Scenario、Plan、Q1/Q2、代码改动和测试结果之间可追溯的证据链；这条证据链还需要通过[[上线运营与反馈验证|Showcase 与真实运行反馈]]继续校准。
