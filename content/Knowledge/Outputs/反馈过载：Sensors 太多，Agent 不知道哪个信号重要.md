> [!info] Agent 交付的七个坏味道 · 07
> 系列基于我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT）。上一篇：[[前馈痴迷：Agent 做完就交，从来没人检查]]

一次任务收尾，屏幕上可能同时出现：构建输出、`UP-TO-DATE`、缓存命中、静态检查警告、文档链接与格式结果、聚合回归、状态诊断，以及任务自己的检查项。

信号多得让人安心。但它们**性质完全不同**：有真实失败，有缓存命中，有环境问题，有历史记录。混在一起时，Agent 会挑错重点。

## 这个坏味道长什么样

不分级的后果是两个极端：

- 把“缓存命中”当成“刚跑过”、把“历史通过”当成“现在通过”、把“结构通过”当成“业务批准”；
- 或者反过来，在一堆警告和几个测试失败之间随机挑一个改，改好一条又弄坏另一条。

共同特征是：**看起来在动，但没有方向**。

## 解法：成功静默、失败完整、按证明力分级

### 成功静默，失败才输出

- 检查器成功时只在标准输出写一行摘要（文档数、链接数、错误数），失败时才把逐条错误写到标准错误并返回非零退出码；
- 状态脚本的“下一个任务”只输出当前候选任务的 JSON，“校验”只输出结构与新鲜度事实，不输出解释性长篇；
- 入口文件写明验证原则：**选择能证明改动行为的最窄、最安静的检查，完整保留失败输出**；
- 运行记录只保存紧凑清单（命令、退出码、时长、环境、输入摘要、日志哈希指针），不复制完整输出——过期记录会被清空，避免噪声稀释当前信号；
- 聚合测试命令串联应用、扩展、技能与文档四段检查，任何一段非零都会让整体失败，不吞掉失败。

一条经验：**工具的默认详略是给调试用的，不是给判断用的**。给人看的输出必须是判断所需的最小集合。

### 按严重程度分级

| 级别   | 典型信号                                                                               | 处理方式                                           |
| ------ | -------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 阻塞级 | 当前任务检查失败、编译/测试/静态分析失败、前置任务未完成、来源或前馈未就绪、环境不可用 | 修完才能继续；环境不可用记为阻塞，不伪装成业务失败 |
| 警告级 | 不阻塞的构建配置警告、语义存疑、既有失败的历史线索                                     | 记录为证据或缺口，不阻塞本轮通过                   |
| 信息级 | 缓存命中、up-to-date、实际执行计数、文档与链接统计、历史检查记录                       | 只作上下文，不当作新运行或当前证据                 |

真实记录里三层是分开写的。例如一次交付会写明：本次强制重跑后有 19 个构建任务实际执行，23 个测试类 148 项测试 0 失败；而默认运行时是 35 个任务全部命中缓存，那属于信息级。缓存命中不是失败，也不是结果。

三层的分界不只是严重程度，也是**责任分界**：阻塞级是 Agent 必须处理的；警告级由 Agent 给出事实、由人决定是否继续完善；信息级只作上下文，通常可以直接转成前馈。再细分只会让 Agent 花力气判断级别，反馈过载换个形式回来。

### 按证明力分级

比严重程度更容易被忽略的是证明范围。项目要求区分三种东西：结构校验、运行验证和人工业务判断。

- 结构自洽、文件写入和命令成功，不能替代业务批准；
- 每条质量命令都配“实际覆盖 / 不证明什么”两栏，让一个信号只承担它能证明的范围；
- 导航文档直接注明：状态脚本检查任务结构，不替代语义检查；文档检查器检查链接与格式，不证明任务就绪。

分级之后，Agent 面对“文档检查通过、测试通过、身份缺口仍未解决”的局面时，不会把绿色读成业务完成，也不会把开放中的缺口误当成现在必须修的测试失败。

### 注意力纪律：只加载需要的信号

反馈过载的另一半来自上下文。把所有指南、全部任务、整个知识库一次性塞给 Agent，重要信号同样会被淹没。所以：按任务选择必要前馈，同一来源只加载一次，长文件只读相关章节与真实源码符号；执行时只加载当前任务的记录、直接前置产物和它引用的来源。

任务状态集中在一个文件的一个字段上，也减少了重复信号——同一件事有两个记录，就等于有两个真相。

### 分级同时是处理顺序

把优先级写成动作而不是标签：

| 情形                           | 动作                         |
| ------------------------------ | ---------------------------- |
| 编译或测试失败                 | 在当前文件范围内修复并重跑   |
| 检查不能证明业务预期           | 修订测试设计，而不是放宽断言 |
| 任务之间有重复或缺失的工作单元 | 停止实施，回到计划           |
| 来源改变                       | 停止使用旧证据，重新编译     |
| 缺业务事实                     | 记录缺口并交回               |
| 环境不可用                     | 标记为阻塞                   |
| 全部通过                       | 写入证据并停止               |

**分级不只是显示顺序，也是修复顺序。**

### 分级不等于隐瞒或降级

反面清单同样是硬约束：

- 失败不得被改写成通过：不删失败测试、不改业务预期、不手改机器报告；
- 缓存命中不得描述为新运行；需要复验时使用强制重跑参数；
- 环境失败与实现失败分开记录，环境阻塞不伪装成业务测试结果；
- 历史检查只在输入、环境和依赖仍有效时作为有限的前置证据；旧记录清空后不再充当证据；
- 完整失败输出保留在工作流日志、合并请求描述或授权保留的运行记录里，即使记录本身只留摘要。

## 演进方向

- 目前没有统一的分级规范文件，也没有把质量命令输出自动分级的开关；分级依赖记录时的字段结构与人工判断；
- 构建与任务编排工具的原生输出仍然较长，任务记录是人工收敛后的摘要；信号继续增多时，可以为常用命令提供静默模式或统一的三级汇总入口；
- 三层的划分目前是示例性的，尚未成为规则字段；语义判断与人工评估无法自动分级，需要在任务内显式说明。

## 收束

反馈不是越多越好，而是要**可比较**。一个信号的价值不在于它说了什么，而在于它能不能被放进一个确定的处理顺序里。信号越多、越没有层级，Agent 就越接近随机行走——看起来很忙，方向由噪声决定。
