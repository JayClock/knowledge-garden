# Agent 不会感到技术债之痛

访谈里有一个很重要的判断：**人会感到代码库复杂带来的痛苦，Agent 不会**。

人类工程师在一个混乱代码库里工作，会被重复逻辑、错误抽象、隐式状态、脆弱测试和难以定位的问题折磨。这个痛感会反过来推动重构：把职责拆开，把命名改清楚，把测试补上，把边界重新划定。

Agent 没有这种“未来维护者”的身体感。它不会在下周继续背负今天多写的抽象，也不会因为一次随手生成的 helper 让排查成本上升而焦虑。它的即时目标通常是完成当前任务、让测试通过、让用户满意。于是它很容易选择局部最短路径：再加一层判断、再复制一段逻辑、再写一个工具函数、再补一个兼容分支。

这就是 AI 生成代码的核心风险：它未必马上失败，但会更快地增加系统熵。功能看起来完成了，代码库却更难理解；PR 看起来很勤奋，维护成本却被转嫁给未来。

所以，AI 时代的工程治理必须把“痛感”外部化，不能指望 Agent 自发感知技术债。

可以外部化的痛感包括：

- 复杂度指标：函数长度、循环复杂度、重复代码、依赖方向。
- 自动检查：typecheck、lint、test、format、dead code 检测。
- 架构约束：模块边界、禁止跨层依赖、核心路径变更必须 review。
- PR 约束：小步提交、变更说明、影响范围、验证证据。
- 重构机制：定期把 Agent 产出的“能跑代码”整理成“可维护代码”。

更重要的是，工程师要在 review 中专门问一类问题：这个实现有没有增加未来理解成本？它是不是为了当前任务牺牲了系统一致性？它有没有把临时知识固化成长期结构？

Agent 可以帮我们更快地写代码，但它不会自动替我们维护代码库的健康。技术债之所以叫“债”，是因为未来有人要还。AI 时代真正危险的地方在于：借债速度变快了，而痛感却被延迟了。
