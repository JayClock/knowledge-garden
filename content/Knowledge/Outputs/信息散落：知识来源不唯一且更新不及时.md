> [!info] Agent 交付的七个坏味道 · 03
> 系列基于我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT）。上一篇：[[隐式约定：规则只存在于人的脑子里]]

知识进了仓库，不等于知识是对的。

业务事实、接口契约、软件范围、架构决定、工程规范、任务状态——它们分散在不同文件里，各有各的更新节奏。只要有一处落后于来源，Agent 就会非常自信地按旧版本执行，而且不会报错。

## 这个坏味道长什么样

一个中等规模的仓库里，同一件事通常有三个以上版本：权威来源、生成投影、以及某个人的聊天记录。常见症状：

- 把生成产物或上次通过的检查当成当前事实；
- 用模型摘要替代架构、规范与代码的真实变化；
- 沿用没有核对版本的上游文档；
- 生成的 wiki 页面在源码改动后仍被当作导航依据；
- 计划还是按旧的接口文件编译的，却已经在派发任务。

最后一条最危险：任务看起来在正常执行，实际上执行的是一个已经不存在的契约。

## 解法：把每条知识当作对外部来源的依赖

来源唯一、随计划登记、开工核对、摘要绑定。四件事都做到，知识过期才会变成一个**可以被检测的事件**，而不是一个悄悄发生的错误。

### 来源唯一，并规定冲突怎么裁决

不变量先定死事实源：业务事实只在业务模型目录，API 设计只在接口设计文件；软件范围、实现设计与当前代码行为分别记录、不能相互冒充，生成产物不是新的事实源。

然后由[来源与冲突处理表](https://github.com/JayClock/Evidence-Framework/blob/main/docs/guides/index.md)为每类问题指定唯一权威位置，并列出“不可替代它的内容”——生成报告、过期 OpenAPI、代码现状都不算数。冲突时停止受影响行动，交由对应拥有者确认，不能按修改时间或“代码已经这样写了”裁决。

### 来源登记：把依赖写成字节，而不是写成约定

[计划文件](https://github.com/JayClock/Evidence-Framework/blob/main/docs/plans/smart-domain/plan.yaml)里的 `sourceManifest` 逐条登记本次交付消费的来源，每条包含路径、稳定的源 ID、适用章节和 sha256 摘要：

```yaml
sourceManifest:
  - path: .evidence/fm/model.yaml
    digest: 45204ba1ba5d5c302f575da64d0982a04e483f894681db1d6a701f1853fabf30
    sourceRefs:
      - context.sales-performance
      - context.customer-information
    purpose: 电话销售绩效协议切片的业务来源；只提供业务事实，不构成软件范围批准。
```

任务再用 `sourceRefs`、`procedureRefs` 声明自己实际消费了哪些来源。于是“知识依赖升级”不再是一句纪律，而是一次可以检测的字节差异：来源变了，摘要不匹配，编译结果失效，必须先重算。

生成物同样带版本。[OpenWiki](https://github.com/JayClock/Evidence-Framework/tree/main/openwiki) 会把每条结论绑定到具体文件，并记录文件级内容版本：

```json
{ "resource": "repo://AGENTS.md", "version": "repo-file-v1:sha256:e46f7179..." }
```

### 开工核对新鲜度，而不是假设新鲜

进入实施前的检查清单里，第三项专门问：依赖是否完成？来源摘要、规范与架构变化、当前代码与检查环境，是否已经让旧证据失效？

这条纪律被写进两个地方：交付流程要求判断哪些业务来源、架构、规范、操作文档、代码或环境变化会让旧证据失效，并明确**不能用模型摘要代替全部新鲜度判断**；计划模板把同样的要求保存在每个任务的 `freshnessRisks` 字段里。

只读状态检查也不假装自己做过这件事。每次运行都会输出一行事实：

```text
sourceFreshness: "not-checked; recompile FM/API inputs before delivery"
```

它提醒你：结构检查通过，不等于来源新鲜。

### 防过时：摘要与版本绑定

| 机制     | 绑定方式                                                                                   |
| -------- | ------------------------------------------------------------------------------------------ |
| 模型校验 | 绑定相对路径与字节内容；标记检查期间输入变动；旧记录不证明当前版本                         |
| 运行记录 | 只保存紧凑清单（命令、退出码、环境、输入摘要、日志 sha256 指针），旧记录清空后不再充当证据 |
| 输入摘要 | 模型、接口、计划各自记录输入与输出的 sha256；不一致时重新编译                              |
| 外部上游 | 固定上游文档的 commit 与核对日期；“main 是定位入口，不是可复现版本标识”                    |
| 生成页面 | 每页记录 `gitHead`、`sourceFingerprint`、`pageVersion` 与完成本次生成的运行 ID             |

生成出来的字节本身也被当成有版本的依赖：投影与派生交付按权威字节交付，格式化工具被配置为不改写生成物，使“用同样的输入逐字节复现”成为可验证的承诺。

### 主动刷新：定时工作流而不是定时提醒

[OpenWiki 更新工作流](https://github.com/JayClock/Evidence-Framework/blob/main/.github/workflows/openwiki-update.yml)每天 08:00 UTC 或手动触发一次，做几件很具体的事：

- `fetch-depth: 0` 拉全历史，让更新能 diff“上次记录到哪个 commit”——浅克隆会退化成空变更摘要；
- 产出走 `openwiki/update` 分支的 PR，并限定可写路径，机器负责刷新，人工合并即审核；
- `continue-on-error` 加 `create-pull-request`：生成失败时仍保留已完成页面，最后由 `exit 1` 把工作流标红；
- 用忽略文件限定读取集，排除依赖、构建与临时输出；运行基线由 manifest 与 last-update 文件推进。

一个细节值得抄：**失败时保留部分成果，但仍然标记失败**。既不因为一次失败丢掉全部产物，也不假装这次运行是成功的。

## 生成物不是事实源

生成的 wiki 在入口文件里被显式降级：它是可选的即时上下文，不是启动必读；源码与测试才是权威；其中列出的未知项与待复核项是验证缺口，不是需求；不要手改生成页面，要改源码或文档让它重新生成。

同一方向的还有检查范围：Guides 检查器只扫描维护中的文档，生成页面不在其中；测试指南明确“生成产物、业务源文件、历史证据和第三方材料不重写为前馈”。

## 演进方向

- 当前没有单一的来源清单文件：来源映射分散在权威表、计划的来源清单、上游依据与生成页元数据中；外部来源变多时再补一份显式清单并入定时核对；
- 非仓库知识源仍靠固定 commit 加人工核对；变化频繁时再建立定时同步；
- 生成内容目前只跑代码模式，需要接入外部连接器时在工作流里追加对应密钥即可。

## 收束

在 Agent 参与交付之后，“文档可能过期”这件事的性质变了：以前它浪费一个人的时间，现在它会稳定地、批量地、无人质疑地执行一个已经作废的决定。把过期变成可检测的字节差异，比反复强调“记得更新文档”有效得多。
