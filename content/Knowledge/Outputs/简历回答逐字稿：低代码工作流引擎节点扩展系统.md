# 简历回答逐字稿：低代码工作流引擎节点扩展系统

关联：[[简历追问：低代码工作流引擎节点扩展系统]]、[[项目介绍：企业级低代码工作流引擎]]。

## 30 秒开场

工作流协议是编辑器与执行引擎之间的执行契约。为了让契约能持续增加新节点，我用 `NodeRegistry + NodeExecutor` 把节点逻辑从核心调度器中拆开：注册中心按类型查找执行器，核心只负责校验、调度、上下文和结果存储，前端配置表单也按节点类型注册。新增节点不需要继续修改调度器的 `switch-case`。

## 如果面试官问：一个节点插件具体包含什么？

项目里确认的执行器抽象可以简化为：

```ts
interface NodeExecutor<TConfig = Record<string, unknown>> {
  type: NodeKind
  validate?(config: TConfig): ValidationResult
  execute(nodeId: string, config: TConfig, context: ExecutionContext): Promise<NodeResult>
  getOutputSchema?(config: TConfig): OutputVariableSchema[]
}
```

`NodeRegistry` 维护节点类型到执行器的映射，`WorkflowEngine` 只依赖这个抽象。前端配置表单由单独的设置注册表按节点类型加载，通过配置与执行解耦，保证了引擎内核的高内聚。

## 如果面试官追：注册模式和策略模式体现在哪里？

注册模式体现在核心引擎维护一个 registry，比如 `registry.register('http', new HTTPExecutor())`。调度器拿到节点 type 后，从 registry 取 executor，而不是写一堆 `switch-case`。

策略模式体现在不同节点有不同执行逻辑和校验方式。HTTP 节点处理请求配置，Condition 节点执行判断并选择分支，Start 与 End 节点负责明确流程输入和输出边界。核心只约定输入、输出、上下文和错误边界，具体策略由节点实现。

## 如果面试官追：新增节点要改哪些地方？

以现有 HTTP 或 Condition 节点为例：定义节点配置和输出，增加对应配置表单，实现 `NodeExecutor`，再注册到执行器注册中心和前端设置注册表。核心调度器不需要新增按类型分支。

## 如果面试官追：插件抛错怎么办？

执行器外层统一处理配置校验、变量解析、错误捕获、耗时记录和输出存储，不能让每个节点重复实现公共流程，保证了单个节点异常不会导致主执行进程崩溃。

## 如果面试官追：历史流程配置怎么兼容？

历史配置兼容是节点体系继续演进时值得考虑的能力，可以通过节点版本号与 migration 函数实现旧配置的平滑升级。

## 如果面试官问：这个插件体系为什么体现渐进式架构？

渐进式不等于动态加载。这里先把 `WorkflowDefinition`、图校验、调度、`ExecutionContext` 和结果存储稳定为编辑器与运行时共同消费的执行契约，再让具体节点以 `NodeExecutor` 策略接入。新增 HTTP、Condition 或其他节点时，变化留在执行器、Schema 和配置表单，核心调度器不需要继续增加类型分支。

这种架构确保了核心调度引擎的稳定性，将业务变化完全隔离在扩展插件边界之内。

## 收尾句

所以当前已完成的核心，是用注册中心和执行器抽象把节点逻辑从调度器中拆开，并让前端配置也按类型注册。配置迁移和统一全栈插件协议是下一阶段可以继续完善的方向。
