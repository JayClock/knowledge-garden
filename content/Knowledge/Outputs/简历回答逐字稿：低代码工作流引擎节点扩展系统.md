# 简历回答逐字稿：低代码工作流引擎节点扩展系统

关联：[[简历追问：低代码工作流引擎节点扩展系统]]、[[15分钟：低代码平台]]。

> [!warning] 回答边界
>
> - 个人直接实现的是 `NodeRegistry + NodeExecutor`、基础执行流程、节点配置注册表及 Start、HTTP、Condition、End 等节点扩展。
> - 配置迁移、Webhook 节点和统一全栈 `NodeDefinition` 属于延展示例，不是当前确认的生产成果。
> - NestJS 与 SSE 服务端由后端同事实现；这里主要讲相关 TypeScript 引擎与编辑器机制。

## 30 秒开场

工作流会持续增加新节点，我用 `NodeRegistry + NodeExecutor` 把节点逻辑从核心调度器中拆开。注册中心按类型查找执行器，核心只负责校验、调度、上下文和结果存储；前端配置表单也按节点类型注册。新增节点不需要继续修改调度器的 `switch-case`。

## 如果面试官问：一个节点插件具体包含什么？

项目里确认的执行器抽象可以简化为：

```ts
interface NodeExecutor<TConfig = Record<string, unknown>> {
  type: NodeKind
  validate?(config: TConfig): ValidationResult
  execute(nodeId: string, config: TConfig, context: ExecutionContext): Promise<NodeResult>
  getOutputSchema?(config: TConfig): OutputVariableSchema[]
}
```

`NodeRegistry` 维护节点类型到执行器的映射，`WorkflowEngine` 只依赖这个抽象。前端配置表单由单独的设置注册表按节点类型加载。把前端组件、配置 Schema、版本迁移和执行器全部合成一个全栈 `NodeDefinition` 是可演进方向，不是当前实现的逐字还原。

## 如果面试官追：注册模式和策略模式体现在哪里？

注册模式体现在核心引擎维护一个 registry，比如 `registry.register('http', new HTTPExecutor())`。调度器拿到节点 type 后，从 registry 取 executor，而不是写一堆 `switch-case`。

策略模式体现在不同节点有不同执行逻辑和校验方式。HTTP 节点处理请求配置，Condition 节点执行判断并选择分支，Start 与 End 节点负责明确流程输入和输出边界。核心只约定输入、输出、上下文和错误边界，具体策略由节点实现。

## 如果面试官追：新增节点要改哪些地方？

以现有 HTTP 或 Condition 节点为例：定义节点配置和输出，增加对应配置表单，实现 `NodeExecutor`，再注册到执行器注册中心和前端设置注册表。核心调度器不需要新增按类型分支。

Webhook 可以用来解释同样的扩展流程，但它不是当前已确认的内置节点，回答时必须说是示例。

## 如果面试官追：插件抛错怎么办？

执行器外层统一处理配置校验、变量解析、错误捕获、耗时记录和输出存储，不能让每个节点重复实现公共流程。

项目可以确认有统一错误捕获和日志反馈；标准 `NodeExecutionError` 字段、retry 策略和失败分级没有完整进入当前主档，因此只能作为继续工程化时的设计方向。

## 如果面试官追：历史流程配置怎么兼容？

历史配置兼容是节点体系继续产品化时必须补的能力，可以通过节点版本和 migration 迁移旧配置。

现有已确认事实没有确认节点配置迁移和历史快照兼容测试已经实现，所以这部分只讨论演进方案，不能说成当前系统已有能力。

## 收尾句

所以当前已完成的核心，是用注册中心和执行器抽象把节点逻辑从调度器中拆开，并让前端配置也按类型注册。配置迁移和统一全栈插件协议是下一阶段可以继续完善的方向。
