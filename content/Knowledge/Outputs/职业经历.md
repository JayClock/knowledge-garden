# 职业经历

## 当前定位

5 年以上软件开发经验，对外求职定位为“全栈偏前端的平台工程师”，行业暂不限制。能力基本盘是 React、TypeScript 与复杂前端平台，同时能够参与业务问题澄清与建模，主导资源和 API 契约、复杂前端、新服务及验证反馈的工程落地；涉及对现有后端项目的侵入性修改时，与原负责人协作。全栈能力不是为了弱化前端优势或替上下游做决策，而是为了沿软件交付知识流贯通问题、模型、契约、执行、验证与运行反馈。长期探索方向是软件交付语境中的[[知识工程师]]：让跨角色知识被准确消费，并借助 AI 持续转化为可验证的软件和团队能力。

稳定的能力主线起源于多端一致性问题。在上海易校的低代码平台中，PC Web 与移动 Web 需要重复维护资源状态、角色、权限和动作判断；为控制规则漂移，我先设计 HATEOAS TypeScript SDK，让不同客户端消费同一套 relation 与 action 契约。落地过程中进一步认识到，SDK 只能降低契约消费成本，不能补救资源边界、生命周期和接口语义本身的混乱，因此继续向上游扩展到业务／领域建模与 RESTful API。上游契约稳定后，再通过 SDK、Schema、OpenAPI 和生成协议把知识交给客户端、执行器与 AI 消费，并通过测试、人工审核、运行状态和监控证据验证消费结果，使反馈能够返回模型、契约或实现。

当前较有代表性的能力主线：

- 复杂前端与平台交互：类 Figma 编辑器、React Flow 建模与工作流编辑器、Tiptap 变量编辑器、动态属性面板，以及视口、拖拽、状态反馈和弱网错误处理。
- 上游模型与资源契约：使用 8X Flow、四色建模澄清合同、权责、业务事件和生命周期，再据此设计 RESTful URI、聚合边界、HATEOAS relation 与动作契约。
- 工程消费接口：使用 TypeScript SDK、React Hooks、HAL / HAL-FORMS、Schema 与 OpenAPI，让客户端、插件、执行器和生成工具能够按统一协议消费模型与契约。
- 可执行与可协作系统：把模型转化为低代码 Schema、工作流 DAG、变量协议和版本快照，并使用 Yjs、WebSocket、Awareness 与 PostgreSQL 支撑多人共享模型。
- 验证与 AI 质量控制：通过运行时校验、单元测试、契约测试、E2E、双浏览器联调、结构化 Proposal、人工审核和质量门禁约束交付结果。
- 运行反馈：通过工作流执行状态、日志、错误反馈及监控 SDK 收集真实运行证据，支持问题返回实现、契约和上游判断。

## 能力演进与知识流闭环

第一阶段是从复杂前端实现走向多端契约。HATEOAS 项目的起点不是后端架构兴趣，而是 PC Web 与移动 Web 的状态和权限规则反复复制；为了让客户端不再各自解释业务状态，我把“当前资源能做什么”收敛为服务端资源表达，并实现统一的 TypeScript 消费层。

第二阶段是从契约消费倒推模型与 API。HATEOAS 落地让我意识到，稳定 relation 的前提是资源本身被正确识别，动作语义也要符合对象生命周期；因此继续学习和实践业务／领域建模、RESTful API 与 HATEOAS 契约设计。这不是从前端转向纯后端，而是为了从根源上稳定复杂前端所消费的知识。

第三阶段是建立从模型到工程实现的消费路径。HATEOAS SDK 与 React Hooks 把资源关系和动作契约交给多端客户端消费；低代码 Schema、工作流协议和执行引擎把模型转化为可运行系统；协同建模平台则把发布模型继续交给 OpenAPI、测试数据和下游代码生成。SDK 是连接契约与工程实现的桥梁，但不是下游的全部。

第四阶段是验证消费结果并形成知识回流。单元测试、契约测试和 E2E 验证预期行为，结构化 Proposal 与人工审核控制 AI 变更，工作流运行状态和监控 SDK 提供真实执行证据；不同证据再返回任务、实现、接口契约或业务模型，而不是停留在下游成为孤立数据。

在易校工作后期，我同时判断 AI 正在显著降低定制软件的开发成本，传统低代码平台以“降低定制成本”为核心的优势会被削弱，因此把职业重心从低代码前端架构继续扩展到全栈平台与 AI 工程化。“全栈工程师”是当前市场中更容易识别的名称，实际探索目标是[[知识工程师|软件知识工程师]]。

#### 完整产品链路与用户体验实现

1. 用户打开项目或导入 `.fig`。项目加载期间显示 `Loading project...`，读取失败则进入独立错误页面；成功后把项目文档转换为 EditorSession 使用的编辑模型。
2. 用户在 Agent 面板输入需求。空 Prompt 的发送按钮保持 disabled；任务启动后发送按钮切换为取消按钮，Enter 不会重复提交，主进程也会拒绝同时启动第二个 Generation Run。
3. Orchestrator 先校验初始文档，再由 Coordinator 生成 Design Variables 和受 JSON Schema 约束的 Plan；Plan 最多包含 5 个 Assignment，并为每个区域写入脚手架。
4. 每次 Variables、脚手架、Fragment 或视觉修复更新都会立即写入项目存储，并通过 `document-updated` 事件替换渲染端文档；渲染端按 revision 确认收到更新后，主进程才继续推进。
5. 多个 Collaborator 并行生成受 Schema 和运行时解析约束的 Fragment。合并操作通过串行 merge queue 依次执行，并使用 `expectedRevision` 检查版本；成功 Fragment 直接替换对应脚手架。
6. 单个 Collaborator 失败时不会让整个任务退出：系统保留该区域的 placeholder，记录失败 Activity、错误原因和 placeholderNodeId，其他区域继续生成，Run 仍可完成。Agent 面板以红色失败图标展示 Activity，并在区域摘要中说明“已生成占位结果”和具体原因。
7. 完整文档进入 Visual Harness 后，系统检查层级、间距、对齐、排版、对比度、溢出和需求满足度；失败时只替换问题 nodeId，默认最多自动修复两轮。超过上限后 Run 进入 failed，并保留当前已生成文档。
8. 用户可以随时取消生成。取消通过 AbortSignal 终止执行，将 Run 持久化为 cancelled；已经写入项目的 Variables、脚手架、Fragment 或修复结果不会自动回滚。
9. Run 结束后，输入区恢复为可提交状态。当前没有独立 Retry 按钮，用户通过调整 Prompt 后重新发起任务；最新 Run 和 Activity 会按项目保存，并在重新打开项目时恢复到 Agent 面板。
10. 编辑器当前支持单节点选择、节点创建、拖拽移动、跨容器重新挂载、内联文字编辑，以及尺寸、位置、Flex Layout、Gap、Padding、填充、描边、效果、圆角和文字等属性修改。项目每 2 秒比较一次标题与文档指纹；若保存进行中又出现变化，则在当前请求完成后补做一次保存。

当前完成标准是：生成流程进入 completed、failed 或 cancelled 终态，最新 Run 与 Activity 已持久化，渲染端与项目存储保存相同 revision 的当前文档，并且已生成结果仍可在编辑器中继续修改。

- 将 LLM 的职责限制在 Variables、Plan、Fragment、Visual Check 和 Repair 的结构化生成，把 Schema 约束、运行时解析、revision 检查、文档组装和历史持久化交给确定性程序执行。

#### 设计 DSL 与可视化编辑器

- 设计 Frame、Rectangle、Ellipse、Icon、Text 等核心节点的可辨识联合类型，以及布局、填充、描边、阴影、文字和 Design Variables 等正交属性模型。
- 使用编译时类型与运行时 guard / diagnostics 校验不可信的 AI 输出、文件导入和用户数据，并通过规范化处理统一单值、多值与缺省字段。
- EditorSession 以不可变文档替换和订阅通知统一图层面板、视口与属性面板状态；当前源码没有实现撤销重做历史栈。
- 视口层处理 camera、zoom、世界坐标、节点路径命中和单节点选择；拖拽过程维护交互草稿，结束时再向 EditorSession 提交位置修改或 reparent 命令。
- 图层面板将嵌套节点展平为可展开树结构，支持层级展开、节点选择以及选中节点祖先自动展开；当前可见性图标只用于展示，没有重命名、隐藏或锁定操作。
- 使用 Schema 注册表和 React Hook Form 驱动右侧属性面板，根据节点类型动态生成位置、布局、外观和文本等属性编辑器，并支持 Flex Layout、Gap、Padding、对齐、填充、描边、效果和文字属性。
- 画布当前为 React DOM 渲染的视口与覆盖层组合，不是 Canvas 2D；当前选择模型只保存一个 `selectedNodeId`，没有框选、多选、批量编辑或吸附对齐实现。
- 自动保存采用 2 秒定时检查而不是防抖：标题或文档指纹变化时写入项目；保存过程中若再次变化，则在当前请求结束后补做一次保存，组件卸载时也会触发保存检查。
- 实现本地 `.fig` 归档从 ZIP 解包、二进制解码、父子关系重建，到节点和样式映射为内部 DSL 的 ETL 流程；当前实现仍存在 Auto Layout、组件实例、复杂矢量节点和样式去重等边界。

#### Agent 生成与质量闭环

- 设计 Codex Provider 抽象层，通过子进程调用 Codex CLI，解析 JSONL 事件流，并以 Thread ID 支持会话延续；Provider 接口隔离具体 Agent Runtime，保留替换实现的空间。
- 实现 Coordinator + Collaborator 的多智能体编排：Coordinator 先生成全局 Design Variables，再将页面拆成最多 5 个 Assignment；规划区域以脚手架写入项目，多个 Collaborator 随后并行生成 Fragment，并通过串行合并队列逐个替换对应区域。
- 使用 Generation Run 状态机表达 queued、preparing、designing、validating、repairing、completed、failed 和 cancelled 等阶段，并将 Activity 作为可观察、可追溯的执行记录。
- 通过统一事件分发生成进度、阶段变更、错误和流式增量，使编辑器可以持续反馈执行过程，并允许用户在明确的任务状态下取消生成。
- 通过 Assignment 与固定 regionId 约束 Fragment 归属，使用共享 Design Variables 控制视觉一致性，并以 `expectedRevision` 检查 Variables、脚手架、Fragment 和 Repair 写入时的版本冲突。
- Fragment 解析会检查格式版本、Assignment 对应关系、固定 regionId、节点结构和重复 ID；文档组装继续检查目标节点、父节点类型及最终文档有效性。
- 当前生成结果会通过 `onDocumentUpdated` 直接写入项目并替换渲染端文档；源码中没有 DesignPatch、pending / applied / rejected 用户确认流程，也没有选中节点后的 `update_nodes` AI 增量编辑。
- 构建记忆、规划、实施、验证四层 Harness：历史记录采用项目隔离、串行队列和临时文件加 rename 的原子写入；规划产出结构化任务；实施阶段完成分片生成与文档组装。
- 使用 JSON Schema 约束 plan、variables、fragment、visual-check 和 repair 等阶段产物，并采用原生 Schema 注入、Prompt 降级、容错 JSON 提取和运行时二次校验组成防御链路。

### 多人实时协同的 AI 辅助领域建模平台

#### 项目定位

面向上海鼎歆内部研发与建模协作场景，设计并实现支持多人实时编辑的 AI 辅助建模平台。此前团队主要通过事件风暴和头脑风暴开展建模，讨论容易发散、难以收敛，长时间会议也未必能形成共识；平台改用 8X Flow 从参与方权责关系出发约束讨论边界，并将结果沉淀为可协作、可审核和可复用的结构化模型。平台已经由业务、产品和研发团队持续使用，建模结果进一步形成业务模型、接口候选和测试场景。在真实的库销存 Agent 场景中，使用 8X Flow 从采购合同出发建模参与方、权责、发货、收货、退货及正常／异常履约事实；发布模型继续用于 RESTful API 设计、AI 生成测试数据，以及经人工审核的 OpenAPI 草稿与下游代码生成。

本人直接完成前端 Yjs 数据绑定、Awareness 协作状态、NestJS WebSocket 协同服务和 PostgreSQL 持久化。由于公司原始源码不能公开，后续额外在公开仓库 [team-ai](https://github.com/JayClock/team-ai) 中重新实现领域模型、HATEOAS、建模画布、AI Proposal、版本与知识图谱等核心能力；公开仓库不是公司原始源码，也不用于证明公司项目的用户规模或生产数据。

#### 可复用项目摘要

独立负责多人实时协同领域建模平台的前端、协同服务与持久化链路。前端基于 React Flow 构建领域对象与关系画布，将共享建模状态接入 Yjs，并通过 WebsocketProvider 和 Awareness 同步增量更新、在线成员与远端光标；服务端基于 NestJS 和原生 WebSocket 处理内容同步、用户状态广播、连接检测与清理，再通过自封装的 PostgreSQL 适配层持久化协同数据。实现过程中通过链路日志与 `transaction.origin` 定位并解决 React Flow 与 Yjs 双向绑定回环，将整图全量回写改为节点、关系和字段级增量同步。AI 只生成结构化 Proposal，由用户逐项采纳或拒绝，确认后再进入草稿、版本和发布流程。

#### 技术栈与产品形态

- 内部项目核心技术：TypeScript、React、React Flow、Yjs、y-websocket、WebSocket、NestJS、PostgreSQL、SSE。
- 可视化模型以节点和关系表达上下文、参与方、角色、Evidence 等领域对象，并支持创建、移动、修改、删除和关系编辑。
- 多人协同以 Y.Doc 管理共享状态，通过 WebsocketProvider 传递增量更新；Awareness 单独承载在线用户、光标和选区等短生命周期状态。
- 根据工作负载拆分普通业务 API 与实时协同服务：前者负责认证、权限、文档 CRUD 和长期持久化，后者负责 WebSocket 长连接、高频增量同步、临时状态和消息广播。这是协同系统的常规服务边界，不作为个人架构创新表述。
- AI 通过 SSE 返回结构化 Proposal，前端按新增、修改、删除节点或关系展示候选变更，用户确认后才写入草稿。

#### 多人协同链路

1. 用户进入建模空间后，客户端创建或恢复对应的 Y.Doc，并以空间标识连接 WebSocket 协同服务。
2. 本地建模操作转化为 Yjs 增量更新，经 WebSocket 广播给同一空间中的其他客户端；Yjs 负责并发更新的确定性合并与最终收敛。
3. Awareness 广播用户标识、颜色、光标、选区和在线状态；这些状态不进入正式模型持久化。
4. NestJS WebSocket Gateway 区分 `messageSync` 与 `messageAwareness`，分别处理模型内容和协作状态，并按空间隔离连接与广播范围。
5. 服务端通过 ping 检测、连接关闭处理和监听清理回收无效连接，避免残留在线状态和无用文档实例。
6. 自封装 PostgreSQL 持久化适配层保存协同数据，使服务重启或用户重新进入后可以恢复共享模型并继续接收增量更新。

CRDT 只保证各客户端最终收敛到相同状态，不自动保证领域语义正确。多人同时修改同一对象后，模型名称、关系和边界是否合理仍需要通过领域评审决定。

#### React Flow 与 Yjs 双向绑定回环

实际开发中曾出现 React Flow 更新写入 Yjs 后，Yjs observer 再次调用 `setNodes`，监听 React 状态的 effect 又把整张图写回 Yjs 的回环。定位时在 `onNodesChange`、`onEdgesChange`、Yjs 写入入口和 `Y.Map.observe` 回调中加入链路日志，记录节点 ID、变更类型和 `transaction.origin`，确认问题不是通过 debounce 可以根治的高频触发，而是缺少来源约束的双向绑定。

解决方式：

1. 以 Yjs 作为共享状态源，只在明确的用户操作中增量写入。
2. 使用 `doc.transact(fn, REACT_FLOW_ORIGIN)` 标记 React Flow 本地事务来源。
3. Yjs observer 跳过本地同源事务，只将远端事务更新到 React Flow。
4. 删除监听整个 `nodes` / `edges` 后全量回写的 effect，改为节点、关系和字段级增量更新。
5. 写入前比较新旧值，过滤无变化更新，并在组件卸载时正确 `unobserve`。

使用两个浏览器窗口手工联调节点增删改、远端同步和事务回环，并结合 `transaction.origin`、Yjs 写入次数与 React Flow 更新次数确认单次操作链路。验证标准是一次本地操作只产生一次 Yjs transaction，远端更新只触发一次界面更新且不再向 Yjs 回写。当前没有把这套验证写成自动化 E2E，不将自动化协同测试表述为已完成成果。

#### AI 辅助与模型生命周期

- AI 不直接覆盖正式模型，而是生成受结构约束的节点与关系变更 Proposal。
- 前端支持定位受影响对象、预览变更、逐项采纳或拒绝，以及确认后保存草稿。
- 模型通过草稿、版本快照和发布状态区分编辑态与正式态，避免协同编辑或 AI 候选直接改变已发布知识。
- 发布后的模型可以转换为项目知识图谱，并成为 RESTful API、OpenAPI 草稿、测试数据和下游代码生成的业务上下文。

#### 8X Flow 与模型驱动交付

真实库销存 Agent 案例以采购合同为业务上下文。客户会用“下个月将滞留货物降低至 20%”这类目标说明分析诉求，但该数字只是客户场景举例，不是已经达成的项目指标。建模重点不是先让 Agent 给结论，而是通过 8X Flow 记录谁发货、谁收货、谁退货，以及对应的履约请求、确认和 Evidence，使正常与异常履约均可追溯。

模型将业务履约审计与库存分析领域逻辑分开：采购合同、参与方、角色和履约 Evidence 负责保存可审计事实；库销存 Agent 消费这些事实分析滞留原因，并将结论关联回具体合同项和履约记录。由于已经忘记客户的具体对象名和规则，发货、收货、退货的详细结构只保留为通用采购场景重构，不冒充客户生产模型。

模型到 RESTful API 采用模型驱动 API 设计：从数据变化而不是页面动作出发，根据聚合边界生成 URI，再组合角色、HTTP Method 与业务场景得到 API 候选；使用 HAL relation 表达资源关系，最后把 API 映射回履约流程验证完整性。发布模型作为上下文交给 AI 生成 OpenAPI 草稿，由人审核后，再将 OpenAPI 用于下游代码生成。测试数据同样由 AI 根据模型约束和正常／异常履约场景生成。

这条链路不是确定性的一键代码生成：AI 生成的是 OpenAPI 草稿和测试数据，正式接口契约必须经过人工审核，平台也不直接生成完整业务系统。

### 多端一致性驱动的 HATEOAS 资源动作契约与 TypeScript SDK

#### 项目背景

低代码平台中的应用、表单和工作流都存在编辑、发布、撤销等动作，并同时服务 PC Web 与移动 Web。工作区内不同权限用户可以访问的页面，还会分别呈现在 PC 侧边栏和移动端首页导航中。过去各端需要根据资源状态、用户角色和权限分别维护判断；后端调整规则或可访问列表时，多个前端都可能需要联动修改和重新回归。

该能力最初在上海易校的大型 Monorepo 中以业务子 lib 形态落地，服务真实的低代码业务；后续将其中通用的资源消费模型进一步抽象为独立维护的 `@hateoas-ts/resource` 与 `@hateoas-ts/resource-react` 两个公开 npm 包。

#### 项目目标

第一目标是解决客户端一致性：把“当前资源允许访问什么、允许执行什么动作”收敛到服务端资源表达中，由 `_links` / `_templates` 返回当前状态和权限上下文下的导航关系、合法动作与 payload 约束，再由统一 SDK 提供给不同前端消费。

随着方案落地，目标进一步延伸到契约质量：HATEOAS 不能补救资源边界混乱或行为式接口语义，因此需要从应用、表单、工作流和工作区导航的业务事件与生命周期出发识别稳定资源，再根据聚合关系设计 RESTful URI、relation 和动作契约。模型与 API 是 HATEOAS 能稳定工作的前提；SDK 负责把这些知识转化为客户端容易消费的工程接口，但实际下游还包括客户端实现、测试验证和运行反馈。

#### 可复用项目摘要

针对 PC Web 与移动 Web 重复维护资源状态、角色和权限规则的问题，主动提出并推动 HATEOAS 资源动作契约改造，先用统一 TypeScript SDK 收敛多端消费，再沿着契约问题向上游完成业务／领域建模与 RESTful / HAL-FORMS API 设计。方案让服务端资源表达成为动作事实来源，前端组件回到交互呈现职责，并通过兼容旧结构的渐进迁移降低试点和回归成本。后续基于这段生产实践，将通用资源消费能力抽象为两个独立 npm 包并持续公开维护。

#### 生产阶段与后续独立维护

- 在上海易校生产阶段，SDK 是大型 Monorepo 中的一个业务子 lib，负责统一 PC Web 与移动 Web 对资源关系、动作契约、缓存和状态更新的消费方式。
- 后续独立维护阶段将通用能力拆分为 `@hateoas-ts/resource` 与 `@hateoas-ts/resource-react`：前者负责资源导航、状态解析、动作提交、缓存和中间件，后者负责 React Provider、资源读取、Suspense 与无限分页适配。
- 当前可验证材料位于 `Knowledge/Sources/hateoas-ts/`。候选人已确认 Git 作者 `JayClock <35857909+JayClock@users.noreply.github.com>` 是本人；仓库历史从 2025-09-30 开始，记录的是独立维护阶段，不代表上海易校生产项目的完整起点。
- 两个 package 已公开发布到 npm，当前版本均为 1.4.3。公开发布只能证明可安装交付，不派生下载量、外部采用、社区影响力或商业收益表述。

#### 技术栈与交付形态

- 主要技术栈：TypeScript、React、REST、HAL / HAL-FORMS、HATEOAS、Standard Schema、Zod、Java API 表达层、Nx、pnpm workspace、Vitest、契约测试和 E2E。
- 个人直接负责领域模型、资源关系与动作契约、TypeScript SDK、React Hooks 和客户端状态刷新；后端实现通过共同确认的模型与契约协作完成。
- 独立维护阶段进一步负责两个 npm package 的源码、测试、TypeDoc 文档、版本管理和 GitHub Actions 发布流程。
- 该项目既可在全栈岗位中证明跨前后端契约设计与推动能力，也可在前端岗位中证明多端状态一致性、类型安全、公共库设计和复杂业务规则收敛能力。

#### 从前端一致性问题倒推模型与资源设计

- 最初关注的是 PC Web 与移动 Web 怎样消费同一套动作事实，而不是先做领域模型或后端重构。
- 在 relation 和 action 设计中发现，只有先回答“资源是什么、生命周期怎样、当前角色在什么状态下能做什么”，契约才不会退化成按钮数组或另一套接口字典。
- 因此不再从既有路径或数据库表反推业务，而是从应用、表单、工作流和工作区导航的业务事件与生命周期入手，识别长期存在的实体、参与角色、描述对象和关键事件。
- 使用四色建模澄清资源关系、状态约束和权限上下文，再根据聚合与生命周期边界设计 RESTful URI、relation 和动作入口。
- 最后将模型中的导航关系和合法状态落实为 HAL / HAL-FORMS 契约，使前端不再根据 `status`、`role`、`permission` 复制一份业务状态机。

#### 我的工作

- 从 PC Web 与移动 Web 的状态、权限和导航规则重复维护中识别一致性问题，提出引入 HATEOAS 资源动作契约。
- 先设计并实现统一的 HATEOAS TypeScript SDK 和 React 消费层，让多端按 relation 与 action 使用同一套资源事实。
- 在契约落地过程中继续向上游参与业务／领域建模，设计 RESTful 资源关系、relation 名称与动作契约，并与后端共同将其落实到 API 表达层；服务端代码不计入个人实现。
- 后续将通用资源消费能力抽象为公开 npm package。
- 实现 `Client`、`Resource`、`ResourceRelation`、`State`、`Action`、`StateFactory`、`Fetcher` 和 `Cache` 等核心模块。
- 通过 `follow()` 按 relation 导航，支持 URI Template 变量和多级 relation 解析，减少业务代码对具体接口路径的依赖。
- 通过 `action()` 消费后端下发的 HAL-FORMS 动作模板，统一处理目标 URI、HTTP Method、Content-Type、表单字段和 payload 提交。
- 使用 TypeScript 泛型约束资源数据、relation 与目标资源类型；通过 Standard Schema 插件接口接入 Zod，对 HAL-FORMS payload 做运行时校验和错误反馈。
- 实现 React Hooks 适配层，让 PC Web 与移动 Web 根据统一资源状态渲染发布、撤销和修改等操作；独立 package 继续提供普通读取、Suspense 和无限分页 Hooks。
- 处理资源缓存、请求去重、更新事件和动作提交后的状态刷新，使同一 URI 的资源实例在客户端保持统一事件源。

#### 可验证 SDK 工程实现

- 以 `Client → Resource / ResourceRelation → State / Action` 划分资源消费职责：`Client` 管理入口和中间件，`ResourceRelation` 延迟解析 relation 链，`StateFactory` 根据响应类型生成统一状态，`Action` 执行服务端下发的动作契约。
- 内置 HAL / HAL-FORMS、JSON:API、Siren、Collection+JSON、HTML、Text、Event Stream 和 Binary 等响应解析，并允许通过 Content-Type 注册自定义 `StateFactory`。
- `get()` 优先复用缓存并对相同进行中请求去重；`refresh()` 使用 `Cache-Control: no-cache` 绕过缓存；unsafe method 成功后依据请求 URI、`Link rel=invalidates`、`Location` 与 `Content-Location` 更新或失效相关资源。
- 资源层通过 `update`、`stale` 和 `delete` 事件表达缓存变化；当前 React 读取 Hook 直接订阅 `update` 与 `stale`，由 `refreshOnStale` 决定是否自动刷新。
- React package 提供 `ResourceProvider`、`useResource`、Suspense 资源读取和基于 HAL `next` relation 的无限分页，使组件可以直接消费 URI、`Resource` 或 `ResourceRelation`。
- 工程使用 Nx / pnpm workspace 统一管理构建、类型检查、测试、TypeDoc 和固定版本发布，并通过 GitHub Actions 按 `v*` tag 发布两个同版本 package。

#### 方案推动与迁移

- 最初选择侧边栏导航作为试点，在 `workspaces` 接口的 API 表达层返回 `_links`，由 PC 侧边栏和移动端首页按 relation 消费当前用户可访问的导航。
- 团队最初担心由前端推动后端改造会增加修改成本；通过方案评审和案例演示，证明 Java 现有生态足以支持资源表达，并且改造只需停留在 API 层，不需要改库改表或破坏旧有返回结构。
- 如果原服务暂时不适合修改，可以退到 BFF 层补充资源关系和动作契约，降低试点阻力。
- 试点确认后，应用、表单和工作流等资源继续沿用相同的 API 表达方式逐步迁移，无需一次性重构整个业务系统。

#### 质量保障

- 在上海易校生产阶段，使用单元测试验证 SDK 核心行为，使用契约测试检查前后端对 `_links`、`_templates` 和 payload 约束的理解是否一致，并通过 E2E 覆盖应用、表单、工作流以及多端导航等真实操作路径。
- 独立 package 的测试覆盖 relation 解析、HAL-FORMS action 与 Zod 校验、HTTP 方法、缓存策略、状态解析、认证与中间件、React 资源读取和无限分页等核心行为。

#### 实际结果

- 后端修改权限规则时，前端不再需要同步修改对应的状态和权限判断。
- 以工作区导航为例，后端新增或调整不同权限用户的可访问页面后，PC 侧边栏和移动端首页导航可以直接消费新的资源关系，前端无需再次修改列表并分别回归。
- 应用、表单和工作流的编辑、发布等动作由 PC Web 与移动 Web 消费同一套资源动作契约，减少多端规则漂移和联动回归问题。
- 前端组件主要负责交互呈现，不再重复实现后端业务状态机。
- 生产实践中的通用资源消费模型后续形成两个可公开安装、独立测试和持续发布的 npm package。

### 企业级低代码工作流引擎

#### 项目背景

公司本身提供低代码平台，需要建设一套通用的企业级工作流引擎，让使用者通过可视化方式编排 Start、HTTP、Condition、End 等节点，并支持工作流发布、执行监控和私有化部署场景。平台面向公司内部人员、企业客户和研发团队使用，实际业务覆盖多个行业。

项目整体包含工作流编辑器、TypeScript 执行引擎、API 服务和执行监控等模块。我负责应用生命周期的领域建模、RESTful / HATEOAS 契约设计、插件化节点体系，以及工作流前端和与其直接相关的 TypeScript 执行引擎；NestJS 与 SSE 服务端代码由后端同事基于共同确认的模型与契约实现。

#### 可复用项目摘要

面向内部人员、企业客户和研发团队建设企业级低代码工作流引擎。个人工作覆盖应用生命周期建模、工作流协议、插件化节点、可视化编辑器、变量编辑和相关 TypeScript 执行引擎，并与后端协作完成发布、测试运行和实时执行反馈。该项目承接资源契约之后的工程消费与执行：把模型转化为 Schema、DAG、变量协议和运行状态，使任意合法配置能够被校验、调度、执行、追踪并映射为用户可理解的反馈。

#### 技术栈与产品形态

- 个人确认使用的主要技术：TypeScript、React、React Flow、Tiptap、DAG、REST / HATEOAS、节点 Schema、Monorepo，以及对 NestJS / SSE 接口的前端集成。
- 产品链路覆盖应用创建、工作流可视化编排、节点配置、变量引用、发布版本、测试运行、执行日志和错误反馈。
- 编辑器负责拖拽、连线、缩放、选择、动态配置表单与未保存状态；执行引擎负责图结构校验、拓扑调度、条件分支和上下文变量传递，两者通过统一协议协作而不是互相嵌入业务逻辑。

#### 应用生命周期、领域模型与资源契约

- 围绕低代码应用从设计、校验、发布到运行的生命周期使用四色建模，识别应用、工作流定义、发布版本、执行记录及其参与角色、关系和约束。
- 区分应用的长期身份、可编辑的工作流定义、不可变的发布版本和一次具体执行，避免设计态修改直接影响已经发布或正在运行的定义。
- 根据领域模型设计 RESTful 资源和 HATEOAS relation / action，由服务端返回当前状态与权限下的资源关系、合法动作及 payload 约束。
- 发布时创建版本记录并保留版本 ID，使发布结果及后续运行能够追溯到明确的工作流定义。
- 将领域模型继续转化为 `WorkflowDefinition`、`Node`、`Edge`、配置 Schema 和变量协议，使同一模型贯穿 API、编辑器和执行引擎。

#### 工作流协议与引擎

- 设计可序列化的工作流协议，以 `WorkflowDefinition` 统一描述工作流，并用 `Node`、`Edge` 表达节点和数据流关系。
- 支持 Start、HTTP、Condition、End 等节点类型；条件节点通过 `sourceHandle` 表达不同输出分支。
- 设计并实现 `WorkflowEngine`、`GraphBuilder`、`ExecutionContext`、`VariableResolver` 等核心模块。
- 使用标准 Kahn 算法完成拓扑排序，将工作流 JSON 转换为可执行顺序；个人工作重点是图结构构建、调度集成、环检测和条件分支处理，而不是发明算法本身。
- 通过邻接表、反向邻接表和入度表管理节点关系，并在执行前检测环路。
- 对 Condition 节点实现动态分支选择和未选分支的子树排除，避免无效分支继续执行。
- 以 `ExecutionContext` 按节点隔离存储输出，通过 `${nodeId.variableName}` 变量协议解析上游结果并注入下游节点。

#### 核心设计难点

支持自定义流程的难点不只是让用户在画布上连线，而是保证任意合法配置都能被正确执行：

1. **图结构有效性**：把节点配置和边转换为邻接表、反向邻接表与入度表，通过拓扑排序和环检测阻止非法流程进入执行阶段。
2. **条件分支调度**：Condition 节点得出结果后动态排除未选分支，避免不应执行的下游节点进入队列。
3. **上下文与变量传递**：通过全局执行上下文隔离保存各节点输出，再按 `${nodeId.variableName}` 精确映射到下游输入。

#### 插件化节点体系

这是我在项目中主要负责的部分。

- 设计 `NodeRegistry + NodeExecutor` 节点扩展机制，由注册中心管理节点类型和执行器。
- 抽象通用执行器接口与基础执行流程，使新增节点能够通过注册接入，而不需要持续修改核心调度器。
- 为节点执行统一处理配置校验、变量解析、错误捕获、执行耗时和输出存储。
- 通过工作流验证器检查 Start / End 节点、节点类型、边引用和节点配置，提前阻止无效流程进入执行阶段。

#### 可视化工作流编辑器

- 基于 React Flow 实现节点拖拽、连线、缩放、自定义节点渲染和选择交互。
- 自主设计节点配置、变量编辑器、发布管理和执行日志等前端模块。
- 为条件节点设计多个输出 Handle，使不同判断结果能够连接到不同下游路径。
- 通过节点配置注册表动态加载不同节点的设置表单，隔离核心编辑器与业务节点配置。
- 管理节点、连线、选中节点、未保存状态和执行记录等编辑器状态，并通过防抖机制降低频繁保存带来的请求压力。

#### 变量编辑器

- 基于 Tiptap 实现文本变量编辑器，让普通文本和节点变量可以在同一输入区域内混合编辑。
- 将 `${nodeId.variableName}` 渲染为不可拆分的变量标签，降低手工输入节点 ID 和字段名造成的配置错误。
- 支持通过 `/` 菜单选择上游节点输出，并在保存时把富文本内容还原为可执行的纯文本变量表达式。
- 通过 `VariableResolver` 在运行时从节点变量存储中读取真实输出，并完成字符串或对象值的替换。

### 全链路埋点与监控 SDK

#### 项目背景

低代码平台包含大量动态页面和业务功能，需要统一观察真实用户环境中的性能、异常、接口请求和操作行为。公司因此建设自有监控平台，以减少不同功能重复接入监控的成本，并让采集协议、扩展能力和数据使用方式能够根据低代码业务持续调整。

整体链路由监控 SDK、数据接收与处理服务、ClickHouse 存储和监控可视化平台组成：SDK 负责采集与上报，数据服务负责过滤、分类和聚合，控制台负责按应用、页面和时间等维度查询性能与异常数据。

#### 可复用项目摘要

面向低代码平台设计并实现低侵入、可扩展的前端监控 SDK，以“核心包 + 框架适配包”隔离通用采集协议与 React、Vue、Vanilla JS 生命周期差异，统一采集真实用户环境中的性能、异常、接口和操作数据。该项目补齐交付知识流中的运行反馈：在不改变原有请求行为、不成为新故障源的前提下，提供真实环境证据，并为判断问题应返回实现、接口还是上游规则保留依据。

#### 技术栈与架构要点

- 主要技术栈：TypeScript、PerformanceObserver、Web Vitals、React、Vue、Vanilla JS、Fetch / XHR、sendBeacon、Sourcemap、pnpm Monorepo。
- 核心包保持框架无关，适配包只处理框架生命周期和接入方式；新增监控项沿用统一协议和发送链路，而不是在不同业务中重复实现。
- 可靠性设计覆盖批量发送、空闲调度、页面卸载、失败重试、弱网和离线场景；异常定位链路覆盖生产 Sourcemap 上传、版本映射和源码堆栈还原。

#### 我的工作

- 设计并实现“核心包 + 框架适配包”的插件化 SDK 架构，以 pnpm Monorepo 管理 `core`、`browser`、`react`、`vue`、`types` 和通用工具等模块。
- 将通用采集、事件协议、队列和发送能力保留在核心层，把框架生命周期差异收敛到适配层，避免核心逻辑依赖具体 UI 框架。
- 独立完成 Vanilla JS、React 与 Vue 适配，使低代码平台中不同技术栈的功能可以消费同一套监控协议。
- 使用 `PerformanceObserver` 与 Web Vitals API 采集 FCP、LCP、CLS、TTFB、INP 等页面加载和交互性能指标。
- 通过全局错误监听和 Promise rejection 监听采集 JavaScript 运行期异常，并支持业务自定义错误上报。
- 代理 DOM 事件、Fetch、XHR 和页面导航，采集用户操作、接口耗时、状态码和页面上下文，同时保持原有业务请求行为。
- 设计统一数据协议和批量发送队列，通过空闲时机发送降低上报对主业务线程的影响。
- 在页面卸载场景使用 `sendBeacon` 上报关键数据，并通过失败重试和离线续传提高弱网、断网环境下的可靠性。
- 接入生产 Sourcemap 上传和版本映射，使压缩后的异常堆栈能够还原到源码位置。

#### 协作边界

我的工作重心是监控 SDK。NestJS 数据接收服务、Kafka、ClickHouse、查询后端和监控控制台由其他同事负责，不能作为我的个人实现写入简历。

#### 实际覆盖

- SDK 覆盖低代码平台中的全部功能，而不是只在单个示例应用中接入。
- 核心采集能力由统一 SDK 提供，业务功能不需要分别建设性能和异常采集逻辑。
- 插件化与框架适配包让新增监控项和不同前端技术栈能够沿用同一核心协议。

#### 线上结算卡死问题定位

客服收到零星反馈，称部分苹果手机用户在结算时出现页面卡死，但开发团队在测试环境无法复现。监控 SDK 捕获到线上未处理异常 `TypeError: Cannot read property 'map' of undefined`，同时上报用户设备型号、iOS 版本和异常发生前的操作面包屑。

AI 基于这些运行上下文完成问题排查，发现问题只出现在特定旧版 iOS 和存在运营商网络注入的环境中，最终定位到第三方广告 SDK 篡改全局变量，并完成修复验证；人类最终审阅变更结果。个人贡献是参与监控 SDK 建设，为这次排查提供异常、设备环境和用户操作路径等可消费的运行证据。

该案例说明监控 SDK 不只是采集数据，还能把难以复现的零星反馈转化为 AI 可以继续消费的异常与运行上下文。目前仍缺少受影响用户数量、事件量、修复后复发率和性能改善数据，因此不补写量化收益。

## 当前职业优势

### 1. 以复杂前端和平台交互为基本盘

长期直接处理编辑器、低代码表单、工作流、SDK 和多端应用中的复杂交互：视口缩放、节点命中与拖拽、动态属性、富文本变量、远端光标、在线成员、缓存更新、错误反馈和运行状态呈现。模型与接口设计的价值最终都要回到这些客户端是否能够稳定、清晰地消费。

### 2. 向上游稳定业务模型与资源契约

HATEOAS SDK 先暴露了 PC Web 与移动 Web 的规则复制和状态漂移，随后进一步认识到稳定契约依赖清晰的资源边界、生命周期和接口语义，因此把能力从前端消费层延伸到四色建模、8X Flow、RESTful URI 和 HATEOAS relation。API 与建模是控制前端复杂度的上游手段，而不是职业重心转向纯后端。

### 3. 用 SDK、Schema 与运行时建立消费路径

SDK 的价值不是代表整个下游，而是把上游模型和接口契约转化为客户端容易使用的工程接口。HATEOAS SDK 与 React Hooks 支撑多端资源消费；工作流 Schema、变量协议和执行引擎让模型进入实际运行；协同建模平台的发布模型继续进入 OpenAPI、测试数据和下游代码生成。

### 4. 明确个人交付与协作边界

除侵入式修改现有后端项目需要原负责人配合外，能够主导业务问题澄清、领域建模、资源与 API 契约、复杂前端、新服务实现和验证反馈；参与上下游协作，但不替业务、产品或后端负责人做其职责内的决策。在上海鼎歆协同建模项目中，前端 Yjs 数据绑定、Awareness、NestJS WebSocket 服务和 PostgreSQL 持久化均由本人直接完成；在上海易校项目中，由后端同事完成的服务端代码仍按共同模型与契约协作，不混写为个人编码成果。公开 `team-ai` 是额外重实现，不冒充公司原始源码。

### 5. 用验证与运行证据形成反馈闭环

通过单元测试、契约测试、E2E 和双浏览器联调验证模型与契约是否被正确实现；通过工作流测试运行、执行日志、人工审核和监控 SDK 观察实际消费结果。证据根据失败性质返回实现、任务、接口契约或业务模型，使交付不止停留在代码生成和功能完成。

### 6. 设计 AI 原生工具的确定性边界

通过内部研发类 Figma AI 设计生成工具与协同建模平台，能够区分哪些任务适合交给 LLM 做语义理解、候选变更、OpenAPI 草稿和测试数据生成，哪些任务必须通过 DSL、Schema、CRDT、人工审核、版本控制与质量门禁保证确定性。这项能力与现有领域建模、低代码工作流、HATEOAS 契约和监控工程经验共同形成“模型与契约 → 工程消费 → 执行验证 → 运行反馈”的可迁移主线。
