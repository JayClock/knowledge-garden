## 二、核心工程能力框架

### 1. 复杂前端与编辑器架构

深度掌握现代富交互前端底座的设计与性能优化：

- **画布与图形**：基于 React Flow 实现流程画布，覆盖节点拖拽、连线、缩放、自定义节点、条件分支与动态配置表单。
- **变量编辑**：在低代码工作流引擎中使用 Tiptap 将变量引用渲染为不可拆分的标签，支持上游输出选择与执行协议序列化。
- **工程韧性**：系统性处理树形状态、浮动上下文菜单与弱网环境下的异常恢复。

### 2. 上游契约、领域建模与模型驱动工程

主动参与业务澄清，将领域模型继续转化为前后端可消费的工程契约：

- 使用 **8X Flow** 与**四色建模法**澄清业务参与方、权责关系、关键事件与生命周期。
- 将业务模型映射为 RESTful 聚合边界、URI 体系、HATEOAS relation 与 HAL-FORMS 动作契约，降低端侧重复维护业务规则的成本。
- 运用**模型驱动工程（Model-Driven Engineering，MDE）**，在 AI 原生工作流中完成业务模型到 API 模型的转换；明确业务范围并核对有效模型结果，设计和校验接口契约，派生 OpenAPI 文档与包含请求、预期结果的静态测试向量，作为 AI Coding 的结构化上下文与验证依据，再用于实现和运行验收；模型持续完善，接口契约按需调整。

### 3. 关联对象建模方法

设计并落地**关联对象建模方法**：

- 将传统实体间的一对多或复杂多对多关联显式抽象并建模为独立的领域对象。
- 建立稳定的接口契约以彻底隔离领域语义与底层数据访问策略，在严守聚合根边界的同时，有效防止非聚合根 Repository 的持久化逻辑泄漏，并从架构层面规避 N+1 查询风险（通用建模思想，不绑定具体技术栈，并在开源代码中完成可验证落地）。

### 4. 渐进式架构与可恢复增强

采用**渐进式架构与受控增强**：

- 优先稳定核心业务模型、任务路径与通信协议基石；
- 将 HATEOAS relation/action、多框架适配、节点插件及 AI 受控增量生成等变化能力隔离为可独立消费和演进的增强层；
- 配合运行时 Schema 校验、降级退路、状态版本控制与人工确认 Gate，严格限定局部失效的爆炸半径。

### 5. 契约消费路径与验证闭环

- **消费层建设**：提供面向下游的 React 适配 Hooks、强类型 TypeScript SDK、HAL/HAL-FORMS 规范解析器及 OpenAPI 契约草稿，抹平成本。
- **验证反馈**：在各项目中使用单元测试、契约测试、E2E、人工评审、执行日志或前端监控验证交付，将失败反馈到模型、契约与实现。工作流执行日志与监控数据采集分别承接各自项目的诊断需求。

### 6. AI 确定性交付与受控候选生成

将 AI 原生工作流中的自然语言理解、业务追问和接口映射，与结构校验、产物生成及人工业务审核分开。AI 原生领域建模与 API 设计平台通过 Pi SDK 驱动 AI 直接增量修改本地模型文件，在生成阶段校验结构与格式，本轮结束后再读取完整模型、刷新图谱，经人确认的业务范围进入下游契约设计；平台内的建模流程进一步区分每批一致性检查、范围完整性及适用场景，并向 API 阶段交接有效结果。这些模型、API 与测试数据以业务语义和契约为稳定边界，剥离具体语言与框架细节，可迁移到不同技术栈的前后端实现与 AI Coding 工作流。

### 7. 持续集成与容器化构建

- **Monorepo 工程**：统一采用 Nx + pnpm 管理项目组织、工作区依赖与工程任务。
- **持续集成**：配置 GitHub Actions 流水线，执行代码检查、测试和构建，将验证步骤纳入统一的自动执行流程。
- **容器化构建**：为 Nx 管理的 React 项目编写多阶段 Dockerfile，将依赖安装、应用构建和运行拆分为不同阶段。

### 项目 1：[[项目介绍：前端埋点与监控 SDK|企业级前端监控 SDK 与数据采集系统]]（上海鼎歆）

- **项目性质**：平台公共基础设施，负责 SDK 与数据采集后端的设计和实现。
- **技术栈**：TypeScript、PerformanceObserver、Web Vitals 指标实现、Fetch / XMLHttpRequest；NestJS、Kafka、ClickHouse、TypeORM、PostgreSQL；Nx + pnpm。
- **核心定位**：以统一事件协议连接多框架采集、批量上报、后端接收处理与存储，并通过生产 Sourcemap 链路支持源码定位，为低代码平台各业务模块提供运行诊断能力。

#### 架构设计与技术实现

1. **下游驱动（Downstream-Driven）与多包工程**：
   - 告别盲目采集，紧密围绕网络排障、页面慢加载、JS 运行时崩溃与业务操作链路设计监控上下文模型；
   - 使用 Nx + pnpm 管理 Monorepo：细分为 `core`（通用调度协议、插件生命周期、内存队列）、`browser`（浏览器 API 封装）、`react` / `vue`（框架组件与生命周期集成）及 `types`。
2. **全面精准的数据采集**：
   - **性能指标**：基于 `PerformanceObserver` 接入 Google Web Vitals 标准，精准采集 FCP、LCP、CLS、TTFB 与 INP 指标；
   - **错误异常**：全面监听 `window.onerror`、`unhandledrejection` 以及资源加载错误；
   - **用户行为追踪**：透明劫持/包装 DOM 事件、原生 `Fetch` 与 `XMLHttpRequest`，在完全不侵入业务行为和返回值的原则下记录完整上下文。
3. **批量队列与弱网弹性上报**：
   - 事件先进入本地内存缓冲区，按设定的时间步长（Interval）、批次阈值或路由跳转动作批量触发上报；
   - 结合失败重试与弱网处理，平衡端侧开销、数据实时性与上报可靠性。
4. **生产 Sourcemap 还原闭环**：
   - 接入生产构建中的 Sourcemap 上传与版本映射，让压缩异常堆栈对应到原始源码文件和行列位置。
5. **数据采集与处理后端**：
   - 使用 NestJS 实现 HTTP 数据接收服务，与 SDK 消费同一套事件协议；
   - 通过 Kafka 将请求接收与后续处理分开，异步处理上报事件，再接入 ClickHouse 完成数据存储与查询，贯通接收、处理和存储链路。

#### 交付与应用情况

- **多技术栈全量接入**：监控 SDK 全面接入低代码平台所有前端模块（覆盖 Vanilla JS、React 和 Vue 多种技术栈），为各业务应用提供统一的前端可观测性基础保障。
- **采集处理链路**：完成 SDK 采集、上报队列、重试机制与事件协议，以及 NestJS 数据接收、Kafka 异步处理和 ClickHouse 存储，并接入 Sourcemap 上传与版本映射。
- **系统响应性能**：数据采集与处理系统的响应性能提升 50%。
- **统一事件协议**：定义并实现 SDK 与数据服务共同消费的事件协议，串联端侧采集、上报与后端接收处理，为运行诊断和异常定位提供统一事件。

### 项目 2：[[项目介绍：AI 原生领域建模与 API 设计平台]]（上海鼎歆）

- **项目性质**：公司级内部业务与研发平台，以桌面端承接 AI 原生增量建模。
- **技术栈**：Electron、React、React Flow、Pi SDK、OpenAPI；Monorepo 采用 Nx + pnpm。
- **核心定位**：以**模型驱动的 API 设计与测试资产生成**解决业务讨论依赖个人经验、接口与测试重复解释业务规则的问题。采用 MDE 方法，以双层循环 Harness 组织权责澄清与模型增量维护；业务方确认明确范围，平台核对有效 FM 结果，API 设计模块检查后派生文档与静态测试向量，支持前后端实现和运行验收。
- **个人职责**：负责建模流程与平台核心能力，推进业务模型到 API 契约的转换；与业务、产品共同核对真实约定，与研发共同确定接口输入、结果和实现约束。

#### 架构设计与技术实现

1. **权责驱动的业务建模**：
   - 以真实约定和合同上下文为共同起点，明确参与双方的权利和义务，用履约请求、确认及相关凭证组织业务过程，将分析结果沉淀为参与方、角色、对象、关系和规则；
   - 由人类提供真实约定，沿履约时间线追溯请求依据与确认凭证，AI 递进追问正常、异常履约及后续责任，为业务、产品和研发提供一致的澄清与核对路径；
   - 以双层循环 Harness 组织过程：外层 PDCA 管范围与阶段，内层 Steering Loop 管单次执行质量；平台的建模流程在同一份 FM 中维护有依据且获授权的内容，未知或冲突保留缺口。
2. **桌面端 AI 增量建模与可视化**：
   - 采用 Electron、React 与 React Flow 承载桌面建模界面，将参与方、角色、领域对象、履约凭证及其关系表达为节点、连线与业务属性；
   - 通过 Pi SDK 驱动 AI 根据每轮讨论直接增量修改本地模型文件，在已有对象、关系和规则上持续补充与修正；模型文件承接多轮建模结果，图谱供业务、产品和研发查看、讨论与审核。
3. **生成校验、任务生命周期与图谱同步**：
   - 桌面端在 AI 生成和修改模型时校验结构与格式，将生成检查与展示更新分开；平台的建模流程每批检查 FM 一致性，范围结束时另查完整性和适用场景，人类确认范围及业务含义；
   - 图谱以本轮 AI 执行结束为重载边界，重新读取完整模型并全量更新 React Flow；增量发生在模型文件层，视图按轮次刷新，避免随多次文件写入展示尚在修改或检查的中间状态；
   - 生命周期衔接设计选用 Pi SDK 的 `agent_settled` 作为本轮最终停止信号，并将结束信号与校验结果分开判断：结束边界用于模型重载，结构检查关注可读性，业务确认决定当前范围的下游语义。
4. **模型转换与 API 契约按需演进**：
   - 在 AI 原生工作流中将业务对象、归属关系、角色和场景映射为 API 模型，属于模型到模型转换（M2M）；以聚合根作为 URI 起点，沿资源关系组织访问，按角色、HTTP 方法和业务场景梳理接口能力；
   - 以 CRM 电话销售作为接口设计示例，沿“绩效协议 → 月度目标 → 联系记录”组织资源与 URI，客户档案通过引用关联；按角色和真实场景筛选接口能力，再以业务流程检查覆盖情况；
   - 在业务方确认范围、下游授权具备后，平台的 API 设计模块消费范围完整且与当前模型摘要匹配的 FM 结果；与研发共同核对接口输入、结果和资源关联，维护唯一 API 设计源并执行自身检查，再接续派生交付与联合审核；契约按实际需要调整。
5. **接口文档与静态测试向量**：
   - API 覆盖与契约检查通过后，从同一设计源派生 OpenAPI 文档、静态消费者流程及合成测试向量，属于模型到文本转换（M2T）；
   - 向量保留请求、预期结果及来源场景，表达正常与异常履约的业务预期；运行环境负责调用者身份和前置数据装配；
   - 前后端依据模型、契约和向量开展实现与对接，实际执行场景并记录结果，再判断实现是否满足业务要求。

#### 交付与应用情况

- **内部持续使用**：业务、产品和研发团队持续使用平台，将业务讨论推进为共同审核和消费的模型、接口契约与测试场景。
- **模型驱动交付**：以权责建模、桌面端增量维护、模型检查与人工范围确认为基础，接续 API 设计和校验、文档与静态测试向量派生，再支持下游实现与运行验收。

### 项目 3：[[项目介绍：企业级低代码工作流引擎|企业级低代码工作流引擎与复杂编排器]]（上海易校）

- **项目性质**：核心商业化平台基础设施（核心负责协议、执行引擎、复杂编辑器与 SSE 实时反馈）
- **技术栈**：TypeScript、React、Next.js、React Flow、Tiptap、Tailwind CSS、Radix UI、React Hook Form、Zod；NestJS、SSE、Prisma、PostgreSQL；Nx + pnpm、Vitest。
- **核心定位**：为内部员工、企业客户及研发人员提供普通业务流程的可视化编排与执行能力，以统一工作流协议连接画布配置、节点调度和执行反馈。

#### 架构设计与技术实现

1. **基于 Kahn 算法的执行调度内核**：
   - 独立实现 TypeScript 执行引擎：构建 `WorkflowEngine`、`GraphBuilder` 与 `ExecutionContext`；
   - 构建邻接表、反向邻接表与入度表，执行前通过 DFS 检测环路，再用 Kahn 算法规划 DAG 拓扑执行顺序；每次运行创建独立 ExecutionContext，按节点 ID 保存本次输出。
2. **条件分支动态剪枝算法**：
   - 设计 Condition 节点分支判定逻辑：执行期沿未命中分支向下递归遍历并排除死分支节点；
   - 引入下游汇合点入度保护机制，在剪枝过程中校验节点是否具有其他活跃入边，避免误伤公共汇合节点。
3. **微内核节点插件体系**：
   - 抽象 `NodeRegistry` 与 `BaseNodeExecutor` 标准接口，将节点输入校验、变量计算、耗时统计、错误隔离与上下文输出全面标准化，便于团队快速扩展自建节点与第三方 API 节点。
4. **Tiptap 结构化变量编辑器**：
   - 解决工作流参数引用的可读性与健壮性难题：基于 Tiptap 富文本开发专用变量节点，将 `${nodeId.variableName}` 渲染为不可拆分的结构化 Token 胶囊；
   - 支持通过 Slash (`/`) 菜单快速检索并插入上游可用变量，保存时自动序列化为规范协议，执行期递归解析嵌套变量。
5. **公式编辑器与 AST 求值链路**：
   - **公式编辑交互**：面向表单字段参与工作流计算的业务场景，实现字段与函数表达式的编辑交互，支持用户配置 `sum(金额1，金额2)` 等业务计算公式；
   - **自研解析与保存校验**：自行编写公式解析器，将表达式解析为抽象语法树（AST），并在保存时执行语法校验以拦截非法或错误公式；AST 中以稳定字段 ID 记录字段引用，将界面呈现的字段名称与底层引用标识解耦；
   - **运行时字段解析与求值**：在工作流节点执行阶段，通过全局变量按字段 ID 读取对应字段的完整信息，基于 AST 完成公式求值，实现从公式编辑、保存校验到运行时节点计算的完整闭环；编辑交互、解析校验与求值链路均由本人独立负责。
6. **执行反馈与日志可观测性**：
   - 实现 SSE 服务端事件推送、前端接入与执行日志界面，并对接发布管理接口；以 `executionId` 唯一标识执行记录，在测试运行面板中实时展示节点状态、耗时、输入输出与错误日志；
   - 在代表性重实现中，将 Trace 面板由画布坐标排序优化为基于 Edge 的拓扑排序，使日志展示顺序与节点依赖保持一致，提供高保真执行反馈。

#### 交付与应用情况

- **核心链路闭环**：完整打通了从工作流协议、节点 Schema、画布交互、变量绑定、公式编辑与 AST 求值、图校验、拓扑调度到状态监控的完整业务链条。
- **全栈协议协同**：独立负责执行引擎、公式解析求值、SSE 服务端推送与端侧交互实现，并与后端协同制定协议、对接其他 API。
- **执行可观测性打通**：通过 `executionId` 标识执行记录与基于 Edge 拓扑排序的 Trace 面板，让工作流从画布配置到节点执行全过程具备高透明度与可追溯性。

### 项目 4：[[项目介绍：HATEOAS|HATEOAS 与 TypeScript SDK]]（上海易校）

- **项目性质**：大型低代码平台基础架构（企业 Monorepo 业务落地，后抽离为通用开源 npm 包）
- **技术栈**：TypeScript、React Hooks、HAL / HAL-FORMS、Zod、Nx + pnpm、Vite、Vitest、MSW、Testing Library、TypeDoc。
- **核心定位**：解决低代码平台复杂权限体系下，前端需要维护与后端一致的权限和操作可用性判断逻辑、后端规则变化牵动前端修改与回归的问题；将权限判断收敛到服务端，通过资源契约驱动 PC Web、移动 Web 的入口展示与动作提交。

#### 架构设计与技术实现

1. **自研强类型客户端 SDK 体系**：
   - 从 0 到 1 架构并开发 `@hateoas-ts/resource` 与 `@hateoas-ts/resource-react`（基于 Nx / pnpm Monorepo 统一治理与发布，目前稳定版本 1.4.3）；
   - 封装 `Client`、`Resource`、`ResourceRelation`、`State`、`Action`、`StateFactory` 与 `CacheManager` 核心抽象；
   - 客户端通过 `follow()` 导航资源关系，通过 `action()` 消费 HAL-FORMS 动作模板，统一资源契约的消费方式；
   - SDK 作为独立资源消费层，由 `Fetcher` 处理网络请求、Client 按 `Content-Type` 选择 `StateFactory`、`Resource` 按绝对 URI 定位与复用；HAL／HAL-FORMS 解析器将业务数据、链接、模板与嵌入资源整理为统一 State，业务通过同一套接口消费。
2. **精准缓存与并发去重**：
   - 实现飞行请求（in-flight request）合并去重；
   - 建立基于 URI 匹配、HTTP `Link` 响应头的 `invalidates` 声明、`Location` 与 `Content-Location` 的缓存协调机制；允许存储时，将 `Content-Location` 对应的本次响应体解析为 State 写回缓存并发出 `update`；
   - 通过 `inv-by` 注册缓存依赖、传播失效，以资源事件连接缓存维护与消费层。
3. **React 深度适配与声明式消费**：
   - 提供 `ResourceProvider`、`useResource` 等 React Hooks，原生支持 React Suspense、错误边界以及基于 HAL `next` 关系的无限流式分页；
   - 读取 Hook 订阅 `update` 更新组件状态，订阅 `stale` 后按 `refreshOnStale` 配置决定主动刷新，默认关闭该自动刷新选项，卸载时清理监听；
   - 业务页面已接入模板驱动的动态表单，根据服务端 `_templates.properties` 生成 Zod 校验与 JSON Schema 表单描述，随当前动作契约动态渲染字段。
4. **渐进式演进与多端落地**：
   - 以低代码平台“工作区全局导航”为试点，在不重构底层数据表的前提下，于 API 表达层增加 `_links` 与 `_templates`，多端直接读取契约渲染菜单与操作项；
   - 与后端协同在工作区响应中提供 `workflow` 工作流入口和基本信息更新模板，PC 与移动端从 service 调用迁移为 SDK 消费，导航入口依据当前 relation 的存在性渲染；
   - 围绕增量改造成本和数据更新风险明确协作边界，保持原有请求参数及保存接口响应不变，将资源契约表达与原有保存接口兼容性分别验证；
   - 架构上保留传统 BFF 作为回退路径，保证低风险平滑迁移。
5. **导航组件的契约消费测试**：
   - 使用 MSW（Mock Service Worker）模拟有、无 `workflow` relation 的工作区响应，在 Vitest 中渲染导航组件，通过 DOM 断言检查工作流入口的契约渲染预期。
6. **workflow 接口的端到端回归**：
   - 用 AI 辅助生成保存与发布的端到端测试，在前后端实现后重新做回归；保存用例使用相同输入对比原有原始响应 JSON，检查已覆盖保存场景的输入输出兼容性。

#### 交付与应用情况

- **业务平滑升级**：支撑了上海易校大型低代码平台在多端一致性上的架构升级，以工作区全局导航等核心模块为试点稳定运行。
- **开源工程交付**：自研客户端 SDK 抽象并公开发布至 npm（`@hateoas-ts/resource` 与 `@hateoas-ts/resource-react`，当前稳定版本 1.4.3），包含 34 个测试套件、233 项自动化测试且全部通过，构建与发布流程完备。
- **前后端协同落地**：由本人主导领域模型、动作契约设计与完整客户端 SDK 研发，并与后端团队协同制定并落地服务端 API 表达层契约。
