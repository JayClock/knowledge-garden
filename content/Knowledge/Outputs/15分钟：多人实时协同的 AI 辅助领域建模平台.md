# 15 分钟深度面谈逐字稿：多人实时协同的 AI 辅助领域建模平台

这个项目延续了我从多端一致性、HATEOAS 资源契约走向业务建模与 RESTful API 的能力主线，只是进一步把“模型本身”做成多人可协作的平台。它是上海鼎歆的内部研发项目，目标不是做一个普通流程图工具，而是让业务、产品和研发围绕同一份模型持续协作，并让 AI 在不破坏正式模型的前提下参与建模。平台已经被团队持续使用，发布模型可以作为 AI 生成 OpenAPI 草稿和测试数据的业务上下文，OpenAPI 经人工审核后用于下游代码生成。我负责从 React Flow 建模画布、Yjs 前端数据绑定，到 NestJS WebSocket 协同服务和 PostgreSQL 持久化的完整实现。（2 分钟）

项目之前的建模过程主要依赖线下会议和头脑风暴，讨论结果缺少可以共同维护和继续消费的结构化载体。平台中的模型由上下文、参与方、角色、Evidence 等领域对象及其关系组成，用户可以创建、移动、修改和删除节点，也可以调整对象之间的关系。单人编辑时，把整张图保存成 JSON 就能工作；但多人同时修改时，整图保存会产生覆盖问题，所以协同层不能只靠定时保存或最后写入者获胜。（3 分钟）

我把整体架构分成四层。第一层是 React Flow 建模编辑器，负责画布交互和领域对象展示。第二层是 Yjs 协同状态层，把本地建模操作转换为可合并的增量更新。第三层是基于 NestJS 与原生 WebSocket 的实时协同服务，负责连接、同步、广播和会话隔离。第四层是 PostgreSQL 持久化与正式模型生命周期，负责恢复协同数据，并把确认后的模型推进到草稿、版本和发布状态。（5 分钟）

前端进入建模空间时，会创建或恢复对应的 Y.Doc，再通过 WebsocketProvider 连接协同服务。模型内容和协作状态分开处理：节点、关系和属性属于需要恢复的共享状态；在线成员、远端光标和选区属于短生命周期状态，由 Awareness 单独广播。这样用户离开后不会把无意义的光标数据写进正式模型。（6 分钟）

服务端通过 NestJS WebSocket Gateway 接入 Yjs 协议，并区分两类消息：`messageSync` 负责模型内容同步，`messageAwareness` 负责在线用户与光标状态。每个客户端被绑定到具体建模空间，Y.Doc 更新后只向同一空间内的其他连接广播。连接关闭或 ping 检测失败时，服务端会清理连接、Awareness 状态和不再使用的文档实例。普通业务 API 继续处理认证、权限、CRUD 和长期持久化，实时协同服务则处理长连接、高频增量同步、临时状态与消息广播；这是按不同工作负载采用的常规服务边界，不包装成个人架构创新。（8 分钟）

开发中最典型的问题是 React Flow 与 Yjs 双向绑定回环。React Flow 的更新写入 Yjs 后，Yjs observer 会再次 `setNodes`，监听 React 状态的 effect 又把整张图写回 Yjs。定位时，我在 `onNodesChange`、`onEdgesChange`、Yjs 写入入口和 `Y.Map.observe` 回调中加入链路日志，记录节点 ID、变更类型和 `transaction.origin`，最终确认这不是靠 debounce 就能根治的高频触发，而是缺少来源约束的双向绑定。（9 分钟）

我的处理方式是以 Yjs 作为共享状态源，只在明确的用户操作中增量写入；使用 `doc.transact(fn, REACT_FLOW_ORIGIN)` 标记本地来源，让 observer 跳过本地同源事务，只把远端事务更新到 React Flow；同时删除整图全量回写的 effect，增加新旧值比较，并在卸载时正确 `unobserve`。我使用两个浏览器窗口手工联调节点增删改、远端同步和事务回环，结合 Yjs 写入次数与 React Flow 更新次数确认一次本地操作只产生一次 transaction，远端更新只触发一次界面更新且不再向 Yjs 回写。（10 分钟）

Yjs 解决的是多人并发状态收敛，而不是业务语义正确。两个用户同时修改同一对象时，CRDT 可以让不同客户端最终得到一致结果，但对象名称、边界和关系是否合理，仍然需要领域评审。这个区别很重要：技术一致性不能替代团队对统一语言的判断。（11 分钟）

协同数据不能只放在内存里，否则服务重启或用户重新进入后无法恢复。项目没有直接依赖 y-websocket 默认的 LevelDB 持久化，而是由我封装 PostgreSQL 适配层，把协同数据接入统一数据库。打开建模空间时先恢复已有状态，再接收新的增量更新。当前能够确认持久化链路已经实现，但还没有把断线重连和服务重启恢复整理成自动化测试成果。（12 分钟）

在多人协同之上，平台还提供 AI 辅助建模。AI 不直接覆盖当前画布或正式模型，而是通过 SSE 返回结构化 Proposal。Proposal 由新增、修改、删除节点或关系等明确操作组成，前端展示受影响对象，用户可以定位、预览、逐项采纳或拒绝。确认后的操作先进入草稿，再由用户保存、创建版本并发布。（13 分钟）

一个真实案例是库销存 Agent。客户会用“下个月将滞留货物降低至 20%”这类目标说明分析诉求，但这个数字只是场景举例，不是项目结果。我使用 8X Flow 从采购合同出发，把参与方、权责、发货、收货、退货，以及对应的履约请求、确认和 Evidence 建模出来，让正常与异常履约都可以审计。库存 Agent 消费这些事实分析滞留原因，并把结论关联回合同项和履约记录。由于已经无法准确回忆客户的具体对象名和规则，面试中只按通用采购场景解释方法，不冒充生产细节。

模型到 API 不从页面按钮倒推 RPC，而是从数据变化和聚合边界生成 URI，再组合角色、HTTP Method 与业务场景得到 API 候选，使用 HAL relation 表达资源关系，并把 API 映射回履约流程验证完整性。发布模型作为上下文交给 AI 生成 OpenAPI 草稿，经过人工审核后再用于下游代码生成；正常和异常履约测试数据也由 AI 根据模型生成。这不是确定性的一键代码生成，AI 不直接发布正式契约或完整业务系统。（14 分钟）

这里实际上有四类控制问题：CRDT 负责多人并发状态收敛，结构化 Proposal 和人工确认负责模型变更边界，草稿、版本和发布流程负责正式模型生命周期，OpenAPI 草稿的人工审核则负责模型进入软件契约时的正确性。把这些问题分开以后，协同编辑和 AI 才不会直接污染正式知识或接口契约。

公司原始源码不能公开，所以我后来额外做了 [team-ai](https://github.com/JayClock/team-ai) 公开重实现。公开版本重新实现了 Workspace、Diagram、LogicalEntity、Version 和 KnowledgeGraph 等领域对象，使用 HATEOAS 暴露资源关系和动作，并实现 React Flow 建模、AI Proposal 的逐项采纳与拒绝、草稿、版本和知识图谱发布。这个仓库可以验证我的工程能力，但我不会把它说成公司源码，也不会用它证明公司项目的用户规模。

如果用一句话总结，这个项目把我早期从复杂前端、多端一致性倒推出来的模型与契约能力，进一步产品化为多人协同建模平台：CRDT 管理并发状态，人工确认控制 AI 候选变更，版本发布管理正式模型，人工审核把模型安全地送入 OpenAPI、测试数据和下游代码生成链路。

当前可以确认团队在持续使用、功能和个人实现范围，以及双浏览器下的节点增删改、远端同步和事务回环验证；还缺少实际协作人数、使用频率、峰值连接数、同步延迟和自动化协同测试。因此面试中不补写高并发或效率提升比例。（15 分钟）
