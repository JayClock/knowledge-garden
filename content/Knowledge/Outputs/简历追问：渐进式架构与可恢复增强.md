# 简历追问：渐进式架构与可恢复增强

关联：[[全栈工程师简历追问地图]]。

## 面试官真正想确认

在契约驱动的全流交付主轴下，你说的“渐进式”是否真能回答契约怎样兼容迁移、隔离失败和保留验证证据，而不是把分层、懒加载、插件化或骨架屏统一换一个名称。它是契约演进方法，不替代知识来源、权威和消费者分析。

## 总追问链

### 1. 找基线

- 每个项目最小但完整的核心任务是什么？
- 去掉 AI、实时协同、监控或高级插件后，哪些能力仍然成立？
- 哪些能力只是体验增强，哪些实际上是业务必要条件？
- 你的“基线”是浏览器原生能力、领域模型、协议、状态机还是人工流程？

### 2. 发现与消费增强

- 客户端怎样发现 relation、action、plugin、adapter 或 Proposal？
- 不认识新增能力的旧客户端会怎样处理？
- 是 capability detection，还是写死版本和客户端类型？
- 增强层是否重新复制了一份核心业务状态机？

### 3. 失败与恢复

- 增强失败时，是回退到基础能力、局部失败、等待人工，还是整页／整次任务失败？
- 哪些失败可以在当前层重试，哪些必须返回上游模型、计划或契约？
- 如何避免生成式修复、插件重试和网络重试无限循环？
- 失败发生后保留了哪些状态、版本、日志和用户工作成果？

### 4. 兼容与验证

- 新增 relation、节点、事件字段或 DSL 节点时，旧消费者怎样继续工作？
- 你实际做过哪些契约、回归和失败注入测试？
- 跨端兼容与降级策略的演进设计是怎样的？
- 怎样从覆盖范围、容灾机制与验证方式证明架构价值？

## HATEOAS

- 为什么资源数据是基线，而 relation／action 是可发现能力？
- `_links` 与 `_templates` 怎样避免退化成按钮数组？
- 当前资源没有 `publish` 时，前端为什么不能根据 status 自己补出来？
- 新增 relation 后旧客户端是否需要发版？当前有哪些真实兼容证据？
- 为什么先做工作区导航试点，并保留 BFF 退路？
- 缓存中的旧资源提交动作失败后，客户端怎样恢复？

## AI Flow

- `WorkflowDefinition` 为什么比 React Flow 画布组件更适合作为基线？
- `NodeRegistry + NodeExecutor` 隔离了哪些变化？
- 新节点增加时，核心调度器、配置表单和执行器分别要改什么？
- 未知节点、插件加载失败或节点配置升级时，旧流程怎样处理？
- SSE 不可用时应如何设计基础状态查询降级方案？
- 哪些错误由节点层处理，哪些由工作流运行时统一处理？

## 多人领域建模

- 不使用 AI 时，手工建模、审核、版本和发布是否能够完整运行？
- Yjs 是基础能力还是协作增强？对这个产品而言为什么？
- CRDT 收敛为什么不能替代领域语义审核？
- AI Proposal 如何被定位、预览、采纳和拒绝？
- AI 或协同服务不可用时，目前实际实现了什么退路？
- 极端弱网与服务异常时的协同恢复策略是怎样的？

## Figma AI

- 为什么 DSL 和可编辑文档比一次性模型输出更适合作为基线？
- 多 Agent 失败以后，已有 Fragment 和人工工作如何保留？
- revision、ownership 和串行合并分别控制什么风险？
- 为什么 Visual Harness 只修局部且最多两轮？
- 为什么 MCP 当前只读？开放写入前还缺哪些事务和恢复能力？
- 在 AI 生成未达预期或局部失败时，系统如何提供可编辑兜底与人工接管机制？

## 监控 SDK

- core、browser、React／Vue adapter 分别面对什么变化？
- `PerformanceObserver` 不存在时插件是否跳过，还是 SDK 初始化失败？
- 一个采集插件抛错是否会阻断其他插件或宿主业务？
- Fetch／XHR 代理怎样证明没有改变原始返回值和异常语义？
- Transport 失败、队列积压和重试怎样避免影响主业务？
- 监控 SDK 如何在不支持相应 Web API 的宿主环境中实现 feature detection 与 fail-open？

## 面试注意事项

- 说明渐进式架构的核心在于界定稳定基线与可独立退化、可恢复的增强层，避免滥用概念标签。
- 阐明 AI 失败时的局部回退策略与状态保留机制（如保留当前文档状态与 Run 历史）。
- 说明跨版本演进时依赖 Schema 契约与 relation 检查的兼容机制。
- 区分已落地的稳定机制与系统演进方向（如复杂降级容灾方案）。
- 重点阐述架构机制、验证方式与工程约束，不使用未经统计口径核验的量化百分比。

## 准备证据

- HATEOAS：改造前后的消费代码、relation／action 契约、导航试点和 BFF 退路；
- AI Flow：WorkflowDefinition、NodeRegistry、执行器与错误边界；
- 领域建模：Proposal Schema、采纳／拒绝、版本与发布；
- Figma AI：DSL、DesignPatch、revision、Visual Harness 和 Run 历史；
- 监控 SDK：包依赖、插件注册、代理保持语义、队列与重试。
