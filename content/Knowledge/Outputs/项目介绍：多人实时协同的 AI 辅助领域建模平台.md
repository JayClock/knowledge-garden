# 项目介绍：多人实时协同的 AI 辅助领域建模平台

## 提取词

业务语义契约 ｜ 8X Flow 与 React Flow ｜ Yjs 与 Awareness 分离 ｜ 页面与协同生命周期联动 ｜ AI Proposal 候选层 ｜ 契约驱动交付闭环

## 2 分钟版本

团队过去主要通过事件风暴和头脑风暴建模，讨论结果容易发散，业务、前端和后端各自保留一部分理解。平台使用 8X Flow 组织参与方、角色、权责和 Evidence，再通过 React Flow 把模型做成可以共同维护、审核和继续消费的业务语义契约。

多人同时编辑时，整图覆盖会造成后写覆盖前写。我把节点、关系和属性放进 Y.Doc，通过 WebsocketProvider 同步增量更新；在线成员、远端光标和选区只在当前会话有效，因此放进 Awareness，不进入数据库。

服务端使用 NestJS 和原生 WebSocket，按空间创建 Y.Doc 并广播增量。针对早期路由切换后残留旧画布的问题，我把协同生命周期与页面标识强绑定，并在部署阶段适配了 WSS 协议与反向代理同源转发。退出活跃状态时由 PostgreSQL 适配层写回最终状态，实时增量与长期持久化职责清晰分离。

Yjs 只能保证副本最终收敛，不能保证领域语义正确。AI 也不能直接覆盖正式模型，所以 AI 输出是结构化 Proposal，由用户逐项采纳或拒绝；确认后再进入草稿、版本和发布。发布模型可以作为 OpenAPI 草稿和测试数据的上下文，但正式契约仍由人工严格审核。

## 5 分钟主讲

我先介绍一下这个项目的背景。在复杂的企业级业务交付中，前端与后端往往会反复解释同一个业务概念。过去团队建模主要依赖白板和会议讨论，结果很难持续维护，前端、后端和业务各自保留一部分理解，经常导致接口做出来后才发现对领域规则的理解根本不一致。为了解决这个痛点，我推动并实现了多人实时协同的 AI 辅助领域建模平台：使用 8X Flow 把参与方、履约角色、权责和 Evidence 结构化沉淀为双方共同审核的业务语义契约，并用 React Flow 提供可视化协作空间。我直接负责前端画布、协同服务与持久化全链路。

多人同时在画布上编辑时，传统的整图保存方案必然会导致后写覆盖前写。为了实现无冲突协同，我把核心的节点、关系和属性放进 Y.Doc，通过 WebsocketProvider 实时广播增量更新。但我做了一个非常关键的架构拆分：把正式模型内容与协同临时状态彻底分开。在线成员、远端光标和多选区只在当前会话有效，因此全部放入 Awareness 协议广播，绝不进入数据库持久化；服务端也分别通过 messageSync 和 messageAwareness 独立处理。这样不仅避免了高频光标事件污染正式模型，也保证了数据库只存储有价值的业务结构。

在系统落地过程中，我遇到的最核心工程难点是**长连接、协同对象与前端页面生命周期的严格联动**。在早期开发联调时，曾出现过页面路由切换后内容依然停留在旧画布的问题。排查后发现，当时 Y.Doc 与 Provider 的实例管理脱离了 React 组件生命周期：虽然路由参数变了，编辑器却还在复用旧的协同连接。这个问题让我深刻意识到“长连接还活着，绝不等于连接到了正确的资源”。我彻底重构了协同生命周期，让数据 Fragment、编辑器初始化与页面标识强绑定，并在页面卸载时显式断开 Provider、清理 Awareness 监听。在部署阶段，针对 HTTPS 环境拦截 WS 混合内容的问题，我也完成了从协议升级到反向代理 Upgrade 同源转发的完整网络拓扑改造。服务端在连接断开或心跳超时时，精确清理会话状态；当房间内最后一个用户离开后，先触发 PostgreSQL 适配层持久化，再安全释放内存文档，彻底杜绝了内存泄漏与无主文档残留。

这里我还做了一层深刻的技术取舍：**CRDT 解决的是副本最终收敛，但绝不代表业务语义正确；AI 也绝不能越权覆盖正式模型**。两个人同时在画布上改连线，Yjs 能保证两边客户端最终看到完全一致的图结构，但这个连线在业务上合不合规，CRDT 是不知道的。因此平台坚决引入草稿、版本与正式发布的治理机制。AI 大模型也只能作为辅助层：AI 根据业务输入通过 SSE 推送新增或修改关系的结构化 Proposal，前端高亮受影响对象，由业务专家逐项采纳或拒绝，只有人工确认后才能合入模型草稿。在真实的库销存场景中，我们从采购合同出发，完整建模了参与方、发货、收货、退货与 Evidence，发布后的模型直接作为 OpenAPI 草稿和测试数据候选的上下文，通过门禁审核保证了交付确定性。

这个项目把前端与后端之间分散的业务知识变成了可协作、可审核、可发布的语义契约。技术难点是让正式模型、临时状态、页面资源、长连接和持久化保持严密一致的生命周期；而技术架构的核心原则是：CRDT 负责状态同步，AI 负责候选生成，业务专家与人工审核掌握最终的正式发布权。

## 高频追问

### 如果面试官问：为什么说这是前端与后端之间的契约平台？

因为它解决的不是“把后端已有的接口画出来”，而是先让业务专家、前端与后端三方对参与方、履约角色、生命周期、关系、权责动作和 Evidence 凭证形成同一份可审核的知识。

传统交付中，接口文档只规定了字段类型，却没讲清业务状态流转背后的权责归属，导致联调时经常产生规则争议。在这个平台上，前端用它理解资源生命周期与合法动作，后端用它设计 RESTful URI 与数据表边界，发布后的正式模型作为 OpenAPI 草稿和自动化测试用例的上下文事实源。

这份契约的权威来自人工评审和发布版本，而不是 AI 或某一方的代码实现。平台提供契约的形成、协作、版本和消费路径，通过人工审核与版本化管理保障业务语义的确定性。

### 如果面试官问：为什么需要 Yjs，而不是保存整张图？

单人编辑时保存整张 JSON 是可行的，但多人同时在线编辑时，整图保存方案必然会导致“后写覆盖前写”，造成灾难性的数据丢失。

Yjs 基于 CRDT（无冲突复制数据类型）算法。每个客户端在本地独立修改状态，修改以增量 Update 的二进制形式通过 WebSocket 广播。Yjs 内部为每个操作打上 ClientID 和 Clock 逻辑时钟，并发到达的操作无需中央锁竞争，在数学上能够保证所有客户端副本最终收敛到完全一致的图结构。

### 如果面试官问：模型内容和在线状态为什么要分开？

因为这两类数据的**生命周期和持久化价值截然不同**：

- **正式模型内容**：包括节点、连线关系、业务属性等，具有长期商业价值，必须可靠持久化到数据库；
- **协同临时状态**：包括在线成员头像、远端实时光标、当前选中的高亮节点，频率极高（每秒数十次），但仅在当前会话中有效，一旦断线立即失效。

因此正式内容进入 Y.Doc 的共享数据类型（Y.Map / Y.Array），通过 `messageSync` 处理；临时状态全部放入 Yjs 的 Awareness 协议，通过 `messageAwareness` 独立广播。这样不仅避免了高频光标事件污染正式模型，也保证了数据库只存储有价值的业务结构，不会把无意义的鼠标坐标写入持久层。

### 如果面试官问：协同服务怎么组织？

服务端基于 NestJS 和原生 WebSocket Gateway 构建：

1. **房间空间隔离**：客户端连接建立时，根据 URL 中的空间 ID（`spaceId`）将其加入对应房间，按空间实例化或从数据库恢复独立的 Y.Doc。
2. **连接管理与心跳**：维护客户端连接集合，处理 Ping/Pong 心跳检测；当连接超时或异常断开时，立即从房间集合中剔除并广播 Awareness 下线事件。
3. **退房持久化与资源释放**：当房间内的最后一个用户离开时，触发 PostgreSQL 持久化适配层将内存文档写回数据库，随后安全释放内存中的 Y.Doc 实例，彻底避免无主文档常驻导致内存泄漏。

普通业务 API 负责认证、鉴权与 CRUD，协同服务专注长连接增量同步，实现了架构上的动静分离。

### 如果面试官问：这个项目真正难在哪里？遇到过哪些典型生命周期问题？

真正的难点是**长连接、协同对象与前端页面生命周期的严格联动**。

在早期开发联调时，遇到过一个典型问题：用户在单页应用中切换路由到另一个画板后，画布依然停留在上一个画板的内容。排查后发现，当时 Y.Doc 与 WebsocketProvider 的管理脱离了 React 组件生命周期：虽然路由参数变了，编辑器却还在复用旧的协同连接。

这个问题让我深刻意识到：“长连接还活着，绝不等于连接到了正确的资源”。我彻底重构了协同生命周期，让数据 Fragment、编辑器初始化与页面标识（`pageId`）强绑定，并在页面组件卸载时显式断开 Provider、清理 Awareness 监听，保证“路由切换即彻底销毁旧连接并重建新上下文”。

另一个难点是网络部署拓扑：在本地开发是普通的 HTTP/WS，上到测试/预发 HTTPS 环境后，浏览器安全策略强制拦截非加密 WebSocket，同时反向代理未配置 `Upgrade: websocket` 导致握手 400 失败。我完成了从 WSS 协议升级到 Nginx / 反向代理同源转发的完整网络拓扑改造，确保长连接在复杂网络环境下的高可用。

### 如果面试官问：PostgreSQL 持久化解决什么？

Y.Doc 只保存在服务端内存中时，一旦服务重启或节点漂移，未保存的数据就会丢失。官方默认方案通常使用本地 LevelDB，但这不符合企业级微服务部署规范。

我封装了 PostgreSQL 持久化适配层：

- 文档首次打开时，适配层从数据库按 `spaceId` 读取历史更新二进制块并应用到内存 Y.Doc；
- 编辑过程中采用防抖合并增量更新；
- 当房间活跃度降为 0（最后一个连接关闭）时，执行最终状态全量合并写回，并打上版本快照，保证了协同状态的长效可恢复性。

### 如果面试官问：网络延迟或断线重连怎么办？

Yjs 的增量更新机制天然具备网络容忍性：

当客户端遭遇弱网断线时，本地仍可基于本地 Y.Doc 正常编辑；连接断开期间产生的所有增量被缓存在本地队列中。当网络恢复触发 WebsocketProvider 自动重连时，客户端与服务端先通过 `SyncStep1` 和 `SyncStep2` 双向交换缺失的时钟向量与增量差异，自动完成双向合并对齐，用户无感知恢复协同。

### 如果面试官问：CRDT 收敛后为什么还需要人工评审？AI 如何参与建模？

**CRDT 解决的是副本数学上的最终收敛，但绝不代表业务语义正确**。两个人同时在画布上改连线，Yjs 能保证两边客户端最终看到完全一致的图结构，但这个连线在业务规则上是否合法，CRDT 是不知道的。

同理，**AI 大模型也绝不能越权直接覆盖正式模型**。平台将 AI 限制为辅助候选层：AI 根据业务输入通过 SSE 推送新增或修改关系的结构化 Proposal，前端高亮受影响对象，由业务专家逐项采纳或拒绝；只有人工确认后才能合入模型草稿。通过“草稿 $\to$ 审核 $\to$ 版本发布”的确定性门禁，将 AI 的生成能力与企业业务严肃性深度融合。

### 如果面试官问：平台产生的模型怎样被下游使用？关联对象怎么设计？

在真实的库销存场景中，我们从采购合同出发，完整建模了参与方、履约角色、发货、收货、退货与 Evidence 凭证。发布后的模型直接作为 OpenAPI 草稿和接口自动化测试用例生成的上下文事实源。

在关联关系落地时，我设计了**关联对象建模方法**：将一对多关系从原始集合提升为具有业务语义的领域对象（如“合同项清单”）。领域层只定义业务导航与操作，具体的分页、批量预加载和延迟加载策略封装在关联对象内部，既严格守住了聚合根边界，又从根源上规避了传统 ORM 容易引发的 N+1 查询性能风险。
