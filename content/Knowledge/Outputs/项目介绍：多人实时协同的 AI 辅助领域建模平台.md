# 项目介绍：多人实时协同的 AI 辅助领域建模平台

## 提取词

业务语义契约 ｜ 8X Flow 与 React Flow ｜ Yjs 与 Awareness 分离 ｜ 页面与协同生命周期联动 ｜ AI Proposal 候选层 ｜ 契约驱动交付闭环

## 5 分钟主讲

我先介绍一下这个项目的背景。在复杂的企业级业务交付中，前端与后端往往会反复解释同一个业务概念。过去团队建模主要依赖白板和会议讨论，结果很难持续维护，前端、后端和业务各自保留一部分理解，经常导致接口做出来后才发现对领域规则的理解根本不一致。为了解决这个痛点，我推动并实现了多人实时协同的 AI 辅助领域建模平台：使用 8X Flow 把参与方、履约角色、权责和 Evidence 结构化沉淀为双方共同审核的业务语义契约，并用 React Flow 提供可视化协作空间。我直接负责前端画布、协同服务与持久化全链路。

多人同时在画布上编辑时，传统的整图保存方案必然会导致后写覆盖前写。为了实现无冲突协同，我把核心的节点、关系和属性放进 Y.Doc，通过 WebsocketProvider 实时广播增量更新。但我做了一个非常关键的架构拆分：把正式模型内容与协同临时状态彻底分开。在线成员、远端光标和多选区只在当前会话有效，因此全部放入 Awareness 协议广播，绝不进入数据库持久化；服务端也分别通过 messageSync 和 messageAwareness 独立处理。这样不仅避免了高频光标事件污染正式模型，也保证了数据库只存储有价值的业务结构。

在系统落地过程中，我遇到的最核心工程难点是**长连接、协同对象与前端页面生命周期的严格联动**。在早期开发联调时，曾出现过页面路由切换后内容依然停留在旧画布的问题。排查后发现，当时 Y.Doc 与 Provider 的实例管理脱离了 React 组件生命周期：虽然路由参数变了，编辑器却还在复用旧的协同连接。这个问题让我深刻意识到“长连接还活着，绝不等于连接到了正确的资源”。我彻底重构了协同生命周期，让数据 Fragment、编辑器初始化与页面标识强绑定，并在页面卸载时显式断开 Provider、清理 Awareness 监听。在部署阶段，针对 HTTPS 环境拦截 WS 混合内容的问题，我也完成了从协议升级到反向代理 Upgrade 同源转发的完整网络拓扑改造。服务端在连接断开或心跳超时时，精确清理会话状态；当房间内最后一个用户离开后，先触发 PostgreSQL 适配层持久化，再安全释放内存文档，彻底杜绝了内存泄漏与无主文档残留。

这里我还做了一层深刻的技术取舍：**CRDT 解决的是副本最终收敛，但绝不代表业务语义正确；AI 也绝不能越权覆盖正式模型**。两个人同时在画布上改连线，Yjs 能保证两边客户端最终看到完全一致的图结构，但这个连线在业务上合不合规，CRDT 是不知道的。因此平台坚决引入草稿、版本与正式发布的治理机制。AI 大模型也只能作为辅助层：AI 根据业务输入通过 SSE 推送新增或修改关系的结构化 Proposal，前端高亮受影响对象，由业务专家逐项采纳或拒绝，只有人工确认后才能合入模型草稿。在真实的库销存场景中，我们从采购合同出发，完整建模了参与方、发货、收货、退货与 Evidence，发布后的模型直接作为 OpenAPI 草稿和测试数据候选的上下文，通过门禁审核保证了交付确定性。

这个项目把前端与后端之间分散的业务知识变成了可协作、可审核、可发布的语义契约。技术难点是让正式模型、临时状态、页面资源、长连接和持久化保持严密一致的生命周期；而技术架构的核心原则是：CRDT 负责状态同步，AI 负责候选生成，业务专家与人工审核掌握最终的正式发布权。

## 2 分钟版本

团队过去主要通过事件风暴和头脑风暴建模，讨论结果容易发散，业务、前端和后端各自保留一部分理解。平台使用 8X Flow 组织参与方、角色、权责和 Evidence，再通过 React Flow 把模型做成可以共同维护、审核和继续消费的业务语义契约。

多人同时编辑时，整图覆盖会造成后写覆盖前写。我把节点、关系和属性放进 Y.Doc，通过 WebsocketProvider 同步增量更新；在线成员、远端光标和选区只在当前会话有效，因此放进 Awareness，不进入数据库。

服务端使用 NestJS 和原生 WebSocket，按空间创建 Y.Doc 并广播增量。针对早期路由切换后残留旧画布的问题，我把协同生命周期与页面标识强绑定，并在部署阶段适配了 WSS 协议与反向代理同源转发。退出活跃状态时由 PostgreSQL 适配层写回最终状态，实时增量与长期持久化职责清晰分离。

Yjs 只能保证副本最终收敛，不能保证领域语义正确。AI 也不能直接覆盖正式模型，所以 AI 输出是结构化 Proposal，由用户逐项采纳或拒绝；确认后再进入草稿、版本和发布。发布模型可以作为 OpenAPI 草稿和测试数据的上下文，但正式契约仍由人工严格审核。

## 30 秒版本

这个项目把前端与后端反复解释的业务知识沉淀为双方共同审核和消费的语义契约。我负责 React Flow 建模前端、Yjs／Awareness、NestJS WebSocket 协同服务和 PostgreSQL 持久化；参与方、权责、事件、领域对象和关系经人工确认后进入版本与发布，再支持 RESTful API、OpenAPI 草稿和测试数据候选。

## 渐进式架构视角

结构化模型、审核、版本和发布是知识基线；Yjs 增强协作，AI Proposal 增强候选生成，OpenAPI 草稿和测试数据增强下游消费。CRDT 负责状态同步，AI 负责候选生成，业务专家与人工审核 Gate 负责正式模型与发布权，实现了敏捷协同与确定性发布的结合。
