> [!info] Agent 交付的七个坏味道 · 05
> 系列基于我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT）。上一篇：[[虚假胜利：Agent 以为自己做完了，其实没有]]

每个 Agent 项目都有一个越来越长的入口文件。

起初它只有几条规则。然后出现一个例外，加一段；再出现一次误判，把同一条规则换个说法再写一遍；旧方案不能直接删，就留一句“以前是……现在是……”。半年后它有了八百行，而 Agent 的表现反而更差。

## 这个坏味道长什么样

指令文件腐化指的是**规则只增不减**。它的四种典型形态：

- 为一个例外往入口文件里加一段；
- 同一条规则在多个文档各写一份，并逐渐互相矛盾；
- 保留“以前是……现在是……”的兼容说明，让旧约束继续参与判断；
- 生成的内容被手工修改后，与它的来源脱节。

规则累积之后，优先级冲突、例外条款，以及模型对长文本中段的注意力衰减叠在一起，Agent 的行为会变得越来越难预测。

这个项目目前入口还很小，但要盯住这些信号：入口文件里“但是/除非”越来越多；同一约束在 skill、指南和任务模板里出现多个版本；过期表述靠注释保留而不是被替换；评审时无法指出 Agent 的行为偏差来自哪条规则。

出现任意一条，应该先处理分层和优先级，而不是继续加规则。

## 解法：分层、单一来源、可执行检查、替换式重构

### 分层入口：只路由，不装细节

[AGENTS.md](https://github.com/JayClock/Evidence-Framework/blob/main/AGENTS.md) 共 39 行：27 行正文（行动入口、不变量、流程与状态、验证底线）加 12 行受管的生成块。它不写操作手册。

[Guides 导航](https://github.com/JayClock/Evidence-Framework/blob/main/docs/guides/index.md)把知识分成四层，并声明自己“只路由，不保存第二份事实、任务状态或完成证据”：

| 层          | 唯一职责                                       | 使用方式         |
| ----------- | ---------------------------------------------- | ---------------- |
| 项目宪法    | 权限、硬约束、停止纪律                         | 每次必读         |
| 项目基线    | 软件范围、业务与接口来源、架构、术语、质量要求 | 按任务选择       |
| 工程指南    | 规范、操作方法、带测试的真实范例               | 按改动类型选择   |
| 任务 Guides | 当前交付结果、来源、局部设计、文件范围、检查   | 执行当前任务必读 |

任务 Guides 只写局部差异和引用，稳定基线由对应文档唯一维护。**分层的作用是让每条规则的归属唯一**——否则它迟早会在三个地方长出三个版本。

### 优先级与冲突裁决

不变量定义不可协商的边界，来源权威表为每类问题指定唯一权威位置；冲突时停止行动、交回拥有者。机制细节见[[隐式约定：规则只存在于人的脑子里]]。优先级存在，规则才不靠篇幅和新旧竞争。

### 让检查器替你发现腐化

腐化可以被机器发现一部分，关键是把它做成命令而不是提醒：

- [Guides 检查器](https://github.com/JayClock/Evidence-Framework/blob/main/tools/guides/check.mjs)扫描 9 个必读文档，加上 `docs/` 全树与规划、交付两个 skill 的 references 与 assets；
- 它检查必读文档是否存在、本地链接是否可解析（相对路径、URL 编码、尖括号路径），并**拒绝过期的架构表述**；
- 它忽略围栏示例、远程链接、锚点与模板变量，只扫描维护中的文档，不扫生成产物与历史证据；
- 检查器自身有回归覆盖八类边界，其中两条很关键：“拒绝过期架构指南，而不是保留兼容段落”“只扫维护文档与工作流模板，不扫生成事实或历史证据”；
- `npm run guides:verify` 由回归测试与实际扫描（含格式化检查）组成，并被并入 `npm run lint` 与项目质量底线。

写这篇文章时的一次实测：40 篇文档、390 个本地链接、0 错误，回归 8 项全部通过。

### 用替换式重构清理，而不是用注释

维护纪律只有一句话：

> 正文直接描述当前有效约束，不保留兼容入口或过期方案说明。替换文档时同步引用它的导航、Skill、任务模板和检查；不删除业务原始材料或历史执行证据。

这条纪律在 Git 历史里能看出来：这个仓库用一批破坏性重构（`refactor(harness)!` 系列）重建过任务级前馈、统一过工作流命名、移除过整套扩展与阶段技能、删掉过一套评审状态。每次重构后入口文件都保持小体积，而不是靠追加说明维持兼容。

判断标准很朴素：**新约束进来时，必须有一条旧约束出去**。加规则和删规则是同一个动作的两半。

### 生成内容要有归属和刷新路径

入口文件里那段 OpenWiki 块由生成器写入，标记了明确的起止位置；生成页面不手工修改，需要改内容就改源码或文档让它重新生成；忽略文件限定生成器能读到哪些内容。

生成内容一旦可以被手工修改，它就变成了第二个事实源——而它的刷新机制并不知道这件事。

## 演进方向

- 目前没有规则登记表（编号、来源、优先级、适用条件、过期条件、状态），也没有定期矛盾审计：优先级靠不变量与来源权威表，清理靠替换式重构与检查器回归；
- 过期检测目前只覆盖一条具体词例（某类过期的架构表述）；**语义矛盾**——同一条约束在不同文档给出不同结论——仍靠人工复核，尚未编号入检查；
- 规则数量继续增长后，可以给规则补编号与过期条件，把矛盾检测做成固定动作；新增规范时必须同时更新导航、skill 与任务模板，并指出对应的测试或人工评估。

## 收束

入口文件不是知识库，是一份权限清单。它的价值不在于写全，而在于**每一条都还在生效**。一个八百行的入口文件之所以危险，不是因为长，而是因为其中大部分内容已经没人知道是否还成立了。
