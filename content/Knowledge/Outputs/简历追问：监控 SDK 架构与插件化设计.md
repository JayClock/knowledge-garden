# 简历追问：监控 SDK 架构与插件化设计

关联：[[项目介绍：前端埋点与监控 SDK]]、[[1.需求评审、项目架构设计与上报数据盘点]]、[[2.指标采集、埋点设计实践与数据上报机制、监控告警实现]]。

## 对应简历描述

> 设计并实现由核心包、浏览器包和 React／Vue 适配包组成的监控 SDK，以插件和 Transport 解耦性能、异常、操作、请求与业务自定义事件；在 AI Flow 中为校验、测试运行和发布添加埋点，并以 `executionId` 关联执行日志。

## 面试官真正想确认

你是否能把下游验收与诊断需要的证据固化为稳定事件契约，再解释跨框架 SDK 的包边界、采集插件和发送通道，而不是只封装一个 `track()` 函数。

## 连续追问链

### 1. 包边界

- core 为什么不能依赖 DOM、React 或 Vue？
- browser 包封装哪些 Web API？
- React、Vue 和 Vanilla 的接入差异在哪里？
- types、utils 和 browser-utils 为什么单独拆包？

### 2. 插件与协议

- 性能、异常、点击和请求采集怎样作为独立插件注册？
- 不同插件怎样输出同一事件协议？
- 新增监控项需要修改哪些包？
- 插件的初始化生命周期与动态扩展机制在工程中如何设计与解耦？

### 3. 业务自定义事件与证据关联

- 为什么不能按照浏览器“能采什么就采什么”？
- AI Flow 的校验、测试运行和发布分别需要什么自定义事件？
- `executionId` 怎样关联前端操作与节点执行日志？
- 为什么前端埋点不能替代服务端执行事实？
- 端侧埋点应聚焦协议定义与全链路关联，如何避免在客户端做过度侵入的业务推断？

### 4. Transport 与上报

- 为什么采集逻辑不能直接发请求？
- Transport 接口怎样隔离环境和发送策略？
- 本地队列怎样按时间、数量和路由触发批量发送？
- 网络异常重试如何避免放大主业务压力？

### 5. 低侵入与协作边界

- Fetch／XHR 和 DOM 代理怎样保留原始业务行为？
- SDK 自身失败时如何旁路？
- 哪些是 SDK 个人成果，哪些是 NestJS、Kafka、ClickHouse 和监控控制台的协作链路？

### 6. 渐进式适配与 fail-open

- core、browser、React／Vue adapter 中，什么是稳定基线，什么是环境增强？
- `PerformanceObserver` 或某类 Web API 不存在时，插件怎样跳过或降级？当前有哪些真实测试？
- 单个插件初始化或回调抛错会不会阻断其他插件？
- Transport 失败和队列积压怎样确保不影响宿主业务？
- 为什么“SDK 自身失败最多丢监控数据”必须通过失败注入证明，而不能只靠架构推断？

## 场景推演题

> 现在要新增一个资源加载错误采集插件。请说明它应放在哪个包、怎样注册、输出什么统一事件、如何进入队列，以及为什么不需要修改 React／Vue 适配包和后端平台。

## 准备证据

- 准备核心包、框架适配、插件注册和上报机制的技术实现说明。
- 可结合工程代码展示 Monorepo 包结构、core / browser 分层、SDK 初始化、插件注册与 Transport 上报机制。
- 准备 AI Flow 中校验、测试运行和发布的自定义事件，以及通过 `executionId` 关联执行引擎日志的说明。

## 面试注意事项

- 准确解释 Monorepo 拆包设计与插件注册体系。
- 说明浏览器埋点与服务端执行日志通过 `executionId` 进行全链路关联的机制。
- 关注端侧采集与上报的高内聚实现，清晰阐述与数据平台的协作界面。
