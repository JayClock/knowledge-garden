# 简历回答逐字稿：低代码工作流引擎 DAG 架构设计

关联：[[简历追问：低代码工作流引擎 DAG 架构设计]]、[[15分钟：低代码平台]]。

> [!warning] 回答边界
>
> - 个人直接实现的是 TypeScript `WorkflowEngine`、`GraphBuilder`、`ExecutionContext`、`VariableResolver`、拓扑调度、环检测和条件分支处理。
> - 项目能力范围以候选人确认和原始文稿为准；`miaoma-aiflow-v2` 是内部重实现，不要求完整镜像公司项目，局部差异不用于收缩项目事实。
> - 内部重实现的执行日志排序 Bug 有 Git 修复记录，但不是公司生产事故。
> - NestJS API、SSE 事件推送与数据持久化由后端同事实现；个人负责共同协议与前端接入。
> - 监控 SDK 已接入 AI Flow，校验、测试运行和发布自定义事件通过 `executionId` 与执行引擎日志关联。
> - 并发限流、节点幂等重试、服务重启恢复和 Loop 容器属于延展设计，不能说成已经上线。

## 30 秒开场

这个项目要把 React Flow 画布定义稳定地转成可执行流程。我用 `WorkflowDefinition`、Node 和 Edge 统一协议，运行前验证节点、边和配置，再由 GraphBuilder 完成环检测、拓扑顺序和条件分支剪枝。节点输出进入 ExecutionContext，下游通过 `${nodeId.variableName}` 读取结果。

## 如果面试官问：图结构怎样校验和执行？

运行前，工作流验证器会检查 Start 和 End 是否存在、节点类型是否已注册、节点配置是否有效，以及边引用的源节点和目标节点是否存在。

通过后再构建图。实现里邻接表用于查找下游，反向邻接表用于查找上游，入度表用于 Kahn 拓扑排序。普通工作流主图不允许环，所以运行前还会做环检测；只有合法 DAG 才进入执行阶段。

Kahn 算法会先把入度为 0 的节点加入队列。节点进入结果序列后，依次减少后继节点的入度；后继入度变为 0 时再进入队列。Kahn 是标准算法。我的工作是把校验、构图、动态分支和执行器调度完整组合起来。

## 如果面试官追：条件分支怎么处理？

Condition 节点通过 `sourceHandle` 返回命中的分支。GraphBuilder 会把其他分支的目标加入排除集合，并递归处理下游。

关键点是不能无条件删除整个子树。两个分支可能在后面汇合到公共节点，所以递归前要检查该节点是否还有其他未排除的前驱。只要仍有活跃入边，它就应该保留；只有没有其他活跃入边时才继续排除。命中分支后重新计算执行顺序，使未选路径不会执行，也不会让公共下游被误删。

这部分完成范围来自候选人确认和原始文稿；内部重实现只用于复现代表性机制，不要求逐行覆盖公司项目。

## 如果面试官追：上下文和变量怎样传递？

每次工作流执行都会创建独立 ExecutionContext，按 nodeId 保存节点输出与完成状态。节点执行前，VariableResolver 递归扫描配置中的字符串、数组和对象，解析 `${nodeId.variableName}` 并读取上游输出。

这样节点之间不共享一块没有边界的全局对象，编辑器保存的变量协议也能被执行器直接消费。找不到变量时，原文稿规定保留 `${nodeId.variableName}`，而不是静默替换成空值；当前不额外声称已经实现发布期变量存在性校验。

## 如果面试官追：多个入度为 0 的节点是否并行？

从 DAG 语义看，同一轮入度为 0 的节点具备并行条件；但当前材料能确认的是拓扑顺序、环检测和条件分支处理，没有证据证明已经完成并发上限、租户隔离和复杂 fan-in 失败策略。

并发调度仍是后续工程化方向，不能把理论上的可并行直接说成生产能力。

## 如果面试官追：失败重试和幂等怎么设计？

当前可以确认统一错误捕获、耗时记录和执行日志，但没有材料证明节点级 attempt、幂等键和服务重启恢复已经完成。

如果讨论扩展，有副作用的 HTTP 节点需要 executionId、attempt、幂等键和持久化执行状态；但我会明确这是演进方案，不是现有 TypeScript 引擎的已交付事实。

## 如果面试官追：支持 Loop 怎么办？

第一版保持主图是 DAG，因为它更容易校验、解释和测试。如果业务必须循环，可以把 Loop 设计成有明确退出条件和最大次数的局部容器，主图仍保持 DAG，而不是允许用户任意连环。

当前项目没有把 Loop 节点作为已完成能力。

## 如果面试官追：前端埋点怎样与执行日志关联？

下游验收需要知道用户是在工作流校验、测试运行还是发布环节失败，因此我在 AI Flow 中接入监控 SDK，为这些关键路径添加自定义事件。节点是否真正执行成功、耗时多久、在哪一步报错，仍由执行引擎日志记录；两侧通过同一个 `executionId` 关联。

这样浏览器 SDK 负责用户操作路径和关键结果，执行引擎负责节点级事实。即使页面关闭或前端事件丢失，也不会让浏览器埋点成为服务端执行结果的唯一来源。当前没有可确认的下游使用方式和量化收益，因此只讲关联机制。

## 收尾句

这个引擎把可视化定义继续落实到了节点与边校验、图构建、拓扑调度、条件分支剪枝和 ExecutionContext 数据传递，并通过 `executionId` 把前端验收路径与节点执行证据连接起来。并发、幂等和恢复则按事实边界作为后续方向。
