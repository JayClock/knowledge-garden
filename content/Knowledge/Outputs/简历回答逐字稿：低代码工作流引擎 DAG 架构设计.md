# 简历回答逐字稿：低代码工作流引擎 DAG 架构设计

关联：[[职业经历]]、[[全栈工程师简历]]、[[简历追问：低代码工作流引擎 DAG 架构设计]]、[[15分钟：低代码平台]]。

> [!warning] 回答边界
>
> - 个人直接实现的是 TypeScript `WorkflowEngine`、`GraphBuilder`、`ExecutionContext`、`VariableResolver`、Kahn 拓扑排序、环检测和条件分支处理。
> - NestJS 与 SSE 服务端代码由后端同事实现。
> - 并发限流、失败恢复、幂等重试和 Loop 容器属于延展设计，不能说成已经上线。

## 30 秒开场

我做这个工作流引擎时，重点不是画一个流程图，而是让画布配置能被相关 TypeScript 运行时稳定执行。核心问题是节点依赖、图结构有效性、条件分支和上下文传递。

所以我把流程协议抽象成 `Node` 和 `Edge`，用 `GraphBuilder` 构建邻接表、反向邻接表和入度表，再用标准 Kahn 算法做拓扑排序和环检测。Start、HTTP、Condition、End 等节点都通过统一协议进入调度。

## 如果面试官问：Kahn 算法在你这里怎么用？

我会这样说：

流程保存或运行前，我会先根据 `edges` 构建邻接表和入度表。所有入度为 0 的节点进入队列。每弹出一个节点，就把它的下游节点入度减 1；如果下游入度变成 0，就说明依赖都满足了，可以进入待执行队列。

如果最后处理过的节点数少于总节点数，就说明图里有环。这个时候不能发布或不能运行，因为普通审批流和自动化流程默认不应该出现无限循环。

我一般会在两个时机做校验：保存时做一次，防止明显错误进入系统；运行前再做一次，防止历史配置或接口导入绕过前端校验。

## 如果面试官追：条件分支怎么处理？

我会说条件分支是 DAG 调度里很容易被低估的点。

比如 Condition 后面有 A、B 两条分支，只命中 A。不能只是让 B 不执行，因为 B 下游可能还有 Join 节点。如果 B 一直保持未完成，Join 的入度永远归不了零，流程就卡死。

所以我的做法是 Condition 执行后，对未命中分支做动态剪枝。未命中的节点会被标记为 `SKIPPED`，同时它们对下游的依赖也要被释放或标记为无效入度。这样命中路径可以继续推进，未命中路径不会阻塞主流程。

## 如果面试官追：并发和 fan-in 怎么办？

我会先说当前确认的核心是拓扑顺序、环检测和条件分支处理，没有材料证明已经完成按租户限流、并发调度或复杂 fan-in 失败策略。

从算法上，同一轮入度为 0 的节点具备并行条件，fan-in 节点则要等待有效上游依赖释放；如果继续工程化，还需要显式设计并发上限和失败策略。这部分只能作为扩展方向。

## 如果面试官追：失败重试和幂等怎么设计？

我会先说明执行记录和日志反馈属于完整系统链路，但 NestJS 与 SSE 服务端由后端同事实现。当前职业主档没有把节点级幂等、attempt 状态机和服务重启恢复列为我的已完成交付。

如果讨论扩展方案，有副作用节点需要 executionId、attempt、幂等键和可恢复状态；但我不会把这套设计说成现有 TypeScript 引擎已经全部上线。

## 如果面试官追：支持 Loop 怎么办？

我会先说第一版我会保持主图是 DAG，因为这样可解释、可测试、也容易恢复。

如果业务确实需要循环，我不会允许用户任意连环，而是把 Loop 做成一个有明确退出条件和最大次数的局部容器。主图仍然是 DAG，Loop 节点内部有自己的执行语义。这样不会破坏整个调度器的可控性。

## 收尾句

所以这个引擎我最看重的不是“画布能连线”，而是工作流定义能被构图、校验、排序和执行。当前最能保真展开的是环检测、条件分支子树排除和 `ExecutionContext` 变量隔离；失败恢复和副作用幂等属于后续扩展。
