# 简历回答逐字稿：低代码工作流引擎 DAG 架构设计

关联：[[简历追问：低代码工作流引擎 DAG 架构设计]]、[[15分钟：低代码平台]]。

## 30 秒开场

这个项目要把 React Flow 画布定义稳定地转成可执行流程。我用 `WorkflowDefinition`、Node 和 Edge 统一协议，运行前验证节点、边和配置，再由 GraphBuilder 完成环检测、拓扑顺序和条件分支剪枝。节点输出进入 ExecutionContext，下游通过 `${nodeId.variableName}` 读取结果。

## 如果面试官问：图结构怎样校验和执行？

运行前，工作流验证器会检查 Start 和 End 是否存在、节点类型是否已注册、节点配置是否有效，以及边引用的源节点和目标节点是否存在。

通过后再构建图。实现里邻接表用于查找下游，反向邻接表用于查找上游，入度表用于 Kahn 拓扑排序。普通工作流主图不允许环，所以运行前还会做环检测；只有合法 DAG 才进入执行阶段。

Kahn 算法会先把入度为 0 的节点加入队列。节点进入结果序列后，依次减少后继节点的入度；后继入度变为 0 时再进入队列。Kahn 是标准算法。我的工作是把校验、构图、动态分支和执行器调度完整组合起来。

## 如果面试官追：条件分支怎么处理？

Condition 节点通过 `sourceHandle` 返回命中的分支。GraphBuilder 会把其他分支的目标加入排除集合，并递归处理下游。

关键点是不能无条件删除整个子树。两个分支可能在后面汇合到公共节点，所以递归前要检查该节点是否还有其他未排除的前驱。只要仍有活跃入边，它就应该保留；只有没有其他活跃入边时才继续排除。命中分支后重新计算执行顺序，使未选路径不会执行，也不会让公共下游被误删。

## 如果面试官追：上下文和变量怎样传递？

每次工作流执行都会创建独立 ExecutionContext，按 nodeId 保存节点输出与完成状态。节点执行前，VariableResolver 递归扫描配置中的字符串、数组和对象，解析 `${nodeId.variableName}` 并读取上游输出。

这样节点之间不共享一块没有边界的全局对象，编辑器保存的变量协议也能被执行器直接消费。找不到变量时保留原表达式 `${nodeId.variableName}`，而不是静默替换成空值，防止脏数据扩散并便于排障定位。

## 如果面试官追：多个入度为 0 的节点是否并行？

从 DAG 语义上看，同一轮入度为 0 的节点具备并行执行条件；在单端执行器中优先保证确定性拓扑串行执行，并发池化调度与多租户限流可作为分布式演进方案继续拓展。

## 如果面试官追：失败重试和幂等怎么设计？

当前引擎重点实现了统一错误捕获、耗时统计与执行日志。在架构演进方向上，对于带副作用的外部请求节点，可引入 executionId、attempt 计数与幂等键，进一步支持跨进程断点续跑。

## 如果面试官追：支持 Loop 怎么办？

第一版保持主图是严格的 DAG，因为它更容易校验、解释和测试。在未来支持复杂循环时，更健壮的做法是将 Loop 设计为带明确退出条件和上限计数的局部子图容器，主图依然保持 DAG 约束，防止任意连环导致死锁。

## 如果面试官追：前端埋点怎样与执行日志关联？

下游验收需要知道用户是在工作流校验、测试运行还是发布环节失败，因此我在 AI Flow 中接入监控 SDK，为这些关键路径添加自定义事件。节点是否真正执行成功、耗时多久、在哪一步报错，仍由执行引擎日志记录；两侧通过同一个 `executionId` 关联。

这样浏览器 SDK 负责用户操作路径与关键结果，执行引擎负责节点级事实，两侧通过共同的 `executionId` 形成完整的执行追溯闭环。

## 收尾句

这个引擎把可视化定义继续落实到了节点与边校验、图构建、拓扑调度、条件分支剪枝和 ExecutionContext 数据传递，并通过 `executionId` 把前端验收路径与节点执行证据连接起来，为后续工程化演进提供了高确定性的底层契约。
