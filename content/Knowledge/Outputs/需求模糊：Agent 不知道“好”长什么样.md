> [!info] Agent 交付的七个坏味道 · 01
> 这一组文章来自我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT）：它把业务建模、API 设计、任务计划和实现串成一条可核验的交付链路。每篇讲一个坏味道，以及仓库里对应的机制。

把一句话交给编码 Agent，它一定会给你一个能跑的系统——只是那个系统是它理解的版本。

写“做一个专栏订阅系统”，它会顺手补齐自己理解的合同、支付与访问控制；写“实现移动支付”，它会自行决定金额、期限和失败语义。这些决定没有一个来自你，但它们会变成代码、测试，和一句“已完成”。

## 这个坏味道长什么样

需求模糊不是需求写得短，而是把需要大量上下文的系统意图压缩成一句话交出去。它会在三个层次上同时出现：

| 层次     | 具体表现                                                       |
| -------- | -------------------------------------------------------------- |
| 业务事实 | 参与方、权责、事件、规则本身没写清楚                           |
| 软件职责 | 哪些活动由软件执行、哪些只是人工辅助、哪些只是系统背景，没分过 |
| 实施结果 | 验收条件和边界情况没落进文件，只在人脑子里                     |

三个诊断信号，严重程度依次上升：

1. Agent 反问“这里我应该怎么做”——还算好的情况，它至少知道自己不知道；
2. 交付“看起来对、用起来不对”——它补齐了一套自洽但从未被授权的语义；
3. 验收时反复出现“我不是这个意思”——通常还伴随优先级丧失：口头修正对 Agent 权重相同，它分不清核心约束、锦上添花和随口一说。

第三个信号最贵。因为每一次纠正都没有地方沉淀成下一轮的约束，同一类错误会在下一个任务里重新出现一次。

## 解法：用三层文件把“猜”降下来

落点顺序是：**先列约束，再列验收，最后从约束里拆出边界情况**。

### 第一层：约束写在入口，但入口不装细节

[AGENTS.md](https://github.com/JayClock/Evidence-Framework/blob/main/AGENTS.md) 共 39 行，只有四段：行动入口、不变量、流程与状态、验证底线。六条不变量写的是不可协商的边界，其中一条直接规定了事实源：

> 业务事实来自 `.evidence/fm/`，API 设计来自 `.evidence/api/api.yaml`；软件范围、实现设计和当前代码行为分别记录，不能相互冒充。生成产物不是新的事实源。

入口只声明边界和停止纪律，不写操作手册。具体要读什么，由 Guides 导航的两张表下发：[来源与冲突处理表](https://github.com/JayClock/Evidence-Framework/blob/main/docs/guides/index.md)为每类问题指定唯一权威位置，并列出“不可替代它的内容”；阅读路由表按任务类型列出必要前馈。约束既具体，又不会在一个文件里堆成需要 Agent 自己判断优先级的清单。

本次授权范围同样被写成约束。[软件范围](https://github.com/JayClock/Evidence-Framework/blob/main/docs/requirements/scope.md)写死当前切片是绩效协议主链：登记绩效协议 → 提出带周期与三项目标（联系总数、电话数、邮件数）的月度请求 → 登记客户联系记录 → 按规则判断月度目标是否完成；并逐条列出非目标：前端页面、生产身份与权限、生产数据库、协议参与方核验与 403、未达标后果、周度进度检查、客户档案生命周期。

“这次不做”写得和“这次做什么”一样具体，Agent 才不会顺手替你补一个 JWT。

### 第二层：验收数据要具体到可以比较

故事与验收使用稳定 ID、Given/When/Then、具体输入与可观察结果。几条真实例子：

- `AC-004-02`：缺少 `agreement_id` 或 `signed_at` → 按 API 契约拒绝（422）且不写入；
- `AC-005-03`：父协议不存在返回 404；相同 `request_id` 已存在返回 409；`evidenceRefs` 为空返回 400；
- `AC-006-05`：`confirmed_at` 恰为 `expired_at`、或位于请求区间之外时，记录仍可形成；是否计入由完成规则判断，**登记不预判完成**。

第三条特别值钱。它把“登记一次联系”和“本月目标是否完成”拆成了两件事——否则 Agent 很容易把一次登记当成本月达标。

任务级再把验收固定成机器可判定的形式：每条验收条件必须引用本任务的 CHECK，并以 `path / operator / expected` 保存保留类型的期望值；命令还不知道就填 `null` 并关联缺口，不允许用“运行相关测试”充当可执行。执行后的真实结果写进 `observedEvidence`，而不是停在口头声称。

### 第三层：边界情况集中单列

正常流程之外的判断不混进主流程，而是集中登记：

- **缺口**：可信身份与实例归属（`GAP-IDENTITY`）、生产数据库选型（`GAP-DATABASE`）、凭证引用寻址（`GAP-EVIDENCE-REFS`）——每条都写明它只阻塞哪些任务；
- **转向**：只读、获授权实施、源业务未知、任务局部设计不足、环境不可用、代码问题六类，每类给出终止与交回规则；
- **质量属性**：`QA-IDENTITY`、`QA-DATABASE`、`QA-AUDIT`、`QA-I18N` 等待决项显式列出，并写明“没有依据的性能、留存、权限或部署指标不填常见默认值”。

边界情况一旦写成字段，就能被机器核对：结构校验要求 `blocked` 的任务必须关联已知缺口，空命令必须关联缺口。缺口只阻塞受影响任务，不通过扩范围或改上游制造通过。

## 用澄清代替猜测

约束写得再全，也会有写不到的地方。剩下的部分用澄清补，而不是让 Agent 自由发挥：

- 问答工具**每次只问一个业务问题**，保存回答或控制状态后再继续，避免一次抛出过多问题导致优先级丧失；
- 发现记录保存用户原话、问题状态、解决依据与下游影响，作为后续判断的凭证；
- 建模区分讨论、编辑、只读验证三种模式——**编辑授权不等于业务审核**；模型文件本身不保存审核状态。

## 开工前先问六个问题

进入实施前逐项核对：授权与目标、来源、前置与新鲜度、设计、做法与环境、验证与退出。最后一项直接问：每条验收条件是否引用了本任务 CHECK，并包含可比较的具体期望值与适用反例？失败后应该局部修复、重规划，还是回去澄清？

检查通过只表示本次行动的**依据就绪**，不表示实现或业务获批。结构通过只说明计划自洽，语义是否就绪仍要人来判断。

## 收束

需求模糊真正的代价不是返工。返工是看得见的。真正的代价是 Agent 用你没有授权的假设填满了空白，并且把它们写成了测试——于是你说不清到底是需求没写清，还是系统本来就该这样。
