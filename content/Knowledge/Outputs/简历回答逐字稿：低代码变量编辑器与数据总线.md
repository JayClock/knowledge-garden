# 简历回答逐字稿：低代码变量编辑器与数据总线

关联：[[简历追问：低代码变量编辑器与数据总线]]、[[项目介绍：企业级低代码工作流引擎]]。

## 30 秒开场

变量编辑器解决工作流里的跨节点参数传递。我用 Tiptap 把 `${nodeId.variableName}` 显示成不可拆分标签，用户通过 `/` 菜单选择上游输出。保存时还原为纯文本协议，运行时再由 `VariableResolver` 从 `ExecutionContext` 取值，让编辑器和执行引擎消费同一份协议。

## 如果面试官问：为什么不用普通 textarea？

textarea 做起来快，但它只能存字符串，无法保证变量引用的结构稳定。

比如用户引用上游节点 A 的 `customerId`。Tiptap 中显示节点名称和变量名，保存时仍落成稳定的 `${nodeId.variableName}`。节点展示名可以变化，但执行协议依赖的是 nodeId，而不是展示文字。

另外，原子节点可以控制用户不能把变量删一半、改一半，这对低代码配置很重要。否则表面看是公式，实际运行时已经变成不可解析字符串。

## 如果面试官追：原子化胶囊怎么防止被破坏？

主要通过 ProseMirror NodeSpec 和交互拦截保证原子性。

项目通过自定义 `variableMention` 原子节点避免变量被拆开编辑。用户选择变量后插入完整标签，保存时再序列化为 `${nodeId.variableName}`。

## 如果面试官追：`${}` 和 `/` 菜单怎么实现？

输入 `/` 时触发 Tiptap Suggestion，展示上游节点可用的变量。用户选择后插入 `variableMention`，编辑器负责高亮显示；保存与回显时在 Tiptap 节点和 `${nodeId.variableName}` 纯文本之间转换。

## 如果面试官追：为什么不用 `eval`？

这个项目聚焦于 `${nodeId.variableName}` 变量引用协议。运行时由 `VariableResolver` 解析并从受控的 `ExecutionContext` 取值，不需要执行任意 JavaScript，因此也不使用 `eval` 或 `new Function`。对于更复杂的表达式计算，可进一步引入 AST 语法树与受控沙箱求值，在保证安全的前提下扩展计算能力。

## 如果面试官追：跨节点数据总线怎么保证不串？

每次流程执行都有一个 ExecutionContext，按 `nodeId` 隔离存储节点输出：

```ts
context.outputs[nodeId] = {
  status: 'SUCCESS',
  data: {...}
}
```

下游节点执行前，变量解析器读取配置中的 `${nodeId.variableName}`，按 nodeId 和变量名从 context 取值。每个节点输出存放在自己的 nodeId 下，避免不同节点的结果相互覆盖。

找不到变量时不会解析成空字符串，而是保留 `${nodeId.variableName}` 原文。这样不会把无效引用伪装成正常空值，也便于在执行反馈中识别原始引用。

## 如果面试官追：异步函数怎么办？

当前变量协议只读取已经进入 `ExecutionContext` 的上游输出。如果未来扩展异步计算，需要单独设计批处理缓存与超时熔断机制，进一步提升异步求值吞吐。

## 收尾句

这块让 Tiptap 负责可视化引用，让纯文本协议负责存储与传输，再由 `VariableResolver + ExecutionContext` 完成运行时取值，避免用户直接手写易错字符串，形成了稳定健壮的跨节点数据流动闭环。
