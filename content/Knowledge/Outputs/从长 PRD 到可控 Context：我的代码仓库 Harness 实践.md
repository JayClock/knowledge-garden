# 从长 PRD 到可控 Context：我的代码仓库 Harness 实践

很多团队构建 Harness 时，会先把 PRD、历史记录、知识库和测试报告保存下来，再尽可能完整地交给大模型。信息似乎越全越好，窗口不够就换成长 Context 或更强的模型。但这种做法把一个本应由人完成的问题留给了模型：哪些信息与当前工作真正相关？

我对这件事的理解来自[[边界判断缺位的资源代价|边界判断与资源消费之间的关系]]。微服务真正重要的是围绕业务能力划定边界，而不是把服务拆得越小越好；Context Engineering 也一样，真正重要的是让模型看到当前工作所需的信息，而不是把窗口填得越满越好。没有在设计阶段消化的复杂度，最终会变成基础设施或模型调用的持续成本。

## 记录信息只是起点

我在公司项目的代码仓库 Harness 中遇到的第一个问题，是 PRD 很长。直接把完整 PRD 交给模型，虽然省去了前置整理，但模型需要在每次执行中重新寻找角色、业务规则、工作范围和验收边界。相同信息会反复占用 Context，模型也可能在大量细节中选择不同重点。

我的处理方式不是删除原始 PRD，而是在 Harness 外层双层循环的 Plan 阶段，先由人完成建模与抽象。具体来说，就是把长 PRD 转换为经过审核的业务模型，再用测试工序形成当前迭代的任务清单。业务模型保存这项工作为什么成立，任务清单规定当前要完成什么以及怎样验证。

这与[[如何用履约建模法给 AI 准备业务上下文]]解决的是同一个前馈问题：原始材料可以保留，但进入 Agent 工作区的应该是已经澄清的业务语义。[[架构与任务分解]]进一步把业务场景映射成可执行边界，避免任务只剩下一组脱离业务目的的技术动作。

## 人在 Plan 阶段控制相关性

这里的“人工筛选”不是要求人每轮逐条挑选文件。人的工作集中在价值更高的 Plan 阶段：审核业务模型是否准确、任务清单是否覆盖当前场景、边界是否合理。完成这些判断后，Harness 再把结果作为前馈控制写入指令系统。

于是，模型执行任务时消费的主要内容不再是完整 PRD，而是两类已经过人确认的信息：

- 业务模型：保留角色、行为、规则和验收边界；
- 任务清单：依据[[测试工序的核心思想和实践要点|测试工序]]限定当前实现与验证范围。

这一步把人的一次判断变成了可以重复执行的 Guides。模型仍然负责理解、生成和调整，但不需要每次从全部材料中重新猜测当前重点。

## 反馈也需要控制信息密度

只控制输入还不够。代码执行之后，测试会产生报告；报告同样可能很长。如果把完整报告原样塞回 Context，反馈循环很快又会变成信息堆积。

在反馈侧，我把测试作为 Sensors。当测试报告过长时，可以直接让模型生成一个提取脚本，再由脚本确定性地处理报告，只保留下一轮修正需要的问题定位段落。模型随后消费的是定位结果，而不是重新阅读整份测试历史。

这里需要区分两件事：模型可以帮助生成脚本，但脚本运行属于计算型控制；模型负责理解定位结果并提出修正，则属于推断型工作。把重复、确定的信息处理留给脚本，既减少 Context，也避免模型每次用不同方式概括同一份报告。

整个循环可以简化为：

```text
外层 Plan：人审核业务模型与任务清单
       ↓
Guides：Harness 注入当前任务需要的业务与实现上下文
       ↓
Action：模型在受控边界内完成实现
       ↓
Sensors：测试产生确定性证据
       ↓
反馈压缩：脚本将长报告转成问题定位段落
       ↓
Steer：模型根据定位结果修正
```

## 从 Context 控制走向完整双层循环

公司项目中的实践主要解决“当前任务应该给 Agent 什么 Context”。我随后在 Evidence 中进一步把项目外层循环、Agent 内层循环和两者之间的状态接口做成了显式的产品能力。这版实现位于私有仓库、现已弃用；2026-09 我把同一方案重写为公开仓库 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)，把机制收敛到单一机器计划与可核验的检查记录上。

Evidence 的外层不是让 Agent 自行规划整个项目，而是由 Server 保存权威状态，并通过不可变 Revision、内容哈希和人工决定推进交付：

```text
Inbox Revision
→ Frozen Intake
→ 人工 Kickoff
→ Story Revision 与 Scenario
→ 人工 Desk Check 批准 Tasking Plan
→ Pair
→ Showcase
→ Respond
```

Agent 可以提出 Candidate、Scenario、Tasking 和 Respond Proposal，但 Proposal 本身没有权威。只有人类完成对应 Gate，候选内容才会成为下一阶段的稳定输入。Server 根据当前权威事实发布唯一 `nextAction`，Web 和 Desktop 只消费它，不在客户端复制另一套流程判断。

Pair 是具体任务的内层操控循环：

```text
Guides：Approved Tasking Plan、Story Revision、Scenario、锁定命令与质量门
→ Action：短生命周期 Test／Production／Refactor Driver 修改隔离 worktree
→ Sensors：Red／Green 命令、独立 Red Reviewer、质量门、diff 与 worktree hash
→ Steer：继续下一 TEST、局部修复、返回 Tasking，或暂停等待人工决定
```

这里的 Red 不能只是“命令失败”。独立 Reviewer 要确认失败来自预期业务行为尚未实现；编译、依赖、配置、网络、fixture 和 timeout 问题属于 Pseudo Red，不能用来跳过测试工序。Controller 只执行批准计划中已经物化并校验的命令，Driver 不能自行执行命令、提交、合并或推送。

反馈也不会统一退回给一个无边界的 Agent。系统按失败所在的知识层级开放不同路由：

| 反馈                            | 调整位置                           |
| ------------------------------- | ---------------------------------- |
| Unexpected Green／Pseudo Red    | 返回测试设计                       |
| Green／Refactor 失败            | 返回实现                           |
| 质量门失败                      | 重试质量门、修复实现或返回 Tasking |
| 路径越界、Git HEAD 或证据不一致 | 返回 Tasking 或停止                |
| Story／Scenario／模型理解错误   | 返回 Kickoff、TQA 或 Modeling      |
| 价值验证不足                    | 创建新的 Showcase Attempt          |

编码通过也不是外层循环的终点。Showcase 会在批准的 commit 上重新执行 Q2，由人记录产品可见结果和 Q3／Q4 风险，再交给独立只读 Reviewer。只有人类确认实现产生了正确价值，Respond 才会提出知识响应和下一项 Probe。这样，内层产生的测试与实现证据能够返回外层，外层又能判断应该局部修复，还是重新打开任务、场景或业务模型。

## Harness 是上下文控制系统

这套实践带来的改善目前是定性的：模型输出更稳定，同时减少了反复输入完整 PRD 和测试报告造成的 Token 消耗。我没有可核验的节省比例，因此不会把它描述成精确的效率指标。

更重要的变化是责任边界变清楚了。人负责理解业务、划定工作范围并审核任务；Harness 负责保存并执行这些选择；测试和脚本负责提供可重复的反馈；模型在这个边界内发挥语义理解和生成能力。

所以，[[大代码库里如何管理上下文|上下文管理的目标不是更多 Token，而是更准确的 Context]]。记录知识和记忆只是 Harness 的基础能力，真正决定结果的是：谁来判断相关性，这个判断在什么时候发生，以及它怎样被写成可重复的前馈与反馈控制。
