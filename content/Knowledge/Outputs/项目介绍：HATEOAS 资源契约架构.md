# 项目介绍：HATEOAS 资源契约架构

> [!tip] 使用方式
> 默认先说 2 分钟版。面试官继续追问时，再从 5 分钟主讲法或文末具体回答中选择一条展开；不要连续背满 15 分钟。

## 提取词

多端状态漂移 ｜ 超媒体动作契约 ｜ 四色建模倒逼资源设计 ｜ TS SDK 状态工厂与 Standard Schema ｜ 渐进试点与开源交付

## 30 秒开场

这个项目解决多端业务规则重复维护与漂移的问题。低代码平台同时服务 PC Web 与移动端，过去两端各自维护状态与权限判断。我推动引入 HATEOAS，把“当前资源能访问什么、能执行什么动作”收敛为服务端的超媒体契约，设计并实现了 TypeScript SDK 与 React Hooks 统一消费，并将通用消费层独立开源，沉淀了 233 项自动化测试。

## 2 分钟项目介绍

低代码平台里的应用、表单、工作流和工作区导航同时服务 PC Web 与移动 Web。过去后端返回 status，各端再根据角色和权限判断按钮、导航和提交字段。规则一变，几个端都要修改，很容易出现一边有动作、另一边没有的情况。

我先推动 HATEOAS 资源动作契约。服务端在资源里返回 _links 和 _templates：relation 表达当前可以导航到哪里或执行什么动作，template 描述提交方式和字段约束。前端只消费 publish、revoke 这类业务 relation，不再复制一份状态机。

为了让几个端稳定使用这套契约，我设计并实现了 TypeScript SDK。Client 管理入口和中间件，Resource 表示 URI 级资源，follow() 沿 relation 导航，action() 按 HAL-FORMS 模板提交；资源缓存和更新事件再驱动 React Hooks。稳定 relation 在 TypeScript 中建模，运行时数据仍通过 Standard Schema 和 Zod 校验。

SDK 落地后也暴露出上游问题：如果资源边界和动作语义本身混乱，SDK 只能统一调用方式。所以我继续从应用、表单和工作流的生命周期出发参与四色建模、RESTful URI 和动作契约设计，再与后端协同完成 API 表达层落地。

## 5 分钟主讲法

### 1. 架构起点：多端规则漂移与超媒体契约选型

低代码平台同时服务 PC Web 与移动端。过去后端返回简单 `status`，各端再根据角色与权限字典判断按钮、导航与提交字段。

这带来的核心痛点是**多端规则漂移**：后端状态或权限一变，两端必须同时修改回归，联调时极易出现一端能点、另一端漏改的不一致。在前端封装 API Service 只能规整代码，解决不了“业务合法性在客户端被重复解释”的根本缺陷。

我推动引入 HATEOAS 超媒体契约：服务端在资源中直接下发 `_links` 与 `_templates`。`_links` 表达导航与动作入口，`_templates` 声明 HTTP Method 与字段约束。前端不再维护状态组合，而是声明式消费当前资源是否下发了 `publish` 或 `approve` 这个 relation。业务合法性的事实源收敛回服务端，前端专注交互呈现。

### 2. 核心难点一：从消费痛点倒逼上游领域模型与 RESTful 设计

真正落地超媒体契约时，阻力往往在服务端原有数据模型。如果资源划分不清、生命周期混乱，`_links` 就会退化成单纯给前端渲染按钮的字符串数组，失去契约价值。

我从应用、表单和工作流的生命周期出发，主动参与上游领域建模。我们采用四色建模法梳理时标性对象、参与方、角色与描述对象，理清聚合根与资源边界。

在接口设计上统一 RESTful URI 规范，将操作收敛为标准资源的生命周期流转。例如不设计形如 `/api/publishWorkflow` 这类 RPC 接口，而是建模为发布版本资源的创建或状态迁移，并自然派生出 `publish` relation。服务端 API 表达由我和后端协同落地，前后端在同一份业务语义契约下协作。

### 3. 核心难点二：TypeScript SDK 消费层抽象与类型安全设计

为让多端稳定消费契约，我设计并实现了 TypeScript SDK。它不是 Axios 的二次封装，而是完整的资源状态消费层：

在资源管理上，`Client` 统一收拢入口与拦截器，`Resource` 基于绝对 URI 实现实例缓存与复用；`StateFactory` 将 HAL 与 HAL-FORMS 解析为统一资源状态。业务层通过 `follow()` 声明式导航，通过 `action()` 结合模板提交表单，彻底摆脱硬编码拼 URL。

在类型安全与运行时校验上，我做了一层取舍：稳定 relation 在 TypeScript 中建模为字面量联合类型，提供 IDE 自动补全；但由于服务端是否下发该 relation 是运行时事实，SDK 强制提供 `hasLink()` 防御判断，并接入 Standard Schema 与 Zod 校验 payload。UI 层进一步封装 React Hooks，组件只需订阅资源状态。

### 4. 渐进试点、工程交付与开源沉淀

落地采取渐进式推进策略：先以低风险的工作区全局导航和页面路由为试点切入，验证端到端契约流转；随后逐步扩展到表单与工作流核心链路，过渡期保留传统 RESTful 兼容降级通道。契约统一后，业务调整时前端不再需要维护状态机，测试回归也从每个端逐一验证按钮显隐，收敛为契约矩阵与消费层测试。

为了沉淀长期工程资产，我将通用消费模型独立抽象并开源为两个 npm 包（`@hateoas-ts/resource` 与 `@hateoas-ts/resource-react`），沉淀了 34 个测试套件、233 项自动化测试与完备的类型定义，持续保持独立维护。

## 渐进式架构视角

这个项目先稳定资源、URI、状态和生命周期，再用 relation 与 action 声明不同客户端可以按需消费的能力。SDK 统一运行时检查和提交方式，工作区导航试点与 BFF 退路则让迁移逐步平滑发生。这套架构既满足了现有 PC 与移动多端的高效消费，也为未来新客户端接入提供了标准契约。

## 收尾句

这段经历让我从前端多端一致性出发，先建立契约消费层，再继续追到上游业务模型与接口契约。HATEOAS 让多个客户端消费同一份“当前资源能做什么”的运行时事实，少写 URL 只是随之带来的结果。
