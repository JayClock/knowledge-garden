# 简历追问：多人实时协同的 AI 辅助领域建模平台

关联：[[职业经历]]、[[全栈工程师简历]]、[[简历回答逐字稿：多人实时协同的 AI 辅助领域建模平台]]、[[10｜将模型实现为RESTful API（上）-如何落地业务建模-极客时间]]、[[11｜将模型实现为RESTful API（下）-如何落地业务建模-极客时间]]、[[如何设计和实现一个支持实时协作的协同文档编辑器？设计过程中需要考虑哪些关键技术点？]]。

## 对应简历描述

> 为业务、产品和研发持续使用的建模平台设计并实现多人实时协同链路，基于 Yjs、WebSocket 和 PostgreSQL 完成增量同步、协作状态与持久化；使用 8X Flow 建立可审计的采购履约模型，由 AI 基于发布模型生成 OpenAPI 草稿和测试数据，OpenAPI 经人工审核后用于下游代码生成。

## 面试官真正想确认

你是否真正处理过多人协同中的状态来源、更新回环和持久化，还是只接入了一个 Yjs 示例；同时确认是否真正使用 8X Flow 建模履约审计、模型如何进入 OpenAPI 和测试数据，以及 AI 生成与人工审核的边界。

## 连续追问链

### 1. 业务与个人范围

- 这个项目怎样承接你从多端一致性、HATEOAS 契约到业务建模与 RESTful API 的能力演进？
- 为什么把模型做成协同产品，不代表职业方向转向纯后端？
- 建模平台中的核心对象是什么？哪些状态需要多人实时共享？
- 为什么普通的整图保存不能满足协同编辑？
- 前端绑定、Awareness、协同服务和持久化分别由谁实现？
- 公司内部项目与公开 `team-ai` 仓库是什么关系？

### 2. CRDT、状态来源与更新回环

- 建模节点、关系、属性和视口分别如何进入 Y.Doc？
- React Flow → Yjs → observer → React effect 的更新回环是怎样形成的？
- 为什么 debounce 不能从根本上解决这个问题？
- `transaction.origin`、单向增量写入和值比较分别承担什么职责？
- 为什么 Yjs 可以作为共享状态源，而 React Flow 只保留界面投影？
- CRDT 的“最终一致”与领域模型的“语义正确”有什么区别？

### 3. Awareness 与连接生命周期

- 在线成员、远端光标和选区为什么使用 Awareness，而不是写入持久数据？
- 客户端加载、卸载和断线重连时如何管理 WebsocketProvider？
- 服务端如何检测失效连接并清理 Awareness 状态？
- 同一用户打开多个页面或设备时，身份和光标如何区分？

### 4. 协同服务与隔离

- NestJS 为什么切换到原生 WebSocket 适配器？
- `messageSync` 与 `messageAwareness` 的职责如何区分？
- 服务端如何按建模空间隔离 Y.Doc 和广播范围？
- 为什么把常规业务服务与实时协同服务分开？

### 5. 持久化与恢复

- 为什么没有直接使用 y-websocket 默认的 LevelDB？
- PostgreSQL 适配层保存的是完整快照还是增量更新？
- 服务重启后如何恢复 Y.Doc？
- 长期更新积累后的压缩、清理和版本边界如何处理？

### 6. AI 变更边界

- AI Proposal 的操作类型和 Schema 是什么？
- SSE 输出不完整或 JSON 不严格时如何处理？
- 用户如何定位、预览、采纳和拒绝单项变更？
- 为什么 AI Proposal 不能直接写入已发布模型？

### 7. 模型生命周期

- 草稿、版本快照、发布模型和知识图谱分别承担什么职责？
- 多人协同状态在什么时候形成可发布版本？
- 发布后继续编辑时如何避免影响旧版本？
- 知识图谱由哪些节点和关系生成？

### 8. 8X Flow 与模型驱动交付

- 为什么库销存 Agent 在分析滞留原因前，需要先建立可审计的履约事实？
- 采购合同、参与方、履约角色、请求、确认和 Evidence 怎样构成追溯链？
- 业务履约审计与库存分析领域逻辑为什么需要分开？
- 为什么客户提出的“滞留货物降低至 20%”不能写成项目结果？
- 如何根据聚合边界生成 URI，再组合角色、HTTP Method 与业务场景得到 API 候选？
- HAL relation 怎样表达采购合同与履约资源之间的关系？
- 为什么还要把 API 映射回履约流程验证完整性？
- AI 生成的 OpenAPI 为什么只能作为草稿？人工审核后怎样进入下游代码生成？
- AI 根据模型生成了哪些正常和异常履约测试数据？

### 9. 验证、应用与边界

- 如何用两个浏览器窗口验证节点增删改、远端同步和事务回环？
- 为什么同时记录 `transaction.origin`、Yjs 写入次数和 React Flow 更新次数？
- 哪些验证已经手工完成，哪些自动化 E2E、断线重连和服务重启恢复仍未完成？
- 业务、产品和研发如何共同使用模型？
- 哪些采购业务细节能够确认，哪些对象名和规则只是通用重构？
- 当前能证明哪些功能，哪些使用规模和性能指标仍缺数据？

## 场景推演题

> 用户 A 在 React Flow 中修改节点后，更新写入 Yjs；Yjs observer 随后调用 `setNodes`，监听 React 状态的 effect 又把整张图写回 Yjs。请说明怎样通过链路日志确认回环、怎样设计事务来源、哪些更新应该进入 observer，以及如何验证修复没有造成远端更新丢失。

继续追：为什么这种问题不能只加 debounce？即使两个客户端最终显示同一结果，怎样判断模型在领域语义上仍然正确？

## 准备证据

- 两个浏览器窗口验证节点增删改、远端同步和事务回环的录屏或操作记录。
- `onNodesChange`、`onEdgesChange`、Yjs 写入入口和 `Y.Map.observe` 的链路日志。
- `transaction.origin`、Yjs 写入次数和 React Flow 状态更新次数记录。
- Y.Doc 共享数据结构、WebsocketProvider 初始化及 `unobserve` 生命周期代码。
- `messageSync`、`messageAwareness`、连接清理和 PostgreSQL 持久化适配层代码；不把尚未完成的恢复测试列为现有证据。
- AI Proposal Schema、逐项采纳/拒绝界面和异常输出样例。
- 库销存 Agent 中使用 8X Flow 建立采购履约审计模型的可脱敏材料；如果无法恢复，只按通用场景讲方法。
- AI 生成的 OpenAPI 草稿、人工审核记录及审核后的 OpenAPI；没有材料时不补编具体审核项。
- AI 根据模型生成的正常／异常履约测试数据。
- `team-ai` 中建模、版本、发布和知识图谱相关实现。

## 容易露馅的回答

- “用了 Yjs，所以天然没有冲突。”
- “多人协同就是 WebSocket 广播整张图。”
- “Awareness 和模型内容一起存数据库。”
- “AI 生成后直接覆盖模型，失败再撤销。”
- “平台可以从模型确定性生成 OpenAPI，并直接生成完整业务系统。”
- “客户滞留货物已经降低至 20%”，但这个数字只是客户场景目标示例。
- 把通用采购合同对象和异常规则说成还能准确回忆的客户生产模型。
- “GitHub 仓库就是公司项目源码。”
- “已经完成自动化协同 E2E 和服务重启恢复测试”，但实际只有双浏览器手工联调。
- “支持高并发”，但说不出统计口径和验证方式。
