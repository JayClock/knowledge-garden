# 简历追问：监控 SaaS 大盘与 ClickHouse 可视化

关联：[[15分钟：前端埋点与监控 SDK]]、[[简历回答逐字稿：监控 SaaS 大盘与 ClickHouse 可视化]]。

> [!warning] 使用边界
>
> - 这份材料用于理解 SDK 数据进入下游后的协作链路，不是个人简历成果。
> - 本人负责 SDK、统一事件协议和上报；NestJS、Kafka、ClickHouse、查询后端与控制台由其他同事实现。
> - 不使用“我搭建大盘”“我设计 ClickHouse 表”或真实查询性能、数据量和业务收益等未经确认表述。
> - 已确认 AI Flow 中的校验、测试运行和发布事件通过监控 SDK 采集，并以 `executionId` 关联执行日志；具体下游使用方式暂不记录。

## 面试官真正想确认

面试官可能借数据平台追问 SDK 事件协议是否从下游判断需求倒推、是否足以支持验收和查询，也会检查你能否说明完整链路而不抢占其他同事的实现成果。

## 连续追问链

### 1. SDK 与下游协议

- SDK 为什么需要稳定的 `app_id`、版本、路由、会话和事件类型？
- 性能、异常、请求和操作事件怎样区分？
- 哪些字段由 SDK 产生，哪些字段由数据服务补充？
- 协议变更怎样避免采集端和查询端口径漂移？

### 2. AI Flow 的业务事件与执行证据

- 为什么验收需要区分工作流校验、测试运行和发布环节？
- 哪些事件由监控 SDK 记录，哪些节点事实由执行引擎日志记录？
- `executionId` 怎样连接前端路径和节点状态、耗时、错误？
- 为什么浏览器埋点不能替代服务端事实源？
- 当前为什么不能补写具体下游使用方式和改善结果？

### 3. 指标口径

- LCP p75 和接口耗时 p95 为什么需要稳定的指标名、数值、版本与路由？
- “错误率”的分母是请求、会话还是页面访问？
- Abort、采样、重复错误和 SPA 路由怎样定义？
- 哪些口径由你共同确认，哪些控制台实现不属于个人工作？

### 4. ClickHouse 技术理解

- 为什么监控事件适合按时间和常用查询维度组织？
- 分区、排序、预聚合和缓存分别解决什么问题？
- 这些设计中哪些有实际项目证据，哪些只是通用讨论？
- 查询性能和表结构为什么必须由数据平台负责人确认？

### 5. 权限与可视化边界

- SDK 上报 tenant 或 app 上下文后，为什么仍不能由前端决定查询权限？
- 大盘出现数据缺失、采样或口径变化时，应该怎样向使用者说明？
- 你能解释哪些端到端链路，又不能把哪些代码说成个人实现？

## 场景推演题

> 下游需要判断 AI Flow 用户是在校验、测试运行还是发布环节失败。请说明 SDK 需要记录哪些业务事件，怎样通过 `executionId` 关联执行引擎日志，以及为什么实际查询和展示仍需由数据平台同事确认。

继续追：如果还需要按 app、version 和 route 查询 LCP p75，SDK 事件至少要提供哪些稳定字段？如果两个版本的“页面访问”口径不同，大盘为什么不能直接比较？

## 准备证据

- SDK 统一事件协议。
- 应用、版本、路由、会话和事件类型字段说明。
- AI Flow 校验、测试运行和发布自定义事件，以及 `executionId` 关联执行日志的说明。
- 与下游共同确认的指标口径；没有记录时不要补写。

## 容易露馅的回答

- 把控制台、ClickHouse 表和查询服务说成个人实现。
- 使用“海量数据”“实时大盘”“精准决策”等宣传语。
- 补写数据量、查询耗时或业务收益。
- 只会讲图表组件，无法解释 SDK 字段和指标口径。
- 把 AI Flow 浏览器埋点说成节点执行事实，或虚构下游使用结果。
