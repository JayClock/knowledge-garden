> 系列基于我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT）。上一篇：[[需求模糊：Agent 不知道“好”长什么样]]

需求写清楚了，Agent 仍然可能交出一套你不认识的东西。因为它遵守的是另一套规则——通用最佳实践，而不是你们团队的约定。

需求模糊时 Agent 会来问你；隐式约定时它不会。它根本不知道自己在违反规则。

## 这个坏味道长什么样

一个多模块后端里有大量没写下来的约定：模块之间的依赖方向、数据归属、事务入口、命名映射、业务边界。这些约定对老成员是“常识”，对新人是谜题，对 Agent 是空白。

空白会被填满。没人告诉它“业务规则不能写进 Resource”，它就会在 Resource 里写业务规则；没人告诉它“跨模块不能访问私有表”，它就会直连数据库；没人告诉它“不要引入 JWT/RBAC”，它就会顺手加一个认证方案——因为这是通用最佳实践。

两个侧面信号：

- 评审时反复出现“这里应该用我们约定的方式”；
- Agent 迟迟完不成任务，不是因为它慢，而是它在从头发明一套解决方案。

比需求模糊更难发现的是：它不会报错，也不会提问，只会产出看起来专业但需要全部返工的代码。

## 解法：把约定分层写下来，并规定冲突怎么裁决

约定只写下来还不够，还要回答“两条约定打架时听谁的”。这两件事一起做，规则才不靠篇幅和新旧竞争。

### 入口层：只写不变量

[AGENTS.md](https://github.com/JayClock/Evidence-Framework/blob/main/AGENTS.md) 承担项目宪法的角色，全部不变量加起来不到十条，例如：

- 保留 Nx、React/TypeScript、Spring Boot/Java；**改变基线需要明确授权及架构决定**；
- 领域行为归实体、Description、Context 接口暴露的角色对象和拥有者关联；**禁止通过 Service、Resource 或 Mapper 接管业务规则**；
- API 与持久化分别依赖领域；跨业务模块不得访问私有表和内部 Mapper。

注意这些不变量都是**结论式**的：它们不解释为什么，只声明边界。理由放在架构文档里，入口不装细节——入口越长，Agent 越容易把重要规则埋在中间。

### 冲突裁决：来源权威表

[Guides 导航](https://github.com/JayClock/Evidence-Framework/blob/main/docs/guides/index.md)为每类问题指定唯一权威位置，并列出“不可替代它的内容”。冲突时的规则是一句话：

> 先说明各自管辖范围及差异，停止受影响行动，交由相应拥有者确认；不能按读取先后、修改时间或“代码已经这样写了”裁决。

裁决顺序大致如下：

| 优先级       | 对应物                                      | 说明                                           |
| ------------ | ------------------------------------------- | ---------------------------------------------- |
| 不可协商     | `AGENTS.md` 不变量                          | 用户一句话不能覆盖；改基线要明确授权加架构决定 |
| 用户指令     | 当前任务的授权：mode、目标、允许改动范围    | 在宪法与来源约束内生效                         |
| 项目级约定   | `docs/engineering/*`、Guides 导航、架构基线 | 适用所有模块与会话                             |
| 模块级决定   | 架构三篇与任务 `design`                     | 记录拥有者、依赖、数据与事务边界               |
| 通用最佳实践 | Skill 通用方法与范例索引                    | 上下文冲突时让步                               |

最后一行是关键：通用实践不是被否定，而是被明确放在**最低优先级**。它的定位是“上下文没说话时的默认值”，不是“永远正确”。

### 模块层：把权衡写到能执行的位置

项目级的技术决定写在架构三篇里：技术决定表与依据、模块职责与允许依赖、概念到实现的映射以及“不允许的推导”（例如：Context 不自动建服务、角色名不等于认证、请求受理不等于到账）。

模块级的取舍则写在[任务计划](https://github.com/JayClock/Evidence-Framework/blob/main/docs/plans/smart-domain/plan.yaml)里，每个切片带 6 条 `designItems`，每个任务带一个 `design` 字段：

```text
behaviorOwner        行为拥有者
businessModule       业务模块、公开契约与允许依赖
dataOwnership        表、迁移和写入口的唯一拥有者
associations         关联访问方式
http                 Root／集合／实体子资源与表示
localTransaction     入口、参与者、事务管理器与回滚范围
externalIntegration  仅记录已确认的远程依赖
nonGoals             本次明确不做的事
```

这相当于**实例级的架构决策记录**：它不写在单独的 ADR 目录里，而是长在任务上，实施时必然被读到。项目当前的例子是：联系记录只引用客户信息上下文里的客户档案，不把它复制成绩效协议模块的 CRUD——这条约定如果只存在于人脑子里，Agent 大概率会给客户档案补一套增删改查。

### 拒绝用默认值填充空白

最容易被“顺手补上”的是安全与基础设施。项目用一张“需要依据的专题”表把这类未知显式化：`QA-IDENTITY`、`QA-DATABASE`、`QA-AUDIT`、`QA-I18N`、`QA-INTEGRATION`、`QA-SLO`，并写明没有依据的权限、留存或部署指标**不填常见默认值**。

一条“待决”比一条错误的约定便宜得多：待决只阻塞受影响的任务，错误的约定会变成一堆要拆掉的代码。

### 固定技术 profile 与上游版本

通用方法和技术基线也有唯一来源：任务规划 Skill 固定引用上游文档的具体 commit（不是 canary 分支）、核对日期与兼容范围，并把“模块化单体、无 Service 层、MyBatis XML 映射、Jersey 子资源”写成 profile。Agent 不需要发明方案：通用方法来自 skill 的 profile，项目取舍来自项目文件，两者都可追溯。

## 演进方向：什么时候才需要更重的机制

这套做法刻意没有上重的治理：

- 不单设决策记录目录——入口承担不变量，架构文档承担项目级决定，模块级取舍随切片与任务记录；**同一问题在两个模块出现不同答案时**，再建立独立目录并接入路由；
- 优先级靠“不变量 + 来源权威表 + 架构变更治理”表达，尚未逐条编号；出现裁决争议时再显式排序；
- 不变量多为结论式，未逐条附理由；架构、模块、工序文档已写明依据，需要时再补。

## 收束

写下来的约定才是约定，没写下来的只是某个人的习惯。Agent 不会继承习惯，它只会用自己的默认值填满你没写的那部分——而且填得非常自信。
