## 30 秒开场

这部分只讲监控 SDK 与数据平台的协作边界。我负责从后续验收和诊断需要的判断倒推事件与上下文，再按统一协议上报。AI Flow 中，我为工作流校验、测试运行和发布添加自定义事件，并通过 `executionId` 关联节点执行日志；NestJS、Kafka、ClickHouse、查询后端和控制台由其他同事负责。

## 如果面试官问：为什么 SDK 需要理解下游怎样消费？

如果只从浏览器能够采什么出发，容易得到大量无法支持判断的数据。AI Flow 的验收需要区分用户是在校验、测试运行还是发布环节失败，所以我为这些路径设计自定义事件；节点状态、耗时和错误仍由执行引擎日志记录，再通过 `executionId` 关联。

这能证明我理解 SDK 字段为什么存在，但不能据此声称由我设计了 ClickHouse 表、查询服务或大盘，也不能补写具体下游使用结果。

## 如果面试官问：ClickHouse 表怎么设计？

ClickHouse 表和查询服务不是我实现的。下面只能从 SDK 协作角度解释，不能说成项目代码：事件协议需要包含能够支持应用、页面、版本、会话和事件类型查询的字段。一个概念性事件模型可能包含：

- `event_time`
- `app_id`
- `tenant_id`
- `version`
- `route`
- `session_id`
- `user_id`
- `event_type`
- `metric_name`
- `metric_value`
- `trace_id`
- `payload`

按日期分区、按常用过滤维度排序、低基数字段优化等属于 ClickHouse 通用设计思路。项目中的实际分区键、排序键和表结构应由负责数据服务的同事确认，我不会在面试中声称由我设计。

## 如果面试官追：怎么查 LCP p75 或接口耗时 p95？

分位数比平均值更适合观察体验尾部，但查询实现不属于我的个人交付。下面的 SQL 只用于说明 SDK 字段怎样被下游消费：

```sql
SELECT
  app_id,
  version,
  route,
  quantile(0.75)(metric_value) AS lcp_p75
FROM events
WHERE event_time >= now() - INTERVAL 1 DAY
  AND event_type = 'web_vital'
  AND metric_name = 'LCP'
GROUP BY app_id, version, route
ORDER BY lcp_p75 DESC
LIMIT 100
```

这说明 SDK 上报的 `app_id`、`version`、`route`、指标名和指标值需要保持稳定口径，才能支持下游计算 p75 / p95。实际查询与大盘由其他同事实现。

## 如果面试官追：数据量大了查询慢怎么办？

查询性能由数据服务和 ClickHouse 负责人处理，我没有可核对的实施细节与性能数据。

如果面试官只想讨论方案，我可以解释时间范围、排序键、预聚合、缓存及聚合与明细分离等通用方向，但会明确这是技术理解，不是个人项目成果。

## 如果面试官追：指标口径怎么保证可信？

指标口径是大盘很容易被忽略的部分。

比如“错误率”要明确分母是请求数、会话数还是页面访问数；Abort 请求是否算错误；采样后如何还原；同一个错误是否去重；SPA 路由切换算不算一次页面访问。

从 SDK 协作角度，我会在协议中区分事件类型和必要上下文，并与下游确认 Abort、SPA 路由、采样和去重口径。控制台怎样展示说明由负责大盘的同事实现。

## 如果面试官追：多租户权限怎么做？

多租户查询权限属于后端和控制台边界，不是 SDK 可以决定的。SDK 可以上报应用与租户上下文，但服务端必须根据当前身份强制限制查询范围，不能依赖前端选择器。

这是整体架构原则，不代表这部分代码由我实现。
