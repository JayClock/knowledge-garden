## 30 秒开场

监控系统整体包含前端 SDK、数据接收与处理服务、ClickHouse 存储和可视化控制台。我的职责主要在 SDK：统一采集性能、异常、接口和操作数据，补充应用、页面、版本等上下文，并以约定协议可靠上报。

NestJS、Kafka、ClickHouse、查询后端和控制台由其他同事负责。因此我可以讲清数据从采集到消费的协作链路，以及为什么指标口径必须前后一致，但不会把后端存储和大盘实现说成我的个人成果。

## 如果面试官问：ClickHouse 表怎么设计？

我会先说明 ClickHouse 表和查询服务不是我实现的，不能把下面内容说成项目代码。只能从 SDK 协作角度解释：事件协议需要包含能够支持应用、页面、版本、会话和事件类型查询的字段。一个概念性事件模型可能包含：

- `event_time`
- `app_id`
- `tenant_id`
- `version`
- `route`
- `session_id`
- `user_id`
- `event_type`
- `metric_name`
- `metric_value`
- `trace_id`
- `payload`

按日期分区、按常用过滤维度排序、低基数字段优化等属于 ClickHouse 通用设计思路。项目中的实际分区键、排序键和表结构应由负责数据服务的同事确认，我不会在面试中声称由我设计。

## 如果面试官追：怎么查 LCP p75 或接口耗时 p95？

我会说分位数比平均值更适合观察体验尾部，但查询实现不属于我的个人交付。下面的 SQL 只用于说明 SDK 字段怎样被下游消费：

```sql
SELECT
  app_id,
  version,
  route,
  quantile(0.75)(metric_value) AS lcp_p75
FROM events
WHERE event_time >= now() - INTERVAL 1 DAY
  AND event_type = 'web_vital'
  AND metric_name = 'LCP'
GROUP BY app_id, version, route
ORDER BY lcp_p75 DESC
LIMIT 100
```

这说明 SDK 上报的 `app_id`、`version`、`route`、指标名和指标值需要保持稳定口径，才能支持下游计算 p75 / p95。实际查询与大盘由其他同事实现。

## 如果面试官追：数据量大了查询慢怎么办？

我会先把问题交回职责边界：查询性能由数据服务和 ClickHouse 负责人处理，我没有可核对的实施细节与性能数据。

如果面试官只想讨论方案，我可以解释时间范围、排序键、预聚合、缓存及聚合与明细分离等通用方向，但会明确这是技术理解，不是个人项目成果。

## 如果面试官追：指标口径怎么保证可信？

我会说这是大盘最容易被忽略的地方。

比如“错误率”要明确分母是请求数、会话数还是页面访问数；Abort 请求是否算错误；采样后如何还原；同一个错误是否去重；SPA 路由切换算不算一次页面访问。

从 SDK 协作角度，我会在协议里区分事件类型和必要上下文，并与下游确认 Abort、SPA 路由、采样和去重口径。控制台怎样展示说明由负责大盘的同事实现。

## 如果面试官追：多租户权限怎么做？

我会说多租户查询权限属于后端和控制台边界，不是 SDK 可以决定的。SDK 可以上报应用与租户上下文，但服务端必须根据当前身份强制限制查询范围，不能依赖前端选择器。

这是整体架构原则，不代表这部分代码由我实现。

## 收尾句

所以这块我表达的是端到端协作能力：我负责让 SDK 产出稳定、可解释的事件协议，并理解下游怎样存储和消费；数据服务、ClickHouse 和大盘实现属于其他同事，不能混写成个人成果。
