# 项目介绍：前端埋点与监控 SDK

## 提取词

下游证据倒推 ｜ Monorepo与插件协议 ｜ 零侵入请求代理 ｜ 本地队列与退避重试 ｜ executionId业务日志串联

## 2 分钟版本

我负责监控 SDK 的采集与上报侧。设计时不是先看浏览器能采什么，而是先确认后续验收和运行诊断需要依据什么证据，再定义通用指标、业务事件、必要上下文和关联标识。

AI Flow 是一个实际接入实例。为了区分用户是在工作流校验、测试运行还是发布环节失败，我为三个关键路径添加自定义事件；节点状态、耗时和错误仍由执行引擎日志记录，前端路径和节点证据通过 `executionId` 关联。

SDK 使用 pnpm Monorepo 拆分 core、browser 和 React／Vue 适配包。core 定义插件协议、统一事件和 Transport，browser 封装 PerformanceObserver、全局错误、DOM、Fetch 和 XHR，框架适配包只处理生命周期差异。性能侧采集 Web Vitals，异常侧覆盖全局 error、`unhandledrejection` 和业务自定义错误；所有代理都必须保留原始业务语义。

事件先进入本地队列，再按时间、数量或路由变化批量发送，并结合失败重试处理网络异常；生产堆栈通过构建版本和 Sourcemap 还原。服务端数据存储与监控控制台由后端及大数据团队负责，我专注保障端侧采集与上报的高可靠与低侵入。

## 5 分钟主讲

我先介绍一下这个项目的背景。作为低代码平台前端架构的基础设施，监控 SDK 跑在所有业务应用中。过去很多前端做监控容易陷入一个误区，就是对着浏览器 API“能采什么就采什么”，结果上报了一堆无用的字段，真正线上出故障时依然看不出是哪个业务环节坏了。我在做这个 SDK 时，确立的核心设计原则是：**绝不从 API 倒推采集，而是从下游验收和排障究竟需要什么证据，来倒推事件、上下文和关联标识**。我直接负责 SDK 的核心架构、采集插件、多框架适配与端侧上报全链路。

在架构设计上，SDK 基于 Monorepo 做了非常清晰的职责解耦：Core 包保持纯粹与框架无关，只负责统一的事件协议、插件生命周期与 Transport 上报；Browser 包封装 PerformanceObserver、全局错误监听、DOM、Fetch 与 XHR 等 Web API；上层再针对 React、Vue 和 Vanilla 提供适配包，抹平框架生命周期的差异。性能、异常、请求和操作行为全部作为独立插件可插拔注册。这样新增一个采集指标无需在各个框架重复写，调整上报策略也不会侵入具体的采集逻辑。

但在工程落地时，监控 SDK 面临的最大挑战是如何做到**极低的性能开销与真正的零业务侵入**。监控代码绝对不能反噬宿主业务：在性能侧，我们通过 PerformanceObserver 采集 Web Vitals（如 FCP、LCP、CLS、INP 和 TTFB），Observer 的回调只做最轻量的内存指标记录，复杂的聚合计算与网络发送绝不占用主线程渲染时机；在请求代理侧，对 Fetch 和 XHR 做切面拦截时，只记录 URL、耗时、状态码和必要链路头，必须严格透传原始参数、返回值和 Promise 状态，绝不破坏业务原有的异步时序，更不能在拦截时消费 stream 导致业务无法再次读取响应体；而且采集层必须做严格的全局错误隔离，即使 SDK 自身报错，原业务请求也必须照常执行或原样抛错。

在网络传输与错误还原上，每个事件立即上报会产生海量零散请求并阻塞网络带宽，因此事件先进入本地内存队列。队列结合时间间隔、数量阈值或路由跳转批量打包发送，并结合指数退避算法处理弱网重试；在页面卸载时结合 sendBeacon 提升终结态上报成功率。对于生产环境被混淆压缩的报错，在 CI/CD 构建阶段生成并上传 Sourcemap 资产并与版本号严格对齐，在线上堆栈捕获时按行列号精准反解为源码文件与行数。

为了真正验证监控对复杂业务的诊断价值，AI Flow 工作流引擎是一个典型的落地案例：为了区分用户究竟是在工作流连线校验、测试运行还是发布环节失败，我为这三个关键业务路径注入了自定义追踪事件；而具体节点成功失败、耗时与堆栈错误由 TypeScript 执行引擎日志精确负责。两端通过同一个 executionId 深度串联，打通了“用户在前端点了什么”到“引擎在底层执行了什么”的完整可观测闭环。

这个 SDK 的核心价值不是采得更多，而是把下游需要的判断变成稳定的证据契约。统一事件、队列和 Transport 构成了稳定基线，多框架适配与自定义事件按环境逐层增强，打通了从前端操作路径到后端引擎事实的全链路追踪闭环。

## 高频追问

### 如果面试官问：为什么要拆 core、browser 和框架适配包？

因为它们面对的变化频率和环境依赖完全不同：

- `core` 包是纯粹与环境无关的基础运行时，只负责统一的事件数据模型、插件生命周期管理与 Transport 抽象接口，没有任何 DOM 或框架依赖。
- `browser` 包封装所有 Web 平台 API：包括 PerformanceObserver、全局错误监听、DOM 事件切面、Fetch 与 XHR 请求拦截。
- 上层的 `react`、`vue` 和 `vanilla` 适配包只负责抹平框架生命周期差异，比如提供 React 错误边界（ErrorBoundary）和 Hooks 接入。

这种分层保证了核心包的绝对稳定。当新增一个采集项时，只需在 browser 中实现一个插件并在 core 中声明事件协议，不需要在 React 和 Vue 两个框架里分别写一遍；当某个框架升级大版本时，底层采集和上报引擎也完全不受影响。

### 如果面试官问：插件化体现在哪里？Transport 为什么要独立？

性能、异常、行为和请求拦截全部作为标准插件实现，统一遵循生命周期钩子（如 `init`、`start`、`destroy`）。SDK 初始化时按需加载插件，插件只负责监听并向核心事件总线推送结构化事件，不直接负责网络发送。

把 Transport 独立出来的原因是：**采集关注“发生了什么”，而 Transport 关注“如何可靠传输”**。
如果两者耦合，每个采集插件都要重复实现队列打包、网络重试和端侧缓冲；一旦要适配微信小程序、Node.js 甚至移动端原生环境，所有插件都要推倒重写。

通过 Transport 抽象，所有采集事件统一推入内存队列，由具体环境的 Transport（如浏览器的 BeaconTransport 或 FetchTransport）负责批量打包发送和网络重试，实现了采集逻辑与传输逻辑的彻底解耦。

### 如果面试官追：Fetch 和 XHR 代理会不会影响主业务？

这是做监控 SDK 最核心的工程红线：**监控代码绝对不能反噬宿主业务**。

1. **严格保持原生语义**：切面拦截 Fetch 和 XHR 时，必须完整透传原始请求参数，原样返回原生 Promise 或 XHR 实例，绝不破坏业务原有的异步时序和微任务队列。
2. **禁止提前消费响应流**：在 Fetch 拦截中，绝不能直接调用 `response.json()` 或读取 body，因为 stream 只能被消费一次，直接读取会导致业务后续读取报“Body already read”错误。SDK 只提取 URL、HTTP 状态码、耗时和标头元信息。
3. **全局沙箱与错误隔离**：所有 SDK 的拦截逻辑均包裹在独立的 `try-catch` 中。即使 SDK 自身在提取参数或计算时间戳时发生运行时错误，必须立即静默降级并照常放行业务原生请求，绝不允许 SDK 的异常阻断主流程。

### 如果面试官问：Web Vitals 核心性能指标怎么采？

指标采集围绕用户的真实体感展开：FCP 关注首次内容渲染，LCP 关注最大内容块可见，CLS 关注页面布局偏移，TTFB 关注服务端首字节响应。

在实现上，通过 `PerformanceObserver` 监听原生 Entry：

- FCP 监听 `paint` 条目；
- LCP 监听 `largest-contentful-paint`，并在用户产生交互（如点击或按键）时锁定最终值；
- CLS 监听 `layout-shift` 条目，过滤包含 `hadRecentInput: true` 的用户预期偏移，按 Session Window 动态累加最大会话窗口分值。

**开销控制**：Observer 的回调函数只做最简单的内存变量赋值，复杂的聚合计算、分位数统计以及网络上报绝不占用主线程渲染时机，防止监控本身引起主线程长任务（Long Tasks）。

### 如果面试官问：运行时异常怎样覆盖？Sourcemap 怎么还原？

在异常覆盖上，SDK 构建了三层捕获网：

1. `window.addEventListener('error', callback, true)` 在捕获阶段捕获常规 JS 语法/运行时报错，并能感知静态资源（如 `<img>`、`<script>`）加载失败；
2. `window.addEventListener('unhandledrejection')` 捕获未处理的 Promise 拒绝；
3. 上层框架适配包提供 React `ErrorBoundary` / Vue `errorHandler` 捕获组件渲染级崩溃。

**Sourcemap 精准还原**：
在 CI/CD 构建发布阶段，流水线生成混淆打包产物与 Sourcemap 文件，将 Sourcemap 资产上传至内部私有存储，并与当前 Git Commit / Release 版本号严格对齐；端侧捕获错误堆栈时，只上报压缩后的文件名、行号与列号；服务端在消费错误日志时，根据版本号拉取对应 Sourcemap，基于 SourceMapConsumer 离线还原出源代码文件路径、方法名及原始行数，既保护了前端源码安全，又实现了生产问题的毫秒级精准定位。

### 如果面试官问：上报请求数怎么控制？弱网与页面卸载怎么处理？

如果每个事件都立即触发 HTTP 请求，不仅会占用海量网络带宽，还会耗尽浏览器并发连接数，劣化主业务性能。

1. **本地内存队列**：事件生成后统一压入内存队列。设置双重触发阈值：事件积压满 30 条立即发送，或等待时间满 3 秒立即批量打包发送；路由发生切换时强制 flush 一次。
2. **指数退避重试**：当批量上报遭遇网络波动或服务端 5xx 时，采用指数退避算法（如 1s, 2s, 4s...）延迟重试，并加入随机抖动（Jitter），防止多客户端集中重试冲垮网关。
3. **页面卸载保障**：在 `visibilitychange`（状态变为 hidden）或 `pagehide` 事件触发时，优先调用 `navigator.sendBeacon` 将剩余队列数据异步推送；`sendBeacon` 由浏览器内核在后台完成传输，即使页面已被用户关闭也不会被强行掐断，显著提升终结态事件上报成功率。

### 如果面试官问：AI Flow 的前端埋点怎样关联执行日志？

很多前端监控最致命的问题是：只能看到“用户点了什么”，但不知道“底层发生了什么”，两端割裂无法形成证据闭环。

在 AI Flow 低代码工作流引擎中，我通过 `executionId` 实现了端到端的精准串联：

- 当用户在前端画布上触发“连线校验”、“运行测试”或“正式发布”时，前端生成或接收统一的 `executionId`，SDK 的自定义事件中强制携带此 ID；
- 底层 TypeScript 执行引擎在各个节点调度、执行、求值和错误捕获时，在引擎日志中全部打印相同的 `executionId`；
- 当排障时，运维或研发只需检索该 `executionId`，就能完整还原出时间轴：从用户在前端点了哪条连线、输入了什么变量，到引擎在第几毫秒执行了哪个节点、抛出了什么堆栈，实现了前端操作路径到后端引擎事实的全链路追踪闭环。

### 如果面试官问：为什么 SDK 需要理解下游数据消费？协作边界是什么？

如果只从浏览器能采什么出发，最终往往会堆积海量看似全面但实际无法支持业务决策的“僵尸数据”。监控的本质是**为下游的排障与验收提供确定性的证据契约**。

在架构分工上，职责边界非常清晰：

- **我直接负责**：端侧 SDK 的核心架构、插件协议、请求切面、内存队列、弱网重试以及端侧自定义上下文（如 `executionId`）的完整定义与采集落地；
- **后端与大数据团队负责**：接入网关、Kafka 缓冲、ClickHouse 时序表设计与指标大盘展示。

在制定契约时，我根据下游对 LCP p75、API 耗时 p95 以及多租户时序聚合的查询诉求，在端侧规范化字段口径（包括 `app_id`、`tenant_id`、`trace_id`、`metric_name`、`metric_value` 等），确保端侧采集的每一个字段都具备清晰的消费场景，减少了大量无效网络开销与后端清洗成本。
