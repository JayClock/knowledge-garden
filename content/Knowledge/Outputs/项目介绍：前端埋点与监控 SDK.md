# 项目介绍：前端埋点与监控 SDK

## 提取词

- **S｜背景**：低代码平台 ｜ React、Vue 与 Vanilla JS 共存 ｜ 验收与运行诊断需要统一数据口径
- **T｜任务**：端侧 SDK 架构、采集与上报 ｜ 跨框架复用 ｜ 控制对宿主业务的影响 ｜ 对齐下游数据需求
- **A｜行动**：证据需求倒推事件 ｜ Monorepo 分层与插件协议 ｜ 性能、异常与低侵入请求采集 ｜ 内存队列与失败重试 ｜ Sourcemap 上传与版本映射
- **R｜结果**：覆盖平台前端各业务模块 ｜ 同一监控协议 ｜ 复用采集与上报 ｜ 压缩堆栈还原到源码

## 项目介绍

这个项目是低代码平台的前端监控 SDK。平台里有多种前端框架，既要复用性能、异常和操作采集，也要让数据真正支持验收与运行诊断，同时控制监控对业务的影响。

我负责 SDK 架构、采集插件、多框架适配和端侧上报。数据存储、查询和监控控制台由后端及大数据团队负责，我先与下游对齐需要哪些证据，再定义事件协议和必要上下文。

实现上，我用 pnpm Monorepo 拆分核心层、浏览器层和框架适配层，分别处理统一协议与队列、浏览器采集、框架生命周期。采集逻辑通过插件接入，具体发送由 Transport 承担。性能侧采集 Web Vitals，异常侧覆盖全局错误、Promise 拒绝、框架异常和业务主动上报。Fetch 与 XHR 代理记录请求元信息，以保持业务调用、返回值和请求行为为约束。事件先进入内存队列，按时间、数量或路由变化批量发送，结合失败重试和弱网处理。我也接入生产 Sourcemap 上传与构建版本映射，支持压缩堆栈还原。

最终，SDK 覆盖低代码平台前端各业务模块，不同技术栈消费同一套监控协议，复用采集与上报机制；业务可以补充自定义事件和上下文，让下游拿到统一口径的性能、异常和操作数据。

## 面试专项突击完整口述

### 原题 7.1：高扩展性与跨框架兼容

**如何设计和实现一个高扩展性、跨框架兼容的前端监控 SDK？设计过程中需要考虑哪些关键技术点？**

**提取词：** 架构分层｜独立采集模块｜插件与 Transport｜批量上报｜TypeScript

在我负责的低代码平台监控 SDK 中，难点是不同技术栈的业务模块需要复用监控能力，同时采集指标、框架接入和上报策略又会分别变化，所以我先把这些变化隔离到不同层。

工程上使用 pnpm Monorepo 管理多个包，主要分成 core、browser 和框架适配三层，再通过 types 和工具包共享类型与通用能力。core 保留统一事件协议、插件接口、队列调度和 Transport 抽象，不依赖具体的浏览器 API 或前端框架。browser 封装性能、异常、请求和用户操作的采集；React、Vue 等适配包处理框架生命周期和错误处理机制。

这样，浏览器性能采集发生变化，不需要在 React 和 Vue 中分别重写；框架接入方式变化，主要调整适配层；上报策略变化，也不用逐个改采集模块。

采集能力按独立模块组织。配置插件使用统一的 `init(transport)` 初始化入口，core 将同一个 Transport 实例传给它们。采集模块关注发生了什么，队列与调度决定何时发送，具体 Transport 执行网络发送。新增监控项时，增加对应的采集模块和事件结构即可复用发送接口。

上报方面，事件先进入本地内存队列，再按时间间隔、数量阈值或路由变化批量发送，减少零散请求，并结合失败重试与弱网处理。

TypeScript 负责约束这些协作接口：`EventData<T>` 约束自定义事件数据，`IIntegration` 约定插件初始化入口，`Transport` 约定统一发送接口。不同采集模块和框架适配层按同一套类型约定协作，避免各自定义不同的数据结构与调用方式。

最终，React、Vue 和 Vanilla JS 业务模块消费同一套监控协议，复用核心采集与上报机制；Transport 抽象也将采集逻辑与具体发送环境分开，为跨环境扩展保留接口。

### 原题 7.2：性能采集、分析与数据准确性

**如何在前端 SDK 中高效采集和分析 Web 性能指标，并确保监控数据的准确性？**

**提取词：** 指标选择｜Observer 与 Entry｜准确性处理｜统一事件｜批量上报｜下游分析

我在低代码平台的监控 SDK 中负责端侧采集和上报。性能监控主要考虑三个问题：采到的数据能不能反映用户体验、指标口径是否准确，以及监控本身会不会增加页面和网络负担。

指标选择上，我用 FCP 看首次内容什么时候出现，用 LCP 看主要内容的绘制情况，用 CLS 看页面布局是否稳定。这几个指标关注不同方面，不能只用页面加载完成时间判断整体体验。

实现上，使用封装好的性能采集函数，底层通过 PerformanceObserver 监听浏览器产生的性能条目。FCP 监听 `paint`，再筛选 `first-contentful-paint`；LCP 监听 `largest-contentful-paint`；CLS 监听 `layout-shift`。采集函数根据 PerformanceEntry 中的时间或偏移分值计算指标，再通过回调交给 SDK。观察器开启 `buffered`，可以获取注册监听之前已经产生的条目。

准确性不能只靠监听到了就上报。FCP 要识别首次内容绘制，而不是把第一次绘制直接当作 FCP。LCP 随候选内容变化更新，在用户交互或页面隐藏时确认最终值。CLS 过滤 `hadRecentInput` 的布局偏移，按会话窗口累加，并取最大的窗口分值，而不是把所有偏移简单相加。

拿到指标后，采集模块把指标名称、数值和页面路径包装成统一的性能事件。采集模块负责得到正确的指标，队列和 Transport 负责上报调度与发送，各个采集模块不用重复实现网络逻辑。

上报流程的优化重点是批量发送。事件先进入本地内存队列，再根据时间间隔、数量阈值或路由变化合并发送，减少每个指标单独上报产生的请求。网络异常时结合失败重试和弱网处理，平衡上报实时性、请求开销与可靠性。

分析侧，我负责保证端侧事件口径和必要上下文一致；数据存储、查询和监控控制台由后端及大数据团队负责。不同业务模块消费同一套性能事件协议，后续才能按统一口径分析页面表现。

所以这个项目的关键，是把指标选择、条目过滤、指标计算和批量上报连起来：既让数据能够解释用户体验，也通过统一队列减少监控产生的请求开销。

### 原题 7.3：异常捕获、覆盖率与准确性

**在前端监控 SDK 中捕获 JavaScript 异常的常见方法有哪些？如何提高异常监控的覆盖率和准确性？**

**提取词：** 全局错误｜Promise 拒绝｜框架异常｜业务主动上报｜堆栈与上下文｜去重过滤

在我负责的低代码平台监控 SDK 中，异常监控分成三类入口：浏览器全局异常、框架内部异常，以及业务主动上报的异常。这样可以覆盖不同技术栈和不同处理方式下的错误。

浏览器层，未捕获的 JavaScript 运行时错误通过 `window.onerror` 捕获，记录错误类型、消息、堆栈和当前页面路径。对于 Promise 异步链中没有被处理的拒绝，通过 `window.onunhandledrejection` 获取拒绝原因，提取消息和堆栈信息，交给统一的 Transport 上报。

只依赖全局监听还不够，因为框架内部也有自己的错误处理机制。框架适配层补充组件级捕获：React 使用 ErrorBoundary 捕获其子组件树中的渲染和生命周期错误，Vue 接入框架的 errorHandler，再把异常交给 SDK 的上报链路。

业务逻辑异常需要主动上报。业务已经在 catch 中处理的异常，不一定会进入全局未处理异常监听，但开发者仍然可能需要记录它。因此 core 提供 `captureException`，让业务把错误主动交给 SDK。这个接口把错误包装成 `customError` 类型的事件，通过当前 Transport 发送，业务不用自己实现网络上报。消息和自定义业务事件则分别使用 `captureMessage` 和 `captureEvent`。

提高准确性方面，我重点保留能够支持定位的信息，而不只是记录一句发生错误。错误类型帮助分类，消息说明错误内容，堆栈用于追踪代码位置，页面路径和浏览器环境帮助判断错误发生的上下文。生产代码经过压缩后，监控平台还可以结合对应的 Sourcemap，将堆栈位置还原到原始源码。

进一步减少错误数据中的噪声时，还可以对重复错误进行去重，过滤常见的非关键性错误，让后续分析聚焦于需要处理的问题。这是原题提出的优化方向。

整体上，全局监听覆盖未处理的运行时异常，框架适配补充组件内部异常，主动上报补充业务已经识别或处理的异常；再通过统一的错误信息和上下文，让这些数据能够用于定位问题。

## 高频追问

### 如果面试官问：为什么要拆 core、browser 和框架适配包？

它们面对不同的依赖和变化：`core` 管统一事件、插件接口、队列调度与 Transport 抽象；`browser` 封装浏览器采集；React／Vue 适配包处理框架生命周期和异常接入。

浏览器采集变化时，各框架复用同一实现；框架接入变化时，主要调整适配层；发送策略变化时，也不必逐个改采集模块。完整讲法见 [[#原题 7.1：高扩展性与跨框架兼容|原题 7.1]]。

### 如果面试官问：插件化体现在哪里？Transport 为什么要独立？

配置插件通过 `init(transport)` 初始化，共享传入的 Transport。插件负责生成采集事件，队列与调度决定何时发送，Transport 执行具体网络发送。新增采集项时，可以复用现有上报链路。

TypeScript 用 `IIntegration` 约定初始化入口，用 `Transport` 约定发送接口，用 `EventData<T>` 描述业务事件数据。这样采集模块按同一套接口协作，具体发送实现也可以按环境替换。

### 如果面试官追：Fetch 和 XHR 代理会不会影响主业务？

代理以保持业务调用、返回值和请求行为为约束，主要记录 URL、状态码、耗时和必要上下文。

Fetch 的响应体只能消费一次，代理如果先调用原始 Response 的 `json()`，业务再次读取就会失败；等待解析完成还会延迟响应交付。因此默认只提取元信息，把未消费的 Response 返回给业务。

XHR 同样围绕原有请求过程采集信息，保持参数、返回结果和业务错误处理语义。监控关注请求发生了什么，不替业务处理响应内容。

### 如果面试官问：Web Vitals 核心性能指标怎么采？

我采集 FCP、LCP、CLS、TTFB 和 INP，分别观察内容出现、主要内容绘制、布局稳定性、首字节时间与交互响应。

性能采集函数基于 `PerformanceObserver` 等浏览器计时能力，处理各指标的计算口径：

- **FCP**：监听 `paint`，筛选 `first-contentful-paint`。
- **LCP**：监听 `largest-contentful-paint`，跟踪候选更新，在交互或页面隐藏时确认最终值。
- **CLS**：监听 `layout-shift`，过滤 `hadRecentInput`，按会话窗口计算最大分值。
- **TTFB**：读取导航条目的 `responseStart`，结合页面激活时间修正。
- **INP**：采集交互到下一次绘制的延迟，反映页面交互响应。

观察器用 `buffered` 获取注册前已有的条目。指标封装为统一性能事件后进入上报链路。完整讲法见 [[#原题 7.2：性能采集、分析与数据准确性|原题 7.2]]。

### 如果面试官问：运行时异常怎样覆盖？Sourcemap 怎么还原？

异常采集有三类入口：浏览器层通过 `window.onerror` 和 `unhandledrejection` 捕获未处理异常；框架层接入 React ErrorBoundary 和 Vue errorHandler；业务通过 `captureException` 主动记录需要保留的异常。

ErrorBoundary 覆盖子组件树的渲染和生命周期错误，事件处理函数、异步回调仍要结合全局监听与业务主动上报。各入口统一错误消息、堆栈、页面路径和浏览器上下文，再复用上报链路。完整讲法见 [[#原题 7.3：异常捕获、覆盖率与准确性|原题 7.3]]。

生产构建生成 Sourcemap，上传到监控后台并关联构建版本。SDK 上报压缩堆栈后，平台用对应版本的 Map 将产物行列号还原到源码。若要避免源码随静态资源公开暴露，可以在上传成功后移除发布目录中的 `.js.map`，后台保留定位文件。

### 如果面试官问：上报请求数怎么控制？弱网怎么处理？

事件先进入内存队列，按时间间隔、数量阈值或路由变化批量发送，减少零散请求。采集模块生成事件，队列与调度控制批次，Transport 执行网络发送。

网络异常时结合失败重试和弱网处理，平衡实时性、请求开销和可靠性。判断失败还需要检查 HTTP 响应状态，Fetch 的 4xx／5xx 通常不会自动触发 Promise rejection。

### 如果面试官问：监控 SDK 如何支持业务自定义事件与上下文？如何避免污染通用协议？

core 提供 `captureException`、`captureMessage` 和 `captureEvent`，分别接收异常、消息和业务事件。接口统一包装事件，再通过当前 Transport 进入上报链路，业务不需要重复实现网络发送。

业务事件通过 `EventData<T>` 的 `eventType` 和 `data` 描述，业务字段保留在数据部分，浏览器上下文由发送层补充，通用事件协议保持一致。

比如业务已在 `catch` 中处理的异常，不会再进入未处理异常监听，但仍可调用 `captureException` 留下诊断记录。错误序列化时需要显式提取 `message`、`stack` 等字段，直接 `JSON.stringify(Error)` 会丢失这些信息。

### 如果面试官问：为什么 SDK 需要理解下游数据消费？协作边界是什么？

我先与下游对齐验收和排障要回答的问题，再确定指标、业务事件和上下文。比如异常除了消息和堆栈，还需要页面路径与浏览器环境，才能支持具体定位。

我负责端侧 SDK 架构、采集与上报，后端及大数据团队负责存储、查询和监控控制台。统一事件口径后，不同技术栈的模块都能为下游提供一致的数据。
