# 项目介绍：企业级前端监控 SDK 与数据采集系统

## 提取词

多框架采集 ｜ 核心层、浏览器层、框架适配层 ｜ TypeScript 与插件接口 ｜ 性能与异常 ｜ 队列、批量发送与重试 ｜ NestJS 数据服务、Kafka 处理与 ClickHouse 存储 ｜ 系统响应性能提升 50% ｜ Sourcemap 上传、版本映射与源码定位

## 项目介绍

这个项目是一套企业级前端监控 SDK 和数据采集系统，主要采集页面性能和运行异常，帮助研发定位问题。我负责 SDK 架构、多框架适配和采集上报，也实现了数据接收、异步处理和存储后端，并接入了生产 Sourcemap 链路。

业务里同时有 React、Vue 多个前端框架，所以我把 SDK 拆成核心层、浏览器层和框架适配层。核心层保留统一事件、插件和队列，浏览器层封装 WEB 采集能力，适配层处理框架生命周期与异常入口。再通过 TS 类型约束模块接口，新增监控项可以复用公共上报能力。

采集侧通过 PerformanceObserver 获取 FCP、LCP、CLS 等性能指标。异常则覆盖全局错误、未处理的 Promise 拒绝、框架异常和业务主动上报，保留消息、堆栈及页面上下文，整理成统一事件。

事件先进入本地队列，按时间间隔、数量阈值或路由变化批量发送，结合失败重试与弱网处理，减少零散请求。我用 NestJS 实现数据接收服务，通过 Kafka 异步处理，再写入 ClickHouse，以统一事件协议串联 SDK 与后端。系统响应性能提升了 50%。

生产代码经过压缩后，直接看堆栈很难定位，所以我接入了 Sourcemap 上传与版本映射，将报错位置还原到源码。最终，不同技术栈的模块可以复用采集与上报机制，为研发提供统一口径的性能数据和可定位的异常信息。

## 可能追问

### 7.1 **如何设计和实现一个高扩展性、跨框架兼容的前端监控 SDK？设计过程中需要考虑哪些关键技术点？**

* **回答思路**：

  * **架构设计**：参考 Sentry，将 SDK 划分为核心包和适配包，核心包提供基础监控功能，适配包接入 React、Vue、Vanilla JS 等不同框架。

  * **模块划分**：异常捕获、性能监控、数据上报、用户行为采集等功能模块化，便于维护和扩展。

  * **数据上报**：使用 HTTP 或 WebSocket 传送数据，兼顾安全性和实时性，并通过批量上报减少请求数。

  * **插件化设计**：通过插件机制加载和扩展自定义监控项或上报逻辑。

  * **静态类型支持**：使用 TypeScript 保障代码质量，减少运行时错误，提高可维护性。

**回答：**

项目里的 React、Vue 和 Vanilla JS 模块需要复用监控能力，所以我把共享逻辑和框架入口分开，组织成核心层、浏览器层和框架适配层。

核心层保留统一事件、插件接口、本地队列和 Transport；浏览器层封装 PerformanceObserver、全局异常等 Web API；框架适配层处理各自的生命周期和异常入口。浏览器采集变化时，各框架复用同一份实现，框架接入方式变化时，也主要调整对应适配包。

性能、异常和数据上报分别组织，采集能力通过插件接入。插件负责生成统一事件，队列决定何时合并发送，Transport 负责具体 HTTP 请求。新增监控项可以沿用这条链路，不必再实现一套网络发送逻辑。

TypeScript 则约束事件结构、插件入口和发送接口，让不同包按一致的类型约定协作。最终，不同技术栈既能保留自己的接入方式，也能共用采集与上报能力。

### 7.2 **如何在前端 SDK 中高效采集和分析 Web 性能指标，并确保监控数据的准确性？**

* **回答思路**：

  * **性能指标选择**：选择 FCP、LCP、CLS 等指标，分析页面加载速度和布局稳定性。

  * **API 使用**：使用 `PerformanceObserver`，结合 `PerformanceEntry` 获取不同类型的性能数据。

  * **数据处理**：对性能数据进行过滤、清洗和聚合，去除无效数据，保证分析口径。

  * **数据上报**：使用 HTTP 批量上报以减少网络开销，并设计重试机制，提高上报可靠性。

  * **性能监控的挑战**：平衡数据实时性与准确性，控制采集对页面性能的影响，合理设计批量上报。

**回答：**

我先根据要观察的页面体验选择指标。FCP 看首次内容出现的时间，LCP 看主要内容的绘制，CLS 看布局稳定性，分别反映加载和渲染的不同方面。

采集时，通过 PerformanceObserver 监听浏览器产生的性能条目，再从 PerformanceEntry 中读取对应数据。FCP 从 paint 条目中识别首次内容绘制，LCP 关注最大内容绘制条目，CLS 处理布局偏移数据。

准确性不只是监听到了条目，还要按指标定义进行筛选、计算和聚合，不能把每一次回调都直接当成最终结果。上报时保留一致的指标名称、数值、单位和页面上下文，让不同模块的数据能够按同一口径使用。

计算完成后，将指标封装成统一事件交给本地队列，而不是每个采集模块单独发请求。队列负责批量发送，网络异常时结合重试和弱网处理，在数据实时性与页面、网络开销之间取得平衡。

### 7.3 **在前端监控 SDK 中捕获 JavaScript 异常的常见方法有哪些？如何提高异常监控的覆盖率和准确性？**

* **回答思路**：

  * **全局异常捕获**：使用 `window.onerror` 捕获未处理的运行时错误，使用 `window.onunhandledrejection` 捕获未处理的 Promise 异常。

  * **错误信息的处理**：解析堆栈，提取来源文件、行号和详细信息，并对重复错误去重。

  * **捕获框架内异常**：接入 React、Vue 等框架的内部错误处理机制，补充组件内异常。

  * **自定义错误上报**：允许开发者主动上报业务逻辑中的错误，扩大异常覆盖范围。

  * **数据清洗和异常过滤**：过滤常见的非关键性错误，让后续处理聚焦关键问题。

**回答：**

全局入口通过 window.onerror 捕获未处理的运行时错误，通过 window.onunhandledrejection 获取未处理的 Promise 拒绝，先覆盖浏览器层的异常。

取得错误后，统一整理消息和堆栈，提取来源文件、行号等定位信息，并带上页面路径和浏览器环境。这样上报的事件既说明发生了什么，也保留了后续排查需要的上下文。

框架内部异常由适配层补充：React 接入 ErrorBoundary，Vue 接入 errorHandler，再把取得的异常交给同一条上报链路。业务已经在 catch 中处理、但仍希望保留的错误，则通过 captureException 主动上报。

提高准确性时，还可以结合去重和过滤规则减少重复错误与非关键性噪声。生产代码经过压缩后，采集到的堆栈再结合对应版本的 Sourcemap 还原到源码，将异常采集和后续定位衔接起来。

### 7.8 上报请求数的控制如何实现？

* **回答思路：**

  * **本地维护上报队列：**将产生的指标内容暂存到队列，延迟合并上报。

  * **按时间间隔出队**：定期合并队列中的指标并发送。

  * **按数量出队**：短时间达到数量阈值时，触发合并上报。

  * **根据页面路由**：路由跳转时，将当前页面指标合并上报。

**回答：**

核心是将采集和发送分开。采集插件先生成统一事件，放进本地队列，队列再按条件合并发送，不为每个指标单独发请求。

发送由三类条件触发：达到时间间隔就发送已有事件，避免低流量页面一直等待；短时间达到数量阈值时提前发送；路由切换时，将当前页面的指标整理后合并上报。

这些触发方式共用一条发送链路，具体 HTTP 请求由 Transport 执行。新增一种采集项时，直接复用现有队列，不必再维护自己的定时器和发送逻辑。

网络异常时结合失败重试与弱网处理。批量发送主要控制请求开销，重试和弱网处理补充可靠性，整体上平衡数据的实时性、网络负担和上报可靠性。

### 7.4 **为什么在数据采集服务中选择使用 Kafka 作为消息队列？如何利用 Kafka 实现高并发数据传输和高可靠性？**

* **回答思路**：

  * **消息队列的必要性**：大量 SDK 数据直接写入数据库容易形成瓶颈，通过消息队列异步处理。

  * **Kafka 的优势**：高吞吐、低延迟、分区机制适合高并发传输，副本机制提高可靠性。

  * **topic 和 partition 的设计**：按数据类型划分 topic，通过 partition 分散处理压力，结合副本备份。

  * **消费端处理**：多实例并行消费，配合容错和重试，提高处理能力与稳定性。

**回答：**

我用 NestJS 实现 HTTP 数据接收服务，将 SDK 上报的统一事件交给 Kafka 异步处理，再写入 ClickHouse。引入队列，是为了把请求接收和后续的数据处理、存储分开，避免接收接口同步等待所有工作完成。

Kafka 的高吞吐、低延迟和分区机制适合集中上报的数据传输。按数据类型划分 topic，再通过 partition 分散处理压力；副本机制用于提高消息可靠性。

消费端可以部署多个实例并行处理，配合容错和重试，提高处理能力与稳定性。这些机制分别解决接收与处理解耦、并行消费和失败处理的问题。

我负责从 SDK 采集、队列上报到 NestJS 数据接收、Kafka 处理和 ClickHouse 存储的实现，通过统一事件协议贯通前后端。系统响应性能提升了 50%。

### 7.6 怎样处理 sourcemap 的问题？

* **回答思路：**

  * 构建时将 Sourcemap 上传至监控平台后台存储。

  * 处理异常时关联对应的 Sourcemap，借助 `source-map-js` 定位源码。

**回答：**

生产代码压缩后，异常堆栈中的文件和行列号指向构建产物，直接看这些位置很难找到原始代码，所以需要 Sourcemap 把产物位置映射回源码。

我接入了生产 Sourcemap 上传与版本映射。构建时生成 Map 并上传到后台保存，让运行中上报的异常能够关联到对应版本的映射文件。

处理堆栈时，先根据构建版本匹配 Map，再通过 source-map-js 查询原始文件和行列位置。这样就能从 SDK 采集到的压缩堆栈继续定位到源码，而不是停留在一条错误消息上。
