# 简历回答逐字稿：企业级类 Figma AI 设计与应用生成

>

## 30 秒开场

这个项目继续沿用我从复杂前端、资源契约和可执行模型中形成的思路：先建立稳定结构，再让不同客户端或 AI 消费。具体来说，我独立从 0 到 1 做了一套桌面端 AI 设计生成工具，它不是让模型直接吐前端代码，而是先把自然语言需求转换成结构化设计 DSL，再经过多智能体分区生成、文档组装和视觉验证，最后进入类 Figma 编辑器继续调整。

我主导并实现了编辑器内核、Agent 生成、MCP 接入和 Electron 交付四层架构。这个项目最核心的思路，是把 LLM 的不确定性限制在规划和内容生成阶段，把数据结构、状态流转、并发合并和质量门禁交给确定性程序控制。

## 1 分钟项目介绍

这个项目面向设计与前端协作场景。传统截图转代码只有像素信息，缺少布局结构、组件语义、设计变量和交互状态，所以我没有选择让大模型直接从截图生成最终代码，而是在中间建立一层设计 DSL。

我个人独立负责从需求分析、架构设计到核心模块实现。整个系统分四层：最底层是设计 DSL 和可视化编辑器；上面是基于 Codex CLI 的多智能体生成与 Visual Harness；再上面是只读 MCP、Bridge 和 Sidecar；最外层是 Electron 桌面应用及 macOS、Windows 构建交付。

一次生成任务会先由 Coordinator 把页面拆成多个互不重叠的区域，再由最多 5 个 Collaborator 并行生成 Fragment。系统通过 Design Variables、区域边界、JSON Schema、revision 乐观锁和固定组装顺序控制一致性。生成完成后，Visual Harness 会截图检查，按 nodeId 做最小范围修复，并设置最多 2 次重试，避免进入无限修复循环。

当前核心交付聚焦高质量设计 DSL 和可编辑设计文档。代码生成和设计代码双向同步在架构上预留了扩展空间，但我不会把它描述成已经完成的生产能力。

## 5 分钟完整讲法

### 1. 为什么做这个项目

这个项目解决的是设计生产链路里的两个问题。

第一个问题是设计和代码之间的信息断层。截图只能表达最终像素，无法完整表达节点层级、布局规则、设计变量和组件关系。让大模型直接从截图生成代码，输出很容易漂移，而且难以稳定验证。

第二个问题是 AI 生成结果不可直接信任。模型可以理解语义、提出布局和生成内容，但文档结构是否合法、多个 Agent 会不会互相覆盖、修复会不会引入新问题，都需要工程机制控制。

所以我的方案不是把所有事情都交给模型，而是建立“自然语言 → 结构化设计 DSL → 可视化编辑 → 验证修复”的受控链路。

### 2. 我的角色

这个项目由我个人从 0 到 1 独立开发。我负责需求分析、整体架构和核心模块实现，范围包括：

- 设计 DSL 与运行时校验；
- 类 Figma 可视化编辑器；
- Codex Provider 和 JSONL 事件流解析；
- Coordinator、Collaborator 与 Generation Run；
- 文档组装、revision 乐观锁和 Visual Harness；
- 只读 MCP Server、Bridge 与 Sidecar；
- Electron Main / Preload / Renderer 三入口构建；
- macOS / Windows 安装包及原生资源打包。

### 3. 编辑器内核与设计 DSL

DSL 是整个系统的单一数据契约。核心节点包括 Frame、Rectangle、Ellipse、Icon 和 Text。布局、视觉样式、变换属性和 Design Variables 分开建模，避免所有节点塞进一个不断膨胀的大对象。

类型层面使用可辨识联合，让 TypeScript 能根据 `type` 收窄节点；运行时再用 Schema 和 guard 校验 AI 输出、文件导入与用户数据。因为 TypeScript 类型在运行时不存在，AI 生成的数据不能只依赖编译期类型。

编辑器状态修改统一走 Command。每次命令基于不可变 Snapshot 生成新状态，再通过 Observer 通知图层面板、画布和属性面板。这样撤销重做、事务打包和多视图同步都有统一入口，不需要每个 UI 模块维护一份状态。

### 4. 多智能体生成链路

Agent 层通过 Codex Provider 隔离具体运行时。Provider 负责启动 Codex CLI 子进程、解析 JSONL 流、管理 Thread，并向上层返回统一事件。这样编排器不直接依赖某个 CLI 的进程细节。

Coordinator 只负责理解需求、拆分区域和分配 Assignment，不直接生成设计。最多 5 个 Collaborator 分别生成自己的 Fragment。拆分时要求任务、Agent、区域和顺序都唯一，区域之间不能重叠；固定的 `order` 保证并行任务无论先后完成，最终组装顺序都可预测。

一次 Generation Run 会经过 `queued → preparing → designing → validating → repairing → completed / failed / cancelled`。状态迁移必须通过合法性校验，UI 因此可以准确展示当前是在规划、生成、验证还是修复，异常也能定位到具体阶段。

### 5. 怎样控制并行一致性

多 Agent 的主要风险不是能不能并行，而是合并以后是否一致。我用了几层约束：

1. Coordinator 先划定每个区域的位置和尺寸；
2. 每个 Collaborator 只拥有自己的区域；
3. 所有 Agent 共享同一套 Design Variables；
4. 所有 Fragment 遵循同一份 DSL Schema；
5. 文档组装使用固定顺序和 revision 乐观锁；
6. 组装完成后再做一次全局视觉验证。

这样不是要求模型自己记住全部约束，而是把约束放进 Assignment、Schema、变量系统和组装器里。

### 6. Visual Harness

结构合法不代表视觉结果可用，所以在 Schema 校验之外，我又增加了 Visual Harness。

它先把完整设计截图交给多模态模型，按布局对齐、层级、文本可读性、色彩对比、组件完整性、变量一致性和边界溢出等维度输出结构化问题。每个问题都关联具体 nodeId。

修复阶段只允许修改问题节点，然后重新截图、重新验证。最多修复 2 次，超过上限就停止自动循环并保留问题，而不是让 Agent 一直修改。这里最重要的不是“让 AI 自己修”，而是最小改动、回归验证和有限重试。

### 7. MCP 与桌面端链路

MCP 层提供 `get_app_state`、`get_selected_node`、`get_nodes`、`get_screenshot` 和 `get_assets` 五类只读工具。结构化节点数据提供精确属性，截图和图片资产补充视觉上下文。

MCP Server 运行在独立 Sidecar 进程中，通过 Stdio 接入 Codex。设计状态在 Electron 应用内部，所以 Sidecar 再通过 Bridge 访问桌面应用：macOS 使用 Unix Domain Socket，Windows 使用 Named Pipe。

Bridge 统一处理请求 ID、10 秒超时、64MB 消息上限、9 类错误码和应用未启动时的优雅降级。每次请求使用独立连接，牺牲少量建连开销，换取更简单的生命周期和故障隔离。

### 8. 桌面端交付

Electron 分为 Main、Preload 和 Renderer 三层。主进程管理窗口、本地资源和 Bridge；Preload 通过 `contextBridge` 暴露受控 API；Renderer 只负责 React UI、编辑器和画布。

Sidecar 和 Schema 文件不能放进 ASAR，因此通过 `extraResource` 进入应用的 resources 目录。开发环境使用项目路径，打包后改用 `process.resourcesPath`。当前可以确认输出了 macOS 和 Windows 可运行安装包；Linux、签名、公证和自动更新不作为已完成交付。

### 9. 项目结果与边界

可以确认的结果是：完成了设计 DSL、可视化编辑器、多智能体生成、Generation Run、Visual Harness、只读 MCP、Bridge / Sidecar 和 Electron 双平台构建链路。

当前核心产物是 L1 设计 DSL 和可编辑设计文档。来源材料没有记录真实客户数量、用户规模、端到端耗时或质量统计，所以我不会用未经验证的效率倍数和合格率包装结果。

## 高频追问

### 如果面试官问：为什么不让大模型直接生成代码？

我会说直接生成代码的问题不是模型完全做不到，而是输出空间太大，而且设计意图缺少稳定中间表示。相同页面可以对应很多种 DOM、组件和样式组织方式，后续很难编辑、比较和验证。

加入 DSL 后，模型只负责生成受 Schema 约束的设计数据。编辑器、历史记录、视觉验证和后续代码映射都围绕同一份结构工作。这样把概率性生成和确定性执行分开，也让当前阶段可以先把 L1 设计资产做稳。

### 如果面试官问：为什么选择 Codex CLI，而不是直接调用 API？

我会说这个项目是本地桌面工具，需要访问设计文档、截图、Schema 和本地文件。Codex CLI 已经具备本地沙箱、文件系统访问、Thread 延续和 MCP 接入能力，比无状态 API 更符合这个场景。

代价是要管理子进程、JSONL 流、启动开销和资源占用。所以我没有让业务层直接调用 CLI，而是增加 Provider 抽象，把进程细节隔离起来。

### 如果面试官问：为什么用多 Agent，不用一个 Agent？

我会说复杂页面由单 Agent 串行生成时，上下文会越来越长，失败也容易导致整页重做。多 Agent 可以按互不重叠的页面区域拆分，每个 Collaborator 只处理自己的 Fragment，失败时也能局部降级或重试。

但我不会只讲并行的好处。它会引入风格漂移、区域冲突和合并顺序问题，所以系统同时需要 Design Variables、区域 ownership、唯一性校验、固定 order、revision 和最终验证。来源没有可核对的实测倍数，因此我只说并行缩短了架构上的关键路径，不声称提升了几倍。

### 如果面试官问：多 Agent 怎样避免相互覆盖？

我会先在规划阶段把页面拆成空间正交的区域，每个 Assignment 绑定唯一的 agentId、regionId 和 order。Collaborator 只生成自己的 Fragment，不直接修改完整文档。

组装器统一应用结果，并通过 revision 检查当前文档版本。如果版本不符合预期，就不能静默覆盖，需要合并或重试。最后再验证完整文档，而不是只验证每个局部结果。

### 如果面试官问：Visual Harness 和普通 Schema 校验有什么区别？

我会说 Schema 只能证明字段、类型和节点关系是否合法，不能证明文字有没有溢出、区域有没有错位、颜色对比是否合理。

所以 Visual Harness 处理的是第二类问题：先截图，再输出带 nodeId 的结构化 Visual Issue，然后做最小范围修复并重新验证。两层校验分别负责结构正确性和视觉可用性，不能互相替代。

### 如果面试官问：为什么修复最多只做 2 次？

我会说生成式修复不是单调收敛的，修复 A 可能引入 B。如果没有上限，系统可能无限消耗资源，甚至越修越乱。

因此我设置有限重试，并要求每次只修改指定节点、每次修改后重新做完整验证。超过上限就停止自动处理，保留剩余问题给用户，而不是为了追求自动化让系统失控。

### 如果面试官问：MCP 和 Function Calling 有什么区别？

我会从边界说。Function Calling 通常是某个模型 API 的调用能力；MCP 是工具提供方与 Agent 客户端之间的开放协议，包含能力发现、输入 Schema、调用和工具语义标注，并支持 Stdio 这种本地进程形态。

这个项目需要让本地 Agent 读取桌面应用里的设计资产，所以 MCP 更适合作为标准接入层。工具实现与具体 Agent Runtime 解耦，Codex 的接入已经可以通过标准配置完成。

### 如果面试官问：为什么 MCP 只读？

我会说设计文档是用户核心资产，开放写入不仅涉及权限，还需要事务、并发冲突、撤销和回滚。当前 MCP 的主要用途是让 Agent 读取节点、截图和资产，再进行设计理解或代码实现，只读已经覆盖核心读取场景。

所以我采用最小权限原则。所有工具都标记只读和幂等，写入仍通过编辑器已有的 Command 和历史机制完成。后续如果开放写入，也应该先接入 revision、事务和回滚，而不是让 Agent 直接改文档。

### 如果面试官问：为什么需要 Bridge 和 Sidecar？

我会说 MCP Server 由 Agent 客户端以独立进程启动，而设计状态在 Electron 应用里，两者生命周期和权限边界不同。Sidecar 负责在 Stdio 一侧讲 MCP，在另一侧通过本地 Socket 请求桌面应用，本身不保存业务状态。

Bridge 则把 macOS 的 Unix Domain Socket 和 Windows Named Pipe 封装成统一接口，并集中处理超时、大小限制、错误码和应用未启动等异常。这样协议层、跨平台通信和编辑器状态没有耦合在一起。

### 如果面试官问：Electron 打包 Sidecar 有什么坑？

我会重点讲两个。

第一，Sidecar 是原生可执行文件，操作系统不能直接执行 ASAR 内部文件，所以必须通过 `extraResource` 单独打包。第二，开发环境和打包后的资源路径不同，生产环境必须从 `process.resourcesPath` 解析，不能写死项目相对路径。

另外 macOS 和 Windows 需要各自构建对应二进制。当前可以确认的是 macOS、Windows 可运行安装包，不把 Linux 正式分发和签名流程说成完成事实。

### 如果面试官问：这个项目为什么可以叫“企业级”？

我不会用客户数量来证明，因为材料没有这类记录。我会从工程要求回答：它不是一个单轮 Prompt Demo，而是有统一 DSL、运行时校验、状态机、并发控制、历史持久化、视觉质量门禁、进程隔离、错误分级、安全边界和桌面端打包链路。

所以“企业级”在这里表达的是系统化的工程约束和可交付形态，不代表我可以声称已经有多少企业客户部署。

### 如果面试官问：你个人到底做了哪些部分？

我会明确回答：这个项目是我个人从 0 到 1 独立开发。我直接负责整体四层架构，以及 DSL、编辑器、Codex Provider、多智能体编排、Generation Run、Visual Harness、MCP、Bridge / Sidecar 和 Electron 构建链路。

同时我会主动说明当前范围：核心产物是 L1 设计 DSL 与可编辑设计文档；完整代码生成和 Design ↔ Code 双向同步是后续方向，实际用户和量化效果也没有足够记录支持我给出数字。

### 如果面试官问：项目还有哪些不足？

我会说当前主要有三类边界。

第一，核心产物仍是 L1 设计 DSL，L2 组件代码、L3 完整页面和双向同步还没有成为已完成交付。第二，本地 `.fig` 导入对 Auto Layout、组件实例、复杂矢量和样式去重等情况还需要继续完善。第三，正式分发所需的 Linux、签名、公证、自动更新以及真实使用指标还没有形成可确认记录。

如果继续演进，我会先保证 DSL 与编辑器稳定，再扩展代码生成和代码回读；同时补齐真实任务上的耗时、失败阶段、修复成功情况和人工接管比例，而不是先追求更复杂的 Agent 数量。

## 收尾句

这个项目对我最大的价值，不是做了一个类 Figma 界面，也不是转向纯 AI 或后端，而是把我从复杂前端、多端契约和可执行模型中形成的主线继续推进：让模型负责理解和生成，让 DSL、Schema、状态机、版本控制、进程边界和质量门禁负责确定性。
