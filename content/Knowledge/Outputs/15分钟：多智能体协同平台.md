## 30 秒开场

AI 编码加快了代码产出，也容易把需求理解、方案取舍和测试证据留在 Agent Session 里，Reviewer 最后只看到 diff。治理型 Agent Harness 的目标，是把交付拆成可观察阶段，沉淀计划、工具调用、文件变更和测试证据，再用 Gate 与人工审批控制继续、退回或接管。

## 2 分钟技术方案

这个方案关注 AI 参与软件交付以后，需求、方案、实现、测试和责任边界容易断开的问题。Agent 是否足够聪明并不是重点。单个长 Session 会混合规划、编码和审查；高频工具事件也很难直接成为团队可以判断的稳定状态。

流程可以拆成“需求澄清 → 计划设计 → 受控开发 → 证据审查 → 门禁放行”。Planner 只产出计划、验收标准、风险和文件范围；Dev Agent 在计划边界内修改代码，并记录命令、文件变更和测试结果；Review Guard 使用最初的验收标准、diff 和证据做比对；Gate 决定继续、退回、暂停或转人工。

运行时需要把 token、工具调用和日志归并成稳定的阶段状态。每一步形成 Trace，记录输入、输出、依赖、工具结果和文件变化。摘要层只保留任务目标、当前阶段、关键证据入口和恢复位置，需要细节时再沿 Trace 下钻，而不是反复把完整聊天历史塞回上下文。

权限也要跟阶段绑定。Planner 不写代码，Dev Agent 只能改计划范围内的文件，Review Agent 只读证据；高风险命令、越界变更和证据缺失需要 Gate 或人工确认。重试必须有次数与退出条件，不能让 Agent 无限自我修复。

效果不能靠“提升多少倍”证明。可以检查 Review 输入是否从单一 diff 变成 `diff + plan + evidence + trace`，任务中断后能否定位具体步骤，以及 Gate 是否真的能拦截缺测试和越界修改。这些都是验证口径，不代表当前已有项目数据。

## 5 分钟主讲法

### 1. 为什么聊天记录不足以支撑交付

软件交付有需求、方案、编码、测试和 Review 等阶段，每一步的责任与退出标准不同。把它们都塞进一个 Agent Session，出错后很难判断问题来自需求理解、计划还是实现。

Reviewer 需要的也不只是最终 diff，还要知道最初验收标准、修改范围、执行过的命令、失败记录和测试证据。

### 2. 用阶段对象代替长对话

中心任务对象可以管理五个阶段：需求澄清、计划设计、受控开发、证据审查和门禁放行。每个阶段都有结构化输入、输出、负责人和退出条件。

Planner 不能直接写代码；Dev Agent 只能在批准的范围内修改；Review Guard 对照验收标准、计划、diff 与测试记录；Gate 根据证据和风险决定继续、退回或人工接管。这样 Agent 承担有限职责，而不是自己决定整条流程。

### 3. 高频事件怎样变成稳定状态

Agent 会持续产生消息、工具调用、命令输出和文件变化。系统不能把原始事件流直接当作协作状态，需要按阶段聚合成“已经完成什么、证据在哪里、风险是否关闭、能否继续”。

状态机负责合法迁移，事件可以缓冲和批量写入，但关键工具结果、文件变更与失败原因不能丢失。UI 展示的是阶段状态与证据入口，不需要把每个 token 都变成业务事件。

### 4. Trace 与 Memory 怎样支持恢复

Trace 记录每一步的输入、输出、依赖、耗时、工具结果和文件变化。Memory 更适合做分层索引：底层保留原始命令与测试日志，中间层保存 Trace 和 Session Digest，上层只保留任务目标、当前阶段、关键证据和恢复路径。

人类或后续 Agent 先读摘要，不够时再逐层下钻。任务中断后，恢复动作必须基于最近一个通过退出条件的阶段，而不是盲目续写上一段对话。

### 5. 多 Agent 拓扑怎样选择

主流程适合 Chain，阶段调度由 Orchestrate 管理，Gate 使用 Route 决定继续或退回。Hierarchy 只在复杂任务中做受限委派；Loop 只用于失败恢复，并设置最大轮次；Parallel 只适合安全、性能、测试等相对独立且结果可以合并的审查任务。

并行数量越多不代表效果越好。上下文、权限和责任范围必须隔离，否则多个 Agent 只会放大噪声。

### 6. 权限、证据和人工介入

工具权限应根据阶段最小化。Planner 只能读需求和代码上下文，Dev Agent 获得受限写入与命令权限，Review Guard 保持只读。计划外文件、危险命令、缺少测试和高风险变更需要 Gate 拦截。

审查证据要保留来源与验收标准的对应关系。大模型输出的 Markdown、HTML 或 diff 还要经过安全渲染，不能因为它出现在 Review 页面就默认可信。

### 7. 怎样验证方案是否有用

验证可以看四件事：Review 是否拿到计划、diff、证据和 Trace；任务中断后是否能定位到具体步骤；后续 Agent 是否能通过分层摘要恢复；Gate 是否能拦截缺测试、越界文件和未满足验收标准的变更。

这些只是建议的验证口径。没有真实任务记录、拦截样例和恢复测试之前，不能声称平台已经产生业务效果。

## 深挖方向

- 高频事件怎样归并为阶段状态。
- 超大 Trace 怎样按阶段、风险和文件下钻。
- Session Digest 与原始证据怎样分层。
- 节点输入、输出和人工补充项怎样用 Schema 描述。
- Gate 怎样把验收标准、diff 和测试证据串成放行依据。

## 收尾句

治理型 Agent Harness 关注的是 AI 交付过程能否被看见、审查和接管。Chain、Trace、Memory 和 Gate 都是设计手段；在事实证据补齐前，这份内容只作为系统设计回答，不作为个人项目成果。
