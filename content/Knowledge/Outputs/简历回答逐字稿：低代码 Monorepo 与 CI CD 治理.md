# 简历回答逐字稿：低代码 Monorepo 与 CI CD 治理

关联：[[简历追问：低代码 Monorepo 与 CI CD 治理]]、[[15分钟：低代码平台]]。

> [!warning] 回答边界
>
> - 项目材料记录的是 pnpm workspace + Turborepo，不是 Nx。
> - 我已确认的个人核心贡献是领域模型、资源契约、工作流前端和相关 TypeScript 执行引擎。
> - Docker、CI/CD 和全栈 Monorepo 可以用于说明整体工程结构与个人理解，但不能说成个人独立负责的生产成果。

## 30 秒开场

项目使用 pnpm workspace 和 Turborepo 组织核心包与应用入口，让共享协议、TypeScript 引擎和前端应用保持版本一致，并通过任务图与缓存减少重复构建。这只是工程背景；Docker 和 CI/CD 不是我的个人成果，我的直接工作仍是模型、契约、编辑器和执行引擎。

## 如果面试官问：仓库怎么分层？

仓库按 `packages` 与 `apps` 划分职责。`packages` 放工作流协议、TypeScript 执行引擎和可复用模块，`apps` 放编辑器、API 服务等应用入口；应用可以依赖核心包，核心包不能反向依赖具体应用。

材料能确认 pnpm workspace 和 Turborepo 的任务编排，但不能确认采用了 Nx `enforce-module-boundaries`，所以不再使用 Nx 规则作为项目事实。

## 如果面试官追：依赖版本冲突怎么处理？

合库时比较典型的问题是多个 React 实例或三方库版本不一致。我的策略是核心技术栈尽量单版本，比如 React、ECharts 这类基础依赖在根 package 管理。

对于 core engine、UI 插件这种被宿主使用的包，React 这类库应该放在 peerDependencies，让运行时只用宿主提供的一份实例，避免 Hooks 因为多 React 实例报错。

同时启用 pnpm 的严格模式，禁止幽灵依赖。代码里用了某个包但 package 没声明，就应该在开发阶段报错，而不是靠 node_modules hoist 侥幸跑通。

## 如果面试官追：Turborepo 缓存怎么保证可靠？

任务输入需要覆盖源码、依赖版本、构建配置和关键环境变量，否则可能命中错误缓存。纯构建、类型检查和单测更适合缓存；依赖外部环境的 E2E 与部署动作要谨慎。

这是我对工程方案的理解。现有已确认事实没有把缓存命中率、affected 构建或 CI 流水线列为个人交付，因此不会补充未经确认的实施细节。

## 如果面试官追：Docker 多阶段构建怎么优化？

Docker 多阶段构建属于项目整体部署链路，不是我的核心个人交付。方案上通常把依赖安装、构建和运行镜像拆开，只把运行所需产物带进最终镜像。

没有材料支持镜像体积或构建耗时数据，因为现有材料没有个人负责范围和可核对数据。

## 如果面试官追：插件和 core 版本不兼容怎么办？

现有已确认事实没有确认插件兼容矩阵和灰度升级由我实现。

从架构上，可以让插件声明 core 版本范围，并在构建时校验；核心 API 变更提供 deprecation 周期和迁移方案。灰度与回滚也需要纳入发布治理。这些只能作为工程理解，不是个人已完成成果。

## 收尾句

这部分只用于说明我对项目工程结构的理解。个人生产成果仍以领域建模、资源契约、工作流编辑器和 TypeScript 执行引擎为主，不把完整 Monorepo、Docker 和 CI/CD 治理都归到自己名下。
