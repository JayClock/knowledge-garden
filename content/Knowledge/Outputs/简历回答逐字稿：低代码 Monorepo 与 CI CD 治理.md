# 简历回答逐字稿：低代码 Monorepo 与 CI CD 治理

关联：[[简历追问：低代码 Monorepo 与 CI CD 治理]]、[[项目介绍：企业级低代码工作流引擎]]。

## 30 秒开场

项目使用 pnpm workspace 和 Turborepo 组织核心包与应用入口，让共享协议、TypeScript 引擎和前端应用保持版本一致，并通过任务图与缓存减少重复构建。在团队协作中，我主要负责业务模型、契约定义、编辑器与执行引擎的实现，并协同推进整体工程规范。

## 如果面试官问：仓库怎么分层？

仓库按 `packages` 与 `apps` 划分职责。`packages` 放工作流协议、TypeScript 执行引擎和可复用模块，`apps` 放编辑器、API 服务等应用入口；应用可以依赖核心包，核心包不能反向依赖具体应用。包间依赖方向通过明确的架构分层与构建约束保持单向清洁，避免循环依赖。

## 如果面试官追：依赖版本冲突怎么处理？

合库时比较典型的问题是多个 React 实例或三方库版本不一致。我的策略是核心技术栈尽量单版本，比如 React、ECharts 这类基础依赖在根 package 管理。

对于 core engine、UI 插件这种被宿主使用的包，React 这类库应该放在 peerDependencies，让运行时只用宿主提供的一份实例，避免 Hooks 因为多 React 实例报错。

同时启用 pnpm 的严格模式，禁止幽灵依赖。代码里用了某个包但 package 没声明，就应该在开发阶段报错，而不是靠 node_modules hoist 侥幸跑通。

## 如果面试官追：Turborepo 缓存怎么保证可靠？

任务输入需要覆盖源码、依赖版本、构建配置和关键环境变量，否则可能命中错误缓存。纯构建、类型检查和单测更适合缓存；依赖外部环境的 E2E 与部署动作要谨慎。

## 如果面试官追：Docker 多阶段构建怎么优化？

在部署链路中，团队通常采用 Docker 多阶段构建，将依赖安装、编译打包与运行镜像解耦，最小化生产运行镜像体积。

## 如果面试官追：插件和 core 版本不兼容怎么办？

从架构设计上，插件应声明兼容的 core 版本范围，并在构建与加载时执行兼容性校验；核心 API 变更遵循语义化版本和渐进废弃（deprecation）周期，确保平台平滑演进。

## 收尾句

良好的 Monorepo 与工程分层，为工作流引擎的核心包抽象、多应用复用与类型安全交付提供了稳固的底座支撑。
