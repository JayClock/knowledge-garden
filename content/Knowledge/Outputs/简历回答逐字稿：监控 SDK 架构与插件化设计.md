# 简历回答逐字稿：监控 SDK 架构与插件化设计

关联：[[简历追问：监控 SDK 架构与插件化设计]]、[[项目介绍：前端埋点与监控 SDK]]。

## 30 秒开场

我负责监控 SDK 的采集与上报侧，把“系统怎样证明契约被正确执行”固化为事件与上下文协议。设计时先确认验收和诊断需要什么证据，再由 core、browser 和 React／Vue 适配包共同消费；AI Flow 中通过 `executionId` 关联校验、测试、发布事件与节点执行日志。服务端数据存储与监控后台由后端团队协同支持。

## 如果面试官问：为什么要拆 core、browser 和框架适配包？

三层面对的变化不同。core 是框架无关的协议和运行时，不应该依赖 DOM、React 或 Vue；browser 封装 PerformanceObserver、全局错误、DOM、Fetch 和 XHR 等浏览器能力；React／Vue 适配包只负责框架生命周期和错误边界等接入差异。

这样新增监控项时只需要在采集插件和统一协议中扩展，不需要在每个框架里重新实现。核心包也不会因为某个框架升级而被迫变化。

## 如果面试官问：插件化体现在哪里？

性能、异常、点击和请求采集分别是独立能力，由核心 SDK 完成初始化和注册。插件只负责采集特定事件，统一交给协议与 Transport；发送逻辑与采集逻辑解耦。

## 如果面试官问：Transport 为什么要独立？

采集关注“发生了什么”，Transport 关注“怎样发送”。如果两者耦合，每个采集插件都要重复处理请求、批量和失败逻辑，也很难替换浏览器与其他环境的发送方式。

核心包定义 Transport 接口，浏览器包提供具体实现。采集事件先进入统一协议和队列，再由 Transport 批量发送。这样新增采集项不会影响上报通道，调整发送策略也不会修改每个插件。

## 如果面试官问：自动采集和业务自定义怎样分工？

Web Vitals、全局异常、Fetch／XHR 和通用操作适合自动采集，因为它们有稳定的浏览器语义。只有业务自己知道的事件，需要从下游要完成的验收或诊断倒推，再通过自定义事件或自定义错误补充。

AI Flow 是已确认的业务接入：为了区分用户在工作流校验、测试运行还是发布环节失败，我为这些关键路径添加自定义事件。

## 如果面试官问：AI Flow 的前端埋点怎样关联执行日志？

前端 SDK 负责记录工作流校验、测试运行和发布路径，执行引擎日志负责节点状态、耗时与错误；两侧使用同一个 `executionId` 关联。这样验收可以从用户操作继续定位到具体执行节点，同时避免把可能丢失的浏览器事件当成服务端执行结果的唯一事实源。

## 如果面试官问：怎么保证 SDK 不影响业务？

core 与采集插件保持较小职责，采集回调只读取必要数据；Fetch／XHR 代理保留原始参数、返回值和错误语义；事件先进入队列，再批量发送，避免在高频交互中同步发请求。

SDK 自身异常时最多丢失监控数据，不能阻断业务事件或请求。通过严格的沙箱隔离与批量机制，保障对宿主运行的极低侵入。

## 如果面试官问：完整监控平台哪些是你做的？

我的工作是 SDK 的采集与上报侧，包括从下游证据需求倒推业务事件、多包架构、框架适配、性能与异常采集、操作和请求采集、统一协议及本地队列。AI Flow 的校验、测试运行、发布事件与 `executionId` 关联是一个实际接入实例。

服务端数据接收、存储与监控大盘由后端及大数据团队负责，我负责端侧采集上报规范与完整数据契约的对接。

## 如果面试官问：这个 SDK 怎样体现渐进式增强？

我先把统一事件、插件协议、队列和 Transport 放在框架无关的 core，再由 browser 接入 Performance、Error、DOM、Fetch 和 XHR，React、Vue 与 Vanilla 只补各自生命周期。这样同一核心协议可以被不同能力的宿主按需增强，新增采集项也不必复制每个框架实现。

更重要的是监控不能反过来成为业务成立的前提：请求代理必须保留原始参数、返回值和异常语义，SDK 自身失败最多损失监控数据，不能阻断宿主业务，确保了监控基础设施在复杂异构环境中的稳健运行。

## 收尾句

这个 SDK 不只是把采集能力做成插件，还把下游验收和诊断所需的证据固化为多端可消费的事件契约；在 AI Flow 中，再用 `executionId` 把前端路径与执行事实连接起来。
