# 简历回答逐字稿：监控 SDK 架构与插件化设计

> [!warning] 回答边界
>
> - 已确认的个人实现是核心包、Vanilla / React / Vue 适配、插件化采集、统一协议和可靠上报。
> - `data-track-event`、Shadow DOM、iframe、微前端去重和远程开关没有进入当前职业主档，只能作为扩展讨论。

## 30 秒开场

我做这个监控 SDK 时，重点不是做一个大而全的数据平台，而是做一套业务前端可以低侵入接入、且不会改变主业务行为的采集基础设施。

架构上我拆成 core 与框架适配包。core 负责统一协议、插件生命周期、采集队列和上报；Vanilla、React、Vue 适配包负责不同运行环境的接入。性能、异常、接口和操作采集都围绕同一协议输出，数据服务和控制台由其他同事负责。

## 如果面试官问：自动采集和手动 `track()` 怎么分工？

我会说性能、全局异常、Fetch / XHR 和通用操作适合由插件自动采集；只有业务才能判断的语义事件，可以通过自定义上报补充。

这样公共能力不需要每个功能重复实现，同时不会让 SDK 猜测所有业务含义。`data-track-event` 是一种可能的声明方式，但现有材料不足以证明项目采用了它，所以不作为生产事实。

## 如果面试官追：core 包和适配包怎么拆？

我会这样说：

core 不依赖 React/Vue，它只提供：

- SDK 初始化和配置。
- 公共上下文管理，比如 user、tenant、session、route、app version。
- 事件队列和上报通道。
- 插件注册、执行和 teardown。
- 错误隔离与降级。

React 适配包可以提供 hook 或 Provider，自动接路由上下文；Vue 适配包可以提供 plugin install；Vanilla 只提供直接初始化。这样 core 体积更可控，也避免为了某个框架引入额外依赖。

## 如果面试官追：插件接口怎么设计？

我会说插件不是随便执行一段代码，应该有生命周期。下面是用于解释机制的简化接口，不是生产代码的逐字还原：

```ts
type MonitorPlugin = {
  name: string
  setup(ctx): void
  teardown?(): void
  onEvent?(event): event | void
  beforeSend?(batch): batch
  onError?(error): void
}
```

比如点击采集、曝光采集、Web Vitals、Fetch/XHR 监控都可以是插件。每个插件内部出错不能影响主业务，也不能影响其他插件。SDK 会在插件调用外层做隔离，插件失败最多丢监控，不拖垮页面。

## 如果面试官追：操作采集怎么避免影响业务？

我会说操作采集必须保留原始事件行为，采集逻辑只读取必要上下文并进入队列，发生异常时直接降级，不能阻止冒泡或修改业务处理结果。

事件委托、`composedPath()`、Shadow DOM 和 iframe 适配可以用于讨论复杂场景，但现有职业主档只确认了 DOM 操作代理和统一上下文，不把这些细节说成全部已经上线。

## 如果面试官追：微前端重复初始化怎么办？

我会先说明现有材料没有确认微前端接入和重复初始化治理已经落地。

如果讨论扩展方案，可以通过 appId、实例命名空间和全局监听责任边界避免重复采集；跨域 iframe 还需要受控的 `postMessage`。这部分只能作为设计思路。

## 收尾句

所以这个 SDK 的核心不是一个 `track()` 方法，而是一套低侵入、可插件化、可隔离、可降级的采集运行时。可以确认的个人成果是多框架 SDK、统一采集协议和可靠上报，不包含后端数据平台与控制台实现。
