# 简历回答逐字稿：渐进式架构与可恢复增强

关联：[[简历回答逐字稿：契约驱动的全流交付]]、[[简历追问：渐进式架构与可恢复增强]]、[[全栈工程师简历候选人回答逐字稿]]。

> [!warning] 回答边界
>
> - 契约驱动的全流交付是职业主轴；这里的“渐进式”是契约演进的支撑方法：先稳定核心任务、模型或协议，再隔离变化能力，并为失败和迁移保留边界。
> - 不把代码分割、骨架屏、流式渲染或插件化自动等同于严格的 Progressive Enhancement；只有增强缺失时基础任务仍成立，才能作严格表述。
> - 不声称 Canvas、协同编辑器或 SPA 在没有 JavaScript 时仍能完成全部任务。
> - 文中的“建议补强”是后续证据和工程工作，不是已经上线的成果。

## 30 秒总回答

在契约形成、消费、执行和验证的主线上，我会先稳定不能失效的核心任务、模型或协议，再把多端 relation、节点插件、框架适配和 AI Proposal 放到可独立演进的增强层。增强通过运行时契约、状态或版本接入，失败时由迁移退路、人工确认、有限重试或错误隔离收住。它解决的是契约怎样安全演进，不替代契约本身的知识来源、权威方、消费方和验证责任。

## 这项能力具体解决什么

```text
核心任务／模型／协议
→ 可独立成立的稳定基线
→ relation、adapter、plugin、collaboration、AI 等增强层
→ runtime check、revision、人工 Gate 与反馈证据
→ 增强失败时回退、局部失败或返回正确阶段
```

我不把“渐进式”理解成单纯的加载顺序，而是用它回答四个架构问题：

1. 最小但完整的核心能力是什么；
2. 哪些变化应该隔离为增强，而不是侵入核心；
3. 客户端或使用者怎样发现、选择和确认增强；
4. 增强缺失、失败或升级时，系统怎样保持可解释、可恢复和可演进。

## HATEOAS：资源基线与多端按需消费

### 可以直接说

PC Web 与移动 Web 原来分别维护状态、权限和动作规则。我先把资源数据和生命周期稳定下来，再由 `_links` 与 `_templates` 声明当前可访问关系和合法动作，TypeScript SDK 用 `follow()`、`action()` 和运行时检查统一消费。迁移时先选工作区导航，只改 API 表达层，并保留 BFF 作为退路，避免一次性重写所有接口和客户端。

### 对应的渐进式结构

- **稳定基线：** 资源、URI、状态和业务生命周期；
- **增强声明：** relation 与 action；
- **消费适配：** TypeScript SDK 与 React Hooks；
- **失败／迁移边界：** relation 运行时检查、缓存失效、契约测试和 BFF 退路。

### 还需补强

- 旧客户端忽略新增 relation 的兼容用例；
- action 缺失、过期或提交冲突时的 UI 恢复矩阵；
- 实际资源数、action 数和回归范围变化。

## AI Flow：稳定执行协议与节点能力扩展

### 可以直接说

AI Flow 先用 `WorkflowDefinition`、Node、Edge、节点 Schema、变量协议和 `ExecutionContext` 统一编辑器与执行器，再通过 `NodeRegistry + NodeExecutor` 接入 HTTP、Condition 等节点策略。调度核心统一处理图校验、变量解析、错误捕获、耗时和输出存储，新增节点不需要继续修改核心 `switch-case`。监控 SDK 和 SSE 界面在执行协议之上补充用户路径与运行反馈。

### 对应的渐进式结构

- **稳定基线：** 工作流协议、图校验、拓扑调度和执行上下文；
- **增强能力：** 节点执行器、配置表单、变量编辑器和运行反馈；
- **隔离机制：** 注册器、执行器抽象和统一错误边界；
- **事实边界：** NestJS API 与 SSE 服务端由后端同事实现。

### 还需补强

- 未知节点的只读／降级展示；
- 插件加载失败不影响基础画布的验证；
- 日志查询作为基础反馈、SSE 作为实时增强的可用性验证；
- 节点版本迁移和历史流程兼容测试。

## 多人领域建模：人工模型基线与 AI 候选增强

### 可以直接说

领域建模平台先把参与方、角色、权责和 Evidence 固化为前端与后端共同审核的业务语义契约，再增加 Yjs 协同和 AI Proposal。Yjs 只负责副本收敛，AI 只生成结构化候选；用户逐项采纳后才进入草稿、版本和发布。发布模型可以继续支持 OpenAPI 草稿和测试数据，但正式接口契约仍由人审核。

### 对应的渐进式结构

- **稳定基线：** 结构化领域模型、草稿、版本和发布；
- **协作增强：** Y.Doc 与 Awareness；
- **AI 增强：** 节点和关系 Proposal；
- **控制边界：** CRDT 不替代语义审核，AI 不直接覆盖正式模型。

### 还需补强

- AI 服务不可用时，人工建模、协同和发布主链路的验证；
- 协同断线、服务重启和恢复测试；
- 实际协作人数、模型规模和使用频率。

## Figma AI：可编辑文档基线与可失败的生成增强

### 可以直接说

Figma AI 先以设计 DSL 建立产品设计与前端实现之间的设计契约，再提供 Canvas 编辑器、命令历史和可编辑文档。多 Agent 只产生受 ownership、regionId 和 revision 约束的 Fragment；Visual Harness 只修复具体问题节点，最多两轮，超过上限保留当前文档和 Run 历史交给用户。只读 MCP 提供外部消费，但不绕过编辑器的事务和撤销边界。

### 对应的渐进式结构

- **稳定基线：** 设计 DSL、可编辑文档和手工编辑器；
- **生成增强：** Coordinator、Collaborator 和 DesignPatch；
- **质量增强：** Visual Harness；
- **外部消费增强：** 只读 MCP、Bridge 和桌面端；
- **失败边界：** revision、有限修复、取消、历史和人工接管。

### 还需补强

- 无 AI 情况下从导入、编辑到保存的完整回归；
- 生成失败阶段、修复结果和人工接管比例；
- 实际任务规模、端到端耗时和质量指标。

## 监控 SDK：核心协议与异构客户端适配

### 可以直接说

监控 SDK 把统一事件、插件协议、队列和 Transport 放在 core，把 Performance、Error、DOM、Fetch 和 XHR 放进 browser，再由 React、Vue 和 Vanilla 适配各自生命周期。采集插件和发送通道彼此隔离，新增监控项不需要复制各框架实现；代理保留原始请求语义，SDK 自身失败不能阻断业务。

### 对应的渐进式结构

- **稳定基线：** 统一事件、队列和 Transport；
- **环境增强：** browser 能力；
- **框架增强：** React、Vue 和 Vanilla 适配；
- **业务增强：** AI Flow 自定义事件与 `executionId`；
- **失败边界：** 错误隔离、批量队列、失败重试和宿主业务优先。

### 还需补强

- `PerformanceObserver` 等能力的 capability detection；
- 单个插件异常和 Transport 失败的 fail-open 测试；
- 上报成功率、采集开销和异常定位效果。

## 协同文档编辑器：Core SDK 与多层消费接口

### 可以直接说

协同文档编辑器先在 ProseMirror／Tiptap 上封装 Schema、Block API、Transaction、Command 和扩展协议，再由 React 包提供组件、Context 与 Hook，UI 包提供工具栏和建议菜单。Yjs 协同、Mention 关系图、Dify 写回和 Tauri 桌面端继续消费同一编辑器内核，而不是让每个界面维护自己的文档语义。

### 对应的渐进式结构

- **稳定基线：** 编辑器 Core SDK 与文档事务；
- **界面增强：** React 与 UI 套件；
- **协作增强：** Yjs、Awareness、WebSocket 和持久化；
- **知识／AI 增强：** Mention 关系图与 Dify 写回；
- **交付增强：** Web 与 Tauri 桌面工程。

### 还需补强

- 协同服务不可用时的单人编辑或只读策略；
- 自动化协同 E2E、断线重连和服务重启恢复；
- 文档规模、协同延迟和峰值连接数。

## Evidence：确定性项目循环与受限 Agent 增强

### 可以直接说

Evidence 先由 Server 权威状态机、不变 Revision、Approved Tasking Plan 和人工决定建立项目基线，再让短生命周期 Agent 执行当前唯一 `nextAction`。Agent 只能提出 Candidate 或在批准边界内执行 Test、Production、Refactor；异常按证据回测试、实现或 Tasking，预算和边界违规会 fail closed。质量门通过后仍需人工检查完整 diff 和 Showcase 价值判断。

### 对应的渐进式结构

- **稳定基线：** 项目权威状态、版本、计划和人工决定；
- **执行增强：** 受限 Agent 和独立 Reviewer；
- **反馈增强：** 测试、日志、哈希、质量门和 Showcase；
- **失败边界：** 唯一下一步、允许路由、有限预算和 fail closed。

### 事实边界

Evidence 是公开维护项目，不等同于生产规模化使用；当前完整 Modeling Profile 尚未完成，最新核对的主 CI 也不是全绿。

## 按岗位选择项目

### 高级前端／前端架构

1. HATEOAS：多端契约与渐进迁移；
2. Figma AI：复杂 Canvas 与可恢复 AI 增强；
3. 监控 SDK 或协同文档：跨框架协议与编辑器内核；
4. AI Flow：插件化执行平台。

### AI 工程化平台

1. Figma AI：DSL、多 Agent、revision 和 Visual Harness；
2. Evidence：权威状态、人工 Gate 和失败路由；
3. 领域建模：人工模型与 AI Proposal；
4. AI Flow：可执行协议与运行反馈。

### 全栈偏前端的平台工程

1. AI Flow：协议、复杂前端、执行和数据链路；
2. HATEOAS：模型、API 契约与多端消费；
3. 领域建模：React Flow、协同服务和持久化；
4. Figma AI：AI 工程化与桌面交付；
5. 监控 SDK 作为横向验证能力嵌入主项目。

## 收尾句

这些项目表面上分别是低代码、SDK、协同、设计工具和 Agent Harness，背后的共同能力是先建立稳定基线，再把变化能力做成可消费、可验证、可失败和可继续演进的增强层。它不是要求所有系统都能无 JavaScript 运行，而是避免让所有能力同时成为系统成立的脆弱前提。
