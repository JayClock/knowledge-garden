# 简历回答逐字稿：监控 SDK 性能与异常采集

关联：[[简历追问：监控 SDK 性能与异常采集]]、[[项目介绍：前端埋点与监控 SDK]]。

## 30 秒开场

性能和异常采集先保证不伤害主业务。SDK 使用 PerformanceObserver 与 Web Vitals 采集核心指标，通过全局 error 和 `unhandledrejection` 获取运行期异常，再旁路记录 DOM、Fetch、XHR 和导航上下文。事件进入本地队列批量发送，生产堆栈结合构建版本和 Sourcemap 还原到源码。

## 如果面试官问：Web Vitals 怎么采？

这些指标需要回到用户体验解释。FCP 看首次内容出现，LCP 看主要内容加载，CLS 看布局稳定，TTFB 看服务端响应，INP 看交互响应。实现上使用 PerformanceObserver 和 Web Vitals API，在指标更新时生成统一事件。

采集时需要控制回调成本，不能在 Observer 里做重聚合和同步网络发送。SPA 场景还要先定义是首屏指标还是自定义路由视图指标，不能把浏览器原生 LCP 直接套到每次路由切换。

## 如果面试官问：异常怎样覆盖？

全局错误监听覆盖未捕获的 JavaScript 错误，`unhandledrejection` 覆盖未处理 Promise，业务还可以主动上报自定义异常。事件需要统一携带消息、来源、位置、堆栈、页面和构建版本等上下文。

不同错误不能只记录一段字符串。至少要区分运行期异常、Promise 异常、请求失败和业务自定义错误，后续数据服务才能过滤、分类和分析。

## 如果面试官追：Fetch／XHR 代理会不会影响业务？

这是最需要小心的地方。代理只能记录请求 URL、耗时、状态码和错误上下文，必须保留原始调用参数、返回值、Promise 状态和异常语义。

监控代码要走旁路并做好错误隔离。即使采集失败，也要继续执行原请求，不能吞掉错误或改变业务结果。读取响应体也需要谨慎，因为直接消费 stream 可能让业务无法再次读取；没有必要时只记录元信息。

## 如果面试官问：上报请求数怎么控制？

事件先进入本地队列，不是每发生一次就立即发送。队列可以按时间间隔出队，也可以在数量达到阈值或路由变化时合并上报。

批量能够减少请求数，但会增加延迟和丢失窗口，所以需要根据事件重要性设置策略。网络异常时进行失败重试，同时控制重试节奏，避免恢复后瞬间放大流量。

## 如果面试官问：Sourcemap 怎样定位生产异常？

构建后的代码已经压缩和混淆，生产堆栈只能指向产物位置。构建阶段需要生成 Sourcemap 并与应用版本、产物文件关联，监控侧再根据行列号还原原始源码位置。

同时要注意源码安全：映射文件用于受控的监控处理，不应该直接公开给终端用户。没有版本和文件映射，即使上传了 Sourcemap 也可能匹配到错误构建。

## 如果面试官问：SDK 自身性能怎样控制？

控制点分三层：包边界按 core、browser 和框架适配拆分；运行时采集回调保持轻量；发送侧进入队列后批量和延迟处理。

效果不能靠“代码不多”证明，需要观察包体、初始化耗时、长任务、首屏指标和高频交互开销。通过精细的控制机制，保证了监控系统自身对宿主业务性能影响最小化。

## 收尾句

这部分需要在采集覆盖率、数据准确性、主业务无害性和上报开销之间做平衡，再用 Sourcemap 把运行证据还原成可定位的问题。
