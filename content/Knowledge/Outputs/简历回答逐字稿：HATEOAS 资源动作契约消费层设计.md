# 简历回答逐字稿：HATEOAS 资源动作契约消费层设计

关联：[[职业经历]]、[[全栈工程师简历]]、[[简历追问：HATEOAS 资源动作契约消费层设计]]、[[15分钟：HATEOAS 资源契约架构]]。

> [!warning] 回答边界
>
> - 真实业务资源是应用、表单、工作流和工作区导航，消费端是 PC Web 与移动 Web。
> - 我负责领域模型、资源关系、动作契约和 TypeScript SDK，并与后端共同落地 API 表达；服务端实现不是个人编码成果。
> - Agent tools、读模型、物化视图以及订单审批示例属于延展或示意，不作为上线事实。

## 30 秒开场

我当时做这块，不是为了追求 HATEOAS 这个概念，而是为了解决 PC Web 与移动 Web 的状态和权限规则漂移。应用、表单和工作流都有编辑、发布、撤销等动作，工作区导航也会随角色和权限变化。以前各端会根据 `status`、`role`、`permission` 重复判断，后端规则一改，多个前端都要联动修改和回归。

所以我的思路是把“当前资源能访问什么、能执行什么”放回资源表达。后端通过 `_links` 和 `_templates` 返回当前上下文下的导航关系、合法动作和 payload 约束；前端消费 `publish`、`revoke` 等 relation，而不是再实现一份业务状态机。

## 如果面试官问：为什么一个前端问题最后会走向建模和 RESTful API？

因为 SDK 只能统一消费方式，不能把一个本身混乱的接口变稳定。真正设计 relation 时，我需要先回答资源是什么、生命周期如何变化、当前角色在什么状态下可以做什么。如果这些问题不清楚，`_links` 最后只会变成按钮数组，HATEOAS 也只是换一种形式复制混乱。

所以我的能力是从前端消费层逐步向上游延伸的：先解决 PC Web 与移动 Web 的规则漂移，再因为 relation 稳定性问题参与业务／领域建模，从应用、表单、工作流和工作区导航的业务事件中识别资源边界，最后设计 RESTful URI 与动作契约，并和后端共同落实到 API 表达层。

这不是我转向纯后端，而是为了从源头控制复杂前端所消费的业务知识。服务端代码仍由后端同事实现，我直接负责的是模型、契约、SDK 和客户端消费。

## 如果面试官问：你具体怎么设计 `_links` 和 `_templates`？

我会这样说：

`_links` 主要表达资源导航和动作入口，比如 `self`、`workflow`、`publish`、`revoke`；`_templates` 更偏动作提交契约，包含 method、content type 和 payload 字段约束。

我没有把它设计成“按钮数组”，因为按钮只是 UI 表现。稳定的是业务 relation：同一个 `publish` 可以在 PC Web 和移动 Web 使用不同交互呈现，但都消费同一份资源动作事实。将 relation 转成 Agent tool 是后续延展，不是这个项目的上线成果。

下面是简化后的机制示意，不是生产响应原样：

```json
{
  "id": "app-1",
  "status": "draft",
  "_links": {
    "self": { "href": "/applications/app-1" },
    "workflow": { "href": "/applications/app-1/workflow" }
  },
  "_templates": {
    "publish": {
      "method": "POST",
      "properties": []
    }
  }
}
```

前端看到 `publish` 就知道当前上下文允许发布，但为什么允许仍由后端状态、角色和权限规则决定。

## 如果面试官追：没有返回某个动作，前端是隐藏还是禁用？

我会先说我们不会让业务页面自己猜，而是做一层统一策略。

动作缺失可能表示当前状态不可执行、当前用户无权限、契约异常或资源尚未加载。UI 可以根据产品需要选择隐藏、禁用或提示，但不能重新写一份 `status + role + permission` 判断来猜原因。需要向用户解释时，原因也应来自服务端契约或标准错误。

这里的原则是：前端可以决定交互呈现，但不要重新实现业务状态机。

## 如果面试官追：列表 100 条资源，每条都算动作，会不会很慢？

我会这样回答：

我会先明确这是服务端组装资源表达时的性能风险。我的职责是模型、契约和 SDK，服务端代码由后端同事实现，所以不能把具体 SQL 或缓存方案说成个人实现。

共同设计时的原则是避免按资源逐条查询权限，让动作计算与资源查询、鉴权上下文一起批量完成，不能让 `_links` 组装产生数据库 N+1。读模型或物化视图只能作为进一步优化思路，现有材料不足以证明已经采用。

## 如果面试官追：这个改造有什么收益？

我会尽量不说空话：

收益主要有三个。第一，多端一致性更好，因为按钮和动作是否可用都来自后端资源契约。第二，接口路径演进更容易，前端依赖 relation，不到处硬编码 URL。第三，测试范围可以收敛，重点测不同角色、状态、租户下后端返回的动作契约，以及 SDK 是否正确消费契约。

如果要量化，我会先限定口径：不是所有前端逻辑都消失，而是原来散在多个端的状态机判断减少了，回归重点从“每个端都重新跑按钮规则”收敛到“契约矩阵 + 消费层”。

## 收尾句

所以我理解的 HATEOAS，不是少写几个 URL，而是从多端一致性问题出发，把“资源当前能做什么”变成 API 层的稳定契约。它也推动我认识到稳定契约依赖业务模型和 RESTful API；这条路径是复杂前端能力向上游延伸，不是职业方向切换成纯后端。Agent 是后续可以讨论的消费端，不属于已经上线的结果。
