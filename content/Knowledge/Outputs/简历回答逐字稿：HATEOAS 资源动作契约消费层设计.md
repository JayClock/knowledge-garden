# 简历回答逐字稿：HATEOAS 资源动作契约消费层设计

关联：[[简历追问：HATEOAS 资源动作契约消费层设计]]、[[项目介绍：HATEOAS 资源契约架构]]。

## 30 秒开场

这个项目位于契约生命周期的发布与消费阶段，解决 PC Web 与移动 Web 重复维护状态、角色和权限规则的问题。我把“当前资源能访问什么、能执行什么”放回服务端资源表达，通过 `_links` 和 `_templates` 发布 relation、合法动作和 payload 约束；多个前端消费同一份运行时业务事实，不再各自实现状态机。

## 如果面试官问：为什么一个前端问题最后会走向建模和 RESTful API？

因为 SDK 只能统一消费方式，不能把一个本身混乱的接口变稳定。真正设计 relation 时，我需要先回答资源是什么、生命周期如何变化、当前角色在什么状态下可以做什么。如果这些问题不清楚，`_links` 最后只会变成按钮数组，HATEOAS 也只是换一种形式复制混乱。

所以我的能力是从前端消费层逐步向上游延伸的：先解决 PC Web 与移动 Web 的规则漂移，再因为 relation 稳定性问题参与业务／领域建模，从应用、表单、工作流和工作区导航的业务事件中识别资源边界，最后设计 RESTful URI 与动作契约，并和后端共同落实到 API 表达层。

这条能力仍然服务于复杂前端：从上游稳定客户端要消费的业务知识。在具体落地中，我与后端团队分工协作：我主导领域模型、契约定义与客户端 SDK 研发，与后端协同完成 API 表达层对接。

## 如果面试官问：你具体怎么设计 `_links` 和 `_templates`？

`_links` 主要表达资源导航和动作入口，比如 `self`、`workflow`、`publish`、`revoke`；`_templates` 更偏动作提交契约，包含 method、content type 和 payload 字段约束。

我没有把它设计成“按钮数组”，因为按钮只是 UI 表现。稳定的是业务 relation：同一个 `publish` 可以在 PC Web 和移动 Web 使用不同交互呈现，但都消费同一份资源动作事实。

下面是简化后的机制示意，不是生产响应原样：

```json
{
  "id": "app-1",
  "status": "draft",
  "_links": {
    "self": { "href": "/applications/app-1" },
    "workflow": { "href": "/applications/app-1/workflow" }
  },
  "_templates": {
    "publish": {
      "method": "POST",
      "properties": []
    }
  }
}
```

前端看到 `publish` 就知道当前上下文允许发布，但为什么允许仍由后端状态、角色和权限规则决定。

## 如果面试官追：没有返回某个动作，前端是隐藏还是禁用？

这类情况不能让业务页面自己猜，需要由统一策略处理。

动作缺失可能表示当前状态不可执行、当前用户无权限、契约异常或资源尚未加载。UI 可以根据产品需要选择隐藏、禁用或提示，但不能重新写一份 `status + role + permission` 判断来猜原因。需要向用户解释时，原因也应来自服务端契约或标准错误。

这里的原则是：前端可以决定交互呈现，但不要重新实现业务状态机。

## 如果面试官追：列表 100 条资源，每条都算动作，会不会很慢？

在与后端团队共同设计契约时，核心原则是避免在接口组装层按资源逐条查询权限，而是将动作计算与资源上下文、批量鉴权深度绑定，从架构层面规避 N+1 查询风险。

## 如果面试官追：这个改造有什么收益？

可以确认的收益包括多端消费同一动作事实、前端减少硬编码 URL，以及测试重点收敛到后端契约矩阵和 SDK 消费行为。

量化时需要限定口径：前端仍保留交互逻辑，减少的是散在多个端的状态机判断；回归重点也从“每个端都重新跑按钮规则”收敛到“契约矩阵 + 消费层”。

## 如果面试官问：这个项目里的“渐进式”具体是什么？

这里不是简单地说接口分阶段上线，而是先保持资源、URI 和状态表达稳定，再由 `_links` 与 `_templates` 声明当前可消费的导航和动作。PC Web 与移动 Web 不必消费所有能力，也不再各自复制服务端状态机；SDK 负责运行时检查 relation、提交 action 和处理资源更新。

迁移方式也遵循同一思路：先用工作区导航验证 relation 消费，只调整 API 表达层，不改库改表，并通过 BFF 退路设计，保证了渐进式迁移的低风险平滑落地。

## 收尾句

HATEOAS 在这个项目里解决的是契约的运行时发布与多端消费：把“资源当前能做什么”变成 API 层的业务事实。它也推动我继续向上游追问契约怎样由领域模型形成；这条路径是复杂前端能力向上游延伸，打通前后端语义对齐的重要实践。
