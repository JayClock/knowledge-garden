# 简历回答逐字稿：Agent Harness 双层循环与可控交付

## 事实边界

> [!warning]
>
> - 公司项目保持匿名；只说明已确认的 Harness 机制。

## 提取词

**目的：** 持续提高 Agent 产出质量｜不是期待一次 Prompt 得到稳定结果

**外层：** 人类主导 PDCA｜Plan 筛选当前有效信息｜根据执行证据调整

**内层：** Do 中的 Agent 操控循环｜前馈｜执行｜反馈｜调整

**Context：** 一个 Context 完成一个边界清楚、可以验证的任务单元

**实践：** 长 PRD → 人工审核业务模型与任务清单 → 指令前馈 → 测试反馈

**边界：** 定性改善稳定性和 Token 消耗｜没有可核验比例

## 90 秒首答

我理解 Agent Harness 的主要目的，是持续提高 Agent 的产出质量，而不是期待通过一次 Prompt 就得到稳定结果。

从结构上看，它是一个双层循环。外层是以人为主的 PDCA：Plan 负责确定目标、筛选当前有效信息和批准任务边界，再根据执行证据决定继续还是调整。PDCA 中的 Do，则由 Agent 主导具体任务的操控循环，也就是前馈、执行、反馈和调整。前馈告诉 Agent 为什么做、做什么以及怎样验收；执行后，再用测试、日志或代码差异提供反馈并修正。

在我的代码仓库实践里，Plan 是最关键的一步。长 PRD 即使全部放进 Context，模型也可能抓不住当前重点。所以我会先形成经过人工审核的业务模型和任务清单，只把当前需要的目标、规则、依赖和验收条件写入指令系统。目的不是让一个 Context 完成整个项目，而是让它完整完成一个边界清楚、可以验证的任务单元。

测试报告过长时，我还会让模型生成提取脚本，再由脚本确定性地保留问题定位信息。实际观察是输出更稳定，也减少了重复输入完整材料产生的 Token 消耗，不过没有可核验的具体比例。

## 追问入口

- **Plan 怎样筛选 Context：** 展开业务模型、任务清单和人工审核边界。
- **内层操控循环怎样工作：** 展开前馈、测试反馈和问题定位脚本。
- **为什么不能一次完成整个项目：** 展开一个 Context 对应一个完整任务单元，以及跨任务需要状态承接的原因。
