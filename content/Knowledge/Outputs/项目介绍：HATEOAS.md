# 项目介绍：HATEOAS

## 提取词

- **S｜背景**：低代码平台 ｜ PC 与移动端 ｜ 权限、状态和动作规则重复维护
- **T｜任务**：多端消费同一份资源契约 ｜ 方案推动 ｜ 模型与契约设计 ｜ SDK 与 React 消费层研发
- **A｜行动**：HATEOAS 职责划分 ｜ 独立 SDK 与动态表单 ｜ 上游建模 ｜ 工作区试点 ｜ 增量改造与回归验证
- **R｜结果**：导航与业务动作落地 ｜ 既有能力内直接消费契约变化 ｜ 两个 npm 包 ｜ 34 个测试文件、233 项通过测试

## 项目介绍

在低代码平台的复杂权限体系下，我们需要在前端维护一份与后端一致的推导逻辑，带来的问题是，后端的权限体系发生变化时，就必须等待前端修订后才可验证，带来了重复沟通与回归成本。

我希望将复杂权限判断收敛回服务端，做到即使后端发生了变化，前端也不需要进行修补与发布

我推动并引入了超媒体资源契约架构，在服务端的接口中通过 `_links` 返回当前能访问的资源，通过 `_tempales` 表达资源的提交方法和字段约束。比如我们用户不能访问其工作区列表，那么就不再 user 接口的 `_links` 对象中，返回 workspaces 属性。

为了让 PC 和移动端统一消费这份契约，我设计并实现了框架无关的 TypeScript 资源 SDK，采用**核心层与框架适配层分离**的架构。核心围绕接口请求的管理、返回数据的快照 和动作建模，并集中处理请求、缓存和失效通知。React 适配层负责状态订阅与声明式消费，让多端复用协议逻辑，业务页面不再分别解析链接和动作模板。

推进过程中，我与后端将改动限定在 API 表达层，保持原有请求参数和响应不变。在前端生成端到端测试生成数据，并在前后端改造完成后重新回归，验证已有流程的兼容性。

最终，低代码平台主页的高频入口，不再需要在后端权限体系发生变化的情况下，进行前端代码修改和回归。相关任务成本直接降低至原来一半。

## 高频追问

### 如果面试官问：为什么一个前端问题最后会走向建模和 RESTful API？

前端重复判断权限和状态，背后是多端在解释同一套业务规则。SDK 可以统一消费方式，但资源边界、生命周期和动作含义，需要先与后端通过业务建模明确，再表达为 URI、relation 和动作模板。

我负责模型与契约设计、TypeScript SDK 和 React 消费层研发，与后端协同落地 API 表达层。这样服务端提供当前可用的资源关系和动作，多端按同一份契约消费。

### 如果面试官问：把权限和请求封装在前端公共模块中复用也能做到多端一致，为什么还要上 HATEOAS？

公共模块能减少重复代码，但权限和状态规则仍在前端维护，服务端规则变化后，客户端还要同步修改和发布。HATEOAS 把当前资源能访问什么、能提交什么，交给服务端根据状态和用户上下文决定；SDK 统一消费这些结果。

如果只是控制一个按钮，返回 `canPublish` 这样的布尔值就够了。我们还需要统一动作目标、HTTP Method、提交字段和约束，所以用 `_links` 与 `_templates` 一起表达，避免多端分别维护这些信息。

### 如果面试官问：你具体怎么设计 `_links` 和 `_templates`？

`_links` 表达资源导航和动作入口，`_templates` 表达动作的提交方式、字段类型和必填等约束。以工作区试点为例，服务端返回 `workflow` 工作流列表入口，以及工作区基本信息更新模板。

契约表达业务关系，前端决定怎样呈现。没有某个入口时，页面按产品设计隐藏或禁用，不再根据角色和状态重新推导可用性。需要展示不可用原因时，可以进一步在服务端契约中设计原因信息。实际提交仍由服务端校验权限和业务状态。

### 如果面试官问：工作区导航试点具体怎样改造与验证？

我与后端协同在工作区响应中增加 `_links` 和 `_templates`，由服务端按权限提供入口与更新模板。PC 与移动端把原来的 service 调用迁移为 SDK 消费，导航直接根据当前 `workflow` relation 的有无渲染。

客户端验证用 MSW 模拟有、无 `workflow` 的两种响应，在 Vitest 中渲染导航组件，通过 DOM 断言检查入口是否按契约出现。

### 如果面试官问：推进中最难的地方是什么，怎样证明改造成本与风险可控？

难点是让后端协作方确认改造范围和数据更新风险。我与后端把改动限定在 API 表达层：资源响应增加超媒体元数据，表结构、原有请求参数和 workflow 保存接口响应保持不变。

我用 AI 辅助生成保存与发布的端到端测试，在前后端实现后重新回归。保存用例以相同输入对比原有响应 JSON，把兼容性讨论落实到具体断言，推动增量改造落地。

### 如果面试官追：导航组件测试与 workflow 端到端回归分别验证什么？

- **导航组件测试**：MSW 模拟响应，Vitest 渲染组件并检查 DOM，验证客户端对有、无 relation 的消费。
- **workflow 端到端回归**：验证已有保存与发布流程；保存用例用相同输入对比原有响应 JSON，检查已覆盖场景的输入输出兼容性。

公开 SDK 的 34 个测试文件、233 项通过测试，是通用消费层的另一组验证，和业务回归分别说明。

### 如果面试官问：SDK 这个独立的资源消费层具体承担什么？

SDK 统一资源导航、动作提交和缓存处理。业务通过 `follow()` 导航，通过 `action()` 获取动作并提交；内部由 `Fetcher` 请求数据，`StateFactory` 解析响应，`Resource` 按绝对 URI 定位和复用。

普通读取优先使用缓存，需要最新状态时调用 `refresh()`。相比通用请求库或查询缓存库，这个消费层还处理资源关系和动作模板，让多端共用协议逻辑。

### 如果面试官问：StateFactory 比直接返回 response.json() 多解决什么问题？

它把协议结构转换成统一的资源状态。Client 根据响应 `Content-Type` 选择 Factory；HAL／HAL-FORMS 解析器把业务属性整理到 `data`，解析链接、动作模板和嵌入资源，并保留 URI 与响应头上下文。

页面通过 `data`、`follow()` 和 `action()` 消费同一个 State 接口，协议解析规则集中在 Factory 中，不散落在各业务页面。

### 如果面试官追：动态 links 怎么做 TypeScript 类型安全？

TypeScript 在编译期约束稳定的 relation 名称、资源数据和目标资源类型，提供检查与补全；当前响应有没有某个入口，则在运行时通过 `state.hasLink()` 判断。调用不存在的动作时，`state.action()` 抛出 `ActionNotFound`。

提交字段来自 `_templates.properties`，SDK 将字段定义转为 Zod 规则，通过 Standard Schema 接入 `action.submit(payload)` 校验。失败时抛出带字段错误的 `ActionValidationError`。业务页面也已根据模板生成 JSON Schema 表单描述，让渲染和校验共同消费当前字段定义。

### 如果面试官追：哪些变化可以不用前端重新发布？

在 relation、动作语义和消费能力保持适用的前提下，服务端调整角色或状态规则，前端直接消费新的入口和动作，不需要同步修改权限推导代码。

字段变化也取决于现有表单能力。比如新增一个必填文本字段，如果已有控件、校验和提交逻辑能够覆盖，就可以按新模板渲染和提交；如果需要新控件、特殊交互，或者 relation 和动作含义改变，仍要调整前端。

### 如果面试官追：资源缓存和 React Hooks 怎么处理？

Resource 实例与响应缓存都按目标绝对 URI 管理，relation 名称只表达关系。`get()` 优先读取已有完整状态缓存，`refresh()` 使用 `Cache-Control: no-cache` 主动刷新，相同进行中的请求会去重。

以成功的 POST 响应为例，缓存协调有两条路径：

- **写回新状态**：响应带 `Content-Location` 且允许存储时，SDK 将本次响应体解析为对应 URI 的 State，写入缓存并发出 `update`，不额外发 GET。
- **通知失效**：按规则处理请求 URI、`Location` 和 HTTP `Link` 头中 `invalidates` 指向的资源，清理缓存并发出 `stale`；也支持用 `inv-by` 登记依赖并传播失效。

React Hook 收到 `update` 后更新组件状态；收到 `stale` 后，仅在开启 `refreshOnStale` 时重新请求，这个选项默认是 `false`。卸载时清理监听。失效通知和取得新数据是两个环节。

### 如果面试官问：`_links` 拿不到页面是不是就废了？

要先区分加载失败和正常响应中缺少某个入口。对于加载失败，我会提供错误与重试入口；已有缓存时可以保留内容展示。正常响应里没有某个 relation，则按产品策略处理入口，不在前端重新推导权限。

如果读取后、提交前权限或状态变化，最终仍由服务端判断请求是否合法。遇到权限拒绝或状态冲突时，我会按接口约定反馈错误，再 `refresh()` 获取新契约，更新入口，让用户重新确认操作，避免直接自动重试修改请求。
