## 项目介绍

这个项目是低代码平台的 HATEOAS 资源契约与 TypeScript SDK。PC 和移动端原先重复维护权限与动作规则，后端规则一变，前端就要同步修改和回归。

我负责资源契约设计、SDK 核心和 React 消费层，与后端协同把权限判断收敛到服务端，让多端消费同一份契约。

协议上，采用 HAL / HAL-FORMS：`_links` 表达可访问的资源关系，`_templates` 描述动作的地址、HTTP 方法和字段约束，前端据此呈现入口与操作。

SDK 上，我把框架无关核心与 React Hooks 适配层分开。核心用 `Resource` 定位资源、`State` 保存响应快照、`Action` 封装提交，统一进行中请求去重与缓存失效；Hooks 订阅 `update` 和 `stale`，更新页面或按配置刷新。

字段消费采用 Schema 驱动：从动作模板生成 Zod 校验与 JSON Schema 表单描述，通过 Standard Schema 接入提交验证，让渲染和校验使用同一份字段定义。

落地先以工作区导航为试点，只增量改造 API 表达层，保持表结构、原有请求参数与保存接口响应不变。我用 AI 辅助生成 workflow 保存与发布的 E2E 测试，改造后回归验证兼容性。

最终，系统 80 % 的功能模块，后端调整权限时，前端不再同步修改判断分支；相关任务成本直接降低至原来的一半。

## 可能追问

### 难点一：动态资源契约的统一消费

#### 为什么不复用前端权限模块，或者只返回 canPublish？

公共模块能减少重复代码，但我当时要解决的是规则的维护位置。即使 PC 和移动端共用一个权限函数，函数里仍要根据角色、资源状态推导能不能操作。服务端规则一变，前端还是要更新这个模块，再让消费它的客户端发布，重复解释业务规则的问题还在。

HATEOAS 的做法是由服务端结合当前用户和资源状态，返回这次可访问的关系与可执行动作。前端消费的是判断结果，不再自己推导。例如工作区响应里有 `workflow` relation，页面就可以提供工作流入口；没有这个关系时，按产品策略隐藏或禁用。具体放在侧边栏还是首页，仍由前端决定。

如果需求只是控制一个发布按钮，返回 `canPublish` 完全可以。我们还需要统一动作提交到哪里、使用什么 HTTP 方法、有哪些字段、哪些字段必填。只给布尔值，剩下这些信息仍要由两端分别维护，所以我用 `_links` 表达资源关系，用 `_templates` 表达提交方式和字段约束。

这也要求先明确资源边界和动作含义。我与后端结合业务事件和生命周期讨论资源，再落实成 URI、relation 和模板；SDK 则把消费方式统一起来。前端按契约展示可用操作，真正提交时，服务端仍校验权限和业务状态。这样把业务规则、协议消费和页面呈现放在各自适合的位置。

#### SDK 怎样分层，Resource、State、Action 和 StateFactory 各做什么？

我把 SDK 分成框架无关的 TypeScript 核心和 React 适配层。核心负责资源、请求、协议解析、动作与缓存，React 层负责状态订阅和组件生命周期。PC 和移动端共用协议消费逻辑，页面不用分别解析链接和动作模板。

核心内部，`Resource` 按绝对 URI 定位，负责读取、缓存访问和事件通知。同一资源可以从不同入口到达，目标 URI 相同就能复用。`State` 是某次响应的快照，承载业务数据、资源关系和动作定义。把它们分开，资源身份保持稳定，响应状态可以随读取和修改更新。

一次需要网络读取的调用，由 Resource 交给 `Fetcher` 发请求。Client 根据响应的 `Content-Type` 选择 `StateFactory`，HAL 或 HAL-FORMS 解析器把业务属性、链接、模板和嵌入资源整理成统一 State，并保留 URI 与响应头上下文。页面拿到的因此是资源状态，而不只是一份原始 JSON。

`Action` 则封装提交目标、HTTP 方法、字段和序列化方式。页面从当前状态取得动作，再调用 `submit()`，不必重新拼请求。比如工作区页面从 `data` 读取基本信息，通过 `follow()` 导航到工作流资源，通过 `action()` 取得更新动作。

写操作后的缓存更新和失效通知也留在核心，React 层订阅事件，再更新组件或按配置刷新。请求管理、状态快照和动作建模各有职责，协议逻辑不会散落到页面中，React 的生命周期也不会反过来侵入核心。

#### 动态契约怎样校验，哪些变化可以不用前端发版？

我把稳定的结构交给 TypeScript，把当前响应才知道的信息交给运行时。编译期约束资源数据、relation 名称和目标资源类型；当前用户有没有入口，则用 `state.hasLink()` 检查。调用不存在的动作时，`state.action()` 会抛出 `ActionNotFound`，不能因为类型里描述过这个动作，就认为每次响应都会提供。

提交字段来自 `_templates.properties`。接入 Zod 插件后，根据字段定义生成校验规则，通过 Standard Schema 接到 `action.submit(payload)`。不符合模板时，在发请求前抛出带字段错误的 `ActionValidationError`。业务页面也已按模板生成 JSON Schema 表单描述，让字段渲染和校验消费同一份定义。

所以是否需要发版，要看现有消费能力能否覆盖变化。例如服务端调整角色规则，已有 `workflow` relation 的有无随之变化，导航直接按新响应渲染，不必同步维护角色分支。假设模板新增必填文本字段，而已有控件、校验和提交能力都支持，也可以沿用当前链路。

如果需要新控件、特殊交互，或者 relation 和动作含义改变，就要调整前端。服务端能返回字段，不代表页面天然理解所有字段；URI 可以跟随契约，入口在产品中的意义仍需要双方约定。

我会沿关系识别、动作理解、字段渲染、校验和提交逐项判断。类型帮助开发时理解稳定结构，运行时消费当前契约，服务端校验最终请求。三个阶段分清楚，才能具体说明哪些规则调整已经不需要前端发版。

### 难点二：写操作后的缓存与页面更新

#### 多个入口怎样共享资源，React 何时重新请求？

共享先要统一资源身份。relation 表示资源之间的关系，目标绝对 URI 才用来定位资源。Client 按 URI 复用 `Resource`，响应状态缓存也按 URI 管理；不同入口指向同一 URI 时，就能共享状态和事件，而不是每个页面各存一份。

这里有三种不同的复用：Resource 实例保留资源的操作入口，State 缓存保存已经取得的快照，进行中请求去重则避免同一时间重复读取。例如两个消费方同时读同一资源，第一个请求还没完成，后一个复用这次读取；结束后清理进行中记录，后续再按缓存策略处理。

普通 `get()` 优先读完整状态缓存，需要主动刷新时调用 `refresh()`，使用 `Cache-Control: no-cache`。React 读取 Hook 订阅资源的 `update` 和 `stale`：收到 `update` 就使用已经取得的新 State 更新组件，不必再为这个快照发 GET。

`stale` 只说明旧状态失效。Hook 仅在开启 `refreshOnStale` 时调用 `resource.refresh()`，默认是 `false`，由调用方决定是否自动刷新。组件卸载时清理监听，把订阅生命周期留在 React 适配层。

比如一个组件完成修改，另一个组件能否立刻显示新状态，要看响应是否直接写回，以及失效后是否开启刷新。我会沿着资源身份、缓存事件和 Hook 配置检查这条链，而不会把“收到了失效通知”直接理解成“所有页面都已更新”。

#### 动作执行后，哪些缓存失效，哪些能直接写回？

我把写操作后的处理分成两件事：哪些旧状态已经不能继续信任，以及这次响应有没有直接带回可用的新状态。一个动作可能同时影响当前资源和关联资源，只改发起操作的组件，其他入口仍可能留着旧数据。

以成功的 POST 响应为例，SDK 会按规则处理请求 URI、`Location`，以及 HTTP `Link` 响应头中 `invalidates` 指向的资源，清理对应缓存并发出 `stale`。缓存层还支持通过 `inv-by` 登记依赖，在资源失效时传播到依赖它的缓存。请求 URI 的默认失效可以通过专用标记控制。

这里的 `stale` 表达的是旧状态失效，并没有提供新数据。能否直接写回，要看响应是否带 `Content-Location`，以及是否允许存储。满足条件时，SDK 把本次响应体解析成那个 URI 的 State，写入缓存并发出 `update`，这一步使用的是已经收到的响应，不额外发 GET。

比如响应说明返回的就是某个资源的新状态，就可以直接更新该资源；另一个关联资源只有失效声明，就先清掉旧缓存，后续再按读取策略获取。`Location` 在这里用于失效处理，`Content-Location` 用来标识响应体对应的资源状态，两者承担的作用不同。

同一次响应可以先触发失效，再写回新状态。React 收到的是明确的两类事件：一个说明旧数据过期，另一个提供新快照。这样缓存维护和页面更新之间就有了可消费的接口。

#### 缺少入口、请求失败、提交前权限变化，怎样区分？

我会先看有没有正常取得资源状态。正常响应里缺少某个 relation，表示当前契约没有提供这个入口；请求失败则是这次没有成功取得状态。两者对界面的含义不同，不能把加载失败直接当成用户没有权限。

正常响应缺少入口时，页面按产品策略隐藏或禁用，不再根据角色和状态重新推导一次。工作区导航就是按当前 `workflow` relation 是否存在来决定入口。契约负责表达当前可访问什么，前端负责决定这种结果怎样呈现给用户。

如果是网络或请求错误，我会展示错误与重试入口；已经有缓存内容时，可以保留展示，但要把读取失败和当前状态区分开。重试针对的是获取资源，不是把一个没有返回的入口强行补出来。也不会在请求失败后退回到前端权限分支，假装已经知道服务端的判断。

还有一种情况是读取时动作可用，但用户真正提交前，权限或资源状态已经变化。这时仍以服务端对实际请求的校验为准。遇到权限拒绝或状态冲突，我会按接口约定反馈错误，再调用 `refresh()` 获取新契约，更新入口或表单，让用户重新确认。

修改请求不适合在这种情况下直接自动重试，因为操作依据已经变了。处理顺序应当是说明失败、取得当前状态，再让用户决定下一步。这样 HATEOAS 提供的是当前可用操作的表达方式，服务端请求校验仍然承担最终的业务判断。

### 难点三：存量系统的增量迁移与兼容性验证

#### 怎样让后端协作方确认改造成本和风险可控？

推进时，后端关心的是改多少、是否影响原来的数据更新，以及出了问题有没有退路。我先把讨论落到具体接口范围：我负责模型、资源契约和客户端 SDK，与后端共同确认 API 表达方式，服务端代码由后端实现。

这次改造在资源响应中增加 `_links` 和 `_templates`，保持表结构、原有请求参数和 workflow 保存接口的响应不变。这里有两个不同范围：读取的资源响应增加契约元数据，原来的保存接口继续保持原有输入输出。把它们讲清楚，才能具体判断哪些地方需要修改，哪些兼容性需要回归。

落地先以工作区导航为试点，让 PC 和移动端从原 service 调用迁移为 SDK 消费；架构上保留 BFF 作为渐进迁移退路。这样可以围绕一条实际消费路径讨论契约和适配，而不是要求所有业务页面一次迁完。

验证方面，我用 AI 辅助生成 workflow 保存与发布的端到端测试，前后端完成实现后重新回归。保存用例使用相同输入，对比原有的原始响应 JSON，把“原有行为是否保持”落实成断言。导航是否按 relation 渲染，则由另一组组件测试检查。

因此，改造成本通过接口和数据结构的范围来讨论，兼容性通过相应场景的回归来判断。AI 帮助形成测试代码，实际验收仍看断言和回归结果。这样的推进方式让双方能够对照具体改动协作，而不是只讨论架构理念。

#### 工作区试点怎样验证，SDK 后续怎样独立交付？

试点从工作区资源响应开始。我与后端协同增加 `_links` 和 `_templates`，由服务端按权限提供 `workflow` 工作流列表入口和工作区基本信息更新模板。PC 侧边栏与移动端首页从原 service 调用迁移为 SDK 消费，根据当前 relation 是否存在渲染导航，再跟随关系访问目标。

导航组件测试用 MSW 模拟包含和不包含 `workflow` 的两种正常响应，在 Vitest 中渲染组件，通过 DOM 断言检查入口。它验证给定契约后的客户端表现；没有 relation 是正常状态，不与请求失败混在一起。

workflow 端到端回归针对保存与发布，我用 AI 辅助生成测试，在前后端实现后重新回归。保存用例使用相同输入，对比原有原始响应 JSON，检查已覆盖场景的输入输出兼容性。它看的是存量业务链路，与导航组件测试的断言对象不同。

这套能力先在企业 Monorepo 中作为业务子 lib 服务低代码平台，随后我把通用资源消费模型独立出来，发布为 `@hateoas-ts/resource` 和 `@hateoas-ts/resource-react`。前者承载框架无关的核心，后者提供 React 消费适配，把业务接入和通用能力维护分开。

公开 SDK 有独立的验证结果：34 个测试文件、233 项测试全部通过，类型检查和两个 package 构建也通过。导航测试检查契约如何呈现，业务回归检查原流程是否兼容，SDK 测试和构建检查通用实现。这三组验证分别支撑业务落地和独立包交付，测试数量也按各自对象说明。
