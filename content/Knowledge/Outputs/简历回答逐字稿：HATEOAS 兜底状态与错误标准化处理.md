# 简历回答逐字稿：HATEOAS 兜底状态与错误标准化处理

关联：[[简历追问：HATEOAS 兜底状态与错误标准化处理]]、[[项目介绍：HATEOAS 资源契约架构]]。

## 30 秒开场

契约驱动以后，前端仍然要处理加载、缓存、错误和交互反馈。当前项目完成了运行时校验、错误反馈、资源缓存、更新事件和动作后的状态刷新，业务合法性则以服务端资源契约为准。离线命令回放、relation path 和 disabled reason 属于后续可演进的技术方向。

## 如果面试官问：`_links` 拿不到页面是不是就废了？

页面不能简单白屏，前端也不能凭空猜业务规则。

如果资源本身没加载出来，那页面应该进入资源不可用或重试状态。如果资源数据有缓存，但动作契约没拿到，我会把它标记成“基于旧快照”或“动作不可确认”，关键动作不应该无提示地开放。

对于弱网场景，使用最后一次资源快照维持只读页面是合理的扩展思路；涉及提交时，可以先禁用动作，避免客户端在未同步时产生不可逆的副作用。

## 如果面试官追：动作缺失和无权限怎么区分？

单纯看没有 `approve`，前端无法知道是无权限还是当前状态不可审批。所以如果业务需要给用户解释，就应该由后端提供更明确的 disabled reason 或者错误资源。

我会把 UI 策略分成两类：

- 非关键动作：没有 relation 就不展示，减少干扰。
- 关键动作：如果用户预期强，比如审批页里的审批按钮，最好展示禁用态，并由后端返回原因，比如“当前状态不可审批”或“你不是审批人”。

但无论怎么展示，前端都不应该重新写一份 `status === pending && role === manager` 来解释。

## 如果面试官追：链式 follow 中间失败怎么办？

这里要避免某个子资源失败以后，整个页面跟着崩掉。

比如从 root follow 到 user，再 follow 到 workspace，再 follow 到 diagram。如果 workspace 加载失败，我会保留上一级 user 状态，并让 workspace 区域显示局部错误和重试。如果继续扩展，SDK 可以把错误带上 relation path，比如：

```ts
root -> default-user -> workspace
```

这样 UI 和日志就能知道是哪段 relation 断了，而不是只看到一个模糊的 fetch error。

如果失败是 401/403，就引导登录或权限提示；如果是 404，说明资源不存在或被删除；如果是 timeout，可以重试；如果是 invalid contract，就应该上报，因为这更像前后端契约事故。

## 如果面试官追：离线点击动作后，恢复网络状态变了怎么办？

这属于扩展方案。离线队列只能提升体验，不能绕过服务端状态机。用户离线点击 approve，本地可以生成一个 command，包含 action relation、resource id、payload、幂等 id、创建时间。UI 可以显示“待同步”，但不能说服务端已经最终成功。

如果后续实现离线队列，网络恢复后再由 SDK 回放 command。如果服务端返回 409，比如这张单已经被别人撤回，我会停止乐观状态，拉取最新资源，并提示用户“操作未生效，因为资源状态已变化”。用户可以基于最新状态重新决策。

离线并不意味着前端变成权威状态机，最终合法性仍由服务端契约和状态机决定。

## 如果面试官追：错误标准化有哪些类型？

如果讨论标准化错误模型，我会用下面的枚举说明设计思路；它不是生产代码的逐字还原：

```ts
type ResourceError =
  | "NetworkError"
  | "Unauthorized"
  | "Forbidden"
  | "NotFound"
  | "ActionMissing"
  | "InvalidContract"
  | "PayloadValidationError"
  | "Conflict"
  | "ServerError"
```

在这套设计里，错误可以携带 resource uri、relation path、action name、http status 和 request id，让 UI、日志和监控使用同一上下文。

## 收尾句

这里的判断是：从前端状态机转向契约驱动 UI，不等于前端职责消失。前端仍要负责缓存、错误、加载、降级和交互反馈，只是不再重新发明业务合法性。实际项目已经有运行时校验、缓存更新和错误反馈；更完整的离线与冲突模型属于后续可以继续演进的部分。
