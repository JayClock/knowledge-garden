# 项目介绍：企业级低代码工作流引擎

## 提取词

低代码工作流协议 ｜ React Flow 画布与表单 ｜ Tiptap 变量引用 ｜ GraphBuilder 拓扑与分支剪枝 ｜ 插件化微内核与 BaseNodeExecutor ｜ SSE 调试反馈与执行日志

## 2 分钟版本

我负责低代码工作流协议、React Flow 画布、Tiptap 变量编辑器，以及 TypeScript 执行引擎，提供工作流的可视化编排、节点配置与测试运行能力。

我先用 `WorkflowDefinition`、节点配置类型与 `${nodeId.variableName}` 统一编辑器与执行器的契约，运行时只消费节点、配置和连线等业务定义。运行前先做节点与边校验，再由 `GraphBuilder` 建立邻接表、反向邻接表与入度表，通过环检测与 Kahn 算法生成拓扑顺序。遇到 Condition 条件分支时，根据 `sourceHandle` 选择路径，递归排除未命中分支，并检查汇合节点的其他活跃入边。

数据引用上，Tiptap 将上游变量显示为不可拆分的标签，保存时还原为规范表达式，回显时再转换为变量节点；运行时通过独立的 `ExecutionContext` 存储上游输出并解析引用。节点系统采用 `NodeRegistry + BaseNodeExecutor`，统一计时、输出存储、日志与异常捕获，并提供深度变量解析方法。最后通过测试运行面板接入后端 SSE，实时呈现节点状态、输入输出、耗时与日志，支持从编排到执行反馈的调试过程。

## 5 分钟主讲

这个项目提供可视化工作流编排与 TypeScript 执行能力，支持节点配置、条件分支、变量引用、测试运行与执行日志。我负责工作流协议、React Flow 编辑器、Tiptap 变量编辑器和执行引擎，并对接后端的执行接口与 SSE 反馈。

我用 `WorkflowDefinition`、Node、Edge、节点配置类型和变量协议组织编辑器与执行器的共享定义。Node 记录类型与配置，Edge 记录源节点、目标节点以及条件分支的 `sourceHandle`。画布中保存节点坐标与交互状态，执行时则提取节点、配置和连线等业务字段；节点配置由对应验证器检查。

在前端编辑侧，我基于 React Flow 搭建了可视化画布，支持节点拖拽、缩放、连线和未保存状态管理，并通过防抖避免高频保存请求；为 Condition 等多分支节点设计了多个输出 Handle，让连线与条件意图精准绑定。

跨节点数据引用采用 Tiptap 变量编辑器：输入 `/` 弹出可用上游变量，选择后插入带有节点展示名的原子标签，底层持久化为 `${nodeId.variableName}`。保存时将 Tiptap 内容转换为协议文本，回显时再将占位符还原为变量节点，展示名称与引用标识分开保存。执行时，基类提供的方法递归遍历配置中的字符串、数组和对象，通过 `VariableResolver` 从当前执行上下文读取上游输出；变量不存在时保留原表达式。

校验通过后，由 `GraphBuilder` 构建邻接表、反向邻接表与入度表，分别用于查询下游、查询上游和计算依赖数量。主流程采用 DAG：先用 DFS 检测环路，再用 Kahn 算法生成满足依赖关系的拓扑顺序，交给 `WorkflowEngine` 调用节点执行器。

这里的核心攻坚是**条件分支（Condition Node）的安全剪枝**。当分支命中后，未选路径需要被排除，但**不能无差别地递归删除整棵子树**。不同分支可能在下游汇合到同一个节点，例如分支 A 和分支 B 都连接到 End。如果无差别递归删除，公共汇合节点也会被移除。我的解决方案是利用反向邻接表做入边活跃度检查：在沿着未选分支排除时，动态检查汇合节点是否还存在来自其他未排除路径的有效前驱。只要该节点仍然有活跃前驱，就必须予以保留；只有当它的全部前驱入边失效时，才继续向下排除，并在分支决策后动态更新执行顺序，兼顾了分支排除与公共汇合。

节点系统采用 `NodeRegistry` 注册表与 `BaseNodeExecutor` 基类。基类的 `execute()` 统一记录节点开始与结束、执行耗时、成功输出和异常结果，具体业务逻辑放在 `doExecute()` 中；另外提供深度变量解析方法、配置验证接口与输出变量定义接口。新增节点时实现对应执行器并注册，不需要改核心调度逻辑。节点异常被转换为失败结果，交给引擎记录工作流失败并停止后续执行。

测试运行面板与执行日志界面接入后端 SSE，接收工作流开始、节点开始、节点结束、日志、工作流结束与错误等事件，展示输入输出、耗时和状态。`executionId` 用于标识执行记录，Trace 面板按 Edge 的拓扑关系组织节点展示。用户可以在发布前运行流程并查看结果，检查配置、变量与执行路径。

这段经历打通了从可视化编排、工作流定义、变量解析、图调度到执行反馈的核心链路。

## 高频追问

### 如果面试官问：GraphBuilder 和 WorkflowEngine 在图执行中如何分工？

两者是“图结构构建与索引”与“执行流程调度驱动”的分工：

- **GraphBuilder 负责静态图分析与拓扑规划**：它接收 `WorkflowDefinition` 中的 nodes 和 edges，构建邻接表、反向邻接表与入度表；提供 `hasCycle()` 环检测与 `getExecutionOrder()` Kahn 拓扑排序计算；在遇到条件分支时，通过 `selectBranch()` 排除未命中分支并维护排除集合，输出合法节点的拓扑序列。它不执行具体的节点业务逻辑。
- **WorkflowEngine 负责生命周期调度与状态推进**：它生成唯一的 `executionId`，初始化 `ExecutionContext` 与执行日志器；先调用验证器与 GraphBuilder 获取初始执行顺序，然后按顺序依次调用各节点的 `NodeExecutor`；在节点开始与结束时触发事件或回调，收集最终输出，处理节点错误并在条件分支产生决策时通知 GraphBuilder 更新拓扑顺序。

### 如果面试官问：图结构怎样做校验和执行？

运行前，工作流验证器检查 Start 和 End 节点是否存在、Start 是否唯一、节点类型是否有对应验证器、静态配置是否通过节点验证器，以及边引用的源节点和目标节点是否存在。

通过校验后由 GraphBuilder 构图：构建邻接表用于查找下游后继，反向邻接表用于查找上游前驱，入度表记录每个节点的依赖计数。主流程必须是严格的 DAG，因此先用 DFS 遍历并在递归栈中检测回边（Back Edge）拦截环路；合法图再交给 Kahn 拓扑排序算法。

Kahn 算法将所有入度为 0 的节点推入就绪队列。节点出队后加入结果序列，并将其后继节点的入度减 1；当后继节点入度降为 0 时进入队列。WorkflowEngine 拿到拓扑序列后，按序调用节点执行器并维护当前执行的上下文。

### 如果面试官追：条件分支怎么处理？为什么不能无差别递归排除？

Condition 节点命中某一分支后，未命中的分支路径需要被排除，但**不能无差别地沿着未选分支递归删除整棵子树**。

不同分支可能连接同一个公共下游，例如分支 A 和分支 B 都连接到 End。如果直接做无差别的整树递归删除，公共汇合节点也会被移除。

我的方案是利用**反向邻接表进行入边活跃度检查**：在沿着未选中分支排除下游时，动态检查汇合节点是否还存在来自其他未排除路径的有效前驱。只要该节点仍然有活跃入边，就必须予以保留；只有当它的所有前驱入边全部失效时，才继续向下排除。分支决策后动态更新执行顺序，兼顾了分支排除与公共汇合。

### 如果面试官追：跨节点上下文和变量怎样传递？

每次执行创建独立的 `ExecutionContext`，保存流程定义、输入参数、变量存储和已完成节点集合。变量存储以 `nodeId` 为键保存节点输出，耗时与错误则记录在执行结果和日志中。

节点执行器通过基类的深度解析方法遍历配置中的字符串、数组和对象。字符串中的 `${nodeId.variableName}` 由 `VariableResolver` 解析，根据节点 ID 和变量名称读取上游输出。

如果变量值不存在，文本解析会**保留原始占位符而不替换为空值**。

### 如果面试官问：为什么不用普通 textarea，而是用 Tiptap 胶囊？怎样防止破坏？

普通 textarea 不便直接展示带独立属性的变量标签。我用 Tiptap 将变量引用表示为 `variableMention` 节点：界面显示节点和变量的可读名称，引用使用 `nodeId` 与 `variableName`，不依赖展示名称。

我引入 Tiptap 开发变量胶囊编辑器：

1. **双向转换与隔离**：界面中展示为不可拆分的原子标签（Label），底层统一持久化为稳定的 `${nodeId.variableName}` 规范字符串。即使节点更名，底层 ID 不变。
2. **原子节点**：将变量节点定义为 `atom: true` 和 `inline: true`，以行内原子标签表示引用，不在标签内部编辑字符。
3. **快捷交互**：输入 `/` 时弹出 Suggestions 菜单，列出当前所有上游可用节点的输出变量供用户直观选择。

### 如果面试官问：一个节点插件具体包含什么？新增节点要改哪些地方？

节点解耦为 `NodeRegistry` 注册中心与 `BaseNodeExecutor` 抽象策略：

```ts
interface NodeExecutor<TConfig = Record<string, unknown>> {
  readonly type: NodeKind
  validate?(config: TConfig): { valid: boolean; errors?: string[] }
  execute(
    nodeId: string,
    config: TConfig,
    context: ExecutionContext,
    logger: ExecutionLogger,
  ): Promise<NodeExecutionResult>
  getOutputSchema?(config: TConfig): OutputVariableSchema[]
}
```

框架提供 `BaseNodeExecutor` 基类，采用模板方法模式：`execute()` 统一负责执行计时、调用 `doExecute()`、保存成功输出、捕获异常与记录日志。基类另外提供 `resolveConfigVariables()` 深度变量解析方法，以及 `validate()` 和 `getOutputSchema()` 接口，供具体节点实现或调用。

新增业务节点时，只需定义其配置 Schema、实现独立的 Executor 类，在前端注册对应的表单组件，最后调用 `registry.register(type, executor)`。核心调度引擎不需要修改任何 `switch-case`，变化完全收敛在插件边界。

### 如果面试官追：节点执行抛错和异常隔离怎么处理？

`BaseNodeExecutor.execute()` 用 `try-catch` 捕获 `doExecute()` 的异常，返回包含 `success: false`、空输出、`Error` 与耗时的 `NodeExecutionResult`，并记录节点结束日志。

WorkflowEngine 检查节点结果，失败时停止本次工作流的后续执行，在外层捕获错误，返回包含执行 ID、耗时、错误与日志的失败结果。前端通过节点结束及工作流结束等 SSE 事件显示失败信息。

### 如果面试官问：测试运行与执行日志怎样展示？

1. **测试运行面板**：输入测试参数后运行工作流，通过 SSE 接收 `workflow:start`、`node:start`、`node:end`、`log`、`workflow:end` 和 `error` 等结构化事件，更新节点状态、结果与日志。
2. **执行记录**：以 `executionId` 标识执行记录，保存输入、输出、状态、耗时、错误和节点追踪信息，供执行历史与详情界面查询。
3. **Trace 面板**：根据节点与 Edge 用 Kahn 算法计算拓扑展示顺序，列出实际收到的节点追踪信息，包括运行状态、输入输出、耗时与日志。

### 如果面试官追：自研 DAG 引擎与 LangGraph 有什么本质区别？适用场景如何划分？

两者的核心差异在于计算模型与适用场景：

- **自研 DAG 引擎**：基于有向无环图，用拓扑排序安排节点顺序，在执行期根据条件结果选择分支。适合依赖结构明确的工作流；循环与复杂状态管理需要另外设计。
- **LangGraph**：基于状态机（StateGraph）驱动，原生支持环路（Loop）、条件动态路由、检查点持久化（Checkpointing）与人机交互（Interrupt）。适合处理多轮自我反思、动态工具调用与未知步数的自主 Agent。

在实际架构中，通常用自研 DAG 引擎负责企业级主业务流程的确定性编排，而在特定需要自主决策的子节点中，可以封装调用 LangGraph Agent，兼顾可控性与灵活性。

### 如果面试官问：Monorepo 怎么分层与组织构建？

项目基于 pnpm workspace 和 Turborepo 组织代码：

- `packages/ai-engine` 存放工作流定义、TypeScript 执行引擎、节点执行器与变量解析等核心逻辑；
- `apps/workflow` 提供工作流编辑器、测试运行和执行管理界面；
- `apps/api-server` 提供执行 API 与服务端功能，`apps/webapp` 提供工作流演示应用。

pnpm workspace 管理应用与共享包，Turborepo 统一编排构建任务，并通过 `dependsOn: ["^build"]` 声明依赖包的构建顺序。
