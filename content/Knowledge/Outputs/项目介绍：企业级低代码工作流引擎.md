# 项目介绍：企业级低代码工作流引擎

## 提取词

业务流程编排 ｜ 工作流协议与引擎 ｜ 判环、排序、条件分支 ｜ 节点注册与公共基类 ｜ Tiptap 变量引用 ｜ SSE 服务端与前端接入 ｜ 测试运行与日志

## 项目介绍

这个项目是公司低代码平台里的业务工作流引擎。用户在画布上拖拽节点、配置条件，再引用上游输出，组合业务流程。我负责工作流协议、TypeScript 执行引擎、变量编辑器，以及 SSE 服务端推送和前端接入，打通配置到执行的反馈。

实现上，编辑器和引擎使用同一份流程定义，用 DAG 描述节点依赖。执行前通过深度遍历判环，再用 Kahn 算法安排执行顺序。条件分支要跳过未选路径，同时检查公共汇合节点是否还有有效前驱，避免把后面应该继续执行的节点一起排除。

我把节点业务和执行逻辑分开，用注册表按类型查找执行器，计时、变量解析和异常处理放到公共基类里。新增节点主要补充配置和执行器，不用改核心执行流程。

变量编辑器用 Tiptap 实现，用户选择上游输出后，界面显示为一个不可拆分的标签，保存时转成表达式。执行时再从本次运行的独立上下文里取值，传给下游节点。让显示、保存和执行期取值各有分工。

为了让用户看到流程跑到了哪一步，我在 NestJS 中实现 SSE 推送，并完成前端接入。节点开始、结束、日志和错误会持续传到前端，再通过执行 ID 和节点 ID 对应到本次运行和具体节点。这样用户在发布前就能测试运行，查看每个节点的输入输出、耗时和错误，定位配置或路径问题。

* **项目简介**：设计并开发了一套企业级工作流编排引擎，支持 DAG 工作流执行。

* **工作内容与成果**：
  * **引擎架构设计**：自主设计并实现了基于 **DAG（有向无环图）** 的工作流执行引擎，通过 **DFS** 实现循环检测，利用 **Kahn 算法** 实现节点拓扑排序，支持复杂业务逻辑编排。
  * **核心模块开发**：设计了基于 **注册模式（Registry Pattern）** 的节点扩展系统，实现了 Condition 节点的执行器，遵循开闭原则。

  * **高性能通信**：在 NestJS 中实现了 **SSE（Server-Sent Events）** 流式响应机制，实时推送节点状态、日志和错误。

## 可能追问

### 如何设计一个支持自定义流程的工作流引擎？核心难点是什么？

整体使用 DAG 描述流程，通过 `WorkflowDefinition` 统一编辑器和引擎的数据结构。节点保存 ID、类型和配置，边用 source、target 表示依赖，条件出口通过 sourceHandle 区分。

引擎拿到整个流程 JSON 后，构建邻接表、反向邻接表和入度表。调度采用 Kahn 算法：先把入度为零的节点入队，每执行一个节点，就减少后继节点的入度，降到零后再入队。比如 A、B 都是 C 的前驱，C 就会排在两者之后。

核心难点主要是环检测、条件分支和数据传递。

环检测使用深度遍历，分别维护全局访问集合和当前路径集合。前者避免重复遍历，后者判断是否回到了当前路径中的节点，回溯时再移出路径。这样可以区分真正的环和两条路径汇合到同一节点的情况。

条件节点执行后返回选中的出口，引擎再排除未选路径。剪枝时要保留公共汇合：假设 A、B 最后都连到 C，选 A 时应跳过 B，但仍然保留 C。我通过反向邻接表检查后继是否还有有效前驱，只有前驱路径全部失效，才继续排除。

数据传递由每次运行新建的执行上下文管理。上游按节点 ID 和变量名保存输出，下游通过 节点ID.变量名的固定表达式取值。

### 如何实现工作流执行过程的流式响应，并实时推送到前端？

工作流会执行多个节点，所以使用 SSE 持续推送过程信息，让前端能显示当前进度，而不只是等待最后的成功或失败。

我在 NestJS 中实现 SSE 服务端推送，通过 Controller 返回事件流，把执行事件编码成 `data: ...\n\n` 格式持续写入响应。前端可以通过 `EventSource` 接收，也可以使用 `fetch` 读取响应流，再通过 `TextDecoder` 逐块解码。事件协议与后端共同制定，SSE 服务端推送、前端接入和日志界面由我实现。

协议需要区分工作流开始、节点开始、节点结束、日志、整体结束和错误等事件。executionId 标识本次运行，节点事件再通过 nodeId 对应到画布中的节点。前端根据事件类型更新状态，展示输入、输出、耗时和错误，让用户可以查看整次执行，也可以定位到具体节点。

### 项目中的变量编辑器（支持 `${}` 高亮）是如何实现的？

普通的 textarea 只能显示纯文本，不能把其中的变量单独渲染成高亮标签，所以项目使用 Tiptap，并通过插件机制实现自定义节点。

用户输入 `/` 后，Tiptap 自带的 Suggestion 插件展示上游节点的可用变量。选中后插入变量标签，标签显示节点和变量的可读名称，内部保存节点 ID 和变量名组合。这个组合作为整体被编辑，避免被误删其中一部分。

保存时，将普通文本和变量节点序列化为包含变量表达式的纯文本。回显时，用正则识别表达式，取出节点 ID 和变量名，再结合节点与输出定义中的名称，还原成自定义的节点标签。

### 如何设计支持插件化扩展的节点系统？

我用注册模式维护节点类型与执行器的对应关系，由不同执行器提供具体的执行策略。调度引擎通过统一契约调用节点，新增节点时主要补充配置和执行器。

我定义`NodeExecutor` 接口约定执行入口与结果格式，实现抽象基类`BaseNodeExecutor` 集中处理日志、变量解析和计时等公共步骤。具体执行器实现 `doExecute()` 抽象方法，由基类的 `execute()` 包装调用，公共能力和节点业务分开维护。

然后使用 `NodeRegistry` 在项目中以节点类型和执行器实例的 Key value 形式注册节点执行器。启动时完成注册，运行时引擎按照 type 查找并调用。

比如新增发送邮件节点，先定义收件人、标题和内容等配置 Schema，再编写继承基类的执行器，最后注册 email 类型。执行过程中遇到邮件节点，就会直接去找到 email 执行器运行。
