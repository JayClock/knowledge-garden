# 项目介绍：企业级低代码工作流引擎

## 项目主轴

为企业低代码平台提供普通业务流程的执行能力，让用户在画布上配置的流程能够被引擎按预期执行。TypeScript 执行引擎消费统一的流程定义，完成校验、调度和节点执行；变量编辑器支持跨节点数据引用，测试运行与日志界面提供执行反馈。

流程配置 → 执行引擎（流程定义、校验、调度与节点执行）→ 调试反馈。

## 项目介绍

这个项目是公司低代码平台的业务工作流能力，用户通过拖拽节点、配置条件来组合业务流程，关键是让画布上的配置能够被正确执行。

我负责整个工作流执行引擎和变量编辑器，并打通流程配置到执行反馈的核心链路

我通过注册模式和策略模式设计了一套节点插件化的工作流执行引擎，在执行前，通过深度遍历进行整个工作流引擎的成环检测，并通过动态剪枝的方式，避免在工作流生成拓扑排序时，将条件分支的公共汇合节点排除。

为了在跨节点引用上游节点数据，基于 tiptap 实现了变量编辑器，将字段引用定义为不可拆分的标签，并保存为统一表达式。

最终达成了从工作流定义和变量引用到流程调度的执行反馈的核心链路。用户可以在发布前测试运行根据节点状态输入输出和日志定位问题。即使新增节点，核心的调度流程也可以不发生变化

## 高频追问

### 如果面试官问：如何设计支持自定义流程的工作流引擎，核心难点是什么？

执行引擎包含流程定义、图校验与调度、节点执行和运行上下文。它以 `WorkflowDefinition` 作为输入契约，用 DAG（有向无环图）表达流程：节点保存类型和配置，边表达依赖关系。执行前先校验定义、构建图并检测环，再生成拓扑顺序，最后按顺序调用节点执行器。

核心难点是保证有效前驱先于后继、在排除未选分支时保留公共汇合节点，以及通过独立上下文传递变量并隔离不同运行的数据。

**GraphBuilder 和 WorkflowEngine 的分工**：`GraphBuilder` 负责图结构与执行顺序，`WorkflowEngine` 负责真正驱动节点执行。

- **GraphBuilder** 接收工作流定义中的 nodes 和 edges，构建邻接表、反向邻接表与入度表；通过 `hasCycle()` 检测环，通过 `getExecutionOrder()` 规划拓扑顺序；条件分支确定后，通过 `selectBranch()` 排除未选路径并维护排除集合。
- **WorkflowEngine** 创建执行 ID、独立执行上下文和日志器，先校验工作流，再取得执行顺序；按顺序读取节点定义中的 `type`，从 `NodeRegistry` 查找执行器并逐个 `await` 调用，处理节点结果、失败与最终输出。

Condition 执行器给出分支选择后，引擎把选择交给 GraphBuilder 更新有效路径，再取得新的执行顺序继续调度。拓扑排序解决“依赖顺序”，条件判断解决“本次哪些路径要执行”，所以初次排序中同时出现的 A、B，在分支决策后可能只保留 A。

引擎用已执行节点 `Set` 避免更新执行顺序后重复调用已经完成的节点。这份集合每次运行新建，属于当前这次执行，不沿用上一轮的记录。

### 如果面试官问：为什么采用拓扑排序，怎样校验图结构和检测环？

直接从 Start 沿连线递归执行，容易在依赖尚未满足时提前调用公共下游。例如 A、B 都是 C 的有效前驱，从 A 递归到 C 时，B 可能还没有执行。拓扑排序保证有效前驱先于后继，C 才能在依赖满足后执行；未选中的条件分支则按分支排除机制处理。

运行前，工作流验证器检查 Start 和 End 是否存在、Start 是否唯一、节点类型与静态配置是否通过验证，以及边引用的源节点和目标节点是否存在。通过后由 GraphBuilder 构建邻接表、反向邻接表和入度表，分别查询下游、查询上游和记录依赖数量。

**环检测使用 DFS，并区分两份集合**：全局访问集合避免重复遍历，当前递归路径集合用于判断回边。访问到已经位于当前路径中的节点，才表示成环；递归返回时移除当前路径中的节点，避免把合法的公共汇合误判成环。

**Kahn 算法使用剩余入度和就绪队列**：初始入度为 0 的节点入队；节点出队后加入排序结果，再将后继入度减 1；后继入度降为 0 时才进入队列。例如 C 的入度为 2，A 出队后降到 1，B 出队后降到 0，随后 C 入队。

这里要区分**构建图、生成顺序和实际执行**：先从 nodes、edges 构建邻接表与入度表，再用 Kahn 算法排序，最后由 WorkflowEngine 按序调用执行器。排序中的“出队”只是在生成执行序列；例如 A 出队、C 的入度从 2 减到 1 时，A 的节点业务还没有被调用。

### 如果面试官问：条件分支怎样对应到连线，如何保留公共汇合节点？

节点的 `id` 标识节点；边的 `source`、`target` 标识连接哪两个节点，`sourceHandle` 标识从源节点的哪个出口出发。对于 Condition，出口对应具体分支，因此引擎可以用分支选择匹配连线，而不是把 `sourceHandle` 当成节点 ID。

命中某一分支后，需要排除未选路径，但不能无差别地递归排除整棵子树。例如 A、B 两条路径最终都连接到 End，选中 A 后，沿 B 无差别递归会把公共 End 一并排除。

我的处理方式是维护排除集合，并通过反向邻接表检查其他活跃入边。沿 B 向下遇到公共节点时，如果还有来自 A 等有效路径的前驱，就保留该节点；只有所有前驱入边都失效，才排除当前节点并继续向下检查。

**保留判据是前驱路径是否仍然有效，不是前驱是否已经执行完成。** 即使 A 已经执行完成，只要 A 是选中路径上的有效前驱，End 仍然应该保留。分支排除后再更新拓扑顺序，保留下来的节点仍需满足有效路径的依赖关系。

### 如果面试官问：跨节点变量怎样传递，如何隔离不同运行的数据？

每次工作流执行都创建独立的 `ExecutionContext`，保存流程定义、输入参数、变量存储与完成节点信息。上游执行成功后，把输出按 `nodeId` 保存到本次上下文中。

下游配置保存的是 `${nodeId.variableName}`。执行器处理配置时，解析引用中的节点 ID 和变量名，从本次上下文的变量存储取值，再替换到配置里供当前节点使用。

配置解析递归处理不同结构：字符串解析变量表达式，数组逐项递归，对象遍历各个 value 后递归，其他值保持原样。变量不存在时保留原表达式，例如 `结果：${A.result}` 找不到 `A.result` 后仍保持原字符串，不替换为空值。

**不同运行的隔离依靠独立上下文，不依靠节点 ID 全局唯一。** 两次运行可以都有节点 A，输出分别保存在各自上下文中，互不覆盖。注册表可以复用同一执行器实例，单次运行的输入、变量和输出仍由当前上下文管理。

### 如果面试官问：变量编辑器（支持 `${}` 高亮）如何实现，引用怎样保存和保持稳定？

我选择 Tiptap 的主要理由，是在普通文本中嵌入结构化、不可拆分的变量引用。通过自定义 Extension 定义 `variableMention` 行内原子节点，标签携带引用属性，能保护引用不被用户从中间删改成残缺表达式；高亮只是展示效果。

这套设计区分编辑、保存、回显和执行：

1. **编辑时**：用户输入 `/`，触发 Suggestion 插件，展示上游节点可用的变量列表；选中后插入 `atom: true`、`inline: true` 的 `variableMention` 标签，显示节点和变量的可读名称，内部不可逐字符编辑。
2. **保存时**：将标签转换为 `${nodeId.variableName}`，与普通文本一起保存，保留稳定的引用标识。
3. **回显时**：从保存文本中识别变量表达式，解析出 `nodeId` 和 `variableName`，结合节点与输出定义中的名称信息，还原为 `variableMention` 节点。例如 `你好，${A.name}` 会恢复成普通文本和变量标签；即使工作流一次也没执行过，标签也能正常回显。
4. **执行时**：由引擎从本次执行上下文取出实际值。编辑态回显需要的是名称信息，不是一次运行产生的实际输出值。

只修改节点显示名称时，`nodeId` 和底层 `variableName` 保持不变，已有引用仍然有效。更改输出字段名则不同：上游从 `amount` 改为只返回 `total`，旧引用 `${A.amount}` 不会自动迁移，用户需要重新选择并保存新引用；执行时找不到旧变量，仍按缺失变量策略保留原表达式。

### 如果面试官问：如何设计支持插件化扩展的节点系统，新增节点要改哪些地方？

我用注册模式管理节点类型与执行器的对应关系，让引擎通过统一契约调用不同节点的执行策略，并把公共步骤与具体业务分开：

| 组成               | 职责                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `NodeExecutor`     | 接口契约：约定节点类型、`execute()` 的调用方式与返回结果，并提供可选的配置校验和输出描述能力 |
| `BaseNodeExecutor` | 公共实现：统一计时、调用业务方法、保存成功输出、捕获异常与记录日志                           |
| `NodeRegistry`     | 注册查找：按节点类型保存执行器实例，供引擎查找并调用                                         |

```ts
interface NodeExecutor<TConfig = Record<string, unknown>> {
  readonly type: NodeKind
  validate?(config: TConfig): { valid: boolean; errors?: string[] }
  execute(
    nodeId: string,
    config: TConfig,
    context: ExecutionContext,
    logger: ExecutionLogger,
  ): Promise<NodeExecutionResult>
  getOutputSchema?(config: TConfig): OutputVariableSchema[]
}
```

接口让引擎依赖统一契约，基类集中复用公共步骤，具体节点继承基类并实现 `doExecute()`。`execute()` 采用模板方法模式组织公共流程，基类另提供 `resolveConfigVariables()` 深度变量解析方法。这样不同节点可以遵守同一种调用方式，业务逻辑留在具体执行器中。

在项目中，注册表作为共享单例使用，内部 Map 的 key 是节点类型，value 是已经创建好的执行器实例，系统启动时通过 `registry.register(type, executor)` 注册。引擎按节点 `type` 取得实例，调用它的 `execute(nodeId, config, context, logger)`，再由基类调用子类实现的 `doExecute()`，而不是直接从 Map 取出一个业务方法。

复用的是执行器，不是节点身份：A、B 即使使用同一种执行器，仍通过传入的 `nodeId` 区分，运行数据通过本次上下文隔离。

**执行侧新增节点接入配置与执行器**：先定义配置 Schema 与校验规则，实现具体执行器，最后调用 `registry.register(type, executor)`。新增节点的变化集中在这几个接入点，核心调度逻辑保持稳定。

以假设新增“文本拼接节点”为例：配置定义 `prefix`、`content` 两个参数；执行器调用变量解析方法后完成拼接，返回 `text` 输出；注册表关联节点类型与执行器。若 `prefix` 是“你好，”，`content` 引用 `${A.name}`，本次上下文中 `A.name` 是“小明”，预期输出就是“你好，小明”。

### 如果面试官问：节点抛出异常后，基类和引擎怎样处理？

这条链路分为节点失败结果和工作流失败结果两层：

1. `doExecute()` 抛出异常，`BaseNodeExecutor.execute()` 用 `try-catch` 捕获，返回包含 `success: false`、空输出、错误与耗时的 `NodeExecutionResult`，并记录节点结束日志。
2. 基类返回的是失败结果，单纯 `await` 这个结果不会自动抛错。WorkflowEngine 检查到 `success: false` 后主动 `throw`，退出后续执行循环。
3. 引擎最外层的 `catch` 捕获主动抛出的错误，返回工作流失败结果，包含失败状态、本次执行的唯一 ID、具体错误、从开始到失败的耗时，以及截至失败时已经收集的日志，供调用方检查本次执行。

这样节点执行器负责将业务异常转换为统一结果，引擎负责根据结果停止流程并收束整次执行。

### 如果面试官问：怎样设计测试，验证未选分支跳过而公共汇合保留？

我会构造一条完整 WorkflowEngine 测试流程，使用 Start、Condition、A、B、C 五个节点，其中 C 是 End：

```text
Start → Condition → A → C（End）
                 └→ B ─┘
```

Start 负责入口，Condition 负责分支决策。固定条件使其选中通向 A 的出口，预期断言为：

| 节点或结果             | 预期       |
| ---------------------- | ---------- |
| Start、Condition、A、C | 各执行一次 |
| B                      | 执行零次   |
| 工作流结果             | 执行成功   |

测试时可以在执行器的 `execute()` 入口记录每次调用的 `nodeId`，再按节点 ID 累加次数。即使 A、B 复用同一个执行器实例，也能分别检查 A 一次、B 零次，而不是仅统计共享执行器的总调用次数。

这组设计同时检查选中路径执行、未选路径跳过、公共汇合保留，以及汇合节点不被重复执行。

### 如果面试官问：变量菜单怎样确定上游范围和可选输出？

上游范围根据连线确定：建立 `target → sources` 的反向边映射，从当前节点向上做 DFS，收集能到达当前节点的上游节点，并用 Set 避免重复访问和收集。

变量菜单展示的是输出定义中的名称、标签和类型，因此工作流还没执行也可以显示候选项。选中后保存节点 ID 与变量名形成引用，实际值留到运行时解析。

**代表性重实现中的具体链路**是：开始节点从 `config.inputs` 生成输出定义，HTTP 等内置节点预先声明输出字段，插件节点读取节点数据中声明的 `outputs`。`getAvailableNodeOutputs()` 把这些定义与节点 ID、名称组合起来，再交给变量编辑器和 `/` 菜单使用。这条菜单链路调用前端 `getNodeTypeOutputs()`。例如 HTTP 节点预先声明 `data`、`status`、`headers`、`success`、`error` 五个候选输出；这些是输出定义，实际值在执行 HTTP 请求后才产生。

### 如果面试官问：测试运行与执行日志怎样展示？

1. **测试运行面板**：输入测试参数后运行工作流，通过 SSE 接收 `workflow:start`、`node:start`、`node:end`、`log`、`workflow:end` 和 `error` 等结构化事件，更新节点状态、结果与日志。
2. **执行记录**：以 `executionId` 标识执行记录，保存输入、输出、状态、耗时、错误和节点追踪信息，供执行历史与详情界面查询。
3. **Trace 面板**：根据节点与 Edge 用 Kahn 算法计算拓扑展示顺序，列出实际收到的节点追踪信息，包括运行状态、输入输出、耗时与日志。
