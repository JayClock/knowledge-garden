# 项目介绍：企业级低代码工作流引擎

## 提取词

工作流协议与双端脱节 ｜ React Flow 与 TS 执行器 ｜ Kahn 拓扑与分支汇合剪枝 ｜ Tiptap 变量与上下文解析 ｜ 插件化节点解耦 ｜ executionId 双向排障

## 2 分钟版本

我负责工作流协议、React Flow 编辑器、Tiptap 变量编辑器与 TypeScript 执行引擎。项目先用 `WorkflowDefinition`、Node、Edge、节点 Schema 和变量协议统一编辑器与执行器，避免画布和运行时各维护一套结构。

运行前，验证器检查 Start、End、节点类型、配置和边引用；GraphBuilder 再建立邻接表、反向邻接表和入度表，通过环检测与 Kahn 算法生成拓扑顺序。Condition 节点命中分支后排除未选路径，但遇到公共下游时会检查其他活跃入边，避免误删仍应执行的节点。

跨节点数据由独立的 `ExecutionContext` 保存。`${nodeId.variableName}` 会被递归解析，前端则用 Tiptap 把变量显示成不可拆分标签。节点扩展采用 `NodeRegistry + NodeExecutor`，新增节点不需要修改核心调度器。

为了让验收和运行诊断能够判断用户在哪个环节失败，我还接入监控 SDK，为工作流校验、测试运行和发布添加自定义事件；节点状态、耗时和错误仍由执行引擎日志负责，两侧通过 `executionId` 关联。服务端由后端协同实现 API 与 SSE 推送，我负责协议定义、端侧接入与执行反馈对接。

## 5 分钟主讲

我先介绍一下这个项目的背景。我们在做企业级低代码 AI Flow 时，最核心的挑战不是简单地在前端用 React Flow 连线画图，而是如何建立可视化编辑器与底层执行引擎之间的严密执行契约。过去工作流最容易出现的架构坏味道，就是前端画布存一套包含坐标和选中态的 JSON，后端执行器又另建一套数据，两边靠胶水代码来回转换，极易在版本演化中脱节。

为了确立统一的执行契约，我先用 `WorkflowDefinition`、Node、Edge、节点 Schema 和变量协议规范了全链路。Node 负责类型与静态配置，Edge 表达数据流与分支流向，Schema 统一约束前端配置表单与执行器输入。编辑器只负责生成合法定义，绝不把画布坐标和拖拽草稿等 UI 状态渗入运行时。

但在执行阶段，由于画布允许用户自由连线，底层的图执行必须建立在严格的形式化验证之上。运行前，验证器会严格检查 Start/End 节点、配置有效性以及边引用的完整性；随后由 GraphBuilder 分别构建邻接表、反向邻接表与入度表。主流程必须是严格的 DAG，因此先做基于 DFS 的环检测拦截非法环路；合法图再通过 Kahn 算法把入度为 0 的节点推入队列，生成确定性的拓扑调度序列。

这里最棘手的技术难点是**条件分支（Condition Node）的动态剪枝**。当分支命中后，未选路径需要被排除，但绝不能简单粗暴地递归剔除整棵子树。因为在实际业务中，不同分支往往会在下游汇合到同一个公用节点，比如无论审批通过还是拒绝，最后都要发送一条通知。如果直接递归剪枝，公用节点就会被错误移除。我的解决方案是结合反向邻接表做入边活跃度检查：在沿着未选分支排除时，动态检查汇合节点是否还存在来自其他未排除路径的有效前驱。只要仍有活跃入边，汇合节点就必须保留，并在分支决策后动态重算拓扑顺序，兼顾了分支排除与公共汇合。

另一个关键攻坚是跨节点变量协议在编辑器与运行时的闭环。节点之间需要消费上游输出，如果让用户盲写变量路径极易拼错，若直接在前端共享一块全局大对象又会导致状态被任意读写，难以做单步排障。在编辑侧，我引入 Tiptap 开发变量胶囊编辑器：将上游变量渲染为不可拆分的原子标签，用户通过斜杠菜单直接选择上游输出；界面显示可读名称，底层持久化为稳定的 `${nodeId.variableName}` 占位符。在运行侧，每次执行实例化独立的 `ExecutionContext` 隔离存储状态；节点运行前由 `VariableResolver` 递归解析占位符并读取上游结果。如果遇到未声明变量，选择**保留原始占位符而不静默替换为空值**，避免掩盖逻辑缺陷，并在执行反馈中准确定位问题引用。

为了防止每新增一个业务节点就修改核心调度代码，我把节点逻辑解耦为 `NodeRegistry` 和 `NodeExecutor` 的插件化架构。通用引擎只负责拓扑编排、变量解析、耗时统计与异常兜底，具体节点的计算和远程调用封装在独立 Executor 中，核心调度器保持绝对收敛。

在可观测层面，为了让研发与运维清晰定位用户是在“前端连线校验”、“联调测试运行”还是“生产发布”环节发生故障，我在 AI Flow 中接入监控 SDK，为关键操作上报自定义事件；具体节点成功失败、执行耗时与堆栈错误由 TypeScript 执行引擎日志精确记录。两端通过同一个 `executionId` 串联，实现了从画布设计到节点运行的全链路证据追踪。

这段经历让我建立了从流程画布到执行系统的共享契约，也让我开始从下游验收和诊断需要什么证据，倒推事件协议与日志关联设计。

## 高频追问

### 如果面试官问：图结构怎样校验和执行？

运行前，工作流验证器会严格检查四件事：Start 和 End 节点是否存在、节点类型是否已注册、节点静态配置是否通过 Schema 校验，以及边引用的源节点和目标节点是否存在。

通过校验后由 GraphBuilder 构图：构建邻接表用于查找下游后继，反向邻接表用于查找上游前驱，入度表记录每个节点的未就绪依赖数。工作流主流程必须是严格的 DAG，因此先用 DFS 遍历并在递归栈中检测回边（Back Edge）拦截环路；合法图再交给 Kahn 拓扑排序算法。

Kahn 算法将所有入度为 0 的节点推入就绪队列。节点出队执行并产出结果后，遍历其后继节点并将其入度减 1；当后继节点入度降为 0 时，该节点即满足触发条件进入就绪队列。我把形式化校验、图构建、动态分支决策与执行器调度完整组合起来，保证了拓扑调度的确定性。

### 如果面试官追：条件分支怎么处理？为什么不能递归剪枝？

Condition 节点命中某一分支后，未命中的分支路径需要被排除，但**绝不能简单地沿着未选分支递归删除整棵子树**。

因为在实际业务中，不同分支经常会在下游汇合到同一个公共节点（比如审批通过或驳回后，最后都要走到“发送通知”节点）。如果直接做子树递归剪枝，公共汇合节点就会被错误移除。

我的方案是利用**反向邻接表进行入边活跃度检查**：在沿着未选中分支排除下游时，动态检查汇合节点是否还存在来自其他未排除路径的有效前驱。只要该节点仍然有活跃入边，就必须予以保留；只有当它的所有前驱入边全部失效时，才继续向下排除。分支决策后动态重算拓扑顺序，兼顾了分支排除与公共汇合。

### 如果面试官追：跨节点上下文和变量怎样传递？

每次工作流执行都会实例化独立的 `ExecutionContext`，按 `nodeId` 隔离存储各节点的执行状态、输出数据与耗时。

节点运行前，由 `VariableResolver` 递归扫描节点配置中的字符串、数组和深层对象，识别形如 `${nodeId.variableName}` 的占位符。解析器根据 `nodeId` 在上下文中定位上游输出并提取属性值。

如果遇到未声明或未执行的变量，选择**保留原始占位符而不静默替换为空值**，避免掩盖配置缺陷，并在执行反馈中准确定位问题引用。

### 如果面试官问：为什么不用普通 textarea，而是用 Tiptap 胶囊？

textarea 只能存储纯文本，无法保证变量引用的结构稳定性。

用户在配置时需要看到上游节点的中文展示名（例如“上游审批人的姓名”），但如果直接把展示名存在文本里，上游节点一旦重命名，下游的所有引用全部失效。

我引入 Tiptap 开发变量胶囊编辑器：界面中展示为不可拆分的原子标签（Label），底层统一持久化为稳定的 `${nodeId.variableName}` 规范字符串。原子节点拦截了光标退格与字符输入，防止用户把变量名删改一半导致解析失败；用户输入 `/` 或 `@` 时弹出 Suggestions 菜单列出可用上游变量，兼顾了配置体验与底层协议稳定性。

### 如果面试官追：Tiptap 原子化胶囊怎么防止被用户破坏？

主要通过 ProseMirror 的 NodeSpec 约束与事务拦截保证原子性：

变量节点定义为 `atom: true` 和 `inline: true`，禁止在节点内部插入字符；Backspace 和 Delete 键针对原子节点只支持整块删除，不支持局部破坏；粘贴外部文本时通过解析器过滤，只有符合协议的字符串才能重新实例化为原子胶囊。

### 如果面试官问：为什么不用 eval？公式计算怎么保证安全？

低代码配置面对的是企业级业务规则，直接使用 `eval` 或 `new Function` 会把用户输入直接暴露在全局 JavaScript 运行环境中，存在原型链污染和安全穿透风险。

在架构设计上，我们将变量取值限制在 `${nodeId.variableName}` 协议内，由安全沙箱 `VariableResolver` 严格按键查找。

在需要支持更复杂的数学与逻辑表达式（如 `sum`、`if`）时，自研公式引擎采用 Lexer 词法分析生成 Token 流，再由 Parser 解析为抽象语法树（AST）。解释器采用严格的白名单机制，只开放受控的基础算子与纯函数，计算上下文严格隔离，从根本上杜绝任意代码执行。

### 如果面试官追：公式编辑器 AST 技术方案具体怎么设计？

这套自研公式解析方案的设计核心是将解析与执行彻底解耦：

1. **语法分析**：词法分析器（Lexer）将输入分解为 IDENTIFIER、FUNCTION、OPERATOR、LITERAL 等 Token；语法分析器（Parser）基于递归下降算法构建 AST 语法树。
2. **安全沙箱**：求值器（Interpreter）只遍历已知类型的 AST 节点，严禁访问 `window`、`document`、`Function` 或对象的 `__proto__` 原型。
3. **交互与反馈**：在编辑器中实现语法与括号匹配的高亮提示；遇到非法字符或语法错误时，Parser 抛出包含行列号的精准定位，驱动 Tiptap 编辑器在光标处下划线报错。

### 如果面试官问：一个节点插件具体包含什么？新增节点要改哪些地方？

节点解耦为 `NodeRegistry` 注册表与 `NodeExecutor` 抽象策略：

```ts
interface NodeExecutor<TConfig = Record<string, unknown>> {
  type: NodeKind
  validate?(config: TConfig): ValidationResult
  execute(nodeId: string, config: TConfig, context: ExecutionContext): Promise<NodeResult>
  getOutputSchema?(config: TConfig): OutputVariableSchema[]
}
```

通用调度引擎只依赖 `NodeExecutor` 接口，负责拓扑编排、变量求值、超时与重试控制。

新增业务节点时，只需定义其配置 Schema、实现独立的 `NodeExecutor` 类，并在前端注册对应的表单组件，最后调用 `registry.register(type, executor)`。核心调度器不需要修改任何 `switch-case`，变化完全收敛在插件边界。

### 如果面试官追：插件执行抛错怎么处理？

节点执行由引擎层统一包裹 `try-catch` 捕获同步与异步异常。

如果插件抛错，引擎将异常包装为统一的 `NodeExecutionError`，记录当前节点 ID、耗时和堆栈；在上下文中标注该节点为失败状态，根据节点重试配置执行指数退避重试；若重试耗尽，终止下游依赖分支的执行，并在最终的流程执行报告中输出结构化错误追踪。

### 如果面试官问：Monorepo 怎么分层与治理依赖版本？

项目基于 pnpm workspace 和 Turborepo 组织代码：

- `packages/` 存放框架无关的 core 协议、TypeScript 执行引擎和 UI 组件库；
- `apps/` 存放低代码工作流设计器前端和 API 服务。

依赖治理上，基础依赖（如 React、TypeScript）在 root 层保持单版本；底层共享包将 React 声明为 `peerDependencies`，确保宿主应用与插件共享同一份 React 实例，彻底避免多实例引发的 Hooks 报错。启用 pnpm 严格依赖模式禁止幽灵依赖，结合 Turborepo 任务图实现构建与测试的高效缓存。
