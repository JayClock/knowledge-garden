# 项目介绍：AI 辅助领域建模平台

## 提取词

方法论落地与记录 ｜ 业务语义契约 ｜ React Flow 可视化建模 ｜ AI Proposal 与人工确认 ｜ 草稿、审核与版本发布 ｜ 固定修订 FM 快照 ｜ MCP 工具与资源 ｜ 本地候选校验与文件更新 ｜ 契约导出与下游消费

## 2 分钟版本

过去团队主要通过会议和白板讨论业务，讨论结果难以长期维护，业务、前端和后端各自保留一部分理解。我设计并实现了 AI 辅助领域建模平台，以 Evidence 与 8X Flow 建模方法为基础，把参与方、角色、权责、事件、领域对象、关系与履约凭证落地并记录为结构化领域资产，形成前后端共同审核和消费的业务语义契约。

我负责可视化建模、模型记录、AI 提案与审核发布链路。前端基于 React Flow，把业务分析结果映射为节点、关系和属性，供团队围绕同一份模型讨论。模型通过草稿、版本快照与正式发布管理演进，让会议中的业务理解有可持续维护的记录。

AI 辅助采用结构化 Proposal：输出受元模型 Schema 约束的节点和关系，用户可以定位、预览、逐项采纳或拒绝。确认后的提案进入模型草稿，再经过人工审核与版本发布形成正式模型。候选生成与业务语义确认分开，正式模型的发布权由人工审核掌握。

服务端按固定修订将模型定义导出为 FM 快照，MCP 提供获取入口，本地程序完成下载、校验和文件更新。发布模型作为 RESTful API 候选、OpenAPI 草稿和测试数据的上下文。在真实库销存 Agent 场景中，我们从采购合同出发，建模参与方、发货、收货、退货及履约 Evidence，跑通模型记录到接口契约消费的路径。交付结果通过单元测试、契约测试、E2E 与人工审核验证。

## 项目主讲

在企业业务交付中，前端与后端往往会反复解释同一个业务概念。过去团队建模主要依赖白板和会议讨论，结果很难持续维护，前端、后端和业务各自保留一部分理解，容易在接口联调时才发现对领域规则的理解不一致。为了解决这个问题，我设计并实现了 AI 辅助领域建模平台，把 Evidence 建模方法论的分析结果落地并记录为结构化资产，转化为前后端共同消费的业务语义契约。

我负责可视化建模、模型记录、AI 提案与审核发布链路。平台把 8X Flow 中的参与方、角色、权责、事件、领域对象、关联关系和履约凭证映射为节点、连线与业务属性，通过 React Flow 提供可视化表达。业务、产品和研发围绕这份模型讨论、澄清与审核，平台负责保存分析结果，并通过草稿、版本快照与正式发布管理模型演进。

在 AI 辅助部分，我把候选生成与正式模型发布分开。AI 输出受元模型 Schema 约束的节点和关系 Proposal，前端提供受影响对象定位、预览和逐项采纳／拒绝交互。经用户确认的提案进入模型草稿，再通过人工审核与版本发布形成正式模型。这样保留了 AI 生成候选方案的能力，同时让业务语义的确认落在业务专家与人工审核环节。

模型同步拆成服务端导出、MCP 接入和本地更新三个部分。服务端按固定修订批量读取多表模型定义，把模型元信息、实体及其属性与引用、关系、规则及 bindings 组装成 FM JSON 对象分片。导出器保留稳定 ID、业务顺序和 CEL 表达式，以确定性的序列化生成一致快照。

MCP 导出工具返回快照清单，其中包含修订、Schema 版本、文件路径、摘要与资源 URI。本地同步程序内置 MCP Client，通过 `resources/read` 获取属于同一快照的文件内容，文件数据由程序直接处理。

本地程序先下载到独立候选目录，检查文件摘要，并对完整候选模型执行 Schema、引用完整性和 CEL 校验。随后对照上次同步清单检查差异与本地修改，获授权后在读写锁下重查并更新模型文件，记录同步修订、摘要与校验结果。删除只作用于同步清单托管的文件；遇到本地修改冲突或下载校验失败时，保留当前有效模型。

发布后的模型继续服务于下游交付：参与方、权责、事件、领域对象和关系成为 RESTful API 候选设计、OpenAPI 草稿及测试数据候选的上下文，正式接口契约经过人工审核。在真实的库销存 Agent 场景中，我们从采购合同出发，建模了参与方、发货、收货、退货以及正常／异常履约 Evidence，跑通了从业务分析、模型记录到接口契约消费的路径。

平台在内部被业务、产品与研发团队持续使用。这个项目的交付是把讨论中的业务理解记录为可维护、可审核、可发布的领域模型，并建立模型到前后端契约的消费路径。AI 负责候选生成，人工审核确认业务语义，发布版本为下游提供明确的模型依据。

## 高频追问

### 如果面试官问：为什么说这是前端与后端之间的契约平台？

因为它把 Evidence 建模方法论的分析成果，落地并记录为可持久化、可版本化追踪的领域资产。业务专家、前端与后端对参与方、履约角色、生命周期、关系、权责动作和 Evidence 凭证形成同一份可审核的知识。方法论提供业务语义，平台提供记录、审核和导出的工程载体。

在这个平台上，前端用模型理解资源生命周期与合法动作，后端用它设计 RESTful URI 与数据边界，发布后的模型作为 OpenAPI 草稿和正常／异常测试数据候选的上下文。

这份契约的权威来自人工评审和发布版本。平台提供契约的形成、记录、版本和消费路径，通过人工审核与版本化管理确认正式业务语义。

### 如果面试官问：AI 如何参与建模？为什么还需要人工审核？

AI 根据业务输入生成受元模型 Schema 约束的节点和关系 Proposal，前端高亮受影响对象，提供预览与逐项采纳／拒绝交互。经用户确认的内容进入模型草稿，再通过“草稿 $\to$ 审核 $\to$ 版本发布”形成正式模型。

结构约束负责检查候选内容的表达形式，业务专家与人工审核负责确认参与方、权责和履约关系是否符合实际业务。AI 负责提供候选，发布版本承载经过审核的业务语义。

### 如果面试官问：建模结果怎样同步到本地？

这是服务端到本地 FM 镜像的单向拉取，完整过程分为四步：

1. **导出一致快照**：服务端先确定本次导出的修订，批量读取模型、实体、属性、引用、关系和规则数据，将规则与 bindings 一起组装为完整 FM 对象，再按对象输出 JSON 分片。一张表是存储结构，一个完整对象才是文件分片的单位；所有读取都固定在同一修订。
2. **通过 MCP 获取**：导出工具返回快照清单，列出修订、Schema 版本、文件路径、摘要与资源 URI。本地 MCP Client 通过 `resources/read` 获取绑定同一快照的内容，保持获取范围一致。
3. **下载并校验候选模型**：文件先进入独立候选目录，按实际输出字节校验摘要，再对完整候选模型做 Schema、引用和 CEL 校验；对照上次清单展示新增、修改与删除，并检查本地托管文件是否被编辑。
4. **授权后更新文件**：校验通过并获授权后，在读写锁内重新检查本地修改，再更新模型文件与同步记录。删除只针对同步程序托管的文件；下载或校验失败、检测到本地修改冲突时，当前有效模型继续保留。

MCP 提供标准化的工具与资源获取入口。模型转换、修订一致性、文件校验和本地更新分别由导出器与本地同步程序承担。

### 如果面试官问：平台产生的模型怎样被下游使用？关联对象怎么设计？

在真实的库销存场景中，我们从采购合同出发，建模了参与方、履约角色、发货、收货、退货与 Evidence 凭证。发布后的模型作为 RESTful API 候选设计、OpenAPI 草稿和正常／异常测试数据候选的上下文，正式接口契约经过人工审核。

在关联关系落地时，我设计了**关联对象建模方法**：将一对多关系从原始集合提升为具有业务语义的领域对象（如“合同项清单”）。领域层只定义业务导航与操作，具体的分页、批量预加载和延迟加载策略封装在关联对象内部，保持聚合根边界，并通过具体加载策略控制 N+1 查询风险。
