# 简历回答逐字稿：契约驱动的全流交付

关联：[[简历追问：契约驱动的全流交付]]、[[全栈工程师简历候选人回答逐字稿]]、[[简历回答逐字稿：渐进式架构与可恢复增强]]。

> [!warning] 回答边界
>
> - “契约”不限于接口文档或 TypeScript 类型，而是跨角色、跨系统可以共同审核、消费和验证的结构化知识。
> - 领域建模平台承载前端与后端之间的业务语义契约；Figma AI 承载产品设计与前端实现之间的设计契约。
> - HATEOAS、工作流协议、监控事件和 Agent Harness 分别处理契约的运行时消费、执行、验证与权威边界。
> - 契约不能脱离业务模型、消费方和验证证据独立成立，也不能把协作成果扩大成个人实现。

## 30 秒定位

我的职业主轴是契约驱动的全流交付。我关注不同角色在哪里重复解释同一份知识，再把它固化成可消费、可执行和可验证的工程契约：领域建模平台连接前端与后端，Figma AI 的设计 DSL 连接产品设计与前端，HATEOAS 和工作流协议负责运行时消费与执行，监控和 Agent Harness 再提供验证、失败回流与人工权威边界。

## 2 分钟职业演进

我的前端基本盘来自编辑器和低代码平台。真正形成契约意识，是在 PC Web 与移动 Web 分别维护状态、权限和动作规则时：几个客户端都在重复解释后端状态。我参与把资源关系和合法动作收敛为 HATEOAS 契约，并实现 TypeScript SDK 与 React Hooks，让多端消费同一份业务事实。

随后在 AI Flow 中，我把契约从“接口如何消费”推进到“模型如何执行”。`WorkflowDefinition`、Node、Edge、Schema 和变量协议同时约束 React Flow 编辑器与 TypeScript 执行引擎，插件节点在稳定协议上扩展，执行日志和 `executionId` 再验证定义是否被正确执行。

在领域建模平台中，契约继续前移。参与方、权责、事件、领域对象和关系被沉淀为前端与后端共同审核的结构化模型，发布后支持 RESTful API、OpenAPI 草稿和测试数据候选；AI 只能提出 Proposal，正式模型与接口仍由人确认。

Figma AI 解决的是另一条协作边界：产品设计与前端实现之间的信息容易在截图和口头交接中丢失。我用设计 DSL 表达图层、布局、样式、变量和资产，让产品设计意图能够被 Agent、Canvas 编辑器、导入链路和只读 MCP 共同消费。当前建立了设计契约和消费路径，但没有把完整页面代码生成或双向同步说成已完成。

所以我的能力并不是单纯做过前端、后端和 AI，而是围绕契约的形成、表达、消费、执行、验证和演进组织工程交付。

## 按职业时间线理解

- **易校：运行时契约、消费体系和执行证据。** 从多端规则漂移进入 HATEOAS 资源动作契约与 TypeScript 消费层，再延伸到 AI Flow 的编辑器—运行时协议、自研公式引擎和监控 SDK 的执行证据。
- **鼎歆：契约形成、治理与跨角色交付。** 领域建模平台把业务知识固化为前端—后端语义契约；Figma AI 把设计意图固化为产品设计—前端实现契约，并用人工审核与 Agent 写入边界治理。

这条时间线不是把所有项目重命名为“契约项目”，而是说明复杂前端基本盘如何逐步向上游知识形成与下游验证延伸。

## 契约全生命周期

```text
发现重复解释的知识
→ 明确权威与边界
→ 固化为模型、Schema、DSL 或状态机
→ 为前端、后端、运行时或 Agent 建立消费接口
→ 用测试、日志、版本和人工审核验证
→ 将失败返回实现、契约或业务模型
```

| 生命周期         | 主要项目                | 契约载体                                    |
| ---------------- | ----------------------- | ------------------------------------------- |
| 形成与治理       | 领域建模平台            | 8X Flow、领域对象、关系、版本与发布         |
| 运行时发布与消费 | HATEOAS SDK             | URI、relation、action、HAL／HAL-FORMS       |
| 可执行化         | AI Flow                 | WorkflowDefinition、Node Schema、变量协议   |
| 产品设计交付     | Figma AI                | 设计 DSL、DesignPatch、revision、MCP        |
| 运行验证         | 监控 SDK                | 事件协议、`executionId`、Sourcemap、队列    |
| Agent 权威与回流 | Evidence／Agent Harness | Revision、Approved Plan、`nextAction`、Gate |

## 领域建模平台：前端与后端的业务语义契约

### 业务问题

需求、白板讨论、前端判断和后端实现容易各自保存一部分业务知识。只交付接口文档，无法保证双方对领域对象、生命周期、角色权责和异常路径理解一致。

### 我的动作

我使用 8X Flow 把参与方、角色、权责、事件和 Evidence 沉淀为结构化领域模型，并实现 React Flow 建模前端、Yjs／Awareness 协同、NestJS WebSocket 服务和 PostgreSQL 持久化。模型经过草稿、版本和发布后，支持 RESTful API、OpenAPI 草稿与测试数据候选。

### 契约边界

- 领域模型是前后端共同审核的业务语义契约，不是前端单方面输出给后端的文档；
- Yjs 保证副本收敛，不保证业务语义正确；
- AI 只生成 Proposal，正式模型和接口契约必须人工确认；
- 当前没有协作人数、同步延迟和完整自动恢复指标。

## Figma AI：产品设计与前端实现的设计契约

### 业务问题

产品设计意图如果只通过截图、视觉稿和口头说明交给前端，图层、布局、变量、资产和组件关系容易丢失；模型直接生成代码又缺少稳定、可编辑的中间表示。

### 我的动作

我建立设计 DSL，把图层、布局、样式、Design Variables 和资产关系变成结构化契约。Agent 生成、Canvas 编辑器、原生 JSON／Pencil／Figma 导入和只读 MCP 都围绕同一结构工作；DesignPatch、ownership 和 revision 控制写入，Visual Harness 检查并局部修复视觉问题。

### 契约边界

- 产品和设计负责确认意图，AI 只生成候选；
- 前端通过可编辑文档和 MCP 消费设计资产，不能把当前只读链路说成完整自动代码生成；
- 产品内完整页面代码生成和 Design ↔ Code 双向同步尚未完成；
- 没有可核验的使用人数、交付效率和质量提升比例。

## HATEOAS：前后端契约的运行时发布与消费

领域建模平台解决契约如何形成，HATEOAS 解决契约如何进入运行时。服务端以 `_links` 与 `_templates` 返回当前资源可访问的关系、合法动作和 payload 约束；TypeScript SDK 用 `follow()`、`action()`、缓存和运行时检查统一 PC Web 与移动 Web 的消费方式。本人负责模型、契约、SDK 和客户端消费，服务端代码由后端同事实现。

## AI Flow：编辑器与执行引擎的执行契约

React Flow 画布不能直接成为运行时事实。我用 `WorkflowDefinition`、Node、Edge、Schema 和变量协议建立编辑器与执行引擎共享的契约，再由 GraphBuilder、ExecutionContext 和 NodeExecutor 负责校验、调度与执行。NestJS API 和 SSE 服务端由后端同事实现，本人负责共同协议、前端接入以及 PostgreSQL／Prisma 数据层。

## 监控 SDK：执行结果与验收诊断的证据契约

契约被定义和执行后，还要知道是否兑现。我从验收和诊断需要回答的问题倒推事件、上下文与关联标识，并在 AI Flow 中用 `executionId` 连接前端校验、测试、发布路径和节点执行日志。个人负责采集与上报 SDK；Kafka、ClickHouse、查询后端和控制台属于团队链路。

## Evidence：人类决策与 Agent 执行的权威契约

当 Agent 进入交付过程，契约还要规定谁能决定什么。Evidence 通过不可变 Revision、Approved Tasking Plan、唯一 `nextAction`、受限 Agent、测试和人工 Gate 区分候选、执行证据与正式决定。当前公开实现证明机制已经落地，但不等同于生产规模化使用，完整 Modeling Profile 也尚未完成。

## 按岗位调整顺序

- **高级前端／前端架构：** HATEOAS → AI Flow → Figma AI → 领域建模，监控 SDK 作为验证能力嵌入。
- **全栈偏前端的平台工程：** 领域建模 → HATEOAS → AI Flow → 监控 SDK → Figma AI。
- **AI 工程化平台：** Figma AI → Evidence → 领域建模 → AI Flow，但始终说明各自的契约载体和人工权威。

项目顺序可以跟随 JD，契约主轴不变。

## 收尾句

我擅长发现业务、产品设计、前端、后端和 Agent 之间容易丢失或重复解释的知识，把它转化为可消费、可执行、可验证的工程契约，并为契约的失败、变更和人工决策保留清晰边界。
