Agent 做错了一件事，你的第一反应是什么？

如果答案是“再加一条规则”，那这个坏味道已经在你身上了。加规则写进入口文件，再复制一份到指南，任务模板里再补一句提醒——规则加了，同类错误还在出现。

## 前馈和反馈不是一回事

前馈提高 Agent 第一次就做对的**概率**，反馈提供“它真的做对了”的**证据**。

只有前馈没有反馈时，Agent 会非常草率地结束任务：写完文件、跑一下类型检查，然后宣布完成。因为它手里没有任何东西能反驳这个判断。

这个坏味道的根源很实际：**写“怎么做”比写“怎么检查”容易**。“亮点要带数据”是过程描述，写起来轻松；“检查亮点是否包含数字、百分比或对比”要求你先想清楚结果长什么样。而后者才是能自动化、能复现、能交接的那一半。

一个仓库里如果规则很多、检查很少，说明它一直在解决“怎么说得更清楚”，从来没解决“怎么证明做对了”。

## 解法：让每条规则都能指到自己的反馈形式

### 把“加规则”变成成对动作

最小改动是一条纪律：写规则时必须同时回答“它由什么检查”。

- `AGENTS.md` 的验证底线：行为变更必须有相应测试，**只有相关检查与项目质量检查实际通过，才能声称完成**；
- 工程规范的变更约束：新增规范应连接实际检查——Java 格式交给 Spotless，前端交给 ESLint，文档交给格式化与 Guides 检查，语义边界交给相应测试和审查；
- [测试指南](https://github.com/JayClock/Evidence-Framework/blob/main/docs/engineering/testing.md)为每条质量命令写明“实际覆盖”和“不证明什么”，让检查的证明范围先于检查结果被写清楚；
- 维护纪律要求新增规范必须指出对应测试或人工评估；检查器的实际覆盖被限定在结构层面，不冒充语义。

这条纪律反过来也约束前馈：**一条约束如果写不出对应检查，要么继续澄清，要么显式记为人工评估，不能只靠提醒**。

### 前馈与反馈成对登记

项目里每一类前馈都能指到自己的检查形式：

| 前馈                                         | 反馈                                                       |
| -------------------------------------------- | ---------------------------------------------------------- |
| 业务规则（1 条 CEL 规则）                    | 2 个验证场景、5 份回放实例与只读模型校验脚本               |
| 用户故事与验收                               | 任务检查项：固定输入、预期、失败不变性、精确命令与所需证据 |
| 工序验收数据                                 | 结构化断言引用具体检查项，拒绝通用工序、文件存在或自评替代 |
| 架构分层：领域不依赖 HTTP、Spring 等         | 后端架构测试（ArchUnit 规则）                              |
| 模块化单体 profile 与任务身份                | 任务编译器测试：profile 覆盖被拒、任务键确定性、依赖环被拒 |
| 计划模板契约与单一状态归属                   | 规划、交付两个 skill 各自的 Guides 契约测试                |
| 前馈文档的本地链接与过期表述                 | Guides 检查器与其自身回归                                  |
| 任务状态与检查项一一对应、检查只读           | 状态脚本测试，含“运行前后字节不变”的断言                   |
| 模型凭证的六类时间                           | 领域时间测试                                               |
| 交互扩展只注册一个命令、一个工具、无隐藏状态 | 扩展的单元测试                                             |
| 格式与风格                                   | Spotless（Java）、ESLint（前端）、Prettier（文档）         |

看第四列会发现：**每一行都能在 CI 或本地命令里被重复执行**。这才是“规范”和“建议”的区别。

### 计算型与推断型分开

交给程序的是结构类判断：任务键、路径、依赖引用、一一对应、唯一性、只读、当前可执行任务集合。

交给 Agent 的是语义类判断：业务模型到业务模块的映射是否成立、切片是否形成最小可验收结果、检查是否真正证明了业务结果、失败属于实现、任务、切片还是来源哪一层。

这条分工来自一个明确认识：**计算通过只证明声明结构自洽，不能证明业务设计合理或测试充分**。把语义判断伪装成脚本检查，比不做检查更危险——它会制造一种虚假的确定性。

### 反馈的边界：证据不是批准

自动检查不是最终裁判。一句话写清了边界：

> 链接可达不等于指南正确，结构覆盖不等于业务批准，测试成功不等于生产保证。

人工评估与自动回归也被分开：各 skill 目录下的评测用例是行为评测的输入与评分器，本身不进入自动回归；**未实际执行的评测保持未执行**，不会因为条目存在就被记成通过。

## 演进方向

- 规则与检查的配对目前靠维护纪律和人工审查保证，还没有“批量把规则改写成检查”的清单或工具；规则继续增加时，先问“它的检查形式是什么”，必要时补测试而不是补规则；
- 语义边界、切片合理性、设计审查只有人工评估入口，没有计算型反馈，这些结论不能由测试通过代替；
- 评测案例保留在目录里但没有执行记录，因此不计入通过。

## 收束

规则回答“应该怎么做”，检查回答“做对了没有”。只有前者时，Agent 的每一次自我肯定都无法被证伪；而当规则多到没人记得住时，真正起作用的其实只剩下检查——那不如一开始就把检查当主角。
