## 30 秒开场

这个项目不是突然从前端转去做后端建模，而是延续我从多端一致性、HATEOAS 资源契约走向业务建模与 RESTful API 的能力主线，把“模型本身”进一步做成多人可协作的平台。它在上海鼎歆内部由业务、产品和研发持续使用，把原本依赖线下会议和头脑风暴的建模过程沉淀为可共同维护的结构化模型。我负责从建模画布到协同服务和持久化的完整链路：前端把共享建模状态接入 Yjs，通过 WebsocketProvider 同步增量更新，用 Awareness 展示在线成员、远端光标和协作状态；服务端基于 NestJS 与原生 WebSocket 处理内容同步和用户状态广播，并通过 PostgreSQL 持久化协同数据。

在协同编辑之上，AI 只生成结构化的节点与关系变更 Proposal，用户可以逐项定位、采纳或拒绝；确认后的模型再进入草稿、版本和发布流程。发布模型可以作为 AI 生成 OpenAPI 草稿和测试数据的上下文，OpenAPI 经人工审核后用于下游代码生成。核心取舍是让 CRDT 负责并发状态收敛，让人分别确认模型语义、AI 变更与正式接口契约。

## 如果面试官问：为什么需要 Yjs，而不是保存整张图？

整图保存适合单人编辑，但多人同时操作时容易出现后保存的人覆盖前一个人的结果。协同层需要传递增量更新，并让不同到达顺序的操作最终收敛到一致状态。

我使用 Y.Doc 管理共享建模数据。每个协作者在本地产生更新，通过 WebSocket 广播给其他客户端；Yjs 根据 CRDT 规则合并并发操作。这样网络延迟和消息先后顺序不会直接变成整图覆盖问题。

不过 CRDT 只保证状态收敛，不保证业务语义一定合理。比如两个人分别修改同一个领域对象的名称和定义，结果在结构上可以合并，但是否符合领域语言仍要通过模型评审解决。

## 如果面试官追：在线状态和光标为什么不用持久化？

模型内容与协作状态的生命周期不同。节点、关系和正文属于需要恢复的持久状态；在线用户、光标和选区属于瞬时状态。

我使用 Yjs Awareness 广播用户标识、颜色、光标和在线状态，并监听状态变化更新远端成员列表。客户端离开时清理监听和 Awareness 状态，服务端也会通过连接关闭与 ping 检测回收失效连接。这样不会把短生命周期的光标信息混入正式模型数据。

## 如果面试官追：协同服务怎么组织？

服务端基于 NestJS 和原生 WebSocket 适配器提供协同 Gateway。连接建立时，根据文档或建模空间标识找到对应的 Y.Doc，并把客户端加入当前协作会话。

消息主要分两类：

- `messageSync` 负责模型内容的增量同步。
- `messageAwareness` 负责在线用户、光标和选区等状态同步。

Y.Doc 更新后，服务端把更新广播给同一协作空间中的其他连接；连接失效时清理连接和 Awareness 状态。普通业务 API 负责认证、权限、文档 CRUD 和长期持久化，实时协同服务负责 WebSocket 长连接、高频增量同步、临时状态与消息广播。两类服务工作负载不同，因此进行拆分；这是协同系统的常规方案，我的贡献是结合建模平台完成边界划分和落地，而不是发明这种架构。

## 如果面试官问：你解决过什么实际协同问题？

开发中曾出现 React Flow 与 Yjs 双向绑定回环：React Flow 更新写入 Yjs，Yjs observer 再次 `setNodes`，监听 React 状态的 effect 随后又把整张图写回 Yjs。

定位时，我在 `onNodesChange`、`onEdgesChange`、Yjs 写入入口和 `Y.Map.observe` 回调中加入链路日志，记录节点 ID、变更类型和 `transaction.origin`，最终确认问题根因不是缺少 debounce，而是双向绑定没有区分更新来源。

解决时，我把 Yjs 收敛为共享状态源，只在明确的用户操作中增量写入；通过 `doc.transact(fn, REACT_FLOW_ORIGIN)` 标记 React Flow 本地来源，让 observer 跳过本地同源事务，只将远端事务更新到 React Flow；同时删除监听整张图后全量回写的 effect，增加新旧值比较，并在组件卸载时正确 `unobserve`。

## 如果面试官追：你怎样验证回环已经消失？

我使用两个浏览器窗口手工联调节点增删改、远端同步和事务回环，并结合 `transaction.origin`、Yjs 写入次数和 React Flow 状态更新次数观察操作链路。

验证标准是一次本地操作只产生一次 Yjs transaction；远端更新只触发一次界面更新，不会再次向 Yjs 回写。当前确认的是这套手工联调，不把后续设计的自动化协同 E2E、断线重连或服务重启恢复测试说成已经完成。

## 如果面试官追：PostgreSQL 持久化解决什么？

仅在内存中维护 Y.Doc，服务重启或最后一个协作者离开后就无法恢复状态。项目没有沿用 y-websocket 默认的 LevelDB 路线，而是封装 PostgreSQL 持久化适配层，将协同更新保存到公司的统一数据设施中。

打开建模空间时先恢复已有协同状态，再继续接收增量更新；连接释放前也会确保需要保留的状态进入持久层。这样实时同步与长期保存各自有明确职责。

## 如果面试官问：AI 如何参与建模？

AI 不直接覆盖正式模型。用户先描述建模需求，服务端通过 SSE 返回结构化 Proposal，Proposal 只包含新增、修改或删除节点和关系等明确操作。

前端解析后展示变更列表，用户可以定位受影响对象，逐项采纳、拒绝或全部确认。确认后的操作先进入本地草稿，再由用户保存和发布。这个设计把 AI 的概率性输出限制在候选变更层，模型状态仍由确定性数据结构和人工决策控制。

## 如果面试官问：平台产生的模型怎样被使用？

平台不是只给研发画图。业务、产品和研发会持续围绕同一份模型协作，把原本在线下会议和头脑风暴中的概念、角色与关系沉淀为结构化模型。

一个真实案例是库销存 Agent。客户会提出类似“下个月将滞留货物降低至 20%”的分析目标，但这只是场景举例，不是已经达成的结果。Agent 要分析这个问题，首先要有可审计的历史事实。我使用 8X Flow 从采购合同出发，识别参与方及其履约角色，把发货、收货、退货拆成请求、确认和 Evidence，使正常与异常履约都可以追溯。库存分析属于领域逻辑，消费这些履约事实并把结论关联回具体合同项和记录。

由于已经无法准确回忆客户的具体对象名和规则，我在面试中只使用通用采购场景解释方法，不把重构出来的 URI、异常规则或对象名说成生产事实。

## 如果面试官追：模型怎样变成 RESTful API 和 OpenAPI？

我采用模型驱动 API 设计，不从页面按钮直接设计 `/ship`、`/receive` 之类的 RPC 接口，而是从操作结束后模型中发生的数据变化出发。首先根据聚合边界生成 URI，再组合角色、HTTP Method 与业务场景得到 API 候选；然后使用 HAL relation 表达资源关系，最后把 API 映射回发货、收货和退货流程验证完整性。

发布模型会作为上下文交给 AI，由 AI 生成 OpenAPI 草稿。OpenAPI 是正式接口契约，因此不能直接采用 AI 输出，需要经过人工审核后才用于下游代码生成。这里不能说平台确定性生成了 OpenAPI，也不能说已经从模型直接生成完整业务代码。

测试数据同样由 AI 根据模型约束和验收场景生成，用于覆盖正常履约、部分收货、退货、缺少确认或 Evidence 等组合；具体数据仍然只是测试样例，不代表客户生产数据。

## 如果面试官追：公开仓库和公司项目是什么关系？

公司项目是实际内部研发项目，但源码不能公开。`team-ai` 是我额外做的公开重实现，不是把公司源码搬到 GitHub。

公开版本重新实现了 Workspace、Diagram、LogicalEntity、Version 和 KnowledgeGraph 等领域对象，并用 HATEOAS 表达资源关系与合法动作；前端包含 React Flow 建模画布、AI Proposal 的逐项采纳与拒绝、草稿保存和模型发布。它能够证明我可以独立复现核心架构，但不能替代公司项目的用户和生产数据。

## 收尾句

这个项目最能证明的不是我接入了 Yjs 或调用了模型，而是我把早期从复杂前端、多端一致性倒推出来的模型与契约能力产品化：并发状态、AI 候选变更、正式模型生命周期和接口契约分别由 CRDT、人工确认、版本发布与人工审核治理，团队共同维护的模型继续进入 OpenAPI、测试数据和下游代码生成链路。
