# 简历回答逐字稿：多人实时协同的 AI 辅助领域建模平台

## 30 秒开场

这个项目把前端与后端反复解释的业务知识，变成双方共同维护和审核的语义契约。参与方、权责、事件、领域对象和关系被沉淀为结构化模型；我负责 React Flow 前端、Yjs／Awareness、NestJS WebSocket 服务和 PostgreSQL 持久化。AI 只生成 Proposal，用户确认后才进入草稿、版本和发布，并用于 RESTful API、OpenAPI 草稿和测试数据候选。

## 2 分钟项目介绍

项目之前的建模主要依赖事件风暴和头脑风暴，讨论容易发散，前端、后端和业务也会各自保留一部分理解。平台改用 8X Flow 约束参与方、角色、权责和 Evidence，并通过 React Flow 把模型做成双方可以共同审核、后续可以继续消费的业务语义契约。

单人编辑时保存整张 JSON 可以工作，但多人协作不能只靠最后写入者获胜。我把正式模型内容存入 Y.Doc，通过 WebsocketProvider 传递增量更新；在线成员、远端光标和选区不进入正式模型，而是由 Awareness 单独广播。服务端按建模空间创建或恢复 Y.Doc，并分别处理 `messageSync` 和 `messageAwareness`。连接建立后加入当前文档的连接集合，Y.Doc 更新只向同一空间广播；连接关闭或 ping 检测失败时，清理连接、Awareness 状态和不再使用的文档实例。

协同数据还需要长期恢复，所以我封装 PostgreSQL 持久化适配层：文档初始化时加载并应用历史更新，文档退出活跃状态时写回最终状态。实时协同负责高频增量和临时状态，数据库负责长期保存，两者职责分开。

内部重实现曾出现路由切换后仍显示旧内容。根因是 Y.Doc、Provider 和编辑器初始化没有随 `pageId` 变化；修复后又两轮处理 HTTPS 下的 WSS 与同源代理入口。这些是开发阶段故障，不是公司生产事故。

Yjs 只能保证副本最终收敛，不能判断模型关系是否符合业务。AI 也不能直接覆盖正式模型。因此平台把 AI 输出限制为新增、修改、删除节点或关系的结构化 Proposal，由用户逐项采纳或拒绝；确认后再进入草稿、版本和发布。发布模型可用于生成 OpenAPI 草稿和测试数据，但正式接口契约必须由前后端和业务共同审核。

## 高频追问

### 如果面试官问：为什么说这是前端与后端之间的契约平台？

因为它解决的不是“把后端接口画出来”，而是先让双方对参与方、领域对象、生命周期、关系、动作和异常路径形成同一份可审核知识。前端用它理解资源、状态和合法动作，后端用它设计 URI、relation、action 与数据边界，发布模型再作为 OpenAPI 草稿和测试数据的上下文。

这份契约的权威仍来自人工评审和发布版本，而不是 AI、前端画布或某一方的代码。平台提供契约的形成、协作、版本和消费路径，但不能自动保证业务语义正确，也不能直接确定性生成完整业务系统。

### 如果面试官问：为什么需要 Yjs，而不是保存整张图？

整图保存适合单人编辑，但多人同时修改时容易出现后写覆盖前写。协同层需要传播增量，并让不同顺序到达的并发操作最终收敛。

我用 Y.Doc 管理共享建模数据，通过 WebSocket 广播增量更新。Yjs 处理并发合并，客户端不需要争抢一把全局写锁。CRDT 只解决状态一致，不解决领域语义是否合理。

### 如果面试官问：模型内容和在线状态为什么要分开？

两类数据生命周期不同。节点、关系和属性需要恢复；在线成员、光标和选区只在当前会话中有意义。

因此正式内容进入 Y.Doc 的共享数据，临时状态进入 Awareness。服务端分别处理 `messageSync` 和 `messageAwareness`，客户端卸载时断开 Provider 并移除 Awareness 监听，服务端关闭连接时也清理对应状态。这样不会把无意义的光标数据写进数据库。

### 如果面试官问：协同服务怎么组织？

服务端基于 NestJS 和原生 WebSocket Gateway。连接建立时，根据建模空间标识获取或创建 Y.Doc，并把客户端加入该文档的连接集合。

Y.Doc 更新后只向同一空间内的其他连接广播。服务端通过 ping 检测和关闭事件处理失效连接；最后一个连接离开后，先处理持久化，再释放内存中的文档实例。普通业务 API 负责认证、权限和 CRUD，协同服务负责长连接、高频增量与临时状态，这是按工作负载划分的边界。

### 如果面试官问：这个项目真正难在哪里？

真正的难点是同时管理页面资源、正式模型内容、Awareness 临时状态、WebSocket 连接和数据库持久化的生命周期。

内部重实现里最直接的表现是：页面路由已经变化，协同对象仍然指向旧资源，连接本身没有报错，但编辑器内容不会更新。这让我把页面标识、Fragment、编辑器初始化、Provider 连接和 Awareness 清理放在同一条生命周期里检查，而不是只看 WebSocket 是否在线。

如果这些边界混在一起，还会出现光标状态被持久化、失效连接残留、无用户文档长期占内存，或者数据库状态与内存 Y.Doc 无法恢复的问题。

### 如果面试官问：PostgreSQL 持久化解决什么？

Y.Doc 只存在内存时，服务退出或文档实例释放后无法恢复。项目没有沿用默认 LevelDB 路线，而是封装 PostgreSQL 适配层，接入统一数据设施。

初始化文档时通过适配层加载并应用历史更新；文档不再活跃时写回最终状态。当前可以确认持久化链路已经实现，但没有材料证明自动化断线恢复和服务重启恢复测试已经完成。

### 如果面试官问：网络延迟或断线重连怎么办？

这里要区分“架构能力”和“已验证结果”。Yjs 与 WebsocketProvider 的增量同步适合处理消息延迟和重新同步，协同服务也有连接检测和清理；但当前没有可核对的自动化断线重连与服务重启恢复测试。

如果继续完善，我会补网络分区、离线编辑、重复更新、重连恢复和文档释放后的重新加载测试，并记录恢复成功率和同步耗时，而不是只根据 CRDT 原理宣称已经可靠。

### 如果面试官问：CRDT 收敛后为什么还需要人工评审？

CRDT 解决的是多个副本能否得到同一状态，不判断状态是否符合业务语言。两个人同时修改对象名称和关系，结构可以收敛，但模型边界可能仍然错误。

因此模型语义仍要经过领域评审；AI 变更也先成为 Proposal，再由用户采纳；正式模型通过草稿、版本和发布管理。技术一致性、业务正确性和发布治理不能混为一层。

### 如果面试官问：AI 如何参与建模？

AI 不直接覆盖画布和已发布模型。服务端返回结构化 Proposal，明确描述新增、修改或删除哪些节点和关系；前端展示受影响对象，用户可以逐项采纳或拒绝。

确认结果先进入草稿，再保存、创建版本和发布。这样 AI 的概率性输出停留在候选层，正式知识仍由确定性数据结构和人工决策控制。

### 如果面试官问：平台产生的模型怎样被使用？

真实库销存 Agent 场景中，我使用 8X Flow 从采购合同出发，建模参与方、履约角色、发货、收货、退货及对应 Evidence。库存分析消费这些可审计事实，再把结论关联回合同项和履约记录。

发布模型作为上下文交给 AI 生成 OpenAPI 草稿和正常／异常测试数据。OpenAPI 经人工审核后才能用于下游代码生成。这里不能说平台确定性生成正式契约，也不能把客户提出的“滞留货物降低至 20%”当成项目结果。

### 如果面试官问：重实现和公司项目是什么关系？

公司项目是真实内部项目，但源码不能公开。`team-ai` 是我额外维护的公开重实现，用代码验证领域模型、React Flow 建模、AI Proposal、版本、知识图谱和 HATEOAS 等能力。

它不能冒充公司源码，也不能证明内部平台的生产规模或 Yjs 协同链路源码。公司项目范围以已确认事实为准；用户数、同步规模或生产指标仍需独立证据。

## 如果面试官问：这个项目里什么是基础能力，什么是增强？

基础是可编辑、可审核、可版本化和可发布的结构化领域模型。Yjs 与 Awareness 增强多人协作，AI Proposal 增强候选生成，OpenAPI 草稿和测试数据则增强下游消费；这些能力不能反过来夺走正式模型的写入权和发布权。

所以 Yjs 只保证副本收敛，AI 只提交 Proposal，用户确认后才进入草稿、版本和发布。这体现的是“稳定知识基线＋受控增强”，不是让 AI 直接替代建模。当前没有单独验证 AI 服务不可用时的完整主链路，也没有自动化断线与服务恢复证据，这些仍属于补强项。

## 收尾句

这个项目让我把前端与后端之间容易分散的业务知识变成可协作、可审核、可发布的语义契约，同时处理页面资源、共享内容、临时状态、连接和持久化的生命周期。AI Proposal、OpenAPI 草稿和测试数据都只能消费已确认模型，不能取代人工权威。
