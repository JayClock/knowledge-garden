> [!abstract] 核心观点
> Agent 交付失败很少来自模型能力不足，更多来自七类结构性缺口：需求没说清、约定没写下、来源会过期、完成靠自评、规则只增不减、只加规则不加检查、反馈没有层级。这七篇各讲一个坏味道和对应的机制。

这组文章来自我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT 许可）：一个 Nx 单仓库，前端是 React／TypeScript，后端是 Spring Boot／Java，交付对象是一个真实业务（CRM 电话销售绩效协议）。它把业务建模、API 设计、任务计划和实现串成一条可核验的链路，每一步都尽量落进文件，而不是留在对话里。

## 七个坏味道

| #   | 坏味道                                                 | 一句话症状                                         | 主要机制                                               |
| --- | ------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------ |
| 01  | [[需求模糊：Agent 不知道“好”长什么样]]                 | Agent 用你没授权的假设填满空白，还把它写成测试     | 入口不变量、来源权威表、结构化验收断言、缺口登记       |
| 02  | [[隐式约定：规则只存在于人的脑子里]]                   | 它不提问，只是按通用最佳实践交出一套你不认识的东西 | 分层约定、冲突裁决顺序、模块级 design 字段、拒绝默认值 |
| 03  | [[信息散落：知识来源不唯一且更新不及时]]               | 同一件事有三个版本，Agent 按旧版本执行             | 来源唯一、摘要绑定、开工新鲜度检查、定时刷新           |
| 04  | [[虚假胜利：Agent 以为自己做完了，其实没有]]           | “完成”是自评，不是证据                             | 可比较的验收数据、只记原始进度、只读校验脚本、失败保留 |
| 05  | [[指令文件腐化：AGENTS.md 越来越长，Agent 反而变笨了]] | 规则只增不减，没人说得清哪条还在生效               | 分层入口、单一来源、检查器查过期表述、替换式重构       |
| 06  | [[前馈痴迷：Agent 做完就交，从来没人检查]]             | 遇到错误先加规则，从不加检查                       | 规则与检查成对登记、计算型与推断型分工、证据不等于批准 |
| 07  | [[反馈过载：Sensors 太多，Agent 不知道哪个信号重要]]   | 信号很多但没有层级，改好一条弄坏另一条             | 成功静默、三级分级、证明力分级、分级即修复顺序         |

## 这组文章的用法

- **按顺序读**：七篇之间有依赖——需求模糊和隐式约定讲入口，信息散落和虚假胜利讲证据，指令文件腐化、前馈痴迷、反馈过载讲维护机制。
- **按症状查**：遇到具体问题时，直接从表格第二列找对应症状。
- **不要照抄**：文章里出现的文件、字段和命令都属于这个项目的约定。可复用的是**判断方式**——每类坏味道对应的检查形式，换到别的仓库要重新设计。

## 事实边界

- 这些机制来自一个个人项目的实践，不是行业结论；公开仓库可核验的范围是仓库内容本身，没有外部采用量或效果数据；
- 项目当前授权切片是绩效协议主链的本地实现，前端只是接口导航页，不等于已上线业务系统；
- 文中提到的测试与检查数字，都是**在本机某次实际执行**的记录，不是持续集成结果——这个仓库目前只有一条定时文档工作流，没有跑测试的 CI。
