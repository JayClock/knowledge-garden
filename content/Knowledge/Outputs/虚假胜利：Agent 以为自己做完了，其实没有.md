> [!info] Agent 交付的七个坏味道 · 04
> 系列基于我开源的项目 [Evidence-Framework](https://github.com/JayClock/Evidence-Framework)（MIT）。上一篇：[[信息散落：知识来源不唯一且更新不及时]]

“完成了”这三个字，是 Agent 交付里最便宜的输出。

文件写完了叫完成，生成页存在叫完成，缓存命中叫完成，结构校验 0 错误也叫完成。这些说法都能找到依据，只是没有一个依据能证明“你要的东西做出来了”。

## 这个坏味道长什么样

虚假胜利指的是：完成声明只有生成者自己的判断，没有独立依据。它以两种面貌出现。

第一种，还没开工就宣布完成——把“文件写完了”讲成“任务完成了”。

第二种更隐蔽：开工之后，Agent 跳过需要深推理的部分，只处理容易的部分，然后对整项任务宣布完成。容易的做得很快，跳过的不说，最后把局部当成全部。

两种面貌的共同点是**自评代替验证**。具体高发场景包括：

- 文件存在或生成页存在就当成实现完成；
- 把历史检查结果、生成报告或缓存命中当成本次通过；
- 把结构校验通过（计划结构合法、文档链接 0 错误）当成语义就绪或业务批准；
- 命令没实际执行就写“运行相关测试”；
- 为了通过而删掉失败测试、改业务预期，或手改机器生成的报告。

最后一条已经从“偷懒”变成“造假”，需要纪律而不只是检查来约束。

## 解法：把“是否完成”从生成者手里拿走

验收条件写成具体数据，进度记原始数据，验证交给只读脚本，失败保留不隐藏。

### 一、验收条件要能比较

任务模板里的 CHECK 逐项要求写清：目的、被测行为、真实依赖或替身及其限制、固定输入与业务时间、正常/边界/反例、失败不变性、测试文件、工作目录、精确命令与所需证据。

验收条件必须引用本任务的 CHECK，并以结构化断言保存期望值：

```text
assertions:
  - path: <稳定路径>
    operator: <受限操作符>
    expected: <保留类型的期望数据>
```

“测试通过”“符合要求”“文件已存在”都不算。命令还不知道就填 `null` 并关联一个缺口，**不允许写“运行相关测试”冒充可执行**。

### 二、进度只记原始数据

任务状态只有一个位置：计划里的 `tasks[taskKey].status`。同一个任务的 `observedEvidence` 只保存真实观察，计划生成时为空；每条证据写明检查 ID、命令、退出码与观察结果，例如：

> 领域测试 4 项通过，3 个构建任务均实际执行；覆盖必填字段缺失、重复编号拒绝，以及失败后集合不变。

而不是“已完成”。审核页只是这些原始记录的投影，不能反向成为状态来源或批准依据。

### 三、验证者必须是只读的

只读状态脚本做四件事，全部是确定性检查：

- 每个任务必须有引用本任务 CHECK 的验收条件与结构化断言；
- 标记为完成的任务必须有非空 `observedEvidence`；
- 进行中或已完成的任务，其前置任务必须已经完成；
- 被阻塞的任务必须关联已知缺口；编译出的任务、任务记录与 CHECK 必须一一对应。

它只报告，不替 Agent 修改状态；在计划与实际检查两个阶段各跑一次。回归测试把这些边界固定下来——完成必须有验收条件与真实证据、验收条件必须引用本任务 CHECK、活跃任务必须有已完成的前置、任务与 CHECK 一一对应、阻塞任务必须有已知缺口。

写这篇文章时我在当前提交上跑过一次：6 个任务全部完成、结构检查通过、无诊断、无剩余可执行任务，同时输出一行 `sourceFreshness: "not-checked"`——**结构通过不假装来源新鲜**。

项目质量命令充当脚本裁判：测试、静态检查、构建、Java 格式与归档检查、指南校验。每条命令都写明“实际覆盖”和“不证明什么”，让一次绿色只承担它能承担的范围。

### 四、区分“实际执行”和“看起来跑过”

构建系统会说 `UP-TO-DATE`，缓存会命中，任务会显示 `from cache`。这些都不是本次的运行结果：

- 需要复验时用强制重跑参数（例如 `--rerun-tasks`、`--skip-nx-cache`），不把缓存命中描述为新运行；
- 记录时分开写：多少个任务实际执行、多少个命中缓存、多少个 up-to-date；
- 环境失败与实现失败分开记录，环境阻塞不伪装成业务测试失败。

本文写作时的一次强制重跑：23 个测试类、148 项测试、0 失败 0 错误，19 个构建任务实际执行，构建成功。这是本机的一次数值，不是持续集成结果——仓库目前只有一条定时文档工作流，没有跑测试的 CI。这个事实也写进证据里，而不是含糊带过。

### 五、失败保留，不隐藏

- 生成类工作流区分“生成失败”和“产物仍然有用”：保留已完成部分并提交，最后由非零退出码标记这次运行失败；
- 失败输出完整保留在日志、PR 描述或授权保留的运行记录里，即使记录本身只留摘要；
- 纪律是硬的：不得删失败测试、不得改业务预期、不得手改机器报告制造通过；不自动提升审核状态。

仓库里真实出现过“既有失败如实保留、并指向基线复现”的阶段，随后由专门的重构任务修掉，而不是把它改写成通过，也没有把它留成永久借口。

### 六、缺口保持为缺口

可执行基线之外的未知登记为缺口，而不是被“看起来做完了”吞掉：

- `GAP-IDENTITY`：可信身份、主体映射、代表权限与实例归属未决定——只阻塞依赖它的接口与验收任务；
- `GAP-DATABASE`：生产数据库引擎、隔离级别与并发策略未确定——只阻塞生产方言与并发验收；
- `GAP-EVIDENCE-REFS`：凭证引用寻址方案未定——只阻塞要求核验引用的能力。

纯领域任务不因它们停工，生产保证也不会被本地测试证据替代。**缺口只阻塞，不蔓延**。

## 仍然做不到的部分

- 验证者目前是同一会话内的只读脚本与项目命令，没有跨会话的独立复核角色；“检查是否真正证明了业务结果”仍属人工判断；
- 人工判断类证据（设计审查、旅程语义）无法脚本化，只能在任务记录里显式写明观察方法、预期与差异；这类证据存在也不等于业务批准；
- 结构校验与语义判断之间的那条线，靠人来守。

## 收束

Agent 说“完成”的时候，它给出的是一个判断，不是一份证据。把判断和证据分开，是让自动化交付可信的第一步——也是最容易被跳过的一步。衡量标准很简单：如果一项目标只有生成者自己说它完成了，那它就没有完成。
