# 简历追问：低代码工作流引擎 DAG 架构设计

关联：[[15分钟：低代码平台]]、[[1.需求分析、项目架构设计与工作流引擎编辑器核心剖析]]、[[3.AI 工作流引擎编辑器与执行器架构设计与实践]]。

## 对应简历描述

> 设计并实现基于 DAG 的 TypeScript 工作流执行引擎，通过工作流验证器、GraphBuilder、拓扑排序、环检测、条件分支剪枝和 ExecutionContext，把可视化定义转成可执行流程。

## 面试官真正想确认

你是否真正做过工作流运行时，能讲清楚协议、图构建、动态分支和上下文，而不是只做了 React Flow 画布；同时能清晰阐述架构核心实现与设计取舍。

## 连续追问链

### 1. 工作流协议

- `WorkflowDefinition`、Node、Edge 和节点 Schema 分别表达什么？
- 编辑器协议与运行时协议为什么要统一？
- 画布选中、拖拽等 UI 状态为什么不能进入执行核心？

### 2. 运行前验证

- Start / End、节点类型、节点配置和边引用分别怎样校验？
- 邻接表、反向邻接表和入度表分别用于什么？
- 环检测与 Kahn 拓扑排序的职责怎样区分？
- 为什么不能只依赖前端禁止用户连环？

### 3. 条件分支

- Condition 怎样通过 `sourceHandle` 选择分支？
- 未选分支怎样进入排除集合？
- 分支重新汇合时，为什么必须检查其他活跃入边？
- 怎样避免误删仍应执行的公共下游？

### 4. 执行上下文

- 每次执行为什么需要独立 ExecutionContext？
- 节点输出如何按 nodeId 隔离？
- `${nodeId.variableName}` 如何在字符串、数组和对象中递归解析？
- 未执行分支或不存在变量时，为什么保留原表达式比静默空值更容易排查？
- 发布期静态校验与运行时动态解析在系统设计中如何权衡？

### 5. 验收路径与执行证据

- 为什么下游验收需要区分校验、测试运行和发布三个环节？
- 哪些事件由前端监控 SDK 记录，哪些状态由执行引擎日志负责？
- `executionId` 怎样关联用户操作、节点状态、耗时和错误？
- 为什么浏览器埋点不能替代服务端执行日志？

### 6. 扩展设计

- 同一轮入度为 0 的节点在执行策略上如何权衡并发与确定性串行？
- 节点幂等、失败重试和服务恢复的演进方案是什么？
- 如果需要 Loop，为什么优先设计成局部容器？

## 场景推演题

> Start → Condition → HTTP A / HTTP B → End。Condition 只选择 A，但 A、B 都连接到 End。请说明未选 B 时，怎样排除 B 又保留仍有活跃入边的 End，并给出新的执行顺序。

继续追：如果 End 又连回 Condition，会在哪一层被拦截？

## 准备证据

- 一个真实或脱敏的 WorkflowDefinition。
- 工作流验证器的节点、边和配置检查。
- GraphBuilder 的邻接表、反向邻接表、入度表和环检测代码。
- 原始文稿中的动态执行流程、`selectBranch` / `excludeSubtree` 和活跃入边判断。
- ExecutionContext 和 VariableResolver 的实现说明。
- AI Flow 中工作流校验、测试运行和发布的自定义事件，以及前端埋点通过 `executionId` 关联执行引擎日志的说明。
- Trace 面板由画布坐标排序改为基于 Edge 的拓扑排序的排障经验。

## 面试注意事项

- 清楚解释条件分支剪枝时对公共下游的入度保护算法。
- 准确区分前端埋点与服务端执行日志在可观测性中的职责分工。
- 准确阐述并发调度、幂等重试等分布式能力的演进设计。
