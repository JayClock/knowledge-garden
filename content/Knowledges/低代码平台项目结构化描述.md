# 低代码平台项目结构化描述 (面试专项版)

## 需求背景介绍

**项目概述**：本项目旨在构建一个高扩展、高性能的企业级 **低代码编排平台**。系统通过可视化的方式，实现从页面 UI 拖拽、业务逻辑编排（工作流）到动态数据绑定的全链路能力，帮助企业快速交付复杂业务应用。项目采用了典型的“协议驱动”架构，通过 JSON Schema 定义一切。

**业务需求**：随着企业业务需求的爆发式增长，传统的研发模式无法满足快速交付的要求。市场上的低代码工具往往面临“易用性与灵活性”的博弈。本项目旨在解决复杂业务逻辑（非简单的 CRUD）在低代码环境下的表达与执行难题，提供深度的自定义扩展能力。

**核心业务需求**：
- **可视化编排引擎**：支持组件拖拽、层级管理、实时属性配置与即时预览。
- **逻辑编排 (Workflow)**：支持基于 DAG 的业务流程可视化设计，集成公式引擎处理分支判定。
- **动态数据绑定**：实现全局变量管理、组件间联动与多源 API 数据的异步绑定。
- **组件插件化**：支持自定义组件的动态注入与版本管理，确保平台能力的持续扩展。
- **高性能运行时**：提供轻量级的 Render Engine（渲染引擎），确保低代码应用在多端环境下的加载与运行性能。

**技术需求**：
- **协议定义**：制定了一套标准化的 **Low-Code Schema (DSL)**，涵盖 UI 树、逻辑流与状态池。
- **核心交互**：利用 **XYFlow (React Flow)** 或 **Dnd-kit** 构建高性能的可视化编排画布。
- **状态管理**：基于 **Immer** 与 **Preact Signals** 构建响应式数据中心，解决跨组件联动的复杂性。
- **工程化**：采用插件化注册机制 (Registry Pattern)，实现物料与编排内核的完全解耦。

## 面试问题与核心思路

**低代码平台的核心难点是什么？你是如何设计 Schema 协议的？**
- **思路**：难点不在拖拽，而在于**逻辑的表达**与**协议的稳定性**。
- **设计**：Schema 采用分层结构：`layout` 定义 UI 树，`logic` 定义行为流，`state` 定义数据池。通过 JSON Schema 确保协议的可扩展性，并利用版本号机制实现向后兼容。

**如何解决低代码平台中复杂的组件联动与全局状态管理？**
- **思路**：采用 **“单向数据流 + 响应式代理”**。
- **实现**：建立全局 **DataBus**。每个组件的属性不再是硬编码的值，而是一个指向 DataBus 的表达式。当源数据变化时，依赖追踪机制（如 Preact Signals）会自动触发相关组件的重绘，避免了复杂的回调嵌套。

**低代码生成的应用性能不如原生代码，你有哪些优化方案？**
- **思路**：1. **静态提升**：在编译阶段将静态 Schema 转换为高效的 React 组件树。2. **按需加载**：物料组件库采用动态导入，仅加载当前页面用到的组件。3. **减少重绘**：通过 `memo` 与细粒度数据订阅（Signal）将渲染范围控制在最小。

**如何让非技术人员也能编排复杂的业务逻辑？**
- **思路**：将复杂的 JavaScript 逻辑抽象为**图形化节点（Action Nodes）**。
- **实现**：通过可视化工作流引擎，将常见的“调用接口”、“弹出提示”、“表单校验”等原子操作封装为开箱即用的节点。用户只需通过连线和简单的公式配置即可完成逻辑拼装。

**自研编排引擎与市面上成熟方案（如 LowCodeEngine）的权衡点？**
- **思路**：成熟方案功能全但包体积大且定制成本高。自研的核心动机在于**业务深度契合**（如特定的 Smart Domain 领域模型支持）以及**极致的轻量化**要求，确保系统能灵活嵌入到现有的复杂业务系统中。
