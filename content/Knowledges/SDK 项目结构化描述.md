# SDK 项目结构化描述 (面试专项版)

## 需求背景介绍

**项目概述**：本项目旨在构建一个高可靠、低入侵的 **全链路数据采集与监控 SDK**。系统涵盖了用户行为埋点（Behavior Tracking）、性能监控（Performance Monitoring）与异常捕获（Error Tracking）三大核心模块，为业务决策与系统稳定性提供坚实的数据支撑。

**业务需求**：传统的零散埋点方案存在代码侵入强、数据口径不一、漏埋错埋多等痛点。企业急需一套标准化的 SDK，在不影响主业务性能的前提下，实现全自动化与声明式的精准数据采集，并具备应对弱网、高并发等复杂环境的弹性能力。

**核心业务需求**：
- **声明式埋点**：通过自定义指令或属性（如 `data-track`）实现零代码侵入的行为采集。
- **全方位监控**：自动采集 FCP、LCP、FID 等核心性能指标，并捕获 JS 错误、Promise 异常及网络请求故障。
- **数据可靠性**：支持本地持久化离线存储、断网续传与智能采样逻辑，确保在极端环境下数据不丢失。
- **灵活的插件系统**：支持业务方根据特定需求动态加载采集插件，保持 SDK 核心包的轻量化。
- **低入侵设计**：利用异步加载与 `requestIdleCallback` 确保 SDK 运行不抢占主线程资源，对页面性能的影响控制在 1% 以内。

**技术需求**：
- **上报协议**：支持 Beacon API 与 1x1 GIF 像素点上报，解决页面销毁时数据丢失的问题。
- **分层架构**：SDK 内部采用“采集层 -> 处理层 -> 上报层”的解耦设计。
- **工程化**：使用 Rollup 构建支持多种模块规范（ESM/UMD）的产物，并建立完整的自动化测试链路确保质量。

## 面试问题与核心思路

**为什么 SDK 上报优先选择 1x1 GIF 或 Beacon API，而不是普通的 AJAX？**
- **思路**：1. **GIF**：跨域友好，且不会因请求挂起导致浏览器进程无法退出。2. **Beacon**：专为上报设计，确保在页面关闭（unload 事件）时仍能异步发送成功，且不阻塞主线程。

**如何衡量一个 SDK 对页面的性能影响？你是如何做性能优化的？**
- **思路**：通过 **Long Task (长任务)** 监控。
- **优化**：1. **代码精简**：无第三方库依赖。2. **执行时机**：非核心代码放入 `requestIdleCallback`。3. **批处理**：将多个埋点合并为一个请求，减少 HTTP 开销。

**如何解决埋点数据丢失的问题？尤其是在页面跳转时？**
- **思路**：1. 利用 **navigator.sendBeacon**。2. 降级方案：在 `localStorage` 中暂存，等下次启动时再进行补偿上报（断网续传）。

**为什么说埋点应该靠近“领域事件”而不是“UI 事件”？**
- **思路**：UI 事件（如 `click`）不稳定且无语义。领域事件（如 `ORDER_SUBMIT`）代表了真实的业务意图。通过在 SDK 中引入语义化标识，可以让埋点数据更具业务分析价值，且不受 UI 交互变动的影响。

**SDK 内部是如何处理版本升级与向前兼容的？**
- **思路**：1. **语义化版本 (SemVer)**。2. **特征检测**：不依赖特定版本号，而是检测当前运行环境是否支持某项 API。3. **API 灰度**：通过服务端配置动态控制 SDK 内部不同能力的开启与关闭。
