# 公式编辑器项目结构化描述 (面试专项版)

## 需求背景介绍

**项目概述**：本项目旨在为低代码平台提供一个功能强大、安全可靠的 **可视化表达式引擎（公式编辑器）**。它集成了基于 AST 的解析校验、高性能安全执行沙箱以及支持变量引用与语法高亮的前端编辑器，使用户能够通过简单的类 Excel 公式实现复杂的业务逻辑联动。

**业务需求**：在低代码/零代码场景中，简单的静态配置无法满足多变的业务逻辑。传统的 `eval` 或静态正则匹配存在严重的安全风险（XSS/注入）且缺乏提示与校验。本项目旨在填补平台在动态数据计算与逻辑判断上的能力空白。

**核心业务需求**：
- **可视化编辑体验**：支持拖拽字段、函数自动补全、语法实时高亮与错误提示。
- **高性能解析执行**：基于 AST 的解析机制，支持数值计算、逻辑判断、字符串处理等 100+ 常用函数。
- **安全沙箱环境**：严禁使用 `eval` 和 `new Function`，通过自定义解释器实现在受限环境下的脚本执行。
- **多端一致性**：确保公式在前端 UI 预览与后端逻辑计算（如工作流网关）中的结果完全一致。

**技术需求**：
- **编辑器内核**：基于 **Tiptap (ProseMirror)** 的无头编辑器，开发自定义 Node 实现变量的原子化引用。
- **语法解析引擎**：采用 **jse-eval** 或自定义递归下降解析器构建 **AST (抽象语法树)**。
- **执行沙箱设计**：通过上下文注入与权限隔离，确保表达式无法访问全局敏感对象（如 `window`, `document`）。
- **质量保障**：采用 **TDD (测试驱动开发)**，积累 500+ 测试用例确保各种边界情况下的计算准确性。

## 面试问题与核心思路

**为什么不能直接用 `eval` 执行公式？你的安全沙箱是怎么设计的？**
- **思路**：`eval` 会直接暴露全局执行上下文，存在恶意脚本注入风险。
- **设计**：通过解析公式生成 **AST**，然后利用自定义的 **Interpreter (解释器)** 模式，只提供受限的 Context（变量池 and 函数映射表），在受控环境下递归求值，从而在根源上杜绝越权访问。

**公式编辑器这种“富文本输入”是如何实现变量高亮和原子化删除的？**
- **思路**：摒弃常规 `textarea`，选用 **ProseMirror (Tiptap)** 内核。将变量定义为 **Inline-level Node**（行内节点），它在编辑器中表现为不可分割的整体，支持单独的样式渲染，且在退格时能够实现一键整块删除。

**AST 解析的核心难点在哪里？你是如何处理公式依赖的？**
- **思路**：核心难点在于**运算符优先级控制**和**嵌套函数递归解析**。
- **依赖处理**：在 AST 遍历阶段，自动提取出所有的 `Identifier` 节点作为依赖路径。当全局数据发生变化时，通过依赖映射表实现“按需计算”，避免全局刷新导致的性能抖动。

**如何确保复杂嵌套公式（如 `IF(SUM(A, B) > 10, C, D)`）的执行效率？**
- **思路**：1. **AST 预编译缓存**：对同一个公式进行 Hash 缓存，避免重复解析。2. **短路求值**：在解释器执行阶段，类似 `IF` 这种条件分支，只对命中的分支进行求值，避免不必要的递归计算。
