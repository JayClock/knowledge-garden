#### 你的分层合理吗？

在我们平时开发中，我们往往会将接口设计分为以下几个层次。
1. **控制器层（Controller Layer）**：负责处理 HTTP 请求，调用服务层的方法，并将结果返回给客户端。
	```ts
	@Controller('users')
	export class UsersController {
	  constructor(private readonly usersService: UsersService) {}
	
	  @Post()
	  create(@Body() createUserDto: CreateUserDto) {
	    return this.usersService.create(createUserDto);
	  }
	
	  @Get()
	  findAll() {
	    return this.usersService.findAll();
	  }
	
	  @Get(':id')
	  findOne(@Param('id') id: string) {
	    return this.usersService.findOne(+id);
	  }
	
	  @Patch(':id')
	  update(@Param('id') id: string, @Body() updateUserDto: UpdateUserDto) {
	    return this.usersService.update(+id, updateUserDto);
	  }
	
	  @Delete(':id')
	  remove(@Param('id') id: string) {
	    return this.usersService.remove(+id);
	  }
	}
	```
2.  **服务层（Service Layer）**：负责业务逻辑的处理，调用仓库层的方法来操作数据库。
	```ts
	@Injectable()
	export class UsersService {
	  constructor(
	    @InjectRepository(User)
	    private readonly usersRepository: Repository<User>
	  ) {}
	
	  create(createUserDto: CreateUserDto): Promise<User> {
	    const user = new User();
	    user.name = createUserDto.name;
	    user.email = createUserDto.email;
	    return this.usersRepository.save(user);
	  }
	
	  async findAll(): Promise<User[]> {
	    return this.usersRepository.find();
	  }
	
	  findOne(id: number): Promise<User> {
	    return this.usersRepository.findOneBy({ id: id });
	  }
	
	  update(id: number, updateUserDto: UpdateUserDto): Promise<UpdateResult> {
	    return this.usersRepository.update(id, updateUserDto);
	  }
	
	  async remove(id: number): Promise<void> {
	    await this.usersRepository.delete(id);
	  }
	}
	```
3. **仓库层（Repository Layer）**：负责与数据库交互，提供数据的增删改查操作。
4. **模型层（Model Layer）**：定义模型对象（如 `Customer`），用于直接映射数据库
	```ts
	@Entity()
	export class User {
	  @PrimaryGeneratedColumn()
	  id: number;
	
	  @Column()
	  email: string;
	
	  @Column()
	  name: string;
	}
	```
这种开发模式下，我们只针对**对象仅仅对简单的数据进行封装，而关联关系和业务计算都散落在对象的范围之外**。我们既不能看出当前实体和其他实体直接有无关联关系，也没法借助实体找到相关的业务逻辑。

这种开发模式较为流行的原因其实很简单，在软件开发早期，我们做的基本上还是较为简单的 CURD。不需要花费大力气去精心设计成**充血模型**，毕竟本身业务行为就不多，做出来的充血模型也比较贫瘠。而且我们在大学学习某一门技术的时候，最难的也就是“XX 管理系统”，CURD 写写就做完了要啥设计，而这样的习惯，延续到了平时工作中，**35 岁危机**的内因不过如此。

在软件规模扩张的过程中，我们会面对**贫血模型**带来的诸多问题。
1. 服务层的无限制扩张，所有的数据变更，就集中在几个 curd 方法中，最终导致代码的僵化，也就是我们平时吐槽的“改不动的代码”。
2. 服务层中往往会出现大量重复的判断逻辑，为了降低重复，我们往往会把这些重复代码封装层各种 util，但是这并没有解决什么问题，我们依旧需要深入实现细节，才能分清 uil 和 service 下做了什么。而且多数情况下，是在上线的压力中，随便把业务逻辑进去。
3. 在上面的案例中，还有一个非常糟糕的问题，那就是**无效的分层**。我们 Repository 中使用 typeorm 的持久化工具，是取决于下层（model）。这也就意味着，如果我们因为性能原因/安全原因，需要修改持久化工具，我们不仅要改动到上层（service），我们也要变动下层（model）。而**有效的分层**，持久化工具的变更，只能影响到 repository 以上的层，model 层是对变化无感知的。

我再举一个在拆解任务的过程中，遇到的一个比较详细的例子：

现在有一个项目，在这个项目中，有三个以 `user` 为前缀的类，它们都可以处理 `user` 数据对象：
1. **UserStore**：使用状态管理工具，用于存储全局用户信息。
2. **UserUtil**：为了减少代码重复，封装了用户相关的逻辑。
3. **UserService**：为了与模型层区分，封装了服务层的逻辑。

现在有一个需求：新增一个判断用户是否有权限的方法。在拆解任务时，我们需要决定将这个逻辑放在哪个类中：
- 放在 **UserStore** 里似乎合理，因为全局可以直接调用。
- 放在 **UserUtil** 里也有道理，因为其他数据接口可能会引用用户相关信息，抽象起来更方便。
- 放在 **UserService** 里也未尝不可，因为 `service` 本身就是用来封装对数据层的处理。

这个就是我们上一课讲到的**理解不了业务，明白不了架构**中的**架构理解部分**。我们只能给出一个**写代码的人觉得有自己的道理，review 代码的人，也在感觉上合理的**的结果。在这样的场景下，我们的 code review 可以说是一个只停留在表面功夫的事情。唯一有用的，也就是打几个标签，来体现自己完成了某一个任务罢了。
#### 问题究竟有多严重了？

这个问题我们有一个相对简单且快速的方法：
1. 团队中已经有“两个披萨”规模的人数，也就是 8 个人以上，这时已经对管理者带来了一定的要求。
2. 找团队中 5 个开发工程师，单独对同一个要迭代的功能进行任务分解，看看大家的分解结果，在大方向上能否一致。

如果这 5 个开发工程师，对任务的拆解各有各的理解，那么这个问题就很严重了。说明平时开发过程中，大家都在按照自己的理解去提交代码，最终的结果就是大家都看不懂对方的代码，最典型的现象就是“我本地没问题的，怎么一合到测试环境就有问题了！”。管理者可能觉得招个人能解决能解决这个问题。但是你招人也得让别人能正确理解当前项目**做了什么，是怎么做的**。对方只能在本就混乱的代码上下文下，按照自己的理解去处理代码。最终的结果就是，我们花大价钱找了一个能力很强的人，但是只得到了一份**只有他自己能理解的代码**。

即使人员不发生变动我们的问题也在变得更加严重，因为我们在让 AI 基于混乱不堪的上下文，生成我们根本无法审核的代码。
#### 技术让位于业务

在各个企业的面试八股文中，各种源码实现、算法层出不穷。却很少有人问起对所做的项目本身的理解，即使问了，候选人的答案也更多的是用了什么语言、框架、工具，提升了多少性能。**重技术，不重视业务**的习惯，让我们误以为学好技术就能做好软件开发。我们对各种框架驾轻就熟，但是在为何学习技术，却和那些毕业一两年的小年轻并没有什么区别。既然真的做起来没什么差别，那为什么不用小年轻呢？我们在缺乏对业务的理解，导致难以发挥我们所学的技术优势，最终陷入“技术无用”的自我怀疑中。当然这里不是鼓吹放弃学习技术，技术和业务并没有哪个更加重要的区别。只是既然我们在做功能，那么**一定是先正确理解业务，再选择合适的技术**。

对于技术如何理解业务，最直接的方式，就是从代码中读。那么**从业务角度出发，构造与技术实现无关，但是与业务强相关的模型，以此快速在技术之间传递信息**的领域驱动设计（Domain Driven Design，即 DDD），就是我们的最佳选择了。
#### 充血模型：描述世间万物

充血模型是一种软件设计模式，特别是在领域驱动设计（DDD）中被广泛应用。它强调将业务逻辑和行为紧密地绑定到对应的实体（Entity）或值对象（Value Object）上，而不是将这些逻辑分散在 service 或 controller 中。通过这种方式，充血模型能够**更好地反映现实世界中的业务规则和交互，使代码更具表达力和可维护性**。

具体来说，充血模型要求在实体上直接定义与该实体相关的业务行为方法。例如，在一个图书借阅系统中，如果需要表达“读者借阅书籍"这一行为，应该在`reader`实体上定义一个`borrowBooks`方法，即 `reader.borrowBooks(booId:number)`，在这个方法里触发对书籍订阅状态的更新，而不是 `userRepository.update(...)` 直接把对数据库的更新暴露出来。 这种设计方式使得实体不仅包含数据（属性），还包含与这些数据相关的行为（方法），从而形成一个“充血”的实体。

现在我们把上面例子中的的 Typeorm 注解的“User 实体”，改造成真正的实体。
1. 首先我们要去除的：是和持久化技术 Typeorm 相关的内容
2. 其次对于实体来说：我们考虑一个对象是不是实体，唯一的判断标准就是它是否有身份（identity）
3. 再来对于实体来说：我们考虑的是这个实体和其它实体之间的关联关系（association），这个后面会讲到。
4. 最后对于实体来说：才是这个实体中具体哪些有哪些值（value）

```ts
export type UserDescription = Readonly<{
  name: string;
  email: string;
}>;

// 这里的使用了 immutable 构造不可变对象
export class User implements Entity<number, UserDescription> {
  private immutableDescription = fromJS(this.description);
  constructor(private identity: number, private description: UserDescription) {}

  getIdentity(): number {
    return this.identity;
  }
  getDescription(): UserDescription {
    return this.immutableDescription.toJS() as unknown as UserDescription;
  }
}
```
#### 谁来操作实体？

对于用户（user）和任务（category），user 与 category 是一对多的关系的情况下，如果我们要添加一个分类，那么自然而然的，我们会把添加分类的逻辑，绑定在 user 实体上，即`user.addCategory(...)`。但是这样，我们却造成一个问题，我们不得不在领域层中，引入具体的技术实现。

```ts
export class User {
  addCategory() {
    db.executeCreate(...)
  }
}
```

那么我们可不可以对 categories 集合设计一个单独的 repository 呢，比如：

```ts
export class CategoriesReository {
  db.executeCreate(...)
}
```

这样也不行，这样就违背了我们使用面向对象构造充血模型的初衷，我们又遇到了把业务逻辑散落散落在各处的问题。

我们可以仔细回想下平时在表中查询数据的过程，比如这个 SQL `SELECT * FROM users WHERE phone_number = '手机号'`；我们在查询某一个内容时，首先第一件事，就是要明确它在哪一个数据表（集合下），而我们的需求则是，希望把这个对数据库操作的具体实现隐藏起来。**那么我们可以对这个集合进行建模**！

比如 user 对 category 的操作，也可以说是在 category 集合下进行操作，但是 category 不可以独立于 user 存在，不然你这功能就没有意义（你用户都没有，你用个啥）。我们既要对 cateory 集合进行建模，又要体现出 user 和 category 之间的关联关系（user 是 category 的聚合根）。最简单的方式就是，把关联关系体现在接口命名上，即 UserCategories。

```ts
// 持久化的时候，不论用什么持久化框架和数据库都与我无关，只要实现单独实现接口就好了
export interface UserCategories {
  addCategory(): Promise<Category>
  findById(): Promise<Category>
}
```

而对于查询 user，由于它已经是模型的入口了，没有上游的聚合根前缀，我们只需要构建一个名为 Users 的接口即可。

```ts
export interface Users {
  findByIdentity(id: number): Promise<User>;
}
```
