# 项目经历简历描述（汇总）

## 使用建议

- 如果岗位偏 AI 平台 / 全栈 / 复杂工作台，优先放 `Team AI`
- 如果岗位偏平台 / 配置化 / 中后台，优先放 `低代码平台与公式编辑器`
- 如果岗位偏基础设施 / 体验治理 / 工程平台，优先放 `监控、埋点与性能治理`
- 如果简历篇幅有限，保留 3 个项目即可；如果岗位很看架构抽象，再补 `HATEOAS 请求管理`

## 项目一：Team AI AI 原生工作台 / 多智能体协同交付平台

一句话：面向软件交付场景的 AI 原生工作台，围绕业务建模、执行控制面、状态回流和流程治理，构建需求到执行的闭环。

三条式：

- 主导 Team AI 核心对象抽象，围绕 project、task、session、board、trace 等对象沉淀统一语义和执行链路。
- 前端基于 React 构建项目工作台、会话页、Kanban 和执行控制面，后端参与任务编排、实时事件流和治理能力建设。
- 将需求 intake、任务拆解、执行委派、Review 和结果回写串成闭环，提升 AI 在真实交付流程中的可用性和可治理性。

## 项目二：轻流低代码平台与公式编辑器

一句话：面向多业务线 SaaS 场景的配置化平台，围绕 schema、编排引擎、渲染运行时和表达式引擎构建统一研发底座。

三条式：

- 负责低代码平台核心能力建设，围绕表单 schema、通用表格、仪表盘编辑器和渲染引擎推进平台化抽象。
- 主导公式编辑器关键能力建设，将业务表达式从输入框问题提升为词法分析、语法分析、AST 和安全执行的表达式引擎。
- 推动统一 JSON / schema 配置模型、插件化扩展机制与 Nx monorepo 工程体系建设，提升复杂业务配置效率和平台演进能力。

## 项目三：前端监控、埋点与性能治理

一句话：围绕监控 SDK、埋点 SDK、Web Vitals 和性能治理闭环，建设可采集、可校准、可告警、可防回归的前端基础设施能力。

三条式：

- 设计并实现监控 SDK / 埋点 SDK 的核心能力，覆盖事件模型、上下文补充、批量上报、失败重试和 `sendBeacon` 兜底。
- 建立 `TTFB`、`FCP`、`LCP`、`INP`、`CLS` 等指标采集、校准、归因和告警机制，将性能问题从主观感知转成可观测数据。
- 结合性能排查、指标治理和防回归机制，推动团队从“修一次卡顿”升级到“持续性能治理”。

## 项目四：HATEOAS 请求管理 / 资源契约消费层

一句话：面向多消费端场景的资源契约消费层，通过 HAL / HAL-FORMS 统一资源导航、动作发现和动态表单消费方式。

三条式：

- 设计并实现基于 HAL / HAL-FORMS 的资源消费模型，支持 follow(rel)、模板解析、分页关系消费和缓存去重。
- 将前端请求逻辑从 URL 和 payload 硬编码提升为资源关系驱动，降低前后端演进耦合。
- 基于 React Hooks 封装单资源读取、分页集合和动作模板消费能力，减少页面样板代码并提升多端一致性。
