# 复杂前端平台项目如何做任务分解

如果面试官追问我在复杂平台项目里是不是只负责局部实现，我会从任务分解角度回答。复杂前端平台最难的地方，不是把某个页面写出来，而是把一个模糊的大目标拆成能并行交付、能验收、能长期维护的模块边界。

我的拆法一般不是按页面拆，而是按能力层拆。

第一层是协议和模型。比如低代码里的 Schema、多智能体平台里的 Task/Plan/Evidence/Trace、HATEOAS 里的 Resource/Link/Template，先把系统里最稳定的对象定义出来。这个阶段重点不是写 UI，而是和产品、后端、测试对齐同一套语言。

第二层是运行时能力。协议确定以后，再拆核心引擎、状态管理、生命周期调度、权限校验、缓存、错误处理这些运行时模块。它们通常是平台的长期资产，不能被单个业务页面污染。

第三层是扩展点。比如插件注册、函数白名单、动作模板、埋点声明、Agent 节点 Schema。扩展点的价值是让业务差异进入系统，但不破坏核心引擎。

第四层才是具体业务接入。业务应用通过公开 API、插件、配置或 SDK 接入平台能力，而不是反向修改底层实现。

这样拆分以后，研发排期也会更清楚：先做最小协议闭环，再做运行时骨架，然后补关键扩展点，最后接业务场景验证。测试也能跟着拆：协议测试、运行时测试、插件兼容测试、业务验收测试分别覆盖不同风险。

如果用一句话总结，我做任务分解时关注的不是“谁写哪个页面”，而是“哪些知识应该沉淀成协议，哪些能力应该进入平台运行时，哪些差异应该留给扩展点”。
