> 高级前端 / 平台型全栈工程师，核心优势是用全流视角把业务问题、领域建模、前端架构、测试验证和上线反馈串成可交付的工程系统。

面试官你好，我做了大约 5 年前端开发和平台型全栈架构设计，核心技术栈是 [[../Knowledges/React|React]]、TypeScript 和 Node.js。我的基本盘是复杂前端系统和前端基础设施，但我不是只从页面实现角度看问题，而是更关注一个需求如何从业务问题出发，经过领域建模、资源契约、工程实现、测试验证，最后进入上线反馈闭环。

所以如果用一句话概括，我更倾向于把自己定位为“高级前端 + 平台工程 + 全流工程能力”的复合型工程师。全栈对我来说是处理前后端资源契约、Node 服务和系统边界的技术能力；全流则是我的项目方法论，也就是沿着业务问题、建模、实现、验证和运营反馈这条链路推动交付。

过去我主导和深度参与的项目，主要可以分成三条线。

**第一条是 AI 工程平台，也就是以 Workspace 为中心的 [[./15分钟面谈：多智能体协同平台|多智能体协同工作台]]。**这个项目我没有把它做成多个 Agent 的聊天窗口，而是把 AI 参与研发后的需求理解、执行过程、测试证据、Review 和 Gate 显式建模出来。前端侧我负责 Kanban 工作台、Schema 驱动的 Agentic UI、SSE 高频流式状态合并、Trace 可视化和 Review Evidence 的安全渲染。它解决的不是“让 AI 多写一点代码”，而是让 AI 产出的代码带着上下文、过程和验证证据进入团队协作。

**第二条是 SaaS 交付平台，包括 [[15分钟面谈：轻流低代码平台|轻流低代码平台]] 和 [[15分钟面谈：公式编辑器|公式编辑器]]。**低代码平台解决的是公司 SaaS 业务扩张后，常规表单、列表、详情和仪表盘不能继续靠研发线性堆人的问题。我把页面、字段、数据源、权限、校验和生命周期抽象成 Schema 和插件体系，让实施、产品、研发、测试围绕同一份结构化协议协作。公式编辑器则进一步把业务规则从字符串和研发经验里抽出来，用 Lexer、Parser、AST 执行沙箱、函数白名单和测试用例承载，让非研发人员也能安全配置规则。

**第三条是工程基础设施，包括 [[15分钟面谈：HATEOAS 请求管理|HATEOAS 请求管理架构]] 和 [[15分钟面谈：前端埋点与监控 SDK|前端埋点与监控 SDK]]。**HATEOAS 不是简单封装 API Service，而是把“当前资源下一步能做什么”放回后端资源契约里，前端、小程序、测试和未来 Agent 都消费同一份 `_links` / `_templates`，减少状态机规则在多端漂移。埋点 SDK 也不是做一个大而全的数据平台，而是把业务事件、曝光事件、接口异常和公共上下文沉淀成低侵入、可降级、可回放的上线反馈链路。

**总结我的核心优势：**
1. **复杂系统抽象能力**：能把低代码 Schema、AST 规则引擎、HATEOAS 资源契约、Agent Trace、埋点协议这类复杂问题沉淀成可复用、可验证、可治理的工程资产。
2. **全流交付视角**：不只关注代码实现，也会关注问题来源、任务分解、上下游协作、测试口径和上线后的数据反馈，减少知识在团队流转中的损耗。
3. **AI 工程化落地经验**：不是只会调用大模型 API，而是能把 AI 输出纳入软件交付流程，让计划、证据、Trace、Review 和 Gate 都能被人审阅、被系统追踪、被流程治理。
