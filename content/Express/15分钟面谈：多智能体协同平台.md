在过去的团队开发中，**Code Review**。因为能把做了什么以及背后的业务逻辑表达清楚的，往往只是少数资深工程师的能力；大量的业务上下文都成了“黑盒” ，只存在于个人的脑子里。

当团队引入了 AI 编程后，这个痛点被放大了。AI 生成代码的速度很快，但**由于交互的分散，那些原本存在人脑子里的知识，现在都散落在大量不同的 Agent Session 中。**

如果我们顺着“让 AI 完成长任务，并做好约束”的思路走，工程上就会陷入死胡同。因为在团队开发中，从来不是某一个人让 Ai 做了什么，而是这个人提交的代码，要足够可信，并获得团队他人的认可。而足够可信的形式，最直接的方式，就是像我们现在的面试流程一样，完整的讲清楚。

现在的大模型足够聪明，可以很容易写出一个描述思路的逐字稿。但是在缺少中间态沉淀的情况下，我们很难衡量，团队成员在使用 ai 时到底是在“理解需求”时造成了偏差，还是在”方案决策“时判断失误。当这些决策失落在大量 Agent session 中时，代码的提交者即使是想提交代码，也很难描述清楚自己的思路。

当约束从 ai，提升到人类之后。我就想到了这么一个思路。既然开发过程中，有非常多的阶段和节点，那么我只要保证每一个节点，都产出结构化的上下文。帮助人类更好地审阅 ai 的输出，并在 ai 地帮助下，真实的学会整个功能的开发思路。

在这个思考之下，我就不再单个 Agent 自主决定一切的 Loop 循环，而是将 Kanban（看板）作为智能体编排的底层状态机总线。将研发拆解为 `Todo -> Dev -> Review -> Gate` 等流转阶段。
负责规划的 Agent 绝不写代码，它的产出是“结构化的执行计划和验收标准”。编码 Agent 只能在这个计划的边界内局部修改。通过这种编排，我们控制了上下文的膨胀，也知道了什么时候该用 Agent，什么时候该用确定的工作流。

当 Dev Agent 写完代码后，它不能直接提交，**必须附带一份详尽的“开发证据 (Dev Evidence)”**（修改了什么文件、跑了什么测试）。随后，负责审查的 Review Guard Agent 会像一个严苛的闸门（Gate），拿着最初的验收标准和这份证据进行比对。通过证据和风险代码的一一比对，人类阅读代码只需要借着 ai 给的入口，可以快速地进行代码的审阅。


上面的观测层中，agent 有可能因为网络波动中断，或者执行命令时间过长导致整个会话消失，又或者是，在我电脑上执行的到 Dev 的流程，需要交给另一个同事能无缝接入。

我的思路是学习 React 的 [[../Knowledges/React Fiber|Fiber 节点]]，我把大模型的执行链路也切成了细粒度的步骤。AI 每做完一步，系统就把当时的上下文和依赖作为 Trace 实体（包含耗时、Token 消耗、工具调用结果）落库保存，这就构成了我们的**观测层**。
带来的直接效果是：在**运行时**，即使 AI 推理中途崩溃，我们的 Blocked Resolver（阻塞分析器）也能精准查到断点。然后系统像 [[../Knowledges/React Fiber|Fiber 树]]恢复渲染一样，提取上一步的 Trace 恢复环境，让 AI 精准地**从断点处继续执行和重试**，彻底告别了“一报错就全盘推倒重来”的黑盒灾难。


这套极度克制的架构上线后，带来了质的飞跃：
1. **建立零信任的安全准入**：强制的“证据收集”与“独立 Review 门禁”，让每一次代码交付都有迹可循，我们建立起了对 AI 生成代码的真正信任，人使用 ai，又担心不可控的恐惧。
2. **知识传递高保真**：通过 Kanban 切分和最小上下文下发，由大模型幻觉和知识遗漏导致的严重 Bug 降低了 80% 以上。
3. **高可追溯的协同闭环**：我们用一条步骤可控、状态完全可追溯的 AI 软件生产流水线，极大降低了长期维护和事后调试的成本。
