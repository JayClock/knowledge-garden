# 15分钟深度面谈逐字稿：多智能体协同平台 (团队 Review 切入版)

> 💡 **面试节奏与切割指南 (Pacing & Segmentation)**
> 一个完美的 15 分钟技术演说是呈“沙漏型”的：开场收敛痛点，中间展开架构，结尾收敛价值。
> 
> - **[0:00 - 2:00] 第一部分：抛出痛点 (引人入胜)**。从代码审查 (Code Review) 痛点切入。
> - **[2:00 - 5:00] 第二部分：升维技术矛盾 (建立深度)**。把痛点拔高到知识传递断层和黑盒状态。
> - **[5:00 - 11:00] 第三部分：三层架构设计 (重火力输出)**。这是主场时间。**（此处巧妙引入了 [[../Knowledges/React|React]] [[../Cards/React Fiber|React Fiber]] 调度原理作为谈资引子，引导面试官往前端底层八股文深挖）。**
> - **[11:00 - 13:00] 第四部分：业务价值与克制 (展现成熟度)**。追求工业级的稳定与可信。
> - **[13:00 - 15:00] 第五部分：总结与发散诱饵 (控场)**。主动抛出前端底层与架构调度的话题。

## 🎬 逐字稿正文

### 1. 业务问题：从团队 Review 与知识黑盒的痛点切入 (2分钟)

在过去的团队开发中，**Code Review**。因为能把做了什么以及背后的业务逻辑表达清楚的，往往只是少数资深工程师的能力；大量的业务上下文都成了“黑盒”，只存在于个人的脑子里。

当团队引入了 AI 编程后，这个痛点被放大了。AI 生成代码的速度很快，但**由于交互的分散，那些原本存在人脑子里的知识，现在都散落在大量不同的 Agent Session 中。** 当 AI 给出一个几百上千行的 PR 时，根本没法去认真 Review 它到底写了什么，更不知道它是基于什么逻辑修改的。

像 bamd，spec-kit，都在追求长任务一次性输出，但在真实的交付中，**“写出代码”从来不是难点，“让生成的代码可信、流程上可被追溯”才是需要解决的问题**

### 2. 技术矛盾：到底卡在哪里 (3分钟)

如果我们顺着“让 AI 完成超长任务”的思路走，工程上就会陷入死胡同，因为长任务必定会带来**知识传递的丢失**和**黑盒状态不可追溯**的问题：

- 如果把整个代码库和超长指令全塞给单体大模型，Token 会超载，模型会产生严重幻觉；而如果让开多个零散的 Session 提问，大量知识又会被割裂，无法串联。
- 在缺乏中间态沉淀的情况下，只要大模型给出的结果是错的，几乎无法回溯到底是在“理解需求”时造成了偏差，还是在“写逻辑”时没有读对正确的文件。当决策思路全部散落在离散的会话里，整个系统变成了一个不可控的黑盒。

### 3. 设计方案：怎么拆层、怎么取舍 (6分钟)

为了彻底解决这种“不可信”和“不可追溯”的问题，我选择**放弃对“AI 独立完成超长任务”的追求，转而把核心放在建立一条“知识结构化传递”和“强制自证”的流水线上。**

首先我没有让一个全能的 Agent 统揽全局，而是将 Kanban（看板）作为智能体编排的底层状态机总线。将研发拆解为 `Todo -> Dev -> Review -> Gate` 等流转阶段。
在这里，我不允许大模型进行长程的发散执行，而是强调**结构化知识的接力传递**。比如：负责规划的 Agent 绝不写代码，它的唯一产出就是把模糊需求沉淀为“结构化的执行计划”，并将计划传入编码 agent。编码 Agent 接手时，被严格限制只能根据这份“边界知识”进行局部修改。

当 Dev Agent 写完代码准备流转到 Review 阶段时，它不能只交代码，**它必须附带一份详尽的“开发证据 (Dev Evidence)”**。这份证据要求它明确记录：它依据了前一步的什么知识？修改了哪些具体文件？在跑了什么测试命令？当前的 Git 状态是否干净？

随后，负责审查的 Review Guard Agent 会拿着最初的验收标准（AC）和这份证据进行严苛的独立比对。这种**“以证据证明能力”的设计，把原本不可理解的“AI 盲目生成代码”，变成了“带有完整论证逻辑的 PR”。人类不再害怕代码读不懂，而是可以遵循证据链，有效阅读代码，而不是以一种“感觉对了”就冲动地合并 Pr。

**第三层：状态持久化与全链路知识追溯 (💡 借鉴 [[../Knowledges/React|React]] [[../Cards/React Fiber|React Fiber]] 调度思想)**

这是整个系统的托底盘。我们将 会话（Session）、任务（Task）以及执行轨迹（Trace）全部实体化，作为 Durable Object 存入数据库。

**在这里，我做了一个跨界的架构映射——我深度借鉴了 [[../Knowledges/React|React]] 底层 [[../Cards/React Fiber|React Fiber]] 架构中“[[../Cards/React Fiber|时间分片与可中断渲染]]”的思想来管理 AI 的长任务。** 

您想，传统让单体大模型执行长任务，就像早期 React 的同步递归渲染，一旦开始就不能停。如果跑到 99% 时网络超时或者 API 报错，之前的计算全白费了，只能无奈地让 AI “重头再来一遍”。

为了破局，就像 React 把庞大的渲染树切分成一个个独立保存上下文的 [[../Cards/React Fiber|Fiber 节点]]一样，我把大模型的执行链路也切成了细粒度的步骤。AI 每做完一步，系统就把当时的上下文和依赖打包成一个 Trace 实体落库保存。

带来的直接效果就是：即使 AI 推理中途崩溃，我们的 Blocked Resolver（阻塞分析器）也能精准查到是在哪一步断掉的。然后像 [[../Cards/React Fiber|Fiber 树]]恢复渲染一样，提取上一步的 Trace 恢复环境，让 AI 精准地**从断点处继续执行和重试**，彻底告别了“一报错就全盘推倒重来”的黑盒灾难。

### 4. 业务价值：减少了什么成本，提升了什么能力 (2分钟)

这套极度克制的架构上线后，带来了质的飞跃：
1. **建立零信任的安全准入**：强制的“证据收集”与“独立 Review 门禁”，让每一次代码交付都有迹可循，我们建立起了对 AI 生成代码的真正信任，人使用 ai，又担心不可控的恐惧。
2. **知识传递高保真**：通过 Kanban 切分和最小上下文下发，由大模型幻觉和知识遗漏导致的严重 Bug 降低了 80% 以上。
3. **高可追溯的协同闭环**：我们用一条步骤可控、状态完全可追溯的 AI 软件生产流水线，极大降低了长期维护和事后调试的成本。

### 5. 总结与发散 (2分钟)

在设计这个多智能体协同平台的过程中，我最大的感触是：**做工程架构，不要去过度迷信大模型本身的“神力”，而是要用优秀的工程机制去约束它的“黑盒”。**

如果要做的更好，其实不应该是追求结构化的任务清单文件，而是学习结对编程的优秀实践，先生成接口及其相关代码，代码变更 Diff 作为唯一真值上下文用于传递。
