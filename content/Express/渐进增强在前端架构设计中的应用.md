渐进增强把所有的 css，Js 等，看做是对网页的增强。Css 是样式的增强，js 则是功能的增强。即使某一个功能增强，也要尽力提供价值。



 在过去的 react 开发中，react 借助的是 js 的原生调用栈。每当组件状态更新时，React 会递归地调用组件的 `render` 方法。这个过程是同步、阻塞的。一旦渲染开始，就必须执行到整个组件树更新完毕。这就带来一个问题，如果组件树过深，或者渲染逻辑复杂，就会让用户明显感知到渲染卡顿。

React fiber 基于渐进增强的思想，带来了这样一个思考方式：我们能不能将组件的渲染排个序，把影响用户交互体验的内容（如用户输入）优先渲染，而数据获取相关的内容，可以被推迟甚至中断，从而避免页面卡顿，提升用户体验。

于是 react fiber 中，就有了以下优先级：

第一个是：立即同步的优先级，不可中断，立即渲染。通过 `flushSync` 告知 ui 立刻渲染。比如我们平时的输入框，通过快捷键弹出一个后，立刻选中第一个菜单项目。

第二种是：需要用户响应的优先级，比如常见的 input onchange 去更新 state

第三种是：最常见的优先级，比如网络请求返回后的数据更新。

第四优级是 react 并发特性（Concurrent Mode）的核心。比如通过输入框搜索列表，当输入框变化时，重新请求并渲染列表。如果两者在相同优先级下，react 会尝试同步更新输入框（快）和列表（慢）。如果列表渲染很慢，导致主线程阻塞，用户就会感觉输入框本身就在卡顿。通过 useTransition 可以将列表渲染标记为"过渡"。这样的话，当用户输入发生变化时，react 会抛弃之前的列表渲染任务，而执行一个新的渲染任务。以此防止 ui 的渲染卡顿。

并发特性的一个重要应用便是 Suspense，当组件在渲染过程中被"挂起"，比如通过 `React.lazy` 动态加载组件或在请求数据时抛出一个 Promise。它会🖕当前组件的渲染，并沿着 `fiber` 树向上遍历，寻找最近的 suspense 边界，并渲染 fallback 中指定的 UI。被挂起的原始组件树的状态会被保存在内存中。当 promise. Resolve 后，React 会在后台重新尝试渲染。在这个过程中 `fallback` 提供了基本的告知用户"内容即将到来"的信息，而当数据，又或者是代码加载完成并渲染出的最终内容，则是体验的"增强层"。

类似的 errorBoundery 也是解决的同样的问题。用户的基础体验是，当代码出现错误时，有一个错误重试机制。比如刷新。正常渲染的内容，则是增强性质的内容。

在 SSR 领域，Fiber 架构带来的便是通过流式 SSR 和选择性注水。传统的 SSR 是"瀑布式"，而在 Fiber 架构下，服务器会立即发送一个 HTML。当服务器上遇到 Suspense 时，它不会等待其内部的数据，而是将 fallback 的 html 发送到流中，然后渲染其余的部分。当服务器上被挂起的数据就绪后，就用同一个 HTTP 链接，将这段 html 流式地追加到客户端。客户端接收到 HTML 后，选择性的注水机制开始工作

最低优先级的则是那些用户完全不可见、可以无限期推迟的任务，比如用户埋点等。
