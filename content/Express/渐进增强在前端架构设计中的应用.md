在访问网页时，页面中会关联 css、js 等所欲的资源，并包含其它页面的链接。浏览器会自动下载对于的 css、js 并完成界面的渲染。我们也可以通过页面中的链接，去访问其它关联的页面。

整个过程中，我们无需考虑 css、js 来自于哪里，关联的页面是否来自于同一个网站。从系统集成角度上来说，网页上对其它资源的引用，实际上表示了对其它服务计算结果的整合。比如 Google Analytics，虽然它是以 js 的形式出现。但当页面引用到了 js 资源时，实际上完成的是对 Google Analytics 的整合。

而点击页面中包含的链接时，浏览器会请求对应网站的资源，并将计算结果在浏览器中展示。这也可以看做对其它系统的集成。更具体来讲，就是浏览器客户端通过延迟（Lazy）调用的方式，整合了其它系统提供的服务。

不论是 js、css 这样的资源，还是通过超链接引用的其它页面，都是服务端返回的页面中描述的。而客户端根据服务端提供的描述，选择恰当的时机，访问这些关联的资源，整合其它系统提供的服务。从这样的角度出发，我们就会发现，css、js 或者是通过超链接引用的其它页面，**都可以看做是对当前页面的增强**。比如 css 增强了当前页面的视觉效果，js 增强了当前页面的交互，页面中的超链接则提供了额外信息。**通过超媒体格式，我们不仅可以描述当前的服务，还可以描述增强的服务**。

假设你正在浏览一个电商网站，查看一个商品（比如一个智能手表）的详情。

**默认服务**：浏览器向服务器请求 `/products/123`，服务器返回描述这个智能手表的 HTML，浏览器将其显示出来。

**增强服务**：服务器在返回的 HTML 中，通过超媒体（`link` 标签或 `a` 标签）声明了与这个产品相关的**其他服务和资源**。

这是一个关于“智能手表 SR-5000”的产品页面的 HTML 片段：

```html
<div class="product" data-product-id="123">
  
  <header>
    <h1>智能手表 SR-5000</h1>
    <img src="/img/watch-sr5000.jpg" alt="SR-5000 手表" />
  </header>
  
  <section class="description">
    <p>这是我们最新款的智能手表，配备 GPS 和心率监测...</p>
    <span class="price">¥1999.00</span>
  </section>

  <link rel="reviews" 
        href="/api/products/123/reviews" 
        type="application/json" 
        title="查看评价 (JSON)" />

  <link rel="add-to-cart" 
        href="/api/cart/add?item_id=123" 
        title="添加到购物车 (操作)" />

  <link rel="alternate" 
        type="model/gltf-binary" 
        href="/models/sr5000.glb" 
        title="3D/AR 模型" />

  <link rel="alternate" 
        type="application/pdf" 
        href="/docs/sr5000-specs.pdf" 
        title="下载完整规格书 (PDF)" />
</div>
```

**对于普通网页浏览器**：它会解析 HTML（`<h1>`, `<p>`, `<img>` 等），把产品信息显示给用户。它会**忽略**所有它不理解的 `rel` 关系（比如 `reviews`, `add-to-cart`, `model/gltf-binary`）

**对于电商 App**：它在显示上述 HTML 基础信息的同时，会扫描 `<link>` 标签。
- 它会找到 `rel="reviews"`，于是自动去 `href` 指定的 API (`/api/products/123/reviews`) 获取 JSON 数据，并将其显示在“用户评价”标签页中。
- 它会找到 `rel="add-to-cart"`，当用户点击“购买”按钮时，它知道应该向哪个 URL (`/api/cart/add...`) 发送请求。

**对于 AR 试戴 App**：这个客户端可能根本不关心 HTML 里的 `<p>` 文本。它只关心一件事：这个产品有没有 3D 模型？
- 它会抓取这份超媒体，然后只寻找 `rel="alternate"` 且 `type="model/gltf-binary"` 的链接。
- 它找到了 `/models/sr5000.glb`，于是下载这个 3D 模型，让用户可以在现实环境中“虚拟试戴”这款手表。

**对于规格对比工具**：这个客户端（爬虫）的目标是收集所有产品的 PDF 规格书。
- 它会寻找 `rel="alternate"` 且 `type="application/pdf"` 的链接。
- 它找到了 `/docs/sr5000-specs.pdf` 并下载它，忽略所有其他信息。

所有的客户端都是用了同样的 API，而这些客户端彼此之间并不知道对方的存在，它们只关心自己关注的资源。这种按需索取，而不要求消费全部关联的服务，被称为渐进式服务消费。

渐进式服务消费的一个基本应用，就是渐进增强：**从最基本的内容和功能出发，逐步添加更丰富的样式和功能**。

现代开发中，我们都是以 esmoudle 的 import 形式有选择性地导入增强功能。比如 lodash-es 中，我们只需要其中一两个方法，而不是整个 lodash 包都被加载。如果这些增强功能需要一个必须导入的增强基座激活呢，其实就是我们的插件化开发模式。比如 sentry 的 interagtions。现在不论是插件还是适配的平台越来越多，集中在单个 npm 包中，会导致客户端下载依赖时耗费无用的时间与占用空间。于是就需要引入 pnpm monorepo 来进行多包管理。比如 react、react-dom、react-native。

首先是对于必须要有的增强，我们优先要做的是，在尽可能短的时间内，下载完整的资源。除去网络等因素，我们要做的就是尽可能减少代码的体积。比如清除所有的换行与空格，删除 console、注释等逻辑无关的内容，tree-shaking 避免打包未被使用的代码。也就是 webpack、vite 等工具干的活。

我们完全可以把 webpack 和 vite 的构建流程，和浏览器渲染的过程一一对应起来。浏览器根据 html 加载资源就等于是构建工具根据 package.json 下载依赖包。浏览器构建 cssom 树和借助 v8 执行资源文件，等于构建工具选择插件，对资源进行处理。

当资源资源下载后，我们需要对增强内容进行排序，把最核心的，和用户体验强相关的增强功能优先加载。在原生时代，把 javascript 放在 body 最后，其实就是希望 css 的增强优先于 js 的增强。

React fiber 处理的核心问题，就是对 react 组件，进行渲染优先级排序，让和用户体验强相关的组件，优先渲染。

在过去的 react 开发中，react 借助的是 js 的原生调用栈。每当组件状态更新时，React 会递归地调用组件的 `render` 方法。这个过程是同步、阻塞的。一旦渲染开始，就必须执行到整个组件树更新完毕。这就带来一个问题，如果组件树过深，或者渲染逻辑复杂，就会让用户明显感知到渲染卡顿。

React fiber 基于渐进增强的思想，带来了这样一个思考方式：我们能不能将组件的渲染排个序，把影响用户交互体验的内容（如用户输入）优先渲染，而数据获取相关的内容，可以被推迟甚至中断，从而避免页面卡顿，提升用户体验。我们对 react 开发的思考方式，就从更新 State 被动等待 react 自身处理完成。变成主动思考哪些交互对用户的优先级更高，手动地进行排序。

于是 react fiber 中，就有了以下优先级：

第一优先级是“现在、立刻、马上执行、不可中断”。通过 `flushSync` 告知 ui 立刻渲染。比如在输入框中，使用 `@` 呼唤出一个快捷菜单，并选中第一个菜单项。

第二优先级是需要用户响应的优先级，"用户在等我，我必须马上响应，如果来了更急的任务，则可以中断"，比如常见的 input onchange 去更新组件的 state，并更新 input 的内容。

第三优先级是最常见的，“不需要立即响应用户，只要正常排队即可”。比如 useEffect 中后端请求接口进行数据更新

第四优先级是过渡优先级：“这个任务可能很慢，别卡住用户界面，先去处理用户的输入。这个任务可以稍后、甚至分片进行。

比如通过输入框搜索列表，当输入框变化时，重新请求并渲染列表。如果两者在相同优先级下，react 会尝试同步更新输入框（快）和列表（慢）。如果列表渲染很慢，导致主线程阻塞，用户就会感觉输入框本身就在卡顿。通过 useTransition 可以将列表渲染标记为"过渡"。这样的话，当用户输入发生变化时，react 会抛弃之前的列表渲染任务，而执行一个新的渲染任务。以此防止 ui 的渲染卡顿。

并发特性的一个重要应用便是 Suspense，当组件在渲染过程中被"挂起"，也就是会卡住用户，比如通过 `React.lazy` 动态加载组件或在请求数据时抛出一个 Promise。它会🖕当前组件的渲染，并沿着 `fiber` 树向上遍历，寻找最近的 suspense 边界，并渲染 fallback 中指定的 UI。被挂起的原始组件树的状态会被保存在内存中。当 promise. Resolve 后，React 会在后台重新尝试渲染。在这个过程中 `fallback` 提供了基本的告知用户"内容即将到来"的信息，而数据或者代码，加载完成并渲染出的最终内容，则是体验的"增强层"。

类似的 errorBoundery 也是解决的同样的问题。用户的基础体验是，当代码出现错误时，有一个错误重试机制。比如刷新。正常渲染的内容，则是增强性质的内容。

在 SSR 领域，Fiber 架构带来的便是通过流式 SSR 和选择性注水。传统的 SSR 是"瀑布式"，而在 Fiber 架构下，服务器会立即发送一个 HTML。当服务器上遇到 Suspense 时，它不会等待其内部的数据，而是将 fallback 的 html 发送到流中，然后渲染其余的部分。当服务器上被挂起的数据就绪后，就用同一个 HTTP 链接，将这段 html 流式地追加到客户端。客户端接收到 HTML 后，选择性的注水机制开始工作

最低优先级的则是那些用户完全不可见、可以无限期推迟的任务，比如用户埋点等。
