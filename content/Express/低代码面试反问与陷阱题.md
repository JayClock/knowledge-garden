# 低代码面试反问与陷阱题

 陷阱 1：低代码是不是就是拖拽几个组件

推荐回答：

> 拖拽只是交互表象，真正核心是 schema、编排引擎、运行时和扩展体系。只会讲拖拽，面试官会觉得你做的是 demo；把它讲成协议设计和状态变更系统，才更像平台能力。

 陷阱 2：为什么不直接改 DOM，做那么复杂干什么

推荐回答：

> 低代码里真正重要的不是 DOM 最后长什么样，而是编辑动作怎么稳定地落成 schema 变更。直接改 DOM 看起来快，但后面做撤销重做、版本管理、diff、协作和运行态渲染都会变得很难。

 陷阱 3：编辑态和运行态为什么一定要分开

推荐回答：

> 因为两者目标完全不同。编辑态关心选中、高亮、拖拽、辅助线和配置面板；运行态只关心真实业务逻辑和页面表现。如果混在一起，前期可能省事，后期复杂度会上升得非常快。

 陷阱 4：你怎么证明自己不是只做了个拖拽 UI

推荐回答：

> 我会把回答往三层拉。第一层是 schema 和数据结构；第二层是编排引擎怎么把动作转成 payload；第三层是运行时怎么消费 schema 把页面和联动跑起来。只要把这三层讲清楚，面试官就会知道你做的不是视觉交互，而是一套平台机制。

 陷阱 5：低代码是不是会把前端替代掉

推荐回答：

> 低代码更适合结构化、重复性高的页面，比如后台、表单、表格和详情页。它不是替代前端，而是把前端经常重复实现的部分抽成平台能力，让研发从重复劳动里解放出来。

 陷阱 6：如果性能很差，你第一反应查哪里

推荐回答：

> 我会先看拖拽过程中是不是做了太多真实 DOM 读取和遍历，或者是不是每次动作都带出了整棵树重渲染。低代码编辑器最常见的问题，通常不是功能做不出来，而是页面一复杂就开始卡。

 一句收口

低代码面试最容易踩的坑，就是把它讲成一个拖拽控件题。更稳妥的讲法是始终把它拉回到 schema、编排引擎和运行时这三件事上。
