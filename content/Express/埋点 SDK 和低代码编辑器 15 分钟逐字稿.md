## 15 分钟逐字稿

大家好，如果让我挑两段最能体现我前端平台化能力的经历，我通常会把埋点 SDK 和低代码编辑器放在一起讲。它们表面上一个偏数据采集，一个偏页面搭建，看起来离得比较远，但我实际做下来会发现，它们底层其实在解决同一类问题：怎么把零散的前端动作，翻译成一套稳定、可扩展、可治理的数据模型和运行机制。

换句话说，我不会把埋点 SDK 讲成“封装几个 `track()` 方法”，也不会把低代码编辑器讲成“做一个拖拖拽拽的页面”。我更愿意把它们定义成两类平台能力：前者是把业务行为稳定地翻译成可分析的事件语言，后者是把编辑行为稳定地翻译成可执行的页面 schema。它们都不是只解决一次开发，而是在解决一类问题怎么长期规模化承接。

我先讲埋点 SDK。

埋点 SDK 这个题，我通常会先讲业务背景。很多团队一开始做埋点，都是谁要分析数据，谁就在页面里补一个事件，最后会出现几个问题。第一，事件命名非常散，今天叫 `button_click`，明天叫 `submit_click`，后面根本没法统一分析。第二，字段口径不一致，同样是来源渠道、页面路径、实验桶，不同业务线写法都不一样。第三，接入完全靠手工，人一多就容易漏埋、错埋。第四，就算采上来了，数据也不一定能用，因为缺字段、重复上报、语义漂移都很常见。

所以如果让我设计埋点 SDK，我最先做的不是 transport，而是事件模型。我会先定义清楚事件到底在描述什么。我的原则是，底层可以保留 click、exposure、route-change 这类技术事件，但真正给业务分析长期使用的，应该尽量往业务事件或者领域事件上靠。比如不要只埋“提交按钮被点击”，而是尽量抽成“订单已提交”“任务已完成”“审批已通过”这种更稳定的业务语义。因为 UI 很容易变，按钮可以换成快捷键、浮层、自动触发，但业务语义不会轻易变。

在这个基础上，SDK 本身我一般会拆成四层。第一层是事件定义层，负责事件名规范、字段 schema、版本控制和分类。第二层是上下文层，自动补齐页面、来源、用户、设备、实验桶、会话这些公共字段，尽量减少业务重复填写。第三层是采集层，这里会同时支持手动埋点、部分自动采集和必要的可视化配置，但我会非常注意边界，避免为了省接入成本把语义做散。第四层是上报层，也就是队列、批量、重试、采样和 `sendBeacon` 兜底这些 transport 能力，保证页面退出、弱网或者高频事件场景下仍然比较稳定。

我觉得埋点 SDK 里最容易被低估的点，其实是数据质量治理。因为埋点最怕的不是少一点，而是看起来很多，实际上完全不能分析。所以我通常会补几件事。第一是 schema 校验和必填校验，保证事件字段至少是可用的。第二是去重和版本管理，避免同一个语义被埋出多个近似名字。第三是调试能力，比如开发环境日志、调试面板、灰度抽样对账，让研发和产品在上线前就能看到事件长什么样。第四是边界划分，比如我会明确告诉团队，监控 SDK 是看系统健康、错误和性能，埋点 SDK 是看业务行为和转化漏斗，这两者底层能力可以复用，但事件模型不能混。

如果从我自己的角色来看，我在这类项目里做的不是简单写几个上报 API，而是把事件语言、接入方式和数据质量机制一起搭起来。也就是说，我更像是在做一套数据采集基础设施。它的价值也不只是“数据能发出去”，而是后面分析平台、告警平台、实验平台都能在同一套语义上继续往上长。

接下来我再讲低代码编辑器。

低代码编辑器这个题，我也不会从拖拽交互开始讲。我一般会先说，它的本质不是“让用户拖一个按钮上去”，而是用一套稳定的数据结构去描述页面、组件、事件和数据联动，再用一套编辑态和运行态机制把这些配置真正跑起来。所以我更关注的是 schema、编排引擎、渲染运行时和扩展体系，而不是单个交互效果。

这个方向的业务背景通常也很明确。企业里会有大量后台、表单、表格、仪表盘、详情页，这些页面 70% 到 80% 都是重复的结构化搭建。如果每个场景都从零开发，交付慢、复用差，而且很多逻辑只是换了字段和规则。所以低代码想解决的，其实不是“替代前端”，而是把前端经常重复实现的页面结构、组件物料、事件联动和权限规则，抽成平台能力，让业务更多通过配置完成。

如果让我拆低代码编辑器，我一般会拆成四层。第一层是协议层，也就是 schema 或 DSL，定义页面上有什么节点、节点怎么嵌套、属性怎么存、事件和数据源怎么挂接。第二层是物料层，也就是组件注册中心，每个组件除了渲染器，还要有属性面板、默认 schema、校验规则和事件描述。第三层是编排层，也就是编辑器本身，负责选中、高亮、拖拽、插入、移动、删除、撤销重做这些编辑行为。第四层是运行时层，负责真正渲染页面，并把按钮点击、接口调用、变量更新、联动刷新这些逻辑串起来。

这里面最核心的是编排引擎。因为用户在画布上看到的是拖拽，但系统真正要处理的是“编辑动作怎么落成 schema 变更”。所以我通常会把页面模型拆成组件树和属性表两部分，类似 tree 加 blocks。这样插入和移动主要改结构，属性修改只改节点数据，后面做 diff、最小更新、撤销重做、版本管理都会更清楚。

具体到拖拽链路，我会把它理解成一个“动作转 payload”的过程。拖拽开始时先收集可投放区域，拖拽过程中持续做碰撞检测，判断当前命中了哪个容器、应该插在某个节点前面还是后面，然后把这个结果通过蓝线或者指示器反馈给用户。真正落地时，不是直接改 DOM，而是产出统一的插入 payload，比如 `parentId`、`relativeId`、`position`，最后交给 store 去修改 schema。这样编辑器表面上是一个交互系统，底层其实是一个状态变更系统。

这类系统还有一个很典型的难点，就是性能。页面节点少的时候，很多实现都能工作；但一旦上百上千个节点，如果每次拖动都去遍历 DOM、反复读布局信息，很快就会卡。我的做法一般是把高频计算前置，比如在拖拽开始时预计算可投放区域，缓存成轻量的坐标对象，拖拽过程中尽量只做纯 JavaScript 的命中判断，而不是不停读写真实 DOM。这样复杂页面下，交互性能会稳定很多。

除了编排引擎，另一个关键点是编辑态和运行态一定要分离。编辑态需要选中、高亮、拖拽、配置面板、辅助线；运行态只关心真实页面渲染和业务逻辑。如果两者混在一起，系统前期可能看不出问题，但一旦需求复杂、组件变多、联动增多，维护成本会急剧上升。所以我会把编辑器能力尽量收敛成对 schema 的生产和修改，把运行时能力收敛成对 schema 的消费和执行。

再往后走一步，低代码真正难的地方其实不是拖拽，而是数据联动和扩展体系。比如全局变量怎么管理，组件之间怎么绑定，按钮点击后怎么调用接口、更新状态、刷新列表，新增一个业务物料怎么接进来，怎么保证现有编辑器核心逻辑不被污染。这时候就不能只靠页面技巧了，必须回到协议设计和插件化设计。平台只认统一协议，不关心具体业务组件内部怎么实现，这样才能长期扩展。

如果把这两个项目放在一起看，我觉得最能体现的，其实是我做前端时的一个稳定方法论。第一，我会先找稳定模型，而不是先堆功能。埋点 SDK 先找事件模型，低代码编辑器先找页面 schema。第二，我会把定义和执行分开。埋点里是事件定义和上报执行分开，低代码里是编辑态和运行态分开。第三，我会主动补治理能力。埋点里是数据质量、调试和对账，低代码里是撤销重做、版本管理、插件边界和性能策略。也就是说，我做的不是一个功能点，而是一套能承载复杂度的机制。

所以如果面试官问我，这两段经历到底证明了什么，我会说它们证明我不只是做业务页面的前端。我更偏向平台型前端，或者说偏基础设施型前端。我的工作重点通常不是把某个页面写出来，而是把一类重复问题抽象成协议、引擎和运行时，让后续团队可以更稳定地复用、扩展和治理。

如果一定要用一句话收尾，我会这样总结：埋点 SDK 解决的是“业务行为如何被稳定地表达和分析”，低代码编辑器解决的是“页面和交互如何被稳定地描述和生成”，而我在这两类项目里沉淀下来的核心能力，就是把前端从页面实现，往模型设计、运行时设计和平台治理推进。

我的介绍大概就是这些。如果您愿意继续展开，我后面还可以细讲两个方向：第一是埋点 SDK 里怎么平衡接入效率和事件语义准确性；第二是低代码编辑器里怎么做精确插入、性能优化和编辑态运行态隔离。

## 10 分钟压缩讲法

如果面试时间没那么长，我会把埋点 SDK 和低代码编辑器放在一条主线上讲：它们本质上都不是单点功能，而是在把前端里的重复问题平台化。埋点 SDK 解决的是业务行为怎么被稳定地表达和分析，低代码编辑器解决的是页面和交互怎么被稳定地描述和生成。

埋点 SDK 这块，我重点会讲三件事。第一是事件模型，要尽量从零散 UI 事件往稳定业务事件收敛；第二是上下文和上报链路，包括公共字段补齐、队列、批量、重试和 `sendBeacon` 兜底；第三是数据质量，比如 schema 校验、必填校验、去重、调试面板和灰度对账。对我来说，埋点 SDK 的价值不在于把事件发出去，而在于后面的分析平台和业务决策能不能真正用这套数据。

低代码编辑器这块，我会重点讲 schema、编排引擎和运行时。也就是先用稳定的数据结构描述页面和组件，再把拖拽、插入、移动这些编辑动作转成对 schema 的修改，最后用运行时把页面和数据联动真正跑起来。这里最值得讲的是编辑态和运行态分离、精确插入、性能优化，以及插件化扩展边界。

所以如果压缩成一句话，我会说这两个项目共同体现的是我的平台型前端思路：先找稳定模型，再把定义和执行分开，最后补上治理和扩展能力，而不是只把某个页面或者某个功能做出来。

## 高频追问

### 如果面试官追问“这些听起来都挺大，那你具体做了什么？”

> 我一般会这么答：
>
> 如果拆开看，埋点 SDK 这块，我做得比较多的是三件事。第一是把事件模型和公共上下文收拢起来，不让各业务线各埋各的；第二是把上报链路补完整，比如队列、批量、重试、页面退出兜底；第三是把调试和校验做起来，不然数据发出去也没人敢用。
>
> 低代码编辑器这块，我主要做的是 schema 设计、编排引擎和运行时边界。比如拖拽怎么落成对 schema 的插入和移动，怎么做精确插入，复杂页面下怎么避免拖一拖就卡，还有编辑态和运行态怎么拆开，避免后面越来越乱。
>
> 所以如果一句话讲我在这两个项目里的角色，我不是只负责把页面做出来的人，我更像是在搭底层规则和核心机制，让这类能力后面可以稳定复用。

### 如果面试官追问“为什么你会把埋点 SDK 和低代码编辑器放在一起讲？”

> 我会说，因为它们表面上看一个偏数据、一个偏页面，但底层都在做同一件事：把前端里的零散动作翻译成稳定模型。埋点是在把业务行为翻译成事件语言，低代码是在把编辑行为翻译成页面 schema。把它们放在一起讲，更能体现我不是只会做功能，而是更偏平台抽象和运行时设计。

## 面试收口提示

- 如果面试官更关注数据平台，就重点展开埋点 SDK 的事件模型、数据质量和监控边界。
- 如果面试官更关注前端架构，就重点展开低代码编辑器的 schema、编排引擎和运行时分层。
- 如果面试官想看你的方法论，就强调这两个项目共同体现的“模型优先、定义与执行分离、平台治理先行”。
